## 精炼段

`03c` 结束时我们手上有一棵 AST，但那棵树上的名字**全是字符串**：`Object{name="x"}` 里的 `"x"` 和三行之外 `let x : Int` 里的 `"x"` 是两个毫无关联的 `std::string`。语义分析的第一件事就是把这些字符串**连成边**——每个引用指向它的声明。这件事叫**名字解析（name resolution）**，它的数据结构叫**符号表**。

本篇不打算把 `symtab.h` 贴给你看。它只有 36 行，贴出来你五秒就"看懂"了，但你不会知道**为什么是这 36 行**。所以我们反过来走：先把名字解析的需求写成三条，然后列出三种候选实现，把它们的复杂度算出来对比，最后你会发现本项目选的那个方案在 Cool 的规模下是最优的——而另外两个候选恰好是 LLVM 和 clang 真实在用的。理解这个三选一，你就理解了符号表；不理解，你只是背下了 `rbegin`。

后半篇处理一个更容易被跳过的问题：**谁负责 push，谁负责 pop**。`checkFeature` 里连着两个 `pushScope()` 不是随手写的，它编码了手册里"形参遮蔽同名属性"这条规则；而 `visit(Let)` 只 push 一次、`visit(Case)` 每个分支 push 一次，这个不对称也有确切理由。最后 §7 交代我实测发现的两个真实缺陷——其中一个会让编译器**自己崩掉**。

## 0. 本篇要回答的六个问题

1. parser 交出来的 AST 上，一个名字到底是什么？"名字解析"具体解析出了什么东西？
2. 符号表为什么是"表的栈"而不是"一张表"？另外两种做法各差在哪，代价能算出来吗？
3. `lookup` 里的 `rbegin()/rend()` 对应手册的哪句话？把它换成 `begin()/end()` 会错在哪个具体程序上？
4. `let x : Int <- 1, x : String <- "a" in x` 里的 `x` 是什么类型？我们的实现靠什么机制做对的（不是嵌套作用域）？
5. `checkFeature` 为什么连着 push 两层而不是一层？哪个真实程序能把这两层的差别暴露出来？
6. 类型名（`Int`、`Ghost`）也是名字。它由谁解析？——这一问会直接引出我实测到的一个崩溃。

## 1. 起点：AST 上的名字只是字符串

先把问题看清楚。拿 `tests/list.cl` 的 `sum` 方法：

```cool
sum(l : List) : Int {
  if l.isNil() then 0 else l.head() + sum(l.tail()) fi
};
```

parser 建出来的树（`03c` §5 的 `--dump` 格式）：

```
method sum(l : List) : Int
  if
    dispatch .isNil
      object l          ← 这里的 "l"
    int 0
    binary +
      dispatch .head
        object l        ← 和这里的 "l"
      dispatch .sum
        object self
        dispatch .tail
          object l      ← 和这里的 "l"
```

三个 `object l` 是**三个独立的 `Object` 节点**，每个里面一个 `std::string name = "l"`。它们之间没有任何指针、没有任何 ID、没有任何东西把它们和 `formals[0]`（那个 `l : List`）联系起来。parser 没有义务建这条联系——`03a` §2 讲过，CFG 只管结构，"名字指向谁"根本不是上下文无关文法能表达的东西（这也是"上下文**无关**"这个名字的由来）。

所以语义分析的第一个任务，用一句话说清：

> **名字解析** = 对 AST 上每一个名字**引用**，找到它对应的**声明**，并把声明里的信息（在 Cool 这里是类型）取出来。

注意"取出来"这个措辞。有两种做法：

| 做法 | 结果 | 谁在用 |
|---|---|---|
| **连边**：在 `Object` 节点上加一个 `Decl* decl` 指针 | AST 变成图，后续任何阶段都能顺着指针拿到声明的全部信息 | clang（`DeclRefExpr::getDecl()`）、rustc（`Res`） |
| **取值**：查到类型就用，不存指针 | AST 仍是树，只在节点上留下结论（`Expr::type`） | 本项目 |

本项目选第二种，因为 Cool 的后续阶段（`06` 类型检查、`09` codegen）只需要类型这一个信息，存指针是过度设计。但你要知道差别在哪：如果将来你想做"跳转到定义""重命名重构"这类 IDE 功能，你**必须**连边——`Expr::type` 里只有 `"Int"` 这个字符串，它不会告诉你是哪一行声明的。这就是 clang 的 AST 能撑起 clangd 而我们的不能的根本原因。

**一句话**：`03c` 说 AST 是"为后续阶段设计的数据结构"，本篇就是第一个后续阶段。它往树上写的东西是 `Expr::type`。

## 2. 从三条需求推出数据结构

这一节是本篇的核心。**不要先看 `symtab.h`**——我们自己把它推出来。

### 2.1 需求

看 Cool 手册第 255 行（原文，`refs` 里没有的话你去 `theory.stanford.edu/~aiken/software/cool/cool-manual.pdf` 抓一份）：

> "Local variables and formal parameters have lexical scope. Attributes are visible throughout a class in which they are declared or inherited, although they may be hidden by local declarations within expressions. **The binding of an identifier reference is the innermost scope that contains a declaration for that identifier**, or to the attribute of the same name if there is no other declaration. The exception to this rule is the identifier `self`, which is implicitly bound in every class."

把它拆成需求：

- **R1（查找）**：给一个名字，返回它的类型。这个操作会被调用**极多次**——AST 上每一个 `Object` 节点、每一个 `Assign` 都要查一次。
- **R2（嵌套）**：作用域会嵌套（方法体里有 `let`，`let` 里还有 `let`）。进入一个构造时要"添加一批绑定"，离开时要"恰好撤销这一批"。
- **R3（内层优先）**："innermost scope that contains a declaration"——同名时内层赢。这叫**遮蔽（shadowing）**。

R2 里的"恰好撤销"值得停一下。为什么不能"离开时把这批名字逐个删掉"？因为遮蔽：

```cool
let x : String <- "outer" in       -- 绑定 x : String
  { let x : Int <- 1 in x;         -- 绑定 x : Int（遮蔽）
    x; }                           -- 内层 let 结束后，x 必须重新是 String
```

如果内层离开时"把 `x` 删掉"，外层的 `x : String` 就跟着没了。所以 R2 要的不是删除，是**恢复到进入前的状态**。这个词很关键——它直接决定了数据结构的形状。

### 2.2 三种候选

**候选 A：一张表 + 进出时存档/读档**

```
pushScope():  snapshot = table 的完整拷贝，压到备份栈
popScope():   table = 备份栈弹出的快照
lookup(x):    table.find(x)          ← O(1)，最快
```

`lookup` 是 O(1)，非常诱人。但 `pushScope` 要**拷贝整张表**。设表里有 N 个名字、程序有 S 个作用域，总代价 O(N·S)。一个有 50 个属性的类、方法体里嵌 5 层 `let`，每层都要拷 50+ 项。而 `lookup` 的 O(1) 省下来的那点时间远远抵不上。

否决。但记住它——**函数式编程里这是标准做法**，因为持久化数据结构（persistent map）的"拷贝"是 O(log N) 的结构共享，不是真拷贝。Haskell / OCaml 写的编译器基本都用候选 A 的变体。

**候选 B：一张表，每项存一个栈**

```
table : name → stack<type>

add(x, T):    table[x].push(T)
lookup(x):    table[x].top()               ← O(1)
pushScope():  记下"本作用域加了哪些名字"（一个 vector<string>）
popScope():   对刚记下的每个名字 table[name].pop()
```

`lookup` O(1)。`pushScope` O(1)。`popScope` 只动**本作用域实际加过的**名字，代价 O(本层名字数)——总代价 O(总声明数)，线性，最优。

这是三个方案里性能最好的。代价是：要维护两个结构（表 + "本层加了谁"的列表），要处理"pop 到空栈就把 key 删掉"这种边界，实现大约 40~60 行。

**这就是 LLVM `ScopedHashTable`（`llvm/ADT/ScopedHashTable.h`）的做法**，clang 的 `Sema` 做名字查找时用的 `IdentifierResolver` 也是这个思路（每个 `IdentifierInfo` 挂一条声明链）。真实工业编译器选它，因为它们要处理几万个名字、几千层作用域。

**候选 C：表的栈**（本项目）

```
scopes : vector<hash_map<name, type>>

pushScope():  scopes.push_back({})                    ← O(1)
popScope():   scopes.pop_back()                       ← O(本层名字数)，析构
add(x, T):    scopes.back()[x] = T                    ← O(1)
lookup(x):    从 scopes 尾部往头部，逐层 find          ← O(作用域深度)
```

`lookup` 退化成 O(深度)。但注意：**是 O(深度)，不是 O(名字总数)**。Cool 程序的作用域深度是多少？方法体那两层（属性层 + self/形参层），加上嵌套的 `let`/`case`。手写代码几乎不会超过 6~8 层。8 次哈希查找和 1 次哈希查找，在一个编译 500 行源码的程序里毫无区别。

而实现代价：**36 行，其中真正的逻辑 6 行**。

### 2.3 对比表

| | A：存档/读档 | B：每项一个栈 | C：表的栈 |
|---|---|---|---|
| `lookup` | **O(1)** | **O(1)** | O(深度) |
| `pushScope` | O(表大小) | O(1) | **O(1)** |
| `popScope` | O(表大小) | O(本层) | O(本层) |
| 总体 | 最差 | **最优** | 够用 |
| 实现行数 | ~30 | ~50 | **~10** |
| 额外结构 | 备份栈 | "本层名字"列表 | 无 |
| 真实使用者 | 函数式编译器（持久化 map） | LLVM `ScopedHashTable`、clang | 教学实现、小语言 |

**结论**：在 Cool 的规模下，C 用 1/5 的代码换来可忽略的性能损失。这是正确的工程判断，不是偷懒。但你要能说出**什么时候该换成 B**——当作用域深度不再有界时（比如你在做一个支持深度嵌套闭包的语言，或者符号表要装几万个名字），`lookup` 的 O(深度) 就会变成热点。

> **这个推导的价值**：以后你看任何编译器的符号表，第一眼就能归类到 A/B/C 的某一种，并立刻知道作者在权衡什么。这比记住 `rbegin()` 有用得多。

## 3. 逐行读 `symtab.h`：每一行对应一条语义规则

现在看代码。全文 36 行（`coolc/src/symtab.h`）：

```cpp
class SymbolTable {                                      // :10
public:
  void pushScope() { scopes_.emplace_back(); }           // :12
  void popScope()  { scopes_.pop_back(); }               // :13

  // 在当前（最内层）作用域声明一个名字
  void add(const std::string& name, const std::string& type) {   // :16
    scopes_.back()[name] = type;                         // :17
  }

  // 从最内层往外查找；未找到返回 nullopt
  std::optional<std::string> lookup(const std::string& name) const {   // :21
    for (auto it = scopes_.rbegin(); it != scopes_.rend(); ++it) {     // :22
      auto found = it->find(name);                       // :23
      if (found != it->end()) return found->second;      // :24
    }
    return std::nullopt;                                 // :26
  }

  bool empty() const { return scopes_.empty(); }         // :29

private:
  std::vector<std::unordered_map<std::string, std::string>> scopes_;
};
```

### 3.1 `:22` 的 `rbegin()` = 手册的 "innermost scope"

`scopes_` 是 `vector`，`push_back` 加在**尾部**，所以尾部 = 最内层。`rbegin()` 从尾部开始。**第一个命中就 `return`**（`:24`），不再往外找。

这三个事实合起来，恰好就是手册那句：

> the binding of an identifier reference is **the innermost** scope that contains a declaration

**把 `rbegin/rend` 换成 `begin/end` 会错在哪？** 别猜，构造程序：

```cool
class Main inherits IO {
  x : Int <- 1;                    -- 属性 x : Int（外层）
  foo(x : String) : String { x };  -- 形参 x : String（内层）
  main() : Object { out_string(foo("hi")) };
};
```

方法 `foo` 的体里那个 `x`：正确答案是 `String`（形参遮蔽属性），返回类型 `String`，程序合法。如果 `lookup` 从外往内找，会先命中属性 `x : Int`，于是报 "body of method 'foo' has type Int but declared return type is String"——**一个完全合法的程序被拒绝**。

实测确认它现在是对的（这个文件我存在 `/tmp/p/a_shadow.cl`）：

```
$ ./coolc.exe a_shadow.cl -o out.ll
wrote out.ll (10749 bytes)          ← 通过
```

**这就是"读代码"和"理解代码"的差别**：`rbegin` 三个字母背后是一条手册规则和一个具体程序。

### 3.2 `:17` 的 `[]` = 手册的 "later bindings hide earlier ones"

`scopes_.back()[name] = type` 用的是 `operator[]`，语义是**存在则覆盖**。如果写成 `insert`，语义是**存在则什么都不做**。

这个选择被一条 Cool 规则逼死了。手册讲 `let`：

> If an identifier is defined multiple times in a `let`, later bindings hide earlier ones.

```cool
let x : String <- "a", x : Int <- 1 in x     -- x 是 Int（后者赢）
```

**关键点在这里**：这两个 `x` 是在**同一个作用域**里的。看 `visit(Let)`（`typechecker.cpp:332`）：

```cpp
void TypeChecker::visit(const Let& e) {
  O_.pushScope();                        // ← 只 push 一次！
  for (auto& b : e.bindings) {
    if (b.name == "self") { error(e.line, "'self' cannot be bound in a let"); continue; }
    std::string declared = resolveSelf(b.type);
    if (b.init) {
      std::string t = typeOf(*b.init);    // ← 先检查初始化
      if (!conforms(t, declared))
        error(b.init->line, "let initializer for '" + b.name + "' has type " + t +
                            " but declared type is " + declared);
    }
    O_.add(b.name, b.type);              // ← 后加入环境
  }
  result_ = typeOf(*e.body);
  O_.popScope();                          // ← 只 pop 一次
}
```

一个 `let` 不管有几个绑定，**只有一层作用域**。所以"后者遮蔽前者"完全靠 `add` 里那个 `[]` 实现的，跟嵌套没关系。

这是个很容易踩的坑：如果你按手册的推理规则字面实现（手册的 [Let-Init] 是一次一个变量、层层嵌套），你会为每个绑定 push 一层。那样也对，而且不依赖 `[]` 的覆盖语义。两种实现都合规——但你必须知道自己选的是哪种，否则把 `[]` 改成 `insert` 就会静默出错。

### 3.3 `add` 和 `typeOf` 的顺序：一条被手册明文规定的坑

再看上面 `visit(Let)` 的循环体。顺序是：**先 `typeOf(*b.init)`，后 `O_.add`**。

反过来行不行？看手册第 556 行：

> First, the initialization `e1` is type checked in an environment **without a new definition for x**. Thus, the variable `x` cannot be used in `e1` unless it already has a definition in an outer scope.

也就是说 `let x : Int <- x + 1 in ...` 里的 `x + 1` **不能**看到正在绑定的这个 `x`。实测：

```
$ ./coolc.exe ae_let_init_sees_self.cl
ERROR: line 1: undeclared identifier 'x'
ERROR: line 1: arithmetic operands must be Int, got Object and Int
type checking failed
```

正确拒绝了（第二条错误是级联的，`06b` §4 会讲为什么会有它、以及为什么这是设计而非 bug）。

而**后面的绑定能看到前面的**——同一个循环，`y` 的 init 检查时 `x` 已经 `add` 过了：

```
$ ./coolc.exe b_letseq.cl        # let x : Int <- 1, y : Int <- x + 1 in out_int(y)
wrote out.ll (10420 bytes)       ← 通过
```

**这两条行为出自同一个循环里语句的先后顺序。** 把 `O_.add` 挪到 `typeOf` 之前，第一条行为就错了；把 `O_.add` 挪到循环外面，第二条就错了。四行代码，两条手册规则，一个顺序。

### 3.4 手工跑一遍栈

拿 `list.cl` 的 `sum`（`tests/list.cl:18`）。跟着 `typeOf` 走，记录每一刻 `O_` 的内容：

```
时刻                                              O_ 的栈（顶在上）
────────────────────────────────────────────────  ─────────────────────────
① checkFeature 开始，push 属性层                  [ {} ]                       ← Main 没有属性
② for kv : attrsOf("Main") → 空，什么都不加         [ {} ]
③ push self+形参层                                [ {}, {} ]
④ add("self","SELF_TYPE")                        [ {}, {self:SELF_TYPE} ]
⑤ 是 Method，add("l","List")                      [ {}, {self:SELF_TYPE, l:List} ]
⑥ typeOf(方法体) → visit(If) → visit(Dispatch)
     → visit(Object{"l"}) → lookup("l")           从顶层找 → 命中 l:List ✓
⑦ ... 递归遍历整棵树，栈不变                        [ {}, {self:SELF_TYPE, l:List} ]
⑧ popScope ×2                                     [ ]
```

**注意 ⑦：整棵方法体遍历期间栈是不变的。** `sum` 里没有 `let`/`case`，所以没人 push。这印证了一条不变式，下一节展开。

如果是 `main`（`list.cl:21`，有一个 `let`）：

```
④ [ {}, {self:SELF_TYPE} ]
⑤ 无形参
⑥ typeOf(body) → visit(Let):332 → pushScope     [ {}, {self},  ]
⑦   typeOf(init) = (new Cons).init(...) → Cons      ← 此时栈里还没有 l！
⑧   conforms(Cons, List) ✓
⑨   add("l","List")                              [ {}, {self}, {l:List} ]
⑩   typeOf(body) = out_int(sum(l))
        → visit(Object{"l"}) → lookup("l")        深度 3，第 1 次就命中
⑪ popScope                                       [ {}, {self} ]
⑫ popScope ×2                                    [ ]
```

⑦ 那一行就是 §3.3 的规则在跑：`l` 的初始化在"还没有 `l`"的环境里检查。

## 4. 谁 push，谁 pop：环境的装配

`symtab.h` 只提供机制，**策略**全在 `typechecker.cpp` 里。这一节讲策略，它比机制难。

### 4.1 `checkFeature` 为什么是两层

`typechecker.cpp:219`：

```cpp
void TypeChecker::checkFeature(const Feature& f) {
  O_.pushScope();   // 属性作用域（外层）                          :220
  for (auto& kv : attrsOf(currentClass_)) O_.add(kv.first, kv.second);  // :221
  O_.pushScope();   // self + 形参（内层）                          :222
  O_.add("self", "SELF_TYPE");                                    // :223

  if (auto* a = dynamic_cast<const Attribute*>(&f)) {
    /* 检查属性初始化 conform 声明类型 */
  } else if (auto* m = dynamic_cast<const Method*>(&f)) {
    for (auto& fm : m->formals) O_.add(fm.name, fm.type);          // :234
    std::string t = typeOf(*m->body);
    std::string declared = resolveSelf(m->type);                   // :236
    if (!conforms(t, declared)) error(...);
  }

  O_.popScope();                                                  // :242
  O_.popScope();                                                  // :243
}
```

两层的理由是**遮蔽方向**。手册要求：局部声明（形参）能遮蔽属性，反过来不行。栈的语义是"内层遮蔽外层"，所以：

- 属性 → **外层**（被遮蔽方）
- `self` + 形参 → **内层**（遮蔽方）

如果只用一层（属性和形参塞进同一张表），`add` 的 `[]` 会让"后加的赢"——形参在属性之后加，恰好也对。**所以一层在功能上也能跑。** 那为什么要两层？

因为一层会丢掉一条信息：**你无法再区分"这个名字是属性还是形参"**。现在不需要这个区分，但 `09` codegen 需要——访问属性要生成"从 `self` 指针加偏移量 load"，访问形参要生成"读局部变量"，两者的机器代码完全不同。两层结构把这个区分留在了数据里。

> **一般原则**：数据结构里保留的"多余"层次，往往是为下游阶段留的。这和 `03c` §1.3 说 `line` 必须留是同一个判据——"后续阶段还要不要"。

顺便：`self` 为什么和形参同层、而且是在形参**之前** `add`？因为 `self` 在前、形参在后，形参里叫 `self` 的话会覆盖掉真正的 `self`——而这正好是我们想要的"报错时机"……不，等等。Cool 禁止形参名叫 `self`。我们的实现检查了吗？`:234` 那个循环直接 `O_.add(fm.name, fm.type)`，**没有检查**。这归到 §7。

### 4.2 一个不变式，以及用它审计代码

**不变式**：对任何 `visit(X)`，进入时和返回时 `O_` 的栈深度必须相同。

理由：`visit` 是递归的，父节点在子节点返回后还要继续用环境。如果某个 `visit` 净增/净减了一层，后面所有查找都错位，而且错法极其隐蔽（不会崩，只会查到错误的类型）。

这条不变式给了你一个**可机械执行的审计动作**：找出所有 `pushScope`，检查每一条能到达函数出口的路径上都有配对的 `popScope`。危险信号是 `return` 和 `continue`。

审 `visit(Let)`（`:332`）：

```cpp
O_.pushScope();
for (auto& b : e.bindings) {
  if (b.name == "self") { error(...); continue; }   // ← continue！
  ...
}
result_ = typeOf(*e.body);
O_.popScope();
```

`continue` 跳的是**循环**，`popScope()` 在循环**外面**，所以照样执行。✅ 安全。实测确认（`let self : Int <- 1 in 1`）：

```
ERROR: line 1: 'self' cannot be bound in a let
type checking failed
```

只有一条错误，没有后续的错位崩溃。✅

审 `visit(Case)`（`:349`）：

```cpp
for (auto& b : e.branches) {
  if (seen.count(b.type)) { error(...); continue; }   // ← continue 在 push 之前
  seen.insert(b.type);
  O_.pushScope();                                     // ← push
  O_.add(b.name, b.type);
  std::string t = typeOf(*b.body);
  O_.popScope();                                      // ← pop，中间无 return
  ...
}
```

`continue` 在 `pushScope` **之前**，push/pop 之间没有任何提前退出。✅ 安全。实测（重复分支类型）：

```
ERROR: line 2: duplicate case branch type 'Int'
type checking failed
```

✅ 一条错误，干净退出。

**这个审计值得你自己做一遍**：把 `typechecker.cpp` 里所有 `pushScope` 找出来（一共 4 处：`checkFeature` 两处、`visit(Let)` 一处、`visit(Case)` 一处），逐个验证。这是审计任何递归下降式代码的通用方法——`03a` §4.2 的"契约"是同一个思路的另一个实例（那里的不变式是"递归前必须消耗 token"）。

### 4.3 `visit(Case)` 为什么每分支一层，`visit(Let)` 为什么整体一层

看出不对称了吗？

| | push 次数 | 为什么 |
|---|---|---|
| `let x:A, y:B in body` | 1 次（整个 let） | 绑定之间要**互相可见**（`y` 的 init 能用 `x`） |
| `case e of x:A=>e1; y:B=>e2; esac` | 每分支 1 次 | 分支之间**必须互不可见**（`e2` 里不该能用 `x`） |

这不是风格差异，是语义差异。`let` 的多个绑定是**顺序累积**的环境，`case` 的多个分支是**互斥**的环境。数据结构的形状精确对应了语义。

自己验证一下：`case 1 of i : Int => 1; j : Int => i; esac` 应该报 `i` 未声明（虽然它会先被"重复分支类型"挡住——换成不同类型试）。

## 6. 工业接轨

### 6.1 三个真实编译器的符号表

| 编译器 | 结构 | 归到 §2.2 的哪一类 | 为什么 |
|---|---|---|---|
| **LLVM** `ScopedHashTable` | 一张哈希表，每个 key 挂一条按作用域分段的链；`ScopedHashTableScope` 是 RAII 对象，析构即 popScope | **候选 B** | 被 `EarlyCSE`、MLIR 的 `SymbolTable` 等复用，规模大、深度不设上限 |
| **clang** `Sema` + `IdentifierResolver` | 每个 `IdentifierInfo` 挂一条声明链，外加 `Scope` 对象组成的树（不是栈——因为 C++ 的名字查找要跨越 namespace、base class、ADL） | **候选 B 的扩展** | C++ 的查找规则太复杂，纯栈根本表达不了（想想 `using`、模板两阶段查找） |
| **rustc** `Resolver` | 独立的 pass（`rustc_resolve`），先建 module graph 再解析，因为 `use` 语句和宏展开会引入前向引用 | **不是栈** | Rust 的名字解析**不能**和类型检查同时做，必须先跑完 |

**rustc 那一行值得你多想一分钟。** 我们的实现里，名字解析和类型检查是**同一趟**（`visit(Object)` 里 `lookup` 的同时就产出类型）。这只在"名字必须先声明后使用"的语言里成立。Cool 的局部变量满足这条，所以我们能省一趟。但 Cool 的**类名**不满足——类可以在使用之后定义。这就是为什么 `buildEnvironments` 必须先跑一遍全局扫描（`05b` §1 的全部内容）。

> **一般规律**：语言里每一处"前向引用"（forward reference）都会在编译器里逼出一趟额外的 pass。C 要写函数原型，就是为了省掉这趟；C++ 的类成员可以前向引用（成员函数体里能用后面声明的成员），所以 clang 必须把成员函数体**延迟**到类定义结束后再解析（这叫 late parsing）。你现在能从语言特性反推出编译器的 pass 结构了。

### 6.2 栈式符号表什么时候不够

**闭包**。看这段（伪 Python）：

```python
def make_counter():
    n = 0
    def inc():
        n += 1      # inc 引用了 make_counter 的局部变量
        return n
    return inc      # make_counter 返回后，n 还活着！
```

栈式符号表的核心假设是"离开作用域就撤销绑定"。闭包直接违反它——`inc` 逃逸出去之后还引用着 `n`。所以支持闭包的语言必须做**变量捕获分析**：判断哪些变量被内层函数引用，把它们从栈上挪到堆上（叫 **boxing** 或 **closure conversion**）。CPython 的 `symtable` 模块干的就是这件事，它会给每个名字标注 `LOCAL` / `CELL`（被捕获）/ `FREE`（捕获自外层）。

Cool 没有嵌套函数，所以我们逃过了这一整块。但你要知道这块存在——**"我的语言没有闭包"是我们能用 36 行符号表的前提之一**。

### 6.3 对你的方向（AI Infra）

符号表这个结构在深度学习编译器里到处都是，只是名字变了：

- **MLIR 的 `SymbolTable`**：`mlir::SymbolTable` 是一个 Operation trait，管理 `@func_name` 这类符号引用。和我们的区别是它**只有一层**（module 级），因为 MLIR 的 block argument 用的是 SSA value 直接引用而不是名字——`03c` 提过 AST 上的名字到 IR 上会变成指针/ID，这里就是那件事的落地。**一旦进入 IR，名字解析就已经做完了，符号表退化成只管全局符号。**
- **Triton 的 `CodeGenerator(ast.NodeVisitor)`**：直接在 Python AST 上跑，用一个 dict 栈管 `local_defs`。这是候选 C 的原样翻版——同一个权衡（规模小、深度浅、代码要短）。
- **TVM 的 `Var` 与 `IRBuilder`**：TIR 的 `Var` 是**唯一对象**（不是名字），`let` 绑定直接持有 `Var` 指针。这是 §1 那张表里的"连边"做法，好处是变量重名完全不成问题（想想你手写 CUDA kernel 生成时反复出现的 `i`、`tid`）。

**给你一个具体的迁移点**：你 W6 在读 nanoGPT 和 KV Cache，将来要做 GPU 计算图优化。图变换里最常见的 bug 之一就是"重写一个子图时，新建的节点引用了已经被删掉的旧变量"——这在本质上是作用域错误。MLIR 的 `dominance` 检查（一个 value 的使用必须被它的定义支配）就是把本篇的"内层能看到外层"泛化到了图上。等你读 MLIR verifier 的时候，回头看 §4.2 那条"进出栈深度相同"的不变式。

## 7. 我实测发现的两个真实缺陷

我把编译器构建起来跑了 20 多个探针程序（构建命令见 `03c` §7.2：`clang++ -std=c++17 -O0 -g -o coolc.exe src/*.cpp`）。这一节只讲和"名字解析"直接相关的两个，其余在 `05b` §7 和 `06b` §7。

### 7.1 类型名从来没被解析过

**这是本篇最重要的发现**，而且它藏在一个很容易忽略的角落：`Int`、`List`、`Ghost` 这些**类型名也是名字**，它们也需要解析（"这个名字对应一个已定义的类吗"）。

代码里确实有解析用的谓词，`typechecker.cpp:11`：

```cpp
bool TypeChecker::isType(const std::string& t) const {
  return t == "SELF_TYPE" || t == "Object" || t == "IO" || t == "Int" ||
         t == "String" || t == "Bool" || classMap_.count(t);
}
```

问题是**它只在一个地方被调用**：`visit(New)`（`:370`）。所有其他声明类型的位置都没查。实测四个探针，全部**静默通过**：

```
$ ./coolc.exe p_undef_attr.cl -o o.ll      # class Main { v : Ghost; ... }
wrote o.ll (9996 bytes)                     ← 应该报错

$ ./coolc.exe q_undef_formal.cl -o o.ll    # f(x : Ghost) : Ghost { x }
wrote o.ll (10201 bytes)                    ← 应该报错

$ ./coolc.exe d_undeftype.cl -o o.ll       # let x : Nonexistent in ...
wrote o.ll (9955 bytes)                     ← 应该报错
```

第四个更严重。`case 1 of x : Ghost => 1; esac`：

```
$ ./coolc.exe r_undef_case.cl -o o.ll
ERROR: unordered_map::at
```

这条 `unordered_map::at` 不是类型检查的错误信息（类型检查的错误都带 `line N:`），它是一个**被 `main.cpp` 的 catch 兜住的 C++ 异常**。我确认了它来自 codegen 而不是 typechecker：在那个 `case` 后面再加一个 `1 + "s"`，输出是

```
ERROR: line 1: arithmetic operands must be Int, got Int and String
type checking failed
```

——只有算术错误，**没有**关于 `Ghost` 的抱怨。说明类型检查这一趟完全放过了 `Ghost`，程序走到了 codegen，在 `codegen.cpp:343` 的 `descendants_.at(br.type)` 上炸掉。

**这是一个教科书式的"缺失检查导致下游崩溃"**。类型检查器的契约是"我通过的程序，下游可以无条件信任"。一旦有漏检，下游的 `.at()`、数组下标、指针解引用都会变成定时炸弹。真实编译器里这类 bug 的表现就是"编译器 ICE（internal compiler error）"——clang 崩掉时让你报 bug 的那个提示。

**修法**（留作 §8.1）：在所有出现声明类型的位置调 `isType`。位置清单：`Attribute::type`、`Method::type`、`Method::formals[i].type`、`Let::bindings[i].type`、`Case::branches[i].type`、`StaticDispatch::type`。六处。

### 7.2 `case` 能绑定 `self`，`let` 不能

## 下一步

本篇处理的是**表达式内部**的名字：局部变量、形参、属性。但还有一整类名字没碰——**类名和方法名**。它们不服从栈式作用域（类是全局可见的，而且可以前向引用），所以需要完全不同的机制。

接着读 `05b_类环境构建.md`：

- **为什么必须先有一趟全局扫描** —— 从"类可以在使用之后定义"这个实测事实推出多趟结构；
- **继承图的六项检查，逐条推出理由** —— 特别是"为什么必须查继承环"，真正的理由不是"不合逻辑"，而是 `conforms` 里那个 `for(;;)` 会**死循环**；
- **`methodsOf`/`attrsOf` 的惰性递归** —— 以及惰性带来的一个实测漏报缺陷；
- **方法重写为什么要求签名完全一致** —— 用手册那个"加字符串到数字上"的例子把类型安全的理由推出来。
