## 精炼段

前十二篇把一个编译器从零拼了出来。本篇要回答的是一个很实在的问题：**学完这些，看现代工业编译器时到底能看懂多少？**

我的答案是：骨架部分你已经全会了，**真正需要新学的只有两件事**——一是"IR 可以有很多层"（MLIR 的 Dialect），二是"编译对象可以不是语句而是算子"（TVM/XLA）。但这两件事都不是凭空冒出来的新范式，它们各自回答了一个具体的失败。所以本篇不按"系统清单"组织，而是按**问题链**：

**§1** 先用 `lli` 把我们自己编译器的输出**真的 JIT 执行**一遍，量出 AOT 和 JIT 的交叉点（实测 5.3 次），把 `11` §5 那个"编译时间算谁的账"的取舍变成一条直线方程。**§2** 问 JIT 凭什么能赢——实测去虚化后整个循环塌缩成一条 `cmovgl`。**§3** 讲 LLVM 的分层，以及它这套设计的边界在哪。**§4** MLIR：为什么"单层 IR"不够。**§5** 是本篇的核心实证：**手工融合快 3.47 倍，而 LLVM 自己不做这件事**——`loop-fusion` 连 `-O3` 都没进。这个落差直接推出了 §6 的深度学习编译器。**§7** 量一下自动调优的搜索空间（一个 tiling 参数就有 2.24 倍的落差）。**§8** 给你的科研方向收口。

## 1. AOT 与 JIT：把取舍量成一条直线

### 1.1 先把我们自己的编译器放进 JIT 里跑

`11` §5 讲线性扫描时说过"JIT 的编译时间是程序运行时间的一部分"。这话很容易听过就算，所以我把它量了出来——而且**用的就是我们自己编译器的输出**。

LLVM 自带一个 JIT：`lli`，它直接执行 `.ll`。我们的 `factorial.ll` 要调 `runtime.c` 里的函数，所以先把运行时也编成 IR 链接起来：

```bash
./coolc.exe tests/factorial.cl -o f.ll
clang -S -emit-llvm -O0 runtime.c -o rt.ll
llvm-link f.ll rt.ll -S -o f2.ll
lli f2.ll          # 输出 120
```

**输出 `120`，和 AOT 编译出来的可执行文件一致。** 同一份 IR，既可以 `clang` 成 `.exe`（AOT），也可以丢给 `lli` 当场编译执行（JIT）——**这正是 `07` §1 那个"IR 是一个稳定的接口"的最好证明**：后端换了一整套，前端一个字都不用改。

> **一个坑值得记**：第一次 `lli` 失败，报 `Symbols not found: [ strdup ]`。原因是 JIT 需要在进程里解析所有外部符号，而 `strdup` 在这个 msys2 环境里没有以 `lli` 能找到的形式导出。把 `runtime.c` 里的 `strdup` 换成自己写的 5 行 `my_strdup` 就通了。**这不是个边角问题**：JIT 必须能解析每一个外部符号，而 AOT 把这件事交给了链接器。**"谁来解析符号"是 AOT 和 JIT 一个真实的工程差别。**

### 1.2 交叉点实测

各取 7 次的中位数（`factorial.cl`）：

| | 耗时 |
|---|---|
| AOT 编译一次（`clang -O2`） | **212 ms** |
| AOT 编译完之后每次运行 | **49 ms** |
| JIT（`lli`）每次运行 | **89 ms** |

写成跑 `n` 次的总耗时：

```
AOT 总耗时 = 212 + 49n
JIT 总耗时 = 89n
```

**交叉点** `n = 212 / (89 − 49) = 5.3` 次：

| n | AOT | JIT | 赢家 |
|---|---|---|---|
| 1 | 261 ms | **89 ms** | JIT |
| 3 | 359 ms | **267 ms** | JIT |
| 5 | 457 ms | **445 ms** | JIT |
| **6** | **506 ms** | 534 ms | **AOT** |
| 12 | **800 ms** | 1068 ms | AOT |

**读数**：跑 5 次以内 JIT 划得来，6 次以上 AOT 开始赢，而且差距线性拉开。

**这就是 `11` §5 那个论断的定量形式**，而且它同时解释了两件看起来矛盾的事：

- **为什么脚本语言用 JIT/解释器**：一个脚本通常只跑一遍，`n = 1`，AOT 那 212 ms 的编译时间纯属浪费。
- **为什么服务端程序用 AOT**：`n` 是几百万，那 212 ms 摊到每次上等于零，而每次省下的 40 ms 是纯赚。

**真实 JIT 比这更聪明**：它不是"全部 JIT"，而是**先解释执行、profile 找出热函数、只编译热的**（V8、HotSpot 都这样）。用上面的模型说：**对 `n` 小的函数走解释（避开编译成本），对 `n` 大的函数走编译（摊销掉）**——这是在**逐函数**地做上面那道交叉点计算。

> **别把 `lli` 的 89 ms 当成"JIT 的固有开销"**。`lli` 每次都从头编译整个模块、不做分层、不缓存。真实 JIT 有多层（V8 的 Ignition/Sparkplug/TurboFan）、有代码缓存。**这个实验量的是"编译时间 vs 执行时间"这个结构，不是某个具体 JIT 的性能。**

## 2. JIT 凭什么能赢：运行时信息

上面的模型有个隐含假设：AOT 和 JIT 生成的代码**一样快**。**实际上 JIT 可以更快**，因为它掌握 AOT 拿不到的信息。

最典型的就是 `10` §7.3 那个去虚化。那里我们靠一条 `!invariant.load` 把三次 vtable 加载提出了循环，但**间接调用本身还在**。JIT 能做得更彻底：它在运行时观察到"这个调用点 1000 次都调到同一个实现"，于是**赌**它就是那个实现，直接内联，并留一个类型检查做后路（**去优化**，deoptimization）。

**实测这个赌注值多少。** 用 C++ 模拟（我们的 Cool 编译器没有去虚化能力）：

```cpp
struct Base { virtual int f(int x) const { return x + 1; } virtual ~Base() {} };
struct Impl : Base { int f(int x) const override { return x + 1; } };
int drive(const Base* b, int n) { int s = 0; for (int i = 0; i < n; i++) s = b->f(s); return s; }
```

`-O2` 编译，数循环内的间接调用：

| 版本 | 循环内间接调用 | 结果 |
|---|---|---|
| `const Base*`（不知道真实类型） | **1** | 循环保留，每轮一次间接调用 |
| `const Impl*` + `final`（知道真实类型） | **0** | 见下 |

第二种情况的**全部**汇编：

```asm
_Z5drivePK4Impli:
	xorl	%eax, %eax
	testl	%edx, %edx
	cmovgl	%edx, %eax
	retq
```

**整个循环消失了。** 推理链条是：知道真实类型 → 去虚化 → 可以内联 → 内联后编译器看穿了 `s = s + 1` 重复 n 次 → **直接算出结果是 `n`**（`cmovgl` 是在处理 `n ≤ 0` 的情况）。

**这才是去虚化的真正价值**：它本身只省一次间接跳转，但它**解除了后续所有优化的封锁**。`10` §1.2 那个命题在这里第二次兑现——**优化的能力取决于可用的前提**，而"真实类型是什么"就是那个前提。

**三种拿到这个前提的方式**，对应三类编译器：

| 谁 | 怎么拿到"真实类型" | 代价 |
|---|---|---|
| C++（AOT） | 程序员写 `final`，或者 LTO 全程序分析 | 要么靠人工标注，要么编译变慢 |
| JVM / V8（JIT） | **运行时 profile** | 需要去优化机制兜底 |
| 我们的 coolc | 拿不到 | 间接调用留在循环里（`10` §7.3 实测） |

## 3. LLVM / Clang：我们手写的那套东西的工业版

**LLVM 的定位不是"一个编译器"，而是"一套可复用的编译器中后端"。** 对照我们十二篇做的事：

| 我们做的 | LLVM 里对应的 |
|---|---|
| `lexer.cpp` + `parser.cpp` + `typechecker.cpp` | Clang 前端 |
| `codegen.cpp` 拼字符串生成 `.ll` | LLVM IRBuilder（C++ API） |
| 手算数据流（`10` §4.2） | `opt` 的上百个 analysis/transform pass |
| 没做（交给 `llc`） | 指令选择、寄存器分配（`11`）、指令调度 |
| `runtime.c` | 各语言自己的运行时 |

**三段式的分界线正是 `07` §1 那个论证**：前端只管"语言语义 → IR"，后端只管"IR → 某个架构"。于是 M 种语言 × N 种架构的工作量从 M×N 变成 M+N。Rust、Swift、Julia、Zig 全都只写前端。

**你已经掌握的部分比你以为的多。** 这十二篇里你手写过词法、语法、类型检查、IR 生成、运行时，手算过数据流分析和干涉图，实测过 pass 的效果和寄存器分配器的差距。**LLVM 内部就是这些东西，只是每一项都做到了工业强度。**

**那它的边界在哪？** LLVM IR 是**单层**且**偏底层**的：它只有标量、向量、指针、`getelementptr`。一个矩阵乘法降到 LLVM IR 之后，就只是三层嵌套循环加一堆访存——**"这是矩阵乘法"这个信息已经丢了**。想做 tiling、想换数据布局、想融合两个算子，在这一层都极其困难，因为你要从循环嵌套里**反推**出原本的语义。§5 的实测会非常直接地展示这个边界。

## 4. MLIR：为什么"单层 IR"不够

**MLIR 的核心主张**：不要把所有语言都直接降到一个底层 IR，而是允许**多层 IR 共存**，每层用自己最合适的抽象做优化，再逐级下降。

一层就是一个 **Dialect**（方言）= 一套自定义的操作 + 类型 + 语义。一个典型的下降链：

```
tf / torch dialect     ← "这是一次卷积"（语义完整）
      ↓ lowering
linalg dialect         ← "这是一次带索引映射的张量收缩"（能做融合、tiling）
      ↓
affine / scf dialect   ← "这是嵌套循环"（能做循环变换）
      ↓
llvm dialect           ← LLVM IR（能做标量优化、寄存器分配）
      ↓
机器码
```

**关键洞察是"在哪一层做优化"**。拿 §5 要实测的算子融合举例：

- 在 `linalg` 层，融合是**改写两个操作的索引映射**，几行的事；
- 在 `llvm` 层，融合意味着**证明两个循环可以合并**（边界相同、无依赖冲突、访存不别名）——`10` §6 那套安全性证明全都要重做一遍，而且大概率证不出来。

**同一个变换，在高层是改写，在底层是定理证明。** 这就是 MLIR 那句"选对抽象层级"的全部含义。

> **MLIR 不是"又一个 IR"，是"定义 IR 的框架"**。它提供的是 SSA、区域、pass 管理、类型系统这些**公共设施**（你在 `07`、`10` 篇学的全部概念），让你不必为每个领域从头写一个编译器。TensorFlow/XLA、Triton、大量 AI 芯片工具链都建在它上面。
>
> 本机没装 `mlir-opt`，所以本篇的 MLIR 部分**是概念性的、没有实测**——我不把没验证的东西写成验证过的。想动手就装 LLVM 完整版跑官方 Toy tutorial（§9 第 5 题）。

## 5. 实测：算子融合值 3.47 倍，而 LLVM 不做

> **这一节是本篇的核心证据。** 它要回答一个很尖锐的问题：既然 LLVM 这么成熟，为什么深度学习还要另造一套编译器？

### 5.1 融合值多少

三个"算子"（乘 2 → 加 1 → relu），8M 个 `float`（32 MB），20 次取最好：

```c
/* 未融合：三个算子各自完整读写一遍数组，像三个独立 kernel 依次启动 */
void mul (float* o, const float* a, int n){ for(int i=0;i<n;i++) o[i]=a[i]*2.0f; }
void addb(float* o, const float* a, int n){ for(int i=0;i<n;i++) o[i]=a[i]+1.0f; }
void relu(float* o, const float* a, int n){ for(int i=0;i<n;i++) o[i]=a[i]>0?a[i]:0; }

/* 融合：一趟做完，中间结果留在寄存器里，从不落内存 */
void fused(float* o, const float* a, int n){
  for(int i=0;i<n;i++){ float t=a[i]*2.0f; t=t+1.0f; o[i]=t>0?t:0; }
}
```

| | 耗时 | 内存流量 |
|---|---|---|
| 未融合（3 趟） | **10.27 ms** | 192 MB（读写各 3 次 32 MB） |
| 融合（1 趟） | **2.96 ms** | **64 MB**（读一次、写一次） |
| | **3.47 倍** | **3.0 倍** |

**加速比 3.47 和流量比 3.0 几乎相等**——这说明这三个算子是**彻底的访存带宽瓶颈**：算术部分（一次乘、一次加、一次比较）根本不是瓶颈，时间全花在搬数据上。**所以融合的收益不是"少算了什么"，而是"少搬了什么"。**

**这正是深度学习负载的典型形状**。elementwise 算子（激活、加偏置、归一化、残差相加）全都是这个样子：算得极少、搬得极多。**融合它们是最高性价比的优化，没有任何一项能与之相比。**

> **一个实验设计上的坑，值得单独说。** 第一版我测出"两个版本都是 0.00 ms"。原因是 `o` 数组算完之后**没人读**，`-O2` 把整个计算连同 `malloc` 一起删掉了——**正是 `10` §7.2 那个 DCE 的条件（无副作用 + 结果不活跃）**。修法是把结果累加到一个会被打印的 `sink` 变量上。
>
> **教训**：**给性能测试喂一个"消费者"**，否则你测的是空循环。这和 `11` §6.2 那两次统计翻车是同一类错误——**先确认你测的东西真的存在**。

### 5.2 LLVM 自己做这件事吗？实测：不做

手工融合快 3.47 倍，那 LLVM 为什么不自动做？把三个循环写在同一个函数里、紧挨着，连中间数组都直接传进去：

```c
void three(float* o, float* t1, float* t2, const float* a, int n){
  for(int i=0;i<n;i++) t1[i]=a[i]*2.0f;
  for(int i=0;i<n;i++) t2[i]=t1[i]+1.0f;
  for(int i=0;i<n;i++) o[i]=t2[i]>0?t2[i]:0;
}
```

用 LLVM 自己的循环分析数顶层循环（比数汇编跳转可靠——那会被向量化和展开污染，这是我第一次数错的地方）：

```bash
clang -O1 -S -emit-llvm -Xclang -disable-llvm-passes autofuse.c -o raw.ll
opt -passes='mem2reg,loop-simplify,loop-rotate' raw.ll -S -o norm.ll
opt -passes='print<loops>' norm.ll -disable-output 2>&1 | grep -c "^Loop at depth 1"
opt -passes='loop-fusion' norm.ll -S -o fused.ll
opt -passes='print<loops>' fused.ll -disable-output 2>&1 | grep -c "^Loop at depth 1"
```

| 情形 | 融合前 | 跑 `loop-fusion` 后 |
|---|---|---|
| 原样（指针可能别名） | 3 | **3** |
| 全部加 `__restrict`（保证不别名） | 3 | **3** |
| 两个**完全独立**的循环 | 2 | **2** |
| 两个独立且**定长** `i<1024` 的循环 | 2 | **2** |

**一个都没融合。** 连"两个独立、定长、不别名"这种最平凡的情形都不融。

**再查一件更说明问题的事**——这个 pass 在默认流水线里吗？

```bash
opt -passes='default<O2>' -print-pipeline-passes /dev/null | tr ',' '\n' | grep -c loop-fusion
```

| pass | 在 `-O2` 流水线里？ |
|---|---|
| `licm` | 在（2 次） |
| `loop-rotate` | 在 |
| `loop-unroll` | 在（2 次） |
| `loop-vectorize` | 在 |
| `loop-deletion` | 在（2 次） |
| `indvars` | 在 |
| **`loop-fusion`** | **`-O2` 不在，`-O3` 也不在** |

**这就是答案。** `loop-fusion` 在 LLVM 里是一个存在但**未启用、能力有限**的 pass。不是 LLVM 团队疏忽，而是**在 LLVM IR 这一层做融合太难**（§4 说的那件事）：一旦降成循环 + 访存，编译器要重新证明边界相同、无依赖冲突、不别名、副作用可交换——`10` §6 那一整套安全性条件。**证得出来的情形太少，收益不确定，所以干脆不进默认流水线。**

### 5.3 所以图级编译器不是"又一个轮子"

把 §5.1 和 §5.2 放在一起：

```
融合的收益：实测 3.47 倍（而且是访存瓶颈型负载的常态）
LLVM 的能力：loop-fusion 连 -O3 都没进，独立定长循环都不融
⟹ 必须在"还知道这是算子"的那一层做融合
⟹ 图级 IR（Relay / HLO / linalg / torch.fx）存在的理由
```

**在图级 IR 上，融合是平凡的**：`relu(add(mul(x, 2), 1))` 是一棵表达式树，融合就是"把这三个节点标成一个 kernel"——**根本不需要证明任何东西**，因为中间张量的生产者和消费者在图上一目了然，依赖关系是显式的。

**一句话总结**：**信息在下降过程中会丢失，而优化需要信息。** 所以要在信息还在的那一层动手。**这是 `10` §1.2 那个中心命题（优化能力取决于可用前提）在整个编译栈尺度上的复述。**

## 6. 深度学习编译器：TVM / XLA / Triton

有了 §5 的实测，这三个系统的设计就都是可推导的，不需要记。

| 系统 | 图级 IR | 算子级 | 定位 |
|---|---|---|---|
| **TVM** | Relay / Relax（融合、图改写、布局变换） | TIR（循环变换、tiling、向量化） | 主打**自动调优**（AutoTVM / Ansor） |
| **XLA** | HLO | 降到 LLVM / TPU 后端 | 编译 TF / JAX 图 |
| **Triton** | —（在 PyTorch 侧由 Inductor 建图） | Python 写 **block 级** kernel | `torch.compile` 的默认 GPU 后端 |

**共同的两层结构，对应我们已经看清的两件事**：

| 层 | 干什么 | 对应本套笔记 |
|---|---|---|
| **图级** | 融合、常量折叠、布局变换、**显存规划** | §5 的融合；`10` §8.2 的对应表；`12` §9.3 的显存规划 |
| **算子级** | tiling、向量化、循环展开、共享内存搬运 | §7 的 tiling 实测；`11` §8 的寄存器压力 |

**Triton 的定位值得单独说一句**，因为它和你的工作最近。它把抽象层级定在"**block**"（一个线程块处理一块数据），程序员写 block 级逻辑，编译器负责线程级的展开、访存合并、shared memory 分配、以及**寄存器分配**（`11` §8 那些约束）。**它是"手写 CUDA"和"全自动编译"之间的一个折中点**——你保留算法决策权，把索引和调度的苦活交给编译器。

**而 `torch.compile` 就是 §1 那个 JIT 模型的深度学习版**：运行时把 `torch.fx` 图融合、生成 Triton kernel、编译、缓存。**它的编译时间也要摊销**，所以第一次调用慢（那就是 §1.2 里 AOT 的那个 212 ms）、之后快——这也是为什么它默认缓存编译结果。

## 7. 实测：自动调优在搜什么

图级融合定了"算什么",算子级还要定"**怎么算**"。这一层的参数多到无法手调，所以要搜——本节量一下搜索空间有多值钱。

512×512 矩阵乘法，只调**一个** tiling 参数 `T`：

| 版本 | 耗时 | 相对 naive |
|---|---|---|
| naive（三层循环） | 65.7 ms | 1.00x |
| tiled `T=8` | 19.5 ms | 3.37x |
| tiled `T=16` | 16.1 ms | 4.09x |
| tiled `T=32` | 11.7 ms | 5.63x |
| tiled `T=64` | 9.7 ms | 6.80x |
| tiled `T=128` | 9.5 ms | 6.94x |
| tiled `T=256` | **8.7 ms** | **7.56x** |

**三个读数**：

1. **分块本身值 3.37 倍起**，和 §5.1 一样是访存局部性的收益：`naive` 版本内层遍历 `B[k][j]` 是跨行访问（步长 512 个 float = 2 KB），每次都是新的 cache line；分块让工作集装进 cache。
2. **同一个算法、只改一个参数，最差和最优差 2.24 倍**（3.37x vs 7.56x）。**这就是自动调优要捡的钱。**
3. **最优点不好猜**。这个实现里 `T` 越大越好，一直到 256；但它依赖具体的循环顺序（我用的是 `ii-kk-jj` + 内层提出 `A[i][k]`）、cache 大小、以及编译器的向量化决策。**换个机器、换个矩阵尺寸、换个数据类型，最优点就会变。**

**第 3 条正是自动调优存在的全部理由**。真实的搜索空间远不止一个 `T`：

```
tiling 各层大小 × 循环顺序 × 是否向量化 × 展开因子
  × 是否用 shared memory × 线程绑定方式 × 是否 double buffer
```

**乘起来轻易上亿。** 所以 Ansor/AutoTVM 的做法是：**cost model 预测 + 进化搜索剪枝 + 少量真机测量校准**。

> **这个模式你在 `11` §3.2 见过一次**：图着色是 NP 完全，但真实干涉图稀疏，所以启发式够用。**这里是同一个工程模式的第二次出现**——搜索空间巨大但有结构（性能是参数的连续函数、局部最优附近有信息），所以引导式搜索够用。**"问题理论上难，但实例有结构，于是启发式够用"是整个编译器领域最反复出现的一条元规律。**

## 8. 接到你的方向

你的研究是「GPU 计算图 / 巨核大模型推理优化」，目标 ≥20% 提升。本套笔记的三个结论直接落在上面：

**① 融合的收益上限由访存瓶颈决定（§5.1）。** 实测加速比 3.47 ≈ 流量比 3.0，说明**先算清流量比，就能预估融合收益的天花板**。你做 AMK 的 profiling 时，`nsys`/`ncu` 的 DRAM 吞吐和 achieved occupancy 就是这个账的两个读数。**如果某次融合的流量比只降了 10%，就别指望它能带来 20% 的提升——去找流量比大的那些融合机会。**

**② 融合粒度受寄存器压力约束（`11` §8）。** 融得越多，同时活跃的中间值越多 → 寄存器压力上升 → 溢出到 local memory 或 occupancy 下降。**所以"最优融合粒度"是一个带约束的优化问题**，而 `11` §4.3 那个溢出代价函数就是约束的形式。**这是你手上最具体的一个可量化取舍**：融合流量收益 vs 寄存器压力代价，两边都能用 `ncu` 读出来。

**③ 中间张量的生命周期在编译期已知，所以不需要 GC（`12` §9.3）。** 巨核里的中间值生命周期就是计算图上的一段，用 `10` §4 的活跃区间分析就能算出来，于是可以**静态复用缓冲区**：运行时零开销、零暂停。**"活跃区间"这一个概念，在寄存器上叫寄存器分配，在堆上叫 GC，在张量上叫显存规划**——你现在对三者是同一套框架这件事有完整的把握了。

**一条可操作的路径**（按对你科研的直接价值排序）：

1. **先把 §5 和 §7 的实验在 H100 上重做一遍**（CUDA 版）。你有真机，这是你相对师姐的独特价值（`nsys` profiling）。量出融合前后的 DRAM 流量比和实测加速比，看两者是否还像 CPU 上那样吻合——**GPU 上带宽和算力的比例不同，结论可能不一样，而这个"不一样"本身就是可写进报告的发现。**
2. **读 Triton 生成的 PTX**，对照 `11` §8 数 registers/thread 和 spill。这把本套笔记的 §6、`11` §8 和你的 AMK 工作接在一处。
3. **MLIR 的 Toy tutorial**（§9 第 5 题），理解 Dialect 和 lowering。有了 `07`/`10` 两篇的底子，这个 tutorial 会比你预期的顺。
4. **读 TVM 和 MLIR 论文**（[TVM](https://arxiv.org/abs/1802.04799)、[MLIR](https://arxiv.org/abs/2002.11054)）。**放在第 4 位是故意的**——先有 §5 那个 3.47 倍的手感，再读论文，你会知道它们每一句在解决什么。

## 12. 本文你掌握了什么 / 易错点 / 下一步

**掌握**：AOT 与 JIT 的取舍可以写成一条直线并算出交叉点（实测 5.3 次），以及真实 JIT 为何要分层+profile；JIT 的真正优势是运行时信息（去虚化解除内联封锁，实测循环整体塌缩）；LLVM 三段式与我们十二篇的逐项对应，以及它"单层偏底层 IR"的边界；MLIR 用 Dialect 把"选对抽象层级"制度化，以及"高层是改写、底层是定理证明"这个判据；**算子融合实测值 3.47 倍而 LLVM 的 `loop-fusion` 连 `-O3` 都没进**——这个落差就是图级编译器的存在理由；TVM/XLA/Triton 的两层结构如何从这个落差推导出来；自动调优在搜什么以及它为什么必要（一个参数 2.24 倍）；以及"活跃区间"这一个概念如何贯穿寄存器分配、GC 与显存规划。

**易错点**：

1. **JIT ≠ 解释器**。JIT 生成**机器码**，只是时机在运行时。
2. **JIT 不是"全部编译"**，是解释 + profile + 只编译热点，即逐函数地算 §1.2 那道交叉点。
3. **MLIR 不是"又一个 IR"**，是定义 IR 的**框架**。
4. **"LLVM 很成熟"不等于"LLVM 什么都做"**。`loop-fusion` 存在但未启用（§5.2 实测），**存在一个 pass ≠ 它在默认流水线里**。
5. **融合的收益来自少搬数据，不是少算**（§5.1 加速比 ≈ 流量比）。对计算密集型算子，融合收益会小得多。
6. **性能测试必须有消费者**，否则 `-O2` 会把被测代码整段删掉（§5.1 我实测踩过）。
7. **数循环个数别去数汇编跳转**——向量化和展开会污染计数；用 `opt -passes='print<loops>'`（§5.2 我第一次就数错了）。
8. **深度学习编译器的优化重点不是寄存器分配**，而是融合 + 内存层次 + 自动调优；但寄存器压力会反过来**约束**融合粒度（§8 第 ② 条）。

**下一步**：读 `14_总装_完整编译器与测试.md`。那一篇把十三篇的所有产出拼成一条可运行的链路、跑完整测试、并对全套知识做一次收口验收。**到那里你会发现，这十三篇里真正新的概念不超过二十个，其余全是同一组概念在不同层级上的复用**——而那正是编译原理值得学的原因。
