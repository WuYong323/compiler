## 精炼段

`07` 篇说过 IR 里的虚拟寄存器"想要多少有多少"，`09` 篇我们就真的这么用了——`fresh()` 是个单调计数器，一个六参数的算术函数实测生成 **187** 个 `%tN`。但 x86-64 只有 16 个通用寄存器，其中还有几个被栈指针、帧指针占着。**这个落差必须有人来填，填它的就是寄存器分配。**

本篇的逻辑链条很短但很紧：先说清寄存器和内存的差距为什么值得大费周章（§1）；然后指出分配的**唯一硬约束**是"同时活跃的两个值不能住同一个寄存器"，而"同时活跃"来自 `10` 篇的活跃变量分析（§2）；接着发现这个约束的数学形式**就是**图着色（§3）——于是立刻得到一个坏消息（NP 完全）和一个好消息（有很成熟的启发式）。§4 讲图着色算法为什么长成"先简化再着色"那个样子，§5 讲 JIT 为什么宁可要更差的分配也要更快的算法，§6 是实测：`fast` 和 `greedy` 两个分配器在同一个函数上的差距，比我预想的大一个数量级。

## 1. 为什么值得大费周章

| | 寄存器 | L1 缓存 | 内存 |
|---|---|---|---|
| 延迟 | ~1 周期 | ~4 周期 | ~200+ 周期 |
| 数量 | 16 个通用 | 几十 KB | GB 级 |
| 寻址 | 指令直接编码 | 需要地址计算 | 需要地址计算 |

溢出到栈的值通常在 L1 里，所以"溢出一次"的代价不是 200 周期而是几周期——**但它还有两个隐性成本**：多出来的 `load`/`store` 指令本身要占**发射带宽**和**指令缓存**，而且会**增加依赖链长度**，妨碍乱序执行。这就是 §6 里 `fast` 版本汇编长 58% 的来源。

**一个必要的澄清**：现代 CPU 有**寄存器重命名**（把架构寄存器映射到上百个物理寄存器，消除假依赖）。那是不是意味着编译器的分配不重要了？**不是。** 重命名解决的是"同名但无关的值互相拖累"，它**不能**把内存变成寄存器——一旦编译器决定把某个值放栈上，那就是一次真实访存，硬件无法撤销这个决定。**编译器决定"谁值得留在寄存器里"，硬件只优化"已经在寄存器里的怎么并行"。**

## 2. 问题的准确形式

### 2.1 唯一的硬约束

> 两个虚拟寄存器可以共用一个物理寄存器 ⟺ 它们**不同时活跃**。

"活跃"就是 `10` §4.1 那个定义。为什么这条是充要的：

- **必要**：若 `a`、`b` 同时活跃（都还有后续的读），共用一个寄存器时后写的会覆盖先写的，先写的那个值就丢了 → 算错。
- **充分**：若不同时活跃，那么在 `b` 开始需要这个寄存器之前，`a` 的值已经再也不会被读 → 覆盖它无害。

**所以寄存器分配的输入不是"变量列表"，而是"活跃区间"。** 这就是 `10` 篇和本篇的接缝：没有活跃变量分析，本篇的问题根本无法定义。

### 2.2 活跃区间 vs 活跃性：一个精度差别

**活跃区间**（live range）常被简化成一个**区间** `[定义点, 最后一次使用点]`。这个简化方便（§5 的线性扫描全靠它），但**它高估了活跃性**：

```
     def a
     ...        ← a 在这里活跃
     use a      ← a 最后一次使用
     ...        ← a 已经死了，但"区间"表示法里 if 分支可能把它拉长
     use a      ← 只在某个分支里
```

真实的活跃性是 CFG 上的一个**集合**（每个程序点一个集合），把它压成一条线段会把"分支里才活跃"的部分也算进去。**图着色用集合（精确），线性扫描用区间（近似）**——这是 §5 那张对比表里"质量"差别的根源之一。

## 3. 约束的形状就是图着色

### 3.1 建图

把约束画出来：节点 = 虚拟寄存器，**边 = 两者同时活跃**。这张图叫**干涉图**（interference graph）。

```
活跃区间:  a: ├────────┤
           b:    ├─────┤
           c:       ├─────┤
           d:          ├──┤

干涉关系:  a-b（重叠）, a-c（重叠）, b-c（重叠）, b-d, c-d
           a-d? 不重叠 → 无边

干涉图:      a ─── b
              \   / \
               \ /   \
                c ─── d
```

现在"分配 K 个物理寄存器"这个问题变成了：

> 用 K 种颜色给干涉图的节点着色，使相邻节点颜色不同。

上图里 `a`、`b`、`c` 互相都有边（一个三角形），所以**至少要 3 种颜色**；`a` 和 `d` 无边，可以同色。**这就是"图着色"三个字的全部来历——它不是一个比喻，是同一个问题。**

### 3.2 坏消息与好消息

**坏消息**：图的 K-着色问题是 **NP 完全**的（K ≥ 3）。所以不存在已知的高效精确算法。

**好消息有两条**：

1. **只要启发式，不要最优。** 编译器不需要"最少颜色"，只需要"用 K 种颜色成功着色，否则挑几个溢出"。
2. **真实程序的干涉图不是随机图**，它相当稀疏（大部分值活得很短），所以简单启发式在实践中效果很好。

**这是一个很典型的工程模式**：问题理论上难，但实例有结构，于是启发式够用。`13` 篇里 TVM 的调度搜索是同一个模式（搜索空间巨大，但用 cost model + 进化搜索就能找到够好的点）。

## 4. 图着色分配：算法为什么长这样

Chaitin/Briggs 算法五步。**重点不是背步骤，是理解第 2 步那个判据是怎么来的。**

### 4.1 关键引理

> 如果节点 `n` 的度数 **< K**，那么把 `n` 从图里摘掉、给剩下的图着完色后，`n` **一定**能着上色。

**证明一行**：`n` 最多 `K-1` 个邻居，它们最多用掉 `K-1` 种颜色，至少还剩 1 种给 `n`。

**这个引理直接给出了算法**：度数小的节点"不用操心"，可以放心推迟决定。于是：

### 4.2 五步

1. **建图**：用 `10` 篇的活跃变量分析结果建干涉图。
2. **简化（simplify）**：反复找度数 `< K` 的节点，从图中移除并**压栈**。（由引理，这些一定能着色。）
3. **溢出（spill）**：若剩下的图里所有节点度数都 `≥ K`，选一个节点标记为**潜在溢出**，移除，回到第 2 步。
4. **着色（select）**：按出栈顺序（= 移除的逆序）逐个放回，给每个节点选一个邻居未用的颜色。
5. **重写（rewrite）**：真溢出的变量在 IR 里改成 `load`/`store` 访问栈槽，然后**重跑整个分析**——因为插入的 `load`/`store` 改变了活跃区间。

**第 5 步的"重跑"容易被忽略但很重要**：溢出会引入新的短活跃区间（`load` 出来用一下），所以干涉图变了。这是个**迭代**过程，和 `10` §3.3 的不动点迭代精神一致——只不过这里每轮都在改程序。

### 4.3 第 3 步的启发式：选谁溢出

引理只说"度数 < K 安全"，没说度数都 ≥ K 时该选谁。常用的代价函数：

```
溢出代价(n) ≈ (n 的读写次数，按循环嵌套深度加权) / 度数(n)
```

两个直觉：**读写越频繁越不该溢出**（分母上的度数越大越该溢出，因为溢出它能给更多邻居腾地方）；**循环里的访问要加权**（乘以 10^嵌套深度 之类），因为循环体执行次数多。

**"循环里的值优先留在寄存器里"这条，和 `10` §4.2 那个结论互为因果**：循环里的活跃区间因为回边而变长 → 干涉更多 → 更可能被选中溢出 → 但它恰恰是最不该溢出的。**所以加权是必须的，否则算法会系统性地做出最差的选择。**

## 5. 线性扫描：为什么 JIT 宁可要更差的结果

**思路**：放弃图，把活跃区间当线段，按起点排序后从左到右贪心。

1. 所有区间按**起点**排序；
2. 维护"当前活跃集合"（active list），按**终点**排序；
3. 扫到一个新区间：先把已经结束的区间从 active 里移出（释放寄存器），然后分配一个空闲寄存器；
4. 若无空闲：在"当前区间"和"active 里终点最晚的那个"之间，**溢出终点更晚的那个**。

**第 4 步为什么选"终点最晚"**：终点越晚的区间占用寄存器的时间越长，溢出它腾出的"寄存器 × 时间"最多。这是个贪心的局部最优判据。

**复杂度 O(n log n)**，对比图着色的建图开销（干涉图边数可能是 O(n²)）。

| | 图着色 | 线性扫描 |
|---|---|---|
| 活跃性表示 | CFG 上的集合（精确） | 线段（近似，§2.2） |
| 质量 | 高 | 略低 |
| 复杂度 | 建图 O(n²)，可能多轮迭代 | O(n log n) |
| 典型使用者 | gcc、LLVM 的优化编译 | HotSpot C1、V8、早期 LLVM |

**JIT 的取舍逻辑**：JIT 的编译时间是**程序运行时间的一部分**。花 100ms 做完美分配、省下 5ms 执行时间，净亏 95ms。所以 JIT 要**快**，质量够用就行；而 AOT 编译器的编译时间是开发者的一次性成本，值得慢。

**这个取舍在 `13` 篇会以另一种形式重现**：TVM 的自动调优可以搜几小时找最优 kernel（AOT 思路），而 `torch.compile` 必须在秒级出结果（JIT 思路）。**"编译时间算谁的账"决定了算法的选择空间。**

## 6. 实测：分配质量值多少

> 这一节是本篇的证据。所有命令可复现。

### 6.1 先看落差有多大

构造一个寄存器压力高的函数（六个参数、大量中间结果都同时活跃）：

```cool
class Main inherits IO {
  main() : Object { out_int(f(2,3,4,5,6,7)) };
  f(a:Int,b:Int,c:Int,d:Int,e:Int,g:Int) : Int {
    (a*b+c*d)*(e*g+a*d)+(b*c+d*e)*(a*g+b*e)
  };
};
```

```bash
./coolc.exe reg.cl -o reg.ll
grep -cE '^%t[0-9]+ = ' <(sed -n '/^define i8\* @Main.f/,/^}/p' reg.ll)
```

**结果：`Main.f` 一个函数定义了 187 个虚拟寄存器。** 而 x86-64 只有 16 个通用寄存器（`rax rbx rcx rdx rsi rdi rsp rbp r8..r15`），其中 `rsp` 必须当栈指针、`rbp` 常被当帧指针 → **实际可分配约 14 个**。

**187 → 14，压缩比 13:1。** 这个落差之所以能填上，靠的是 §2.1 那条约束：187 个值里绝大多数活得极短（装箱/拆箱的临时值用一次就死），真正同时活跃的很少。

### 6.2 三个分配器的实测差距

```bash
opt -O2 reg.ll -S -o reg_o2.ll
for ra in basic greedy fast; do llc -regalloc=$ra -O2 reg_o2.ll -o reg_$ra.s; done
```

统计 `Main.f` 的函数体：

| `-regalloc=` | 汇编行数 | **溢出槽位** | 栈写 | 栈读 | 通用寄存器 |
|---|---|---|---|---|---|
| `greedy`（默认） | **111** | **0** | **0** | 5 | 12 |
| `basic` | 112 | **0** | **0** | 6 | 12 |
| `fast` | **175** | **15** | 22 | 53 | **5** |

**先说清"溢出槽位"这一列是怎么数的**，因为这里有个陷阱我自己先掉进去了。一开始我只 `grep` 了"带 `(%rsp)` 操作数的指令"，得到 greedy=5、fast=75，就写成了"溢出访存 5 次 vs 75 次"。**但这个数不对**——栈上的访问不全是溢出。真正的判据是：

> **溢出槽必须先被写、后被读**。只被读、从不被写的栈地址，是**调用方传进来的参数**，不是溢出。

按"既被写又被读"重新分类后，结论变了：

```
greedy: 栈写 0 次  →  真实溢出槽 0 个
        那 5 次栈读全部落在 144/152/160(%rsp)，且这三个地址从未被写
fast:   15 个槽位既写又读  →  真实溢出
```

`Main.f` 有 **7 个指针参数**（`self` + 6 个形参），而 Windows x64 调用约定只用 4 个寄存器传参（`rcx rdx r8 r9`），**第 5-7 个参数由调用方压栈**，被调方只能从固定偏移读——那就是 144/152/160。

**所以 `greedy` 在这个函数上一次溢出都没有。** 187 个虚拟寄存器，12 个物理寄存器，零溢出。

四个读数：

1. **`greedy`/`basic` 零溢出**，说明 §6.1 那个 13:1 的落差**完全被吸收了**——靠的是绝大多数临时值活得极短、互不干涉。
2. **`fast` 溢出 15 个槽位、75 次栈访存**，而且**只用了 5 个通用寄存器**（`rax rcx rdx r8 r9`），空着 7 个不用。`fast` 不做全局活跃性分析，基本"用完就放回"，所以它**根本没试图把值长期留在寄存器里**。
3. **汇编 111 → 175 行（+58%）**，多出来的几乎全是栈 `mov`。
4. **`basic` 和 `greedy` 几乎一样**（112 vs 111）。对这个规模的函数，精细启发式的边际收益很小——`greedy` 的优势要在更大的函数上才显出来。

**`fast` 的存在意义**：它是为 `-O0` 设计的，目标是**编译得快**而非**跑得快**。这正好印证 §5 那个取舍，它是"极端偏向编译速度"的那一端。

> **两个测量教训**（都是我实测时踩的，值得记住）：
> ① **数寄存器要先归一化名字**。`%r12` 和 `%r12d` 是同一个寄存器的 64/32 位视图，`%eax`/`%rax` 同理；而且 `%entry`、`%bb1` 这种标签也会被 `%[a-z0-9]+` 匹配到。我第一次数出 19 个，归一化并排除标签后是 12 个。
> ② **数溢出要区分"写过的栈地址"和"只读的栈地址"**，否则会把传参当成溢出——这个错误会让你得出"默认分配器也溢出了 5 次"的错误结论，**方向完全反了**（真相是零溢出）。
> 共同的教训：**统计前先定义清楚"什么算一次"**，否则 grep 出来的数字会很自信地骗你。

### 6.3 顺带看一眼：为什么我们的 IR 寄存器压力这么高

187 个虚拟寄存器里，很大一部分是**装箱/拆箱的产物**。`09` §2.2 算过：一次 `unboxInt` 就是 3 条指令 3 个名字，一次 `boxInt` 是 5 条。上面那个表达式有 11 次算术运算，每次都要拆两个箱、装一个箱 → 光装箱拆箱就占了上百个名字。

**所以"装箱设计"的账在这里第三次被翻出来**：`08` §6 说它浪费内存（16 字节装 4 字节），`09` §7 说它制造堆分配（`-O2` 删不掉），而本篇要问的是——它是否也抬高了**寄存器压力**？直觉上应该会：上百个额外的名字总得住在什么地方。

**实测给出的答案是"不会"。** `greedy` **一次溢出都没有**，说明压力虽然看起来高，实际完全可控——因为那些临时值**活得极短**（拆箱出来算一下、装箱进去就死），彼此几乎不干涉。**"名字多"不等于"压力大"，压力只取决于同时活跃的数量。**

所以装箱的代价只有**两**层是实打实的：内存浪费（`08` §6）和堆分配（`09` §7）。我原本预期的第三层"抬高寄存器压力"在实测面前**不成立**——那上百个名字被 `instcombine` 和分配器一起消化掉了。**这是本篇唯一一处"我预期会有代价、实测发现没有"的地方，值得记住：代价要量，不要推。** 如果我当初只是顺着 §6.1 的 187 这个数字往下写，就会写出一条听起来很顺、实际是错的结论。

## 7. 溢出与调用约定：`08` 篇那张表的来源

**溢出**（spill）= 把某个值放进栈帧的溢出槽，用到时 `load`、改了再 `store`。

而**函数调用**会强制一批溢出，原因是调用约定（`08` §2）：

| 寄存器类别 | 谁负责保存 | 对分配器意味着什么 |
|---|---|---|
| **caller-saved**（易失） | 调用方 | 跨调用活跃的值**不能**放这里（被调函数会覆盖） |
| **callee-saved**（非易失） | 被调方 | 跨调用活跃的值放这里，但被调函数要先存后恢复 |

**所以"跨函数调用"这件事本身就是寄存器分配的一个大麻烦**：一个在调用点两侧都活跃的值，要么放 callee-saved（代价：被调函数多两条 `push/pop`），要么在调用前溢出（代价：两次访存）。

**这解释了 §6.2 的一个细节**：`greedy` 用了 `r12/r13/r14/r15`——这些正是 x86-64 的 callee-saved 寄存器。我们的 `Main.f` 里有一次递归/动态调用，所以分配器选择把跨调用活跃的值放进 callee-saved 里，宁可在函数头尾多几条保存指令。**这是分配器在做 §7 这张表里的权衡，而且做对了。**

## 8. 接到你的方向：GPU 的寄存器压力

这一节对你最有用，因为它是你已有经验的理论背面。

**GPU 的寄存器分配和 CPU 同源但约束更紧**：

| | CPU | GPU（CUDA） |
|---|---|---|
| 寄存器数 | 16 个通用 | 每个 SM 有 64K 个 32 位寄存器，**按线程分配** |
| 溢出到哪 | 栈（通常在 L1） | **local memory**（实际在显存，极慢） |
| 额外约束 | — | **寄存器用量决定 occupancy** |

**那条额外约束是关键**：每个线程用的寄存器越多，一个 SM 能同时驻留的线程块就越少（occupancy 下降），延迟隐藏能力变差。所以 GPU 上的寄存器分配是个**双目标优化**：既要少溢出，又要控制每线程用量。

这就是你调 kernel 时见过的那些现象的来源：

- `nvcc --maxrregcount=N` / `__launch_bounds__`：**人为设一个 K**，强迫分配器多溢出以换取更高 occupancy。这是在手动做 §4.3 的代价权衡。
- "register spilling to local memory" 警告：`ptxas -v` 报的 spill stores/loads，就是 §6.2 那张表的 GPU 版本。
- 循环展开（unroll）提高性能但可能**反而变慢**：展开增加了同时活跃的值 → 寄存器压力上升 → 溢出。**`10` §4.2 那条"回边让活跃区间变长"在这里变成了"展开让活跃区间重叠"。**

> **你做 AutoMegaKernel 的 profiling 时，这套语言是直接可用的**：把"巨核"融合成一个大 kernel，最直接的副作用就是**寄存器压力暴涨**（融合后同时活跃的中间值变多），于是 occupancy 掉、或者溢出到 local memory。**"融合到什么粒度最优"本质上是一个寄存器分配约束下的取舍**，而 `nsys`/`ncu` 里的 register-per-thread 和 spill 计数就是本篇 §6.2 那张表。

## 12. 本文你掌握了什么 / 易错点 / 下一步

**掌握**：寄存器与内存的真实差距（以及为什么硬件重命名不能替代编译器分配）；分配的唯一硬约束及其充要性证明；活跃区间（线段）对活跃性（集合）的高估；干涉图与图着色的等同；NP 完全但实例稀疏所以启发式够用；Chaitin 五步及其核心引理的一行证明；溢出代价函数为什么必须按循环深度加权；线性扫描的贪心判据与 JIT 的取舍逻辑；三个分配器的实测差距；调用约定如何强制溢出；GPU 寄存器压力与 occupancy 的双目标结构。

**易错点**：

1. **干涉图的边是"同时活跃"**，不是"先后使用"、也不是"出现在同一个块里"。
2. **引理的条件是度数 `< K`**，不是 `≤ K`（§9 第 3 题）。
3. **溢出后必须重跑分析**（活跃区间变了），是迭代过程。
4. **线性扫描溢出"终点最晚"的那个**，不是"最早"。
5. **统计汇编里用了几个寄存器要先归一化名字**（`%r12`/`%r12d` 是一个寄存器），否则会多算（§6.2 我实测踩过）。
6. **"虚拟寄存器很多"不等于"寄存器压力大"**——187 个名字，`greedy` 零溢出（§6.3）。压力只看同时活跃的数量。
7. **"栈上有访存"不等于"发生了溢出"**。溢出槽必须**先写后读**；只读不写的栈地址是调用方传进来的参数（§6.2）。
8. **硬件寄存器重命名不能把内存变回寄存器**，编译器的决定是不可撤销的（§1）。

**下一步**：读 `12_垃圾回收.md`。本篇处理的是"值放哪"这个问题在**寄存器**这一侧；`12` 处理它在**堆**那一侧——而我们的堆现在有个明确的问题：实测 `cool_alloc` 被调用 17 次（算 `5!`）、20002 次（循环 10000 次），而 `free` **一次都没有**。下一篇讲怎么把这些内存收回来。
