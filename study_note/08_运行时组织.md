## 精炼段

旧版这一篇有个结构性问题：它花了大半篇幅讲**栈帧、sp/fp、caller-saved/callee-saved 寄存器**，然后在 §3 末尾用一句话交代"因为我们生成 LLVM IR，这些细节由 LLVM 自动处理"。也就是说，**讲得最细的部分是我们完全不碰的部分**，而我们真正要自己设计的部分（对象布局、vtable 槽位分配、类 tag）反而只有示意图。

本篇倒过来：**我们控制什么，就重点讲什么。**

栈帧和调用约定压缩到 §2 一节讲清（它们仍然重要，但重要在"读懂优化后的代码"，不在"我们要实现它"）。真正展开的是三件我们必须自己算的事，而它们共享同一个思路：

> **运行时不做查找。** `obj.x` 不能在运行时搜索属性名，`l.head()` 不能在运行时搜索方法名，`case` 不能在运行时比较类名字符串。全部要在编译期变成常数：下标、槽位、整数。

§3 从"子类对象必须能当父类用"这一条要求，推出**前缀扩展布局**，并实测验证（`%A = {i8*, i8*, i8*}`、`%B = {i8*, i8*, i8*, i8*}`，同一个属性在父子类里的字段下标相同）。§4 读 `codegen.cpp:90` 那 5 行真实的槽位分配算法，解释它为什么保证"重写复用槽位"。§5 讲 `case` 怎么用整数 tag + 后代集合实现类型测试。

§6–§8 是实测部分。我在验证这些布局时发现了**三个真实缺陷**，其中两个会让编译器产出**非法 IR**（`llvm-as` 直接拒绝）：静态分派到**继承来的**方法会调用一个不存在的函数；`case` 分支体里只要含控制流就会生成畸形 φ；还有一个是 `case` 选分支的规则和手册不符（我们按源码顺序，手册要求按最具体类型）。**11/12 个测试全绿的同时存在这些 bug**，§8.4 解释为什么——这是本篇最值得记住的一课。

## 1. 内存四区：我们实际用到哪些

```
高地址
┌──────────────┐
│   栈 Stack   │  ← 函数调用帧。我们通过 alloca 使用，布局由 LLVM 决定
├──────────────┤
│      ↓       │
│    空闲区     │
│      ↑       │
├──────────────┤
│   堆 Heap    │  ← 所有 Cool 对象。我们通过 cool_alloc(=malloc) 使用
├──────────────┤
│  数据 Data   │  ← vtable、类元信息、Int/String 字面量（全是 constant）
├──────────────┤
│  代码 Text   │  ← 编译出的函数
低地址
```

**对照我们生成的 IR，四区一一对应得上**：

| 区 | IR 里的东西 | 例子 |
|---|---|---|
| Text | `define` 的函数 | `define i8* @Main.fact(...)` |
| Data | `constant` 全局量 | `@vtable_Main`、`@class_Int`、`@int_0` |
| Heap | `call @cool_alloc` 的结果 | 每个 `new`、每次装箱 |
| Stack | `alloca` | 每个变量的栈槽（`07` §4.1） |

**一个值得注意的事实**：Cool 的对象**全部在堆上**，没有栈上对象。`new A` 一定是 `cool_alloc`。这和 C++ 不同（C++ 的 `A a;` 在栈上），和 Java 相同（Java 对象全在堆上，只有基本类型在栈上）。**代价是分配频繁**（`07` §6.4 实测：算 `5!` 是 17 次分配、264 字节），好处是**不用区分两种对象的生命周期**——这也是 Java 能用统一 GC 的前提。

## 2. 栈帧与调用约定：为什么本篇不展开

### 2.1 概念（够用的版本）

每次函数调用在栈上开一块**栈帧**，存这次调用的参数、返回地址、局部变量。两个关键寄存器：**sp** 指栈顶（随压栈移动），**fp** 指本帧固定位置（函数执行期间不动，所以局部变量用 `fp + 常量偏移` 访问）。

**调用约定**是调用双方的合同，规定：参数放哪（前几个用寄存器，多的压栈）、返回值放哪（`rax`）、寄存器谁负责保存：

- **caller-saved（调用者保存）**：被调者可以随便破坏，调用者想保留就自己先存。
- **callee-saved（被调者保存）**：被调者要用就得先存后恢复，调用者可以放心用。

记法：**"调用者保存"= 被调者可以破坏**（名字说的是"谁有责任"，不是"谁能用"）。

### 2.2 为什么这些我们不实现

因为我们生成 LLVM IR，**栈帧布局和寄存器分配是 `llc` 的工作**。我们只做两件事：

```llvm
%t0 = alloca i8*                       ; 我说"我要一个槽"，不说它在 fp-8 还是 fp-16
%r = call i8* @Main.fact(i8* %s, i8* %n)   ; 我说"调用"，不说参数放哪个寄存器
```

LLVM 负责把无限虚拟寄存器挤进 16 个物理寄存器（`11` 篇）、决定栈帧大小、插入 prologue/epilogue、遵守目标平台的 ABI。

**那为什么还要懂？** 三个真实场景：

1. **读优化后的汇编**。性能问题往往出在"某个值被 spill 到栈上了"，看得懂栈帧才能诊断。
2. **调用约定是跨语言边界的契约**。我们的 `runtime.c` 是 C 函数，`declare i8* @cool_alloc(i32)` 能正确调用它，靠的就是双方遵守同一个 ABI。**FFI（外部函数接口）出错几乎总是 ABI 理解错误。**
3. **你的方向直接相关**。CUDA kernel 的参数传递、寄存器压力（register pressure）、spill 到 local memory——这些是 GPU 性能的头号问题，和这里是同一套概念。GPU 上寄存器溢出的代价比 CPU 大得多，因为 local memory 是显存。

**所以本篇的取舍是**：概念讲清，不展开实现（因为我们没有实现），把篇幅留给我们真正要算的东西。

## 3. 对象布局：从一条要求推出前缀扩展

### 3.1 要求

`obj.x` 必须是 **O(1)** 的。理由很实在：属性访问是最频繁的操作之一，如果每次都要按名字查哈希表，程序会慢得不能用。

O(1) 意味着：**属性 `x` 在对象里的位置，必须在编译期就是一个确定的常数偏移**。

### 3.2 但还有第二个要求，它才是关键

考虑：

```cool
class A { x : Int; getx() : Int { x }; };
class B inherits A { z : Bool; };
```

`(new B).getx()` 调用的是 `A.getx`，而 `A.getx` 的代码是**编译 `A` 时生成的**——它只知道 `A` 的布局，用的是"`x` 在偏移 1"这个常数。但它此刻操作的对象是个 `B`。

**所以要求是：`x` 在 `B` 对象里的偏移，必须和在 `A` 对象里相同。** 否则 `A` 的方法作用在 `B` 对象上会读错字段。

这个要求直接锁定了布局方案：

| 方案 | 可行？ | 为什么 |
|---|---|---|
| 子类属性排**前面**，父类属性在后 | ✗ | 父类属性偏移改变，`A.getx` 读错位置 |
| 按属性名**哈希**到槽位 | ✗ | 不同类哈希冲突不同，偏移不稳定 |
| 按属性名**字典序**排 | ✗ | 加一个名字靠前的属性会挤动其他所有属性 |
| **父类布局在前，子类属性追加在后** | ✓ | 父类部分逐字节不变 |

**只有最后一个可行。子类布局 = 父类布局 + 追加，即"前缀扩展"。**

### 3.3 这就是 soundness 的内存版

`06a` §1.2 讲 soundness 时说过一句："子类布局是父类布局的前缀扩展，所以槽位下标稳定"。现在这句话有了完整含义：

> **类型系统允许"`B` 用在期望 `A` 的地方"（`B ≤ A`），内存布局就必须让"`B` 对象用在期望 `A` 对象的代码里"真的可行。**
>
> **前者是编译期的许可，后者是运行期的兑现。前缀扩展就是兑现方式。**

这也解释了 `05b` §6 那条规则——**属性不能重定义**。如果 `B` 能把继承来的 `x : Int` 改成 `x : String`，那么 `A.getx` 读偏移 1 会拿到一个 String 当 Int 用。**偏移还在，类型错了。** 所以禁止重定义不是语言洁癖，是布局约束的必然。

（对比**方法可以重写**：重写只是换 vtable 里那个槽位的函数指针，槽位下标不变 → 前缀扩展仍然成立 → 免费。**同一个约束，对属性是禁令，对方法是许可**，因为一个占内存布局、一个占表格槽位。）

### 3.4 实测验证

```cool
class A { x : Int <- 7; y : String <- "hi"; getx() : Int { x }; };
class B inherits A { z : Bool <- true; getz() : Bool { z }; };
class Main inherits IO { main() : Object { out_int((new B).getx()) }; };
```

生成的结构体定义：

```llvm
%A = type { i8*, i8*, i8* }           ; meta + x + y
%B = type { i8*, i8*, i8*, i8* }      ; meta + x + y + z   ← 前 3 个字段和 A 逐字对应
```

**`%B` 的前三个字段和 `%A` 完全相同，第四个是新增的 `z`。前缀扩展，肉眼可见。**

字段访问的下标：

```llvm
; A.getx 里访问 x
%t2 = getelementptr %A, %A* %t1, i32 0, i32 1      ← 字段 1
; B.getz 里访问 z
%t6 = getelementptr %B, %B* %t5, i32 0, i32 3      ← 字段 3
```

运行：

```
$ ./lay.exe
7
```

`(new B).getx()` 正确返回 7——**`A` 的方法读 `B` 对象的字段 1，拿到的确实是 `x`**。前缀扩展生效。

### 3.5 为什么字段下标要 `+1`

`attrOffset` 返回属性在列表里的序号（`codegen.cpp:26-31`），从 0 开始；但 GEP 用的是 `off + 1`（`codegen.cpp:245`）。差的这个 1 就是**字段 0：类元信息指针**。

```
对象内存:
┌─────────────────┐ 字段 0
│ i8* → class_meta│  ← 每个对象都有，动态分派/type_name/case 全靠它
├─────────────────┤ 字段 1
│ 属性 0           │
├─────────────────┤ 字段 2
│ 属性 1           │
└─────────────────┘
```

**每个 Cool 对象的第 0 个字段都是类元信息指针**，无一例外。这是"对象知道自己是什么类"的唯一途径，`§4`（动态分派）、`§5`（case）、`type_name()` 三件事都从这里出发。

### 3.6 对象大小

`codegen.cpp:20-24`：

```cpp
std::string CodeGen::sizeOf(const std::string& cls) {
  if (cls == "Int" || cls == "Bool") return "16";
  if (cls == "String") return "24";
  return std::to_string((1 + attrs_.at(cls).size()) * 8);
}
```

一般类：`(1 + 属性个数) × 8`——那个 `1` 是元信息指针，`8` 是 64 位指针大小。实测（从生成的 `class_meta_t` 里读出）：

| 类 | 属性数 | 实测 size | 算式 |
|---|---|---|---|
| `Object` / `IO` / `Main` | 0 | 8 | (1+0)×8 |
| `A`（x, y） | 2 | 24 | (1+2)×8 |
| `B`（x, y, z） | 3 | 32 | (1+3)×8 |
| `Int` / `Bool` | — | 16 | 硬编码 |
| `String` | — | 24 | 硬编码 |

**`Int` 为什么是 16 而不是 12？** 结构是 `{ i8*, i32 }` = 8 + 4 = 12 字节，但要按 8 字节**对齐**，所以补 4 字节填充到 16。`07` §6.4 实测算 `5!` 分配 264 字节，其中约 1/4 是填充。

**三个基本类型硬编码，是因为它们的布局不由属性决定**（它们在 Cool 里没有属性，值直接放在结构体第二个字段）。这是 `05b` §4 讲的 `installBuiltins` 硬编码取舍在 codegen 侧的延续。

## 4. 分发表：槽位编号如何分配

### 4.1 动态分派 = 三次间接寻址

`07` §5.4 已经逐行读过那 7 条指令，这里给出它的结构：

```
对象 ──字段0──→ class_meta ──字段1──→ vtable ──[槽位 k]──→ 函数指针 ──call──→ 目标方法
      (1次load)            (1次load)         (1次load)
```

**关键：`k` 是编译期常数。** `codegen.cpp:255` 就一行：

```cpp
int idx = methodIndex_.at(e.method);
```

运行时**不查名字**，直接用这个整数索引。三次 load 的代价是固定的，与类层次深度、方法个数都无关——**这是 O(1) 分派**。

对比：Python/Ruby 的方法调用要沿 MRO 查字典，是 O(继承深度) 且涉及哈希。**静态类型语言用编译期信息把这个开销消掉了**，这是静态类型最实在的性能收益之一。

### 4.2 槽位分配算法（真实代码 5 行）

`codegen.cpp:89-94`：

```cpp
auto assign = [&](const std::string& n) {
  if (!methodIndex_.count(n)) methodIndex_[n] = nextMethodIndex_++;
};
for (auto& b : builtins)
  for (auto& kv : methods_[b]) assign(kv.first);
for (auto& c : prog_.classes)
  for (auto& kv : methods_[c->name]) assign(kv.first);
```

**方法名是全局编号的**：同名方法在所有类里共享同一个槽位。`assign` 里那个 `if (!count(n))` 是全部机关——**第二次见到同名方法时不分配新槽位**。

于是"重写复用父类槽位"**自动成立，不需要任何额外逻辑**：`A.f` 和 `B.f` 都叫 `f`，`f` 只被 `assign` 一次，两个类的 vtable 里 `f` 都在同一个下标。

实测（`factorial.cl`，12 个槽位）：

```llvm
@vtable_Main = constant [12 x i8*] [
  @Object.copy, @Object.type_name, @Object.abort,          ; 槽 0,1,2
  @IO.in_string, @IO.out_string, @IO.in_int, @IO.out_int,  ; 槽 3-6（继承 IO，直接复用）
  null, null, null,                                        ; 槽 7,8,9（String 的方法，Main 没有）
  @Main.main, @Main.fact                                   ; 槽 10,11
]
```

**两个观察**：

- **`Main` 用不到的槽位填 `null`**（槽 7–9 是 `substr`/`concat`/`length`）。这是"全局编号"的代价：**vtable 大小 = 全程序不同方法名的总数**，每个类都得开这么大的表，用不到的填空。程序里有 100 个不同方法名，每个类的 vtable 就有 100 项。
- **继承的方法直接填父类函数**（槽 3–6 指向 `@IO.*`）。`Main` 自己没有 `out_string`，但它的 vtable 里有——这就是继承在内存里的样子。

**真实编译器怎么避免那些 null？** C++ 的 vtable 只包含该类实际可调用的虚函数，编号**按类**而非全局，代价是"同一个方法名在不同继承链里槽位不同"，所以 C++ 需要在多继承时做指针调整（thunk）。我们选全局编号，换来的是**槽位绝对稳定**（实现简单），代价是表变大。**这是空间换实现复杂度的经典取舍**，对教学编译器是对的选择。

### 4.3 一个值得标注的脆弱点

`methods_` 是 `unordered_map`（`codegen.h:36`），所以 `for (auto& kv : methods_[b])` 的**遍历顺序是未指定的**。这意味着槽位编号依赖哈希表的实现细节。

**这不影响正确性**（同一次编译内部一致：vtable 生成和 `methodIndex_.at()` 用的是同一张表），但它意味着**换一个 STL 实现版本，生成的 IR 可能不同**。对需要可复现构建（reproducible build）的场景这是真问题。修法是改用 `map` 或显式排序——`05b` §6.3 记录的 `attrsOf` 返回 `unordered_map` 是同类问题。

> 我标注一下证据边界：这是我**读代码推断**的，没有实测两个不同 STL 版本的输出差异（这台机器上只有一套）。但 `unordered_map` 不保证遍历顺序是标准明文规定的。

## 5. `case` 怎么做运行时类型测试

### 5.1 用整数 tag，不用字符串

每个类在编译期分到一个整数 ID（`codegen.cpp:41-52`）：内建类先占 0–4（`Object`=0, `IO`=1, `Int`=2, `String`=3, `Bool`=4），用户类从 5 开始按源码顺序。这个整数存在 `class_meta_t` 的字段 3。

`case` 的实现（`codegen.cpp:332-347`）：取出对象的 tag，然后对每个分支，检查 tag 是否等于"该分支类型的任一后代"：

```llvm
%t = load i32, i32* %idf              ; 取出对象的 tag
%c1 = icmp eq i32 %t, 5               ; 是不是 Cons?
%c2 = icmp eq i32 %t, 6               ; 是不是 Nil?
%o1 = or i1 %c1, %c2                  ; 任一成立 → 匹配 List 分支
br i1 %o1, label %body, label %next
```

**为什么要枚举后代？** 因为 `x : List => ...` 要匹配的是"动态类型 conform 到 `List` 的所有对象"，也就是 `List` 及其全部子类。`descendants_`（`codegen.cpp:54-58`）就是为此预计算的"自身 + 所有后代"集合。

这正好是 `06a` §2 讲的"`conforms` 往上走，`descendants` 往下走"的对偶：

| | 方向 | 复杂度 | 谁用 |
|---|---|---|---|
| `conforms(a, b)` | 从 `a` **往上**走到 `b` | O(继承深度) | typechecker（编译期） |
| `descendants_[T]` | 从 `T` **往下**收集子树 | O(后代数)，**预计算** | codegen（生成运行时检查） |

**编译期能预计算，所以运行时只需要几条 `icmp`。** 又一次"把查找变成常数"。

**代价**：一个 `case` 分支若类型是 `Object`，`descendants_[Object]` 是全部类，于是生成 N 条 `icmp` + N-1 条 `or`。真实编译器的做法是给每个类分配**区间编号**（子树内的 tag 连续），于是"是不是 T 的后代"变成一次范围比较 `lo ≤ tag ≤ hi`——两条指令，与后代数无关。**这是 §9.6 的题。**

### 5.2 但选分支的规则错了

手册 `:319` 说得很明确：

> Next, from among the branches the branch with **the least type** `<typek>` such that `C ≤ <typek>` is selected.

**"least type"= 最具体的那个类型**，不是"源码里第一个匹配的"。而 `codegen.cpp:341` 是 `for (auto& br : e.branches)`，按**源码顺序**取第一个匹配。

两者在什么时候不同？当分支类型之间有继承关系、且源码顺序把**更一般的**类型写在前面时。实测：

```cool
class Main inherits IO {
  d(x : Object) : String {
    case x of
      o : Object => "Object";
      i : Int    => "Int";
    esac
  };
  main() : Object { out_string(d(42).concat("\n")) };
};
```

```
$ ./caseord.exe
Object          ← 手册要求输出 Int（Int 比 Object 更具体）
```

**我们输出 `Object`，手册要求 `Int`。** 这是 §8.2 那条缺陷。

为什么 `tests/case_test.cl` 没发现？因为它把 `o : Object` 写在**最后**：

```cool
i : Int    => "Int";
s : String => "String";
b : Bool   => "Bool";
o : Object => "other";      ← 兜底分支在最后
```

**源码顺序恰好就是从具体到一般**，于是"取第一个匹配"和"取最具体"给出同样结果。**测试碰巧和实现的错误假设一致。**（`06b` §8.2 那条 `"abc" < "abd"` 是同一类现象——这已经是第二次了，§8.4 展开。）

## 6. 装箱与运行时库

### 6.1 一切皆对象的代价

Cool 的 `Int`/`Bool`/`String` 都是类，所以 `1` 在运行时是个堆对象。`07` §5.4 逐行读过装箱代码，这里只记结论：

- 每个算术结果、每个比较结果都要 `cool_alloc(16)` 装箱；
- 用之前又要 `bitcast` + `getelementptr` + `load` 拆箱；
- `07` §6.4 实测：算 `5!` 是 **17 次堆分配、264 字节**（运行时插桩计数，`12` §1.2 给方法），且全部未释放。

**真实语言的三条出路**：Java 让基本类型不是对象（`int` ≠ `Integer`，代价是泛型要装箱、于是有了 `IntStream` 这类特化）；C# 用 value type（`struct` 在栈上）；JS/Python 靠 JIT 的逃逸分析 + 标记指针在运行时消除。**我们保留装箱，因为它让 codegen 统一（所有值都是 `i8*`），这是教学实现的合理取舍。**

### 6.2 `runtime.c`：71 行

运行时库只做三件事：内存（`cool_alloc`/`cool_copy`）、IO（`print_int`/`print_str`/`read_int`/`read_str`）、字符串（`str_len`/`str_concat`/`str_substr`/`str_cmp`）。

两处值得看：

**① `print_str` 在运行时解释转义。** `01` §3.6 讲 Cool 的 lexer **不翻译** `\n`——它就是反斜杠加 n 两个字符。那谁翻译？这里：

```c
void print_str(const char* s) {
  for (; *s; s++) {
    if (*s == '\\') {
      s++;
      if (*s == 't') putchar('\t');
      else if (*s == 'n') putchar('\n');
      else { putchar('\\'); putchar(*s); }   ← 其他转义保持字面，符合手册
    } else putchar(*s);
  }
}
```

**`01` §3.6 说的"由 IO/运行时解释"，兑现处就是这 10 行。** 一个语言设计决策（lexer 不翻译）在整条管线上的最终落点。

**② `cool_alloc` 就是 `malloc`，而且没有 `free`。**

```c
void* cool_alloc(int n) { return malloc(n); }
```

整个 `runtime.c` 里**没有任何 `free`**。也就是说我们的 Cool 实现**从不回收内存**——所有对象泄漏到进程退出。

对测试程序无所谓（跑完就退出），但一个长时间运行的 Cool 程序会耗尽内存。**这正是 `12` 篇（垃圾回收）存在的理由**：Cool 语义里没有 `delete`，程序员无法手动释放，所以要么泄漏（我们现在这样），要么实现 GC。而 `07` §6.4 量出的分配频率说明这不是小事——**分配越频繁，GC 越不可回避**。你做 KV Cache 内存管理的直觉在这里通：**分配模式决定内存管理策略**。

## 7. 我们到底控制什么

回答 §0 的问题 6。把本篇涉及的东西按"谁负责"分类：

| 事项 | 谁决定 | 在哪 |
|---|---|---|

## 8. 我实测发现的三个缺陷

这一节的三个 bug 都是我在验证本篇布局说法时撞到的。**其中两个会产出非法 IR**（`llvm-as` 拒绝），比"运行结果不对"更严重——它意味着编译器输出的东西根本不是合法 LLVM IR。

> **状态**：§8.1 和 §8.3 **我已经修好并验证了**（两处都是 codegen 的小改动，见各节末的"修法与验证"）。§8.2（`case` 分支顺序）**留给你**，它是 §9.3。
>
> 我修前两个是因为它们产出非法 IR——在这个状态下继续读 `09` 篇会很别扭（代码里有明显的洞）。第三个不影响 IR 合法性，而且修它需要设计一个排序判据，是很好的练习。

### 8.1 静态分派到**继承来的**方法 → 调用不存在的函数

`codegen.cpp:270-279` 的 `visit(StaticDispatch)`：

```cpp
emit(r + " = call i8* @" + e.type + "." + e.method + "(" + ca + ")");
```

**它用字符串拼接造函数名**：`@<类名>.<方法名>`。但如果这个类**没有定义**该方法（继承来的），那个函数就不存在。

```cool
class A { f() : Int { 1 }; };
class B inherits A { };                      -- B 没有定义 f
class Main inherits IO { main() : Object { out_int((new B)@B.f()) }; };
```

```
$ ./coolc.exe sdinh.cl -o sdinh.ll
wrote sdinh.ll (11228 bytes)                 ← 编译器自认为成功

$ grep "@B\.f\|@A\.f" sdinh.ll
define i8* @A.f(i8* %self_arg) {             ← 只有 @A.f 被定义
%t5 = call i8* @B.f(i8* %t1)                 ← 却调用了 @B.f

$ llvm-as sdinh.ll -o /dev/null
error: use of undefined value '@B.f'         (EXIT=1)
$ clang -O0 -o sdinh.exe sdinh.ll runtime.c
error: use of undefined value '@B.f'         (EXIT=1)
```

**对照实验**（证明问题确实是"继承"而非静态分派本身）：让 `B` 自己定义 `f`：

```cool
class B inherits A { f() : Int { 2 }; };
```
```
llvm-as EXIT=0      output=[2]      ← 完全正常
```

**根因和修法都很清楚**：`buildClassInfo` 已经建好了 `methods_`，它**正确处理了继承**——`B` 的 vtable 里存的就是 `@A.f`：

```
$ grep @vtable_B sdinh.ll
@vtable_B ... @Object.copy @Object.type_name @Object.abort @A.f
```

**同一份正确数据，vtable 用了，静态分派没用。**

**修法与验证（已应用）。** 查表而非拼字符串：

```cpp
// 不能用 "@" + e.type + "." + e.method 拼函数名：若 e.type 只是继承了该方法而没有
// 定义它，那个函数并不存在（会生成 call @B.f 而只有 @A.f 被定义）。
// methods_ 已按继承链解析好，查表即可（存在性由 typechecker 保证）。
const MethodRef& ref = methods_.at(e.type).at(e.method);
emit(r + " = call i8* " + ref.funcName + "(" + ca + ")");
```

（`e.type` 的合法性、方法存在性都已由 typechecker 保证，所以 `.at()` 安全。）

**顺带一个观察**：`emitMain`（`codegen.cpp:715`）本来就写着 `methods_.at("Main").at("main")`——**正确的写法在同一个文件里已经存在**，静态分派只是没用它。这类"同一个问题在一处做对、在另一处做错"的 bug 很常见，而且很难靠读代码发现（两处都各自看起来合理）。

修后实测：

```
$ ./coolc.exe sdinh.cl -o f_sdinh.ll && llvm-as f_sdinh.ll -o /dev/null
IR OK        output=[1]
$ grep -o "call i8\* @[AB]\.f" f_sdinh.ll
call i8* @A.f          ← 现在正确指向定义它的类
```

### 8.2 `case` 选分支按源码顺序，而非最具体类型

§5.2 已完整展开。手册 `:319` 要求选 "the least type"，我们选源码里第一个匹配的。实测 `case 42 of o : Object => "Object"; i : Int => "Int"; esac` 输出 `Object`，手册要求 `Int`。

**修法**：生成检查代码前，先把分支按"类型特异性"排序——具体类型在前。判据就是 `conforms`：若 `Ti ≤ Tj` 则 `Ti` 更具体，排前面。这是一次拓扑排序（对继承偏序），**而不是**简单的深度比较（不同继承链上的类型互不可比，它们的相对顺序无所谓）。

### 8.3 `if` / `case` 分支体含控制流 → 畸形 φ（影响面最大的一个）

`codegen.cpp:363` 记录 φ 的前驱块时用的是 `bodyL`——**进入分支体时的那个标签**：

```cpp
std::string bodyL = freshLabel();
...
emit(bodyL + ":");
std::string r = codegenExpr(*br.body);      // ← 如果它内部开了新块……
emit("br label %" + endL);
results.push_back({bodyL, r});              // ← 这里记的还是 bodyL，错了
```

如果分支体自己含控制流（`if`/`while`/嵌套 `case`），它会开新的基本块，那么**跳到 `endL` 的实际前驱是那个新块，不是 `bodyL`**。φ 的前驱标签于是对不上。

```cool
class Main inherits IO {
  d(x : Object) : Int {
    case x of
      i : Int => if 1 < 2 then 10 else 20 fi;      -- 分支体含 if
      o : Object => 30;
    esac
  };
  main() : Object { out_int(d(42)) };
};
```

```
$ ./coolc.exe casephi.cl -o casephi.ll       → 生成成功（EXIT=0）
$ llvm-as casephi.ll -o /dev/null
assembly parsed, but does not verify as correct!
PHI node entries do not match predecessors!
  %t37 = phi ptr [ %t24, %bb2 ], [ @int_30, %bb7 ]      (EXIT=1)
$ clang -O0 -o casephi.exe casephi.ll runtime.c         (EXIT=1)
```

**这是 `07` §3.4 规则 2 的直接违反**（"φ 的实参必须与前驱块一一对应"）。

**`visit(If)` 有完全相同的缺陷**（`codegen.cpp` 的 If 分支同样预先记 `thenL`/`elseL`）：

```cpp
emit(phi + " = phi i8* [ " + tv + ", %" + thenL + " ], [ " + ev + ", %" + elseL + " ]");
```

我一开始以为 If 只是"恰好没被触发"，实测证明**它也是坏的**。真实范围比单个 `case` 大得多——我用 5 个探针量出了准确边界：

| 分支体形态 | 结果 |
|---|---|
| `if 1<2 then 10 else 30 fi`（字面量） | IR OK，输出 `10` |
| `if 1<2 then {5; 10;} else 30 fi`（块） | IR OK，输出 `10` |
| `if` 里套 `if` | **IR INVALID** |
| `if` 分支体含 `while` | **IR INVALID** |
| `if` 分支体含 `case` | **IR INVALID** |

**判据很清晰：分支体只要自己开了新的基本块，φ 的前驱标签就错。** 字面量和块不开新块（块只是顺序求值），所以没事；`if`/`while`/`case` 都开新块，所以全坏。

**修法与验证（已应用）。** 不要预先记标签，而是在生成完分支体**之后**记录"当前所在的块"。

关键设计选择：**不要在十处 `emit(label + ":")` 上分别维护 `currentBlock_`**（那样迟早漏掉一处），而是把"开块"这个动作封装成一个函数，让不变式无处可逃：

```cpp
// codegen.h
std::string currentBlock_;   // 当前正在填充的基本块标签（phi 前驱用）

// 开一个基本块，并记住"当前所在的块"。
// phi 的前驱必须是控制流真正流出的那个块，而子表达式（if/while/case）会自己开新块，
// 所以不能用"进入分支时的标签"，必须用生成完之后的 currentBlock_。
void emitLabel(const std::string& l) { emit(l + ":"); currentBlock_ = l; }
```

然后 `visit(If)`：

```cpp
emitLabel(thenL);
std::string tv = codegenExpr(*e.then_);
std::string thenExit = currentBlock_;   // then 支可能自己开了新块
emit("br label %" + endL);
emitLabel(elseL);
std::string ev = codegenExpr(*e.else_);
std::string elseExit = currentBlock_;   // else 支同理
emit("br label %" + endL);
emitLabel(endL);
emit(phi + " = phi i8* [ " + tv + ", %" + thenExit + " ], [ " + ev + ", %" + elseExit + " ]");
```

`visit(Case)` 同理（记 `bodyExit = currentBlock_`）。另外两处也必须改，否则 `currentBlock_` 会读到过期值：

- **`visit(While)` 的三个标签**——它自己没有 φ，但**外层的 `if` 要读 `currentBlock_`**。`while` 结束后当前块是它的 `endL`，不更新就会让外层 φ 指向 `while` 之前的块。
- **函数入口 `entry`**（`emitMethod` / `emitMain`）——否则函数体顶层就是一个 `if` 时，`currentBlock_` 是空串或上一个函数的残留。

**这两处"顺带必须改"的地方，正是"把不变式集中到一个函数里"的价值**：改成 `emitLabel` 之后，只要新代码开块都走它，就不会再出现这类漏洞。（内建方法里那 10 处 `emit("entry:")` 是手写 IR、不含用户表达式，不影响。）

修后实测——§8.3 表格里三个失败用例全部转好，且输出正确：

```
t_nestif   IR OK  output=[10]
t_whileif  IR OK  output=[10]
t_caseif   IR OK  output=[10]
casephi    IR OK  output=[10]
```

12 个测试**全部 IR 合法、运行输出与修改前逐字节相同**（`hello`→`Hello, compiler!`、`factorial`→`120`、`list`→`5`、`case_test`→`Int/String/Bool/Bool/other`、`static_dispatch`→`B/A/B`、`io_test` 四行交互一致……）。**零回归。**

> **这个 bug 的严重性值得强调**：`if` 里套 `if`、`case` 分支里写 `if`——这是**最普通的 Cool 代码**，真实程序里几乎必然出现。也就是说我们的编译器目前只能处理控制流不嵌套的程序。而 12 个测试全绿，因为它们**恰好**没有一个嵌套控制流（§8.4）。

### 8.4 为什么 11/12 测试全绿还能有这些 bug

这是本篇最值得记住的一课。三个 bug 全部逃过了测试，原因各不相同：

| bug | 为什么没被发现 |
|---|---|
| 静态分派继承（§8.1） | `tests/static_dispatch.cl` 只写了 `x@A.who()` / `x@B.who()`，而 `A` 和 `B` **都定义了** `who` |
| case 分支顺序（§8.2） | `tests/case_test.cl` 把 `o : Object` 写在最后，**源码顺序恰好等于特异性顺序** |
| `if`/`case` 的 φ 前驱（§8.3） | 12 个测试里**没有一个嵌套控制流**——所有 `if`/`case` 的分支体都是字面量、块或简单调用 |

**共同点：测试覆盖的是"实现恰好能处理的那些情况"。** 这不是巧合——测试和实现由同一个人在同一时间写成，共享同一套假设。`06b` §8.2 那条 `"abc" < "abd"` 是同一个现象的第三个实例。

**所以"测试全绿"证明的是"实现在测试覆盖的情况下自洽"，不是"实现符合规范"。** 要跳出这个循环，测试必须从**规范**生成，而不是从实现的行为生成：

- 读手册 `:319` 的 "least type" → 写一个分支顺序反过来的 case；
- 读手册的 static dispatch 规则 → 写一个 `@T.f` 其中 `T` 继承 `f`；
- 读 `07` §3.4 的 φ 规则 → 写一个分支体含控制流的 case。

**这三条我都是先读手册/规范，再构造程序，然后才发现 bug 的——顺序很重要。** 如果我只是"多跑几个程序看看"，大概率还是会写出和现有测试同构的程序。

**另一个教训**：`llvm-as` 应该是 CI 的一部分。§8.1 和 §8.3 这两个 bug，`llvm-as` 一跑就抓到，而它们在"编译器退出码 0、写出了 .ll 文件"这个层面看完全正常。**`07` §6.1 建议把 `llvm-as` 加进测试流程，这里是它的第一份回报。**
