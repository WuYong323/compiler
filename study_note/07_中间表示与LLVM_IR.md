## 精炼段

旧版这一篇（和 DeepSeek 写的其他几篇一样）的问题是：它讲了一个**理想化的 IR**，然后我们的编译器生成了一个**完全不同的 IR**，两者从未对上。它给的例子是

```llvm
define i32 @fact(i32 %n) { ... }
```

而 `coolc` 实际生成的是

```llvm
define i8* @Main.fact(i8* %self_arg, i8* %arg_0) { ... }
```

参数变成了两个、类型全是 `i8*`、函数名带类前缀、函数体里有 4 个 `alloca` 和 65 条 load/store。**如果笔记只给你看理想版，你打开 `fact.ll` 的那一刻会完全懵掉**——这正是你对 03 篇的原始抱怨（"给我看的十分糊涂"）。

所以本篇的结构是：

**§1–§2 先把"为什么需要 IR"和"为什么是三地址码"从需求推出来**，而不是宣布。三地址码的真正理由不是"像汇编"，而是**每个中间结果都需要一个名字，否则优化器无法引用它**。

**§3 SSA。** 这是本篇的理论核心。我不会只说"每个变量赋值一次，优化变简单"——我会让你看到：不用 SSA 时"x 在这一点的值"是一个需要**数据流分析**才能回答的问题（`10` 篇的活儿），用了 SSA 之后它退化成"看 `%x` 的那一条定义"。**同一个问题从 O(分析) 变成 O(1) 查表，这才是 SSA 的全部价值。**

**§4 是本篇最有价值的一节，也是旧版完全没有的**：我们的 codegen **不生成 φ**。它用 `alloca` 把变量放进内存，读写全走 `load/store`，于是 SSA 约束自动满足（每个 `%tN` 确实只赋值一次）。我实测了 `mem2reg` 把它还原成真 SSA 的效果，并且——关键控制实验——**验证了 clang 自己也这么干**。这不是偷懒，这是工业标准做法。

**§5 逐行读真实 IR**，包括那些让人一眼懵的 `bitcast`/`getelementptr`/装箱。**§6 我实测的四组数据**（IR 合法性、mem2reg 效果、优化头寸、装箱代价）。**§7** 工业接轨到 MLIR 和你的 GPU 图优化课题。

## 1. 为什么需要 IR

### 1.1 教科书理由：N+M 而不是 N×M

```
          N 种源语言              M 种目标机器
       Cool  C  Rust  Swift      x86  ARM  RISC-V  WASM
          \   |   |   /            \    |    |    /
           v  v   v  v              v   v    v   v
        ┌──────────────┐        ┌──────────────────┐
        │   N 个前端    │        │     M 个后端      │
        └──────┬───────┘        └────────┬─────────┘
               └───────────┬─────────────┘
                           v
                     ┌──────────┐
                     │    IR    │
                     └──────────┘
```

没有 IR 要写 N×M 个翻译器（4×4=16），有了 IR 只需 N+M（4+4=8）。规模越大收益越大：LLVM 支持约 20 种前端语言 × 十几种后端架构，省下的是两个数量级。

**这个理由是对的，但它不完整**——它只解释了工程复用，没解释 IR 为什么长这个样子。如果只为了复用，IR 完全可以就是"带类型的 AST"（我们 `06b` 末尾手上那棵树），N+M 一样成立。

### 1.2 真正塑造 IR 形状的理由：优化需要一个能被引用的表示

考虑一个具体优化——**公共子表达式消除**：

```cool
(a * b) + (a * b)
```

要把第二个 `a * b` 替换成第一个的结果，优化器必须能说出"**第一个 `a*b` 的结果**"这句话。在 AST 上，那个结果没有名字——它是 `Binary` 节点的一个**隐含**返回值，只存在于求值过程中。你能指向那个节点，但指不向它的**值**。

三地址码给每个中间结果一个显式名字：

```
t1 = a * b
t2 = a * b        ← 优化器现在能说"t2 的定义和 t1 的定义相同，删掉 t2，用 t1"
t3 = t1 + t2
```

**所以三地址码的本质不是"像汇编"，而是"给每个中间值命名"。** 命名之后，"这个值在哪里被定义""它被谁使用"才成为可以机械回答的问题——这是一切优化的前提。`10` 篇讲的 def-use 链、活跃变量分析，全都建立在"值有名字"之上。

### 1.3 第三个理由：控制流被显式化

AST 里的控制流是**结构化**的：`If` 节点有 then/else 两个子树，`While` 节点有 body。机器码里没有这种结构，只有跳转。IR 处在中间：它用**基本块 + 跳转**表示控制流，既比 AST 接近机器，又保留了足够的结构（`08`/`09` 会用到）。

这个转换是不可逆的降级：`if`/`while`/`case` 全都变成 `br`，看不出源头是哪种语句。**信息损失是有意的**——优化器不需要知道"这是个 while 还是个 goto 拼出来的循环"，它只需要知道控制流图长什么样。

三个理由合起来才是 IR 的完整动机：

| 理由 | 解决什么 | 塑造了 IR 的哪个特征 |
|---|---|---|
| 前后端解耦 | 工程复用 N+M | IR 与源语言/机器都无关 |
| **中间值需要名字** | 优化器能引用 | **三地址码 + 无限虚拟寄存器** |
| 控制流显式化 | 接近机器 | 基本块 + 终结指令 |

## 2. 三地址码

### 2.1 定义与拆解

每条指令形如 `x = y op z`：至多一个运算符，至多三个"地址"（变量/常量/临时变量）。

```
源码:   a <- b * c + d * e

TAC:    t1 = b * c
        t2 = d * e
        t3 = t1 + t2
        a  = t3
```

**拆解规则就是 AST 的后序遍历**：每个内部节点产生一条指令，它的操作数是子节点的结果名字。这正是 `09` 篇 codegen 的核心循环——`visit(Binary)` 先递归生成两个子表达式（得到两个名字），再发一条指令。

**所以"AST → 三地址码"不需要什么算法，它就是一次带返回值的后序遍历。** 你在 `06b` 写 `typeOf` 时已经做过一模一样的事：递归算出子节点的东西（那里是类型，这里是名字），组合成自己的。

### 2.2 临时变量有多少个

无限个。IR 层面 `%t0, %t1, ... %t9999` 想要多少有多少，它们叫**虚拟寄存器**。真实机器只有十几个物理寄存器，把无限映射到有限是**寄存器分配**（`11` 篇）的工作。

**这个分层很重要**：codegen 阶段完全不必操心"寄存器够不够"，随便编号就行。我们的 `fact.ll` 里 `Main.fact` 一个函数用到 `%t0`–`%t51`，52 个虚拟寄存器，而 x86-64 只有 16 个通用寄存器——`llc` 会负责挤进去。

（`06b` §8.3 那个栈溢出崩溃就是这个计数器失控的副产品：gdb 回溯里栈顶是 `%t4212`，说明已经生成了四千多个临时变量。注意真正打爆的是**栈**而不是名字空间——`%tN` 本身确实要多少有多少。）

## 3. SSA：把"分析问题"变成"查表事实"

### 3.1 先看没有 SSA 时的困难

```
    x = 1
    if c goto L2
L1: x = 2
L2: use(x)        ← 问题：这里的 x 是多少？
```

要回答"`use(x)` 用的是哪个 `x`"，你必须**分析控制流**：从 `L2` 往回看所有可能到达它的路径，收集路径上最后一次对 `x` 的赋值。这叫**到达定义分析（reaching definitions）**，是 `10` 篇的内容，需要在控制流图上做不动点迭代。

代价是：**每次优化器想知道一个变量的值，都要跑一遍分析。** 而且赋值和使用之间的关联靠"名字相同"这种弱约定维系，一旦有别名（指针）就更糟。

### 3.2 SSA 的做法

**规则：每个名字在整个函数里只被一条指令赋值。** 要"改"一个变量，就造一个新名字。

```
    x1 = 1
    if c goto L2
L1: x2 = 2
L2: x3 = φ(x1, x2)        ← 汇合点显式声明"值来自哪条边"
    use(x3)
```

现在"`use(x3)` 用的是什么"这个问题的答案是：**看 `x3` 的定义**。只有一条，就在上面一行。不需要分析，不需要遍历控制流图——**查定义即可**。

这就是 SSA 的全部价值，一句话：

> **SSA 把"某变量在某点的值"从一个需要数据流分析的问题，变成一个查定义就能回答的事实。**

因为每个名字只有一个定义，"名字"和"定义它的那条指令"是**一一对应**的。LLVM 的 C++ API 里这一点被做到了极致：`llvm::Value` 这个类**既表示值又表示定义它的指令**（`Instruction` 继承自 `Value`）。你拿到一个 `Value*`，就等于同时拿到了它的定义点。**数据结构直接编码了 SSA 不变式。**

### 3.3 于是这些优化变得平凡

| 优化 | 没 SSA | 有 SSA |
|---|---|---|
| 常量传播 | 跑到达定义分析，确认所有到达定义都是同一常量 | `%x = add i32 1, 2` → 所有用到 `%x` 的地方直接换成 `3` |
| 死代码消除 | 跑活跃变量分析 | `%x` 的 use 列表为空 → 删掉 |
| 公共子表达式 | 要确认两处之间变量没被改过 | 名字相同即值相同（因为不可能被改） |

第三行最能说明问题。没有 SSA 时，`t1 = a*b` 和后面的 `t2 = a*b` **不一定**相等——中间可能有 `a = 5`。所以你得先证明"`a` 和 `b` 在两点之间没被修改"。有了 SSA，`%a` 就是 `%a`，**永远不可能被修改**，所以 `%a * %b` 在任何两处都是同一个值。**证明消失了，因为不变式被数据结构保证了。**

### 3.4 φ 函数不是一条真指令

`φ(x1, x2)` 的语义是"如果控制流从 `L1` 这条边来就取 `x1`，从 `L0` 来就取 `x2`"。这在真实机器上**没有对应指令**——没有 CPU 能问"我是从哪跳过来的"。

φ 的实现方式是**消除**它：在每条前驱边上插入一条 `mov`。

```
    x1 = 1
    if c goto L2'
L1: x2 = 2
    x3 = x2          ← 在这条边上插 mov
    goto L2
L2':x3 = x1          ← 在这条边上插 mov
L2: use(x3)
```

这一步叫 **φ 消除（phi elimination）**，发生在寄存器分配前后（`11` 篇）。所以 φ 是一个**纯粹为了表示而存在的虚构指令**——它只活在 IR 里。

**几个必须记住的 φ 规则**（写 codegen 时会踩）：

1. φ 必须在基本块的**最开头**，所有 φ 连续排列，前面不能有普通指令。
2. φ 的实参个数必须**等于该块的前驱块个数**，且每个前驱都要列出来。
3. 多个 φ 在同一块里是**并行**语义（同时取值），不是顺序执行。
4. φ 的实参可以是常量，也可以是**尚未出现在文本中**的值（循环回边的情况）。

第 4 条是 codegen 最麻烦的地方：生成循环时，回边的 φ 实参是循环体末尾才算出来的名字，而 φ 要写在循环头。这意味着你得**先占位、后回填**。

**而这正是我们选择不生成 φ 的原因。** 下一节。

## 4. 我们的 codegen 不生成 φ：`alloca` + `mem2reg`

### 4.1 做法

`coolc` 对每个变量（形参、`let` 变量、`self`）都在函数入口 `alloca` 一个栈槽，读变量 = `load`，写变量 = `store`：

```llvm
%t0 = alloca i8*              ; 给参数 n 分配一个栈槽
store i8* %arg_0, i8** %t0    ; 把参数存进去
...
%t1 = load i8*, i8** %t0      ; 每次用到 n 就 load 一次
```

**为什么这样就绕过了 SSA 难题？** 因为 SSA 约束管的是**虚拟寄存器 `%`**，不管**内存**。`%t0` 是那个栈槽的地址，只被 `alloca` 赋值一次 ✓。`%t1` 是某次 load 的结果，只被这条 load 赋值一次 ✓。变量的"多次赋值"全都发生在**内存里**，而内存不受 SSA 管辖。

于是"循环里 `i` 被改了 5 次"变成"对同一个地址 store 了 5 次"——完全合法的 SSA。

**代价**：IR 很啰嗦，且每次访问变量都走内存，未优化的话性能差。

### 4.2 实测：`mem2reg` 把它还原成真 SSA

`mem2reg`（promote memory to register）这个 pass 的职责就是：找出那些"只被 load/store 访问、地址从不逃逸"的 `alloca`，把它们提升成虚拟寄存器，**并在需要的地方自动插入 φ**。

我用这个循环程序实测（`while` 里有 `i <- i + 1`，是最需要 φ 的场景）：

```cool
class Main inherits IO {
  main() : Object {
    let i : Int <- 0 in {
      while i < 3 loop i <- i + 1 pool;
      out_int(i);
    }
  };
};
```

```bash
./coolc.exe w.cl -o w.ll
opt -passes=mem2reg -S w.ll -o w_m2r.ll
```

`Main.main` 函数体内的统计：

| | alloca | φ | load | store |
|---|---|---|---|---|
| 我们生成的 `w.ll` | 2 | **0** | 12 | 7 |
| `mem2reg` 之后 | **0** | **1** | 8 | 4 |

**`mem2reg` 合成出了那个我们从未生成的循环 φ**：

```llvm
%t0.0 = phi ptr [ @int_0, %entry ], [ %t26, %bb1 ]
```

读这一行：`i` 的值在循环头处，要么来自 `%entry`（初值 `@int_0`，即常量 0），要么来自 `%bb1`（循环体算出的 `%t26`）。**这正是 §3.4 第 4 条说的"回边实参"**——那个我们不想手动回填的东西，`mem2reg` 替我们填了。

两个版本都能跑，结果相同：

```
$ ./w.exe        →  3
$ ./w_m2r.exe    →  3
```

对 `factorial.cl` 同样测了一遍（`Main.fact` 函数体内）：

| | alloca | φ | load | store |
|---|---|---|---|---|
| `fact.ll` | 2 | 1 | 14 | 8 |
| `+ mem2reg` | **0** | 1 | 10 | 6 |

（`fact.ll` 本来就有 1 个 φ，是 `visit(If)` 汇合分支值时生成的——**这是我们主动生成 φ 的唯一场景**，因为 `if` 是表达式、有值，而且两支的值在汇合点就位、不存在回边回填问题。）

### 4.3 关键控制实验：clang 自己也这么干

到这里你可能怀疑：`alloca` 满地是不是我们这个教学编译器偷懒？**我实测了 clang，答案是否**。

```c
int fact(int n) { if (n == 0) return 1; return n * fact(n - 1); }
int loop(int n) { int i = 0; while (i < n) i = i + 1; return i; }
```

```bash
clang -O0 -S -emit-llvm c1.c -o c1_O0.ll
```

```
clang -O0 : alloca=4  phi=0  load=8  store=6
```

**clang 在 `-O0` 下生成 4 个 alloca、0 个 φ——和我们的策略完全一致。**

我顺手试了对它跑 `mem2reg`，结果**毫无变化**（alloca 仍是 4）。这一开始让我以为搞错了什么；查下去发现原因是 clang 在 `-O0` 给每个函数打了 `optnone` 属性：

```
attributes #0 = { noinline nounwind optnone uwtable ... }
```

`optnone` 会让优化 pass 跳过该函数。把它去掉再跑：

```bash
sed 's/ optnone//g' c1_O0.ll > c1_noopt.ll
opt -passes=mem2reg -S c1_noopt.ll -o c1_noopt_m2r.ll
```

```
strip optnone + mem2reg : alloca=0  phi=2  load=0  store=0
clang -O1 （参照）       : alloca=0  phi=2  load=0  store=0
```

**两行数字完全相同。** 也就是说：clang 前端生成 alloca 版 IR，`mem2reg` 把它变成 SSA 版，而这个结果和 clang `-O1` 的输出一致。**"前端生成 alloca，靠 mem2reg 提升"就是 LLVM 的标准工作流**，写在 LLVM 官方文档里（关键词：*LLVM Tutorial, mutable variables, mem2reg*）。

这个发现值得记住，因为它改变了你对这件事的判断：

> 我们的 codegen 不生成 φ **不是简化，是正确做法**。手动维护 φ（尤其是回边回填）是出名的易错活儿，而 `mem2reg` 实现的 SSA 构造算法（基于支配边界，Cytron et al. 1991）比手写可靠得多。

**LLVM 的设计哲学在这里显形**：把难的部分（SSA 构造、寄存器分配、指令选择）做成可复用的 pass，前端只负责生成**语义正确但朴素**的 IR。这也是为什么写一个 LLVM 前端比写一个完整编译器容易一个数量级。

### 4.4 那还需要理解 SSA 吗

需要，而且更需要。三个理由：

1. **`10` 篇的所有优化都在 SSA 上定义**。你要读懂 LLVM 的 pass、要自己写 pass，绕不开。
2. **调试时看到的是 SSA**。跑 `opt -O2` 之后的 IR 全是 φ，看不懂就没法定位问题。
3. **MLIR/TVM 也是 SSA**（§7）。你的 GPU 计算图方向，天天面对的是 SSA 形式的张量 IR。

区别只是：**你不必手写 φ，但必须读懂 φ**。

## 5. 逐行读我们真实生成的 IR

现在打开 `fact.ll`，从头读。这一节的目的是让你**第一次打开生成的 IR 时不再懵**。

### 5.1 四层结构

```
Module（整个 .ll 文件 = 一个编译单元）
  ├─ 类型定义        %Int = type { i8*, i32 }
  ├─ 全局常量        @int_0, @vtable_Main, @class_Main
  └─ Function        define i8* @Main.fact(i8* %self_arg, i8* %arg_0)
       └─ Basic Block    entry: / bb0: / bb1: / bb2:
            └─ Instruction   %t8 = icmp eq i32 %t4, %t7
```

**基本块**：只能从第一条指令进入、只能从最后一条指令离开的直线代码。最后一条必须是**终结指令**（`br` / `ret` / `switch` / `unreachable`）。不存在"执行完掉落到下一块"这回事——想到下一块必须显式 `br`。

我们生成的 `Main.fact` 有 4 个块：`entry`（算条件）、`bb0`（then 支）、`bb1`（else 支）、`bb2`（汇合）。注意 `bb0` 的内容只有一行 `br label %bb2`——**空的 then 支也必须有终结指令**。

### 5.2 类型定义：对象布局在 IR 里的样子

```llvm
%Int    = type { i8*, i32 }              ; { 类元信息指针, 整数值 }
%Bool   = type { i8*, i32 }
%String = type { i8*, i32, i8* }         ; { 类元信息, 长度, 字符数据 }
%Object = type { i8* }                   ; 只有类元信息指针
%Main   = type { i8* }
%class_meta_t = type { i8*, i8**, i32, i32 }  ; { 类名, vtable, 对象大小, tag }
```

**每个对象的第 0 个字段都是 `i8*` 指向类元信息**——这是 `08` 篇要详细讲的对象布局，动态分派和 `type_name()` 都靠它。`%Object` 和 `%Main` 只有这一个字段，因为它们没有属性。

`%class_meta_t` 里的 `i8**` 是 vtable（函数指针数组的首地址）。

### 5.3 全局常量：vtable 长什么样

```llvm
@vtable_Main = constant [12 x i8*] [
  i8* bitcast (i8* (i8*)* @Object.copy to i8*),        ; slot 0
  i8* bitcast (i8* (i8*)* @Object.type_name to i8*),   ; slot 1
  i8* bitcast (i8* (i8*)* @Object.abort to i8*),       ; slot 2
  ... @IO.in_string, @IO.out_string, @IO.in_int, @IO.out_int ...
  i8* null, i8* null, i8* null,                        ; slot 7,8,9（String 的方法，Main 没有）
  i8* bitcast (i8* (i8*)* @Main.main to i8*),          ; slot 10
  i8* bitcast (i8* (i8*, i8*)* @Main.fact to i8*)      ; slot 11
]
```

**这张表就是 `05b` 讲的方法表落到内存里的样子。** 几个要点：

- 12 个槽位是**全程序统一编号**（`08` §下标分配算法）。`Main` 用不到的槽位填 `null`。
- `Main` 继承 `IO`，所以 slot 3–6 直接复用 `@IO.*` 的函数——**重写就是换这个槽里的指针**，这是 `05b` §6.1 "方法可重写"的物理根据。
- 所有函数指针都 `bitcast` 成 `i8*` 存进去，调用时再 bitcast 回来。因为数组要求元素类型一致，而各方法签名不同。

### 5.4 `Main.fact` 逐行

函数头：

```llvm
define i8* @Main.fact(i8* %self_arg, i8* %arg_0) {
```

和源码 `fact(n : Int) : Int` 比，三处不同：

| 差异 | 原因 |
|---|---|
| 名字 `Main.fact` | 不同类可以有同名方法，需要**名字修饰（name mangling）** |
| 多一个 `%self_arg` | `self` 是隐式参数——`06b` §1 那条 `O.add("self", ...)` 在 IR 层的兑现 |
| 类型全是 `i8*` 不是 `i32` | **一切皆对象**：Cool 的 `Int` 是个类，运行时是堆上的 `%Int` 结构体，传的是指针 |

入口块：

```llvm
entry:
%self = alloca i8*                    ; §4.1：给 self 开栈槽
store i8* %self_arg, i8** %self
%t0 = alloca i8*                      ; 给参数 n 开栈槽
store i8* %arg_0, i8** %t0
```

取 `n` 的整数值（**这是最关键的一段，装箱的代价全在这里**）：

```llvm
%t1 = load i8*, i8** %t0              ; 读出 n 这个对象的指针
%t2 = bitcast i8* %t1 to %Int*        ; 把 i8* 当成 %Int* 看
%t3 = getelementptr %Int, %Int* %t2, i32 0, i32 1   ; 取第 1 个字段的地址
%t4 = load i32, i32* %t3              ; 读出那个 i32
```

**四条指令才拿到一个整数。** 逐条解释：

- `bitcast`：**纯类型转换，不产生任何机器指令**。IR 是强类型的，`i8*` 不能直接当 `%Int*` 用，必须显式告诉 LLVM"我知道这个指针其实指向 `%Int`"。
- `getelementptr`（GEP）：**计算字段地址，不访问内存**。`i32 0, i32 1` 读作"第 0 个 `%Int`（即不偏移数组）的第 1 个字段"。第一个索引几乎总是 0，这是 LLVM 最容易搞混的地方（官方 FAQ 有专门一节 *The Often Misunderstood GEP Instruction*）。
- `load`：真正的内存读。

比较并装箱结果：

```llvm
%t8  = icmp eq i32 %t4, %t7           ; 比较，结果是 i1
%t9  = zext i1 %t8 to i32             ; i1 扩展成 i32
%t10 = call i8* @cool_alloc(i32 16)   ; 堆上分配 16 字节
%t11 = bitcast i8* %t10 to %Bool*
%t12 = getelementptr %Bool, %Bool* %t11, i32 0, i32 0
store i8* bitcast (%class_meta_t* @class_Bool to i8*), i8** %t12   ; 写类元信息
%t13 = getelementptr %Bool, %Bool* %t11, i32 0, i32 1
store i32 %t9, i32* %t13              ; 写值
```

**`n = 0` 这一个比较，生成了一个 16 字节的堆对象。** 然后立刻又把它拆开来用：

```llvm
%t16 = load i32, i32* %t15            ; 又读出来
%t17 = icmp ne i32 %t16, 0            ; 转回 i1
br i1 %t17, label %bb0, label %bb1    ; 终结指令
```

装箱、马上拆箱。**这是纯粹的浪费，也是 Cool"一切皆对象"语义的直接成本**。真实语言用两种办法避免：Java 的基本类型不是对象（`int` ≠ `Integer`）；Python/JS 靠 JIT 的逃逸分析和标记指针（tagged pointer）在运行时消除装箱。我们保留它，因为 §6.3 会让你看到优化器能吃掉多少。

动态分派（递归调用 `fact` 那一处）：

```llvm
%t35 = load i8*, i8** %t22            ; 取 self 的第 0 字段 = 类元信息指针
%t36 = bitcast i8* %t35 to %class_meta_t*
%t37 = getelementptr %class_meta_t, %class_meta_t* %t36, i32 0, i32 1
%t38 = load i8**, i8*** %t37          ; 取出 vtable 首地址
%t39 = getelementptr i8*, i8** %t38, i32 11   ; 第 11 个槽位 = fact
%t40 = load i8*, i8** %t39            ; 取出函数指针
%t41 = bitcast i8* %t40 to i8* (i8*, i8*)*    ; bitcast 成正确的函数类型
%t42 = call i8* %t41(i8* %t22, i8* %t31)      ; 间接调用
```

**这七条就是 `08` 篇"动态分派 = 三步"的展开**：对象 → 类元信息 → vtable → 槽位 11 → 函数指针 → 调用。槽位 11 是编译期就定下来的常数（`05b` 的方法表 + `08` 的下标分配），**运行时不查名字**。

汇合点，唯一的 φ：

```llvm
bb2:
%t51 = phi i8* [ bitcast (%Int* @int_1 to i8*), %bb0 ], [ %t47, %bb1 ]
ret i8* %t51
```

从 `bb0`（then 支）来就取常量 1，从 `bb1`（else 支）来就取 `%t47`。**两个前驱、两个实参**（§3.4 规则 2）；φ 在块首（规则 1）；实参之一是常量（规则 4 的前半）。

**为什么这个 φ 我们敢主动生成，而循环的不敢？** 因为 `if` 的两支在汇合点**都已经生成完毕**，实参名字是现成的。循环的 φ 需要引用循环体末尾的名字，而生成循环头时那个名字还不存在——需要占位回填。**难的是回边，不是 φ 本身。**

### 6.2 `mem2reg` 的效果（§4.2 已给，汇总）

| 程序 / 函数 | alloca | φ | load | store |
|---|---|---|---|---|
| `w.ll` `Main.main`（含 while） | 2 → **0** | **0 → 1** | 12 → 8 | 7 → 4 |

### 6.4 装箱代价

`Main.fact` 一个函数里有 **3 次 `cool_alloc`**（整个 `fact.ll` 有 10 次）。这是**静态**计数（IR 里有几处调用），而真正要紧的是**动态**计数（实际跑了几次）。

我后来在 `runtime.c` 里给 `cool_alloc` 加了计数器实测（`12` §1.2 给出方法），`factorial.cl` 的真实数字是：

```
[heap] cool_alloc=17 (264 bytes)  freed=0
```

**17 次分配、264 字节，只为算一个 `5!`，而且一个字节都没释放。** 每个 `%Int` 16 字节（8 元信息 + 4 int + 4 填充），所以其中约 1/4 是对齐填充。

> 早先我在这里按"递归 6 层 × 每层 3 次"估成"约 18 次、近 300 字节"。实测 17/264 —— 估算的量级对，但**静态乘法算不准动态次数**（递归深度、常量复用、`main` 里的分配都会让它偏差）。凡是能插桩实测的量，就不要用乘法估。

对照：C 的 `fact(5)` 是零分配，全在寄存器里。

**这个数字是"高级语言抽象成本"的一个具体度量**，也是 `12` 篇（垃圾回收）为什么必要的直接原因——分配这么频繁，不回收几秒就耗尽内存。你做 KV Cache 内存管理的直觉在这里是通的：**分配频率决定了内存管理策略的重要性**。

## 7. 工业接轨

### 7.1 为什么我们"直接打印文本 IR"

三个理由（`index.md` 开头的实现栈选型"直接生成文本 LLVM IR"，现在能给出更实的依据）：

1. **零依赖**：不用链接 LLVM 库。我们的编译器只有 6 个 `.cpp`，`clang++ src/*.cpp` 就编译完。
2. **完全可见**：生成的是可读文本，出问题直接看。§5 那种逐行读，用 C++ API 是做不到的（IR 在内存里）。
3. **直面约束**：手写 IR 迫使你真正理解 SSA、终结指令、强类型这些约束。

**代价**：没有类型安全（拼错的指令要等 `llvm-as` 才发现）、没法用 `IRBuilder` 的便利、性能差（字符串拼接）。

真实编译器（Rust、Swift、Julia）都用 **LLVM C++ API**：`IRBuilder<>` 建指令、`Value*` 表示 SSA 值、`verifyFunction()` 做检查。它们的好处是类型安全 + 直接拿到内存中的 IR 供 pass 处理。**但底层生成的东西和我们一样**——`IRBuilder::CreateAdd` 最终就是产生一条 `add` 指令。

### 7.2 从 LLVM IR 到 MLIR：为什么需要多一层

| | LLVM IR | MLIR |
|---|---|---|
| 层级 | **单一固定层级**，指令集写死 | **多级**，Dialect 可自定义 |
| 抽象高度 | 接近机器（`add i32`、`load`、`br`） | 任意高（`linalg.matmul`、`tf.Conv2D`） |
| 类型 | 标量、指针、向量、结构体 | 含**张量**（`tensor<4x8xf32>`）、内存引用（`memref`） |
| 共同点 | **SSA + 基本块 + pass 管线** | 完全一样 |

**关键问题：深度学习编译器为什么不能直接用 LLVM IR？**

因为一个矩阵乘在 LLVM IR 里是**三层嵌套循环 + 一堆 GEP 和 load/store**。一旦降到这个形式，"这是一个矩阵乘"的信息就**永久丢失**了——而算子融合、tiling、循环变换这些优化，**全都需要知道"这是个矩阵乘"**。从三重循环里恢复这个信息（叫"提升 raising"）极其困难。

MLIR 的方案：**让 IR 有多个层级，在每一层做适合那一层的优化，逐级降低**。

```
tf.Conv2D                        ← 这一层能做算子融合
   ↓ lowering
linalg.conv_2d                   ← 这一层能做 tiling、循环变换
   ↓ lowering
scf.for + arith.mulf             ← 这一层能做循环优化
   ↓ lowering
LLVM IR / NVVM                   ← 这一层能做指令选择、寄存器分配
```

**每一级都是 SSA，每一级都用同一套 pass 基础设施。** 这就是 MLIR 说自己是 "Multi-Level IR" 的意思——**它把 LLVM 的成功经验（SSA + pass）泛化到任意抽象层级**。

所以你在本篇学的东西一点没浪费：**SSA、基本块、支配关系、pass 管线，在 MLIR 里是原封不动的同一套概念**，只是指令集换了。

### 7.3 对你的方向（AI Infra / GPU 计算图）

三条直接的连接：

**① 计算图就是 IR。** 你课题里的"GPU 计算图"在 PyTorch 里是 `torch.fx.Graph`，在 TVM 里是 Relay/Relax，在 ONNX 里是 protobuf 图。它们全都是**SSA 形式的三地址码**——`torch.fx` 的每个 `Node` 有唯一的名字、一个 `target`（运算）、一个 `args` 列表，**和 `t3 = t1 + t2` 是同一个结构**。你打印一张 fx graph 出来对照 §2.1，会发现它就是三地址码。

**② 算子融合 = 公共子表达式消除的近亲。** 两者都建立在"值有名字、def-use 关系已知"之上（§1.2）。融合判断"这两个算子能不能合并"，需要的正是 def-use 链——`10` 篇会讲。

**③ "巨核"优化在改的就是 lowering 策略。** 你小米那个"巨核大模型推理优化"课题，本质是决定"在哪一级、以什么粒度把图降级成 kernel"。这正是 MLIR lowering 的核心问题：降得太早丢信息（§7.2），降得太晚没法生成代码。**你现在理解这个 tradeoff 的语言，就是本篇建立的。**

**④ φ 和控制流。** GPU kernel 里的控制流（`if`/`for`）在 Triton 编译后也是 SSA + φ。你 profiling 时看 NVVM IR 或 PTX，会直接遇到 §3.4 那些规则。

## 下一步

你现在能读懂我们生成的每一行 IR 了，也知道了 SSA 是什么、为什么我们不手写 φ。但有几个问题本篇只是指了指：

- `%Int` 为什么是 `{ i8*, i32 }` 而不是别的布局？
- vtable 那 12 个槽位的编号是怎么定的？为什么重写的方法能复用父类槽位？
- `cool_alloc(16)` 里的 16 是谁算出来的？
- 函数调用时参数和返回值到底放在哪？

接着读 `08_运行时组织.md`：

- **对象布局** —— 为什么每个对象都以类元信息指针开头，以及子类布局为什么是父类布局的**前缀扩展**（这正是 `06a` §1.2 讲 soundness 时说的"槽位下标稳定"的物理根据）；
- **分发表与下标分配** —— 那 12 个槽位的编号算法，以及"方法可重写、属性不可重定义"的最终解释（`05b` §6 欠下的账在这里还）；
- **栈帧与调用约定** —— 参数、返回值、局部变量各自的位置。

读完 `08`，`09` 的代码生成就只剩"把这些规则写成 C++"这一件事了。
