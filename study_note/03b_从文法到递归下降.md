## 精炼段

`03a` 证明了左递归必须消除，也给出了"消完 → 结合性错 → 加累加器 → 尾递归拉成循环"这四步。本篇解决剩下的两个问题：**该消到什么程度**，和**多条产生式怎么选**。FIRST/FOLLOW 就是这两个问题的工具，但它们的价值不在定义——而在你亲手算完 Cool 的 `expr` 层之后会发现：**`ID <- expr` 和 `ID` 的 FIRST 集撞了，Cool 文法不是 LL(1)**。这个冲突有且只有一处，`parser.h` 多带一个 `nxt_` 成员就化解了。这才是 FIRST 集的真实用途：**它是一份"你需要几个 token 前瞻"的诊断报告**。后半篇从 `01` 篇那张八层优先级表出发，用一条机械规则推出 `parseExpr → parseNot → … → parsePrimary` 这条函数链，并证明它为什么真的能实现优先级（§3.4 的层级契约）。最后 §5 把 `1 + 2 * 3` 塞进调用栈逐帧跑一遍——这一节不看，递归下降就永远是玄学。

## 1. 先把分层文法写出来（本篇的操作对象）

`03a` §2.2 那份 Cool 文法有 8 条左递归产生式，全部挤在一个 `expr` 里。按 `01` 篇 §5 的优先级表（**由紧到松**）：

```
.  @          ← 最紧
~
isvoid
*  /
+  -
<=  <  =
not
<-            ← 最松
```

反过来**由松到紧**编号，每级一个非终结符（`E0` 最松，`E8` 是原子）：

```
E0 → ID '<-' E0                                   -- 赋值，右结合
   | E1
E1 → NOT E1                                       -- not，前缀
   | E2
E2 → E3 [ ('<=' | '<' | '=') E3 ]                 -- 比较，非结合（方括号 = 至多一次）
E3 → E4 ( ('+' | '-') E4 )*                       -- 加减，左结合
E4 → E5 ( ('*' | '/') E5 )*                       -- 乘除，左结合
E5 → ISVOID E6 | E6                               -- isvoid，前缀
E6 → '~' E6 | E7                                  -- 取负，前缀
E7 → E8 ( '.' ID '(' Args ')'
         | '@' TYPEID '.' ID '(' Args ')' )*      -- 分派，后缀
E8 → ID                                           -- 变量引用
   | ID '(' Args ')'                              -- self 分派
   | INT_CONST | STR_CONST | TRUE | FALSE
   | '(' E0 ')'                                   -- ★ 括号内重置到最松层
   | IF E0 THEN E0 ELSE E0 FI
   | WHILE E0 LOOP E0 POOL
   | '{' (E0 ';')+ '}'
   | LET ID ':' TYPEID ['<-' E0] (',' ID ':' TYPEID ['<-' E0])* IN E0
   | CASE E0 OF (ID ':' TYPEID '=>' E0 ';')+ ESAC
   | NEW TYPEID

Args → [ E0 (',' E0)* ]
```

这份文法**怎么来的**是 §3 的内容，先别管。现在只把它当成给定输入，用它来练 FIRST/FOLLOW —— 因为 §2 算出的结论会反过来影响 §3 的设计。

**注意 `E8 → '(' E0 ')'` 这一条**：括号里从 `E0` 重新开始，不是 `E8`。这就是"括号重置优先级"的文法层表达，`03a` §4 的四步变换里没有它的位置，它是独立的一条。

## 2. FIRST 与 FOLLOW：算出来到底干什么用

### 2.1 动机先行：递归下降在哪一步会卡住

递归下降的每个函数对应一个非终结符。函数体要干的事是"在多条产生式里挑一条"。比如 `E8` 有 11 条产生式，`parseE8` 怎么知道该走哪条？

**唯一的信息来源是当前 token。** 所以问题变成：

> 给定当前 token `t`，哪些产生式**可能**以 `t` 开头？
>
> - 恰好一条 → 直接选它，没有歧义；
> - 两条以上 → **卡住了**，1 个 token 不够，得想别的办法。

"一个符号串可能以哪些终结符开头"——这个集合就是 **FIRST**。

**所以 FIRST 集的用途是：诊断"1 个 token 前瞻够不够"。** 不是为了填表考试，是为了知道你的 parser 要不要多带一个 `nxt_`。

### 2.2 FIRST 的定义与计算规则

**定义**：对任意符号串 `α`，

```
FIRST(α) = { t | t 是终结符，且 α ⇒* t β 对某个 β 成立 }
         ∪ { ε | 若 α ⇒* ε }
```

白话：**从 `α` 出发，第一个可能蹦出来的终结符都有哪些**；如果 `α` 可能整个消失，就把 `ε` 也算进去。

计算规则（三条，按需反复应用直到不再变化）：

| 情形 | 规则 |
|---|---|
| `α` 是终结符 `a` | `FIRST(a) = { a }` |
| `α` 是 `ε` | `FIRST(ε) = { ε }` |
| `α = X₁X₂…Xₙ` | 从左往右累加 `FIRST(Xᵢ)\{ε}`；只要 `ε ∉ FIRST(Xᵢ)` 就停。若全都含 `ε`，则 `ε ∈ FIRST(α)` |
| `A` 是非终结符，有 `A → α₁ \| … \| αₖ` | `FIRST(A) = ⋃ᵢ FIRST(αᵢ)` |

> **为什么第三条要"只要不含 ε 就停"？** 因为 `X₁` 如果不可能消失，那第一个终结符一定来自 `X₁`，`X₂` 之后的都被挡住了，够不到开头位置。只有 `X₁` 可能整个消失时，`X₂` 才有机会站到开头。

### 2.3 手算：Cool 表达式层的 FIRST（★ 动手做）

**从最底层往上算**（因为上层依赖下层）。我先做 `E8`，你接着往上算 `E7` 到 `E0`。

**FIRST(E8)** —— 把 11 条产生式的开头符号收集起来：

| 产生式 | 开头 |
|---|---|
| `ID` | `ID` |
| `ID '(' Args ')'` | `ID` |
| `INT_CONST` | `INT_CONST` |
| `STR_CONST` | `STR_CONST` |
| `TRUE` / `FALSE` | `TRUE`, `FALSE` |
| `'(' E0 ')'` | `(` |
| `IF …` | `IF` |
| `WHILE …` | `WHILE` |
| `'{' … '}'` | `{` |
| `LET …` | `LET` |
| `CASE …` | `CASE` |
| `NEW TYPEID` | `NEW` |

```
FIRST(E8) = { ID, INT_CONST, STR_CONST, TRUE, FALSE, '(', IF, WHILE, '{', LET, CASE, NEW }
```

12 个元素，没有 `ε`（`E8` 不可能为空）。

**现在你来（纸笔，5 分钟）**：算出 `FIRST(E7)` … `FIRST(E0)`。提示：`E7 → E8 (…)*`，星号部分可以零次，所以 `E7` 的开头完全由 `E8` 决定。

```
FIRST(E7) = FIRST(E8)                                    （星号可零次，开头只能来自 E8）
FIRST(E6) = { '~' } ∪ FIRST(E7)                          （13 个）
FIRST(E5) = { ISVOID } ∪ FIRST(E6)                       （14 个）
FIRST(E4) = FIRST(E5)                                    （E4 → E5 (…)*，同理）
FIRST(E3) = FIRST(E4)
FIRST(E2) = FIRST(E3)
FIRST(E1) = { NOT } ∪ FIRST(E2)                          （15 个）
FIRST(E0) = FIRST(ID '<-' E0) ∪ FIRST(E1)
          = { ID } ∪ FIRST(E1)
          = FIRST(E1)                                    ← ID 本来就在里面！
```

```

              IF, WHILE, '{', LET, CASE, NEW, '~', ISVOID, NOT }
```

### 2.4 ★ 收获：Cool 文法不是 LL(1)，而且只坏在一处

**LL(1) 的判定条件**：对每个非终结符 `A` 的任意两条产生式 `A → α | β`，

1. `FIRST(α) ∩ FIRST(β) = ∅`；
2. 若 `ε ∈ FIRST(α)`，则 `FIRST(β) ∩ FOLLOW(A) = ∅`（反之亦然）。

满足 → 看 1 个 token 就能唯一选产生式；不满足 → 1 个 token 不够。

**现在检查 `E0`**：

```
E0 → ID '<-' E0        FIRST = { ID }
   | E1                FIRST ⊇ { ID }        （因为 E1 ⇒* E8 ⇒ ID）
                       ─────────────────
                       交集 = { ID } ≠ ∅     ✗ 违反条件 1
```

**结论：Cool 的表达式文法不是 LL(1)。**

直觉上也很明显——看到一个 `ID`，你不知道它是：

```cool
x <- 5        -- 赋值，走 E0 第一条
x + 1         -- 变量引用，走 E1 → … → E8
f(3)          -- self 分派，走 E1 → … → E8
```

**第一个 token 全是 `ID`，三条路完全无法区分。** 但看**第二个** token 就一清二楚：`<-` → 赋值；其它 → 交给下层。

顺手检查 `E8` 里 `ID` 和 `ID '(' Args ')'` 这一对：FIRST 也都是 `{ID}`，同样撞了。

**两处冲突，两种修法**：

| 冲突位置 | 为什么撞 | 修法 |
|---|---|---|
| `E0`：`ID '<-' E0` vs `E1` | 都可能以 `ID` 开头 | **2 token 前瞻**：看 `nxt_` 是不是 `<-` |
| `E8`：`ID` vs `ID '(' …` | 都以 `ID` 开头 | **左因子分解**：先吃掉 `ID`，再看下一个是不是 `(` |

> **为什么 `E8` 能用左因子分解，`E0` 不能？**
>
> 左因子分解 = 把公共前缀提出来：`ID (ε | '(' Args ')')`。先无条件消耗 `ID`，再决策。`E8` 里两条分支**都留在 `E8` 内部**，吃掉 `ID` 后本地就能处理完。
>
> `E0` 不行：如果不是赋值，控制权要交给 `parseNot`，而那个 `ID` 是下层 `parsePrimary` 需要看到的。你已经把它吃掉了，就得把它**当参数穿过 7 层函数**传下去——签名全得改，丑陋且易错。**多带一个 `nxt_` 成员便宜得多。**

**这就是 `parser.h:22` 那行注释的完整来历**：

```cpp
Token cur_;   // 当前 token
Token nxt_;   // 下一个 token（前瞻 2）
```

以及构造函数里为什么要 `next()` 两次：

```cpp
explicit Parser(std::string src) : lexer_(std::move(src)) {
  cur_ = lexer_.next();
  nxt_ = lexer_.next();     // 预读第二个，维持"双缓冲"
}
```

和 `advance()` 为什么是移位而不是重读：

```cpp
void advance() { cur_ = nxt_; nxt_ = lexer_.next(); }
```

> **FIRST 集的价值，就是这个结论。** 不算，你只会觉得 `nxt_` 是"作者随手多存了一个"；算了，你知道它是**唯一一处 LL(1) 冲突的最小修补**，而且知道换个语言该怎么判断要不要它。
>
> **工业对照**：C++ 的文法冲突比这严重得多——`T(x);` 既可以是变量声明也可以是函数调用表达式，靠任意长度的前瞻都区分不了（需要符号表信息）。Clang 的解法是 `TentativeParsing`：**先试着按一种解释 parse，失败就回溯重来**。所以 Clang 的 parser 里有 `TentativeParsingAction` 这种"存档/读档"机制。我们运气好，Cool 只需要 `k=2`。

### 2.5 FOLLOW：算出来干什么用

**定义**：

```
FOLLOW(A) = { t | 存在推导 S ⇒* α A t β }     ∪  { $ | 若 S ⇒* α A }
```

白话：**在所有合法推导里，紧跟在 `A` 后面可能出现的终结符**。`$` 是输入结束标记。

**它有两个用途，第二个才是关键：**

**用途 ①（教科书版）**：处理 ε-产生式。当 `A → ε` 时，`parseA` 无法从"下一个 token 属于 FIRST"来决定要不要走空产生式，得看"下一个 token 是不是 FOLLOW(A) 里的"——是则走空，否则报错。

**用途 ②（实战版）**：**告诉你循环该在哪里停。**

`E3 → E4 ( ('+'|'-') E4 )*` 这个星号循环，什么时候该退出？`03a` §4.6 的代码写的是"看到的不是 `+` 也不是 `-` 就退"。但另一种等价写法是"看到 FOLLOW 里的东西就退"。两者的区别在**错误处理时机**，§2.7 会讲。

### 2.6 手算 FOLLOW(E0)

`E0` 在哪些位置出现？把 §1 文法里所有出现 `E0` 的地方找出来，看它右边紧跟什么：

| 出现位置 | `E0` 右边紧跟 | 贡献 |
|---|---|---|
| `feature → ID '(' formals ')' ':' TYPEID '{' E0 '}'` | `}` | `}` |
| `feature → ID ':' TYPEID '<-' E0 ';'` | `;` | `;` |
| `E0 → ID '<-' E0` | 串尾 → 继承 FOLLOW(E0) | （自身，无新增） |
| `E8 → '(' E0 ')'` | `)` | `)` |
| `E8 → IF E0 THEN …` | `THEN` | `THEN` |
| `E8 → IF … THEN E0 ELSE …` | `ELSE` | `ELSE` |
| `E8 → IF … ELSE E0 FI` | `FI` | `FI` |
| `E8 → WHILE E0 LOOP …` | `LOOP` | `LOOP` |
| `E8 → WHILE … LOOP E0 POOL` | `POOL` | `POOL` |
| `E8 → '{' (E0 ';')+ '}'` | `;` | `;` |
| `E8 → LET … '<-' E0 (',' …)* IN E0` | `,` / `IN` | `,`, `IN` |
| `E8 → LET … IN E0` | 串尾 → 继承 | （无新增） |
| `E8 → CASE E0 OF …` | `OF` | `OF` |
| `E8 → CASE … '=>' E0 ';'` | `;` | `;` |
| `Args → E0 (',' E0)*`，在 `'(' Args ')'` 中 | `,` / `)` | `,`, `)` |

汇总：

```
FOLLOW(E0) = { '}', ';', ')', ',', THEN, ELSE, FI, LOOP, POOL, IN, OF, ESAC, $ }
```

因为 `E1` … `E8` 都能出现在 `E0` 的末尾位置（`E0 → E1`、`E1 → E2`、…），所以：

```
FOLLOW(Eₖ) ⊇ FOLLOW(E0)   对所有 k
```

再加上各层自己的运算符。例如 `E4`（乘除层）出现在 `E3 → E4 (('+'|'-') E4)*` 里，所以 `FOLLOW(E4) ∋ '+', '-'`。

### 2.7 这个集合在代码里长什么样

**看清楚 `FOLLOW(E0)` 这 13 个 token 是什么：全是"表达式结束的信号"。**

- `}` `;` `)` `,` —— 结构闭合与分隔
- `THEN` `ELSE` `FI` `LOOP` `POOL` `IN` `OF` `ESAC` —— 复合结构的关键字边界
- `$` —— 文件结束

于是 FOLLOW 集的实战含义变得很具体：

> **任何一层的循环，遇到 FOLLOW 里的 token 就必须停下来，把控制权交还给调用者。** 因为这些 token 不属于表达式，属于包着它的那个结构（`;` 属于 block，`THEN` 属于 if，`)` 属于括号或实参表）。

现在对照 `parser.cpp:128` 的真实写法：

```cpp
while (at(Tok::PLUS) || at(Tok::MINUS)) { … }      // 正向：只在自己的运算符上继续
```

而不是：

```cpp
while (!inFollowSet(cur_.kind)) { … }              // 反向：不在 FOLLOW 里就继续
```

**两种写法在合法输入上行为完全相同，在非法输入上差别很大：**

| 写法 | `1 + 2 @` 会怎样 | 错误信息 |
|---|---|---|
| 正向（真实代码） | 循环见 `@` 不是 `+/-`，正常退出；`@` 留给上层；最终落到某个 `expect` | `line N: expected ';' but got '@'` —— 指出真实的语法位置 |
| 反向（FOLLOW 版） | 循环发现 `@` 不在 FOLLOW 里，继续循环 → 然后发现它也不是 `+/-` → 得在循环内部再写一套报错 | 需要额外代码才能给出同等质量的信息 |

> **所以手写 parser 普遍用正向写法**：FOLLOW 集是**设计阶段的分析工具**（帮你确认"停在这里是对的、不会漏吃合法输入"），而不是运行时的数据结构。**这就是为什么你在 `parser.cpp` 里找不到任何 FOLLOW 集合**——它在设计时被用过了，然后被编译进了循环条件的形状里。
>
> 反过来，**表驱动**的 LL(1) parser（生成器产出的那种）会把 FIRST/FOLLOW 算出来做成真实的二维表。`04` 篇的 LR 分析表同理。**手写 = 把分析结果编码进控制流；生成 = 把分析结果编码进数据表。** 这是两条路线的根本差异。

### 2.8 小结：这两个集合各自的岗位

| | 回答什么问题 | 在本项目的具体产物 |
|---|---|---|
| FIRST | 看 1 个 token 够不够选产生式？ | **发现 `E0` 处 LL(1) 冲突 → `parser.h` 加 `nxt_`**；`E8` 处冲突 → 左因子分解 |
| FOLLOW | 循环/递归该在哪停？空产生式何时走？ | 确认各层循环条件正确；`parseBlock`/`parseCase` 用 `}`/`ESAC` 当终止条件 |

`parseBlock` 正是 FOLLOW 思路的直接应用（`parser.cpp:303`）：

```cpp
std::unique_ptr<Expr> Parser::parseBlock() {
  Token t = cur_; advance();                 // 吃掉 '{'
  auto n = std::make_unique<Block>(); n->line = t.line;
  while (!at(Tok::RBRACE)) {                 // ← '}' 是终止信号
    n->exprs.push_back(parseExpr());
    expect(Tok::SEMI, "';'");
  }
  expect(Tok::RBRACE, "'}'");
  return n;
}
```

## 3. 优先级爬升：从优先级表机械地推出函数链

上一版 03 笔记的最大问题在这里：它直接甩出一张八层函数表和一句"为什么这样排"。你没法从优先级表自己推出那条链，换个语言就又不会了。这一节把它变成**可复现的推导过程**。

### 3.1 输入与目标

**输入**：`01` 篇 §5 的优先级表 + 结合性说明。

**目标**：一份无二义的分层文法（就是 §1 那份），以及对应的函数链。

### 3.2 推导规则（四步，机械可执行）

**第 1 步：按优先级由松到紧编号。**

优先级表是"由紧到松"给的，反过来写，最松的编号 0：

| 级 | 运算符 | 结合性 | 形态 |
|---|---|---|---|
| 0 | `<-` | 右结合 | 二元中缀 |
| 1 | `not` | — | 前缀 |
| 2 | `<= < =` | **非结合** | 二元中缀 |
| 3 | `+ -` | 左结合 | 二元中缀 |
| 4 | `* /` | 左结合 | 二元中缀 |
| 5 | `isvoid` | — | 前缀 |
| 6 | `~` | — | 前缀 |
| 7 | `. @` | 左结合 | **后缀** |
| 8 | （原子） | — | primary |

**第 2 步：每级配一个非终结符 `Eₖ`。** 一共 9 个（0…8），`E8` 是原子层。

**第 3 步：按"形态"套模板写产生式。** 这是全节的核心，五个模板：

| 形态 | 模板 | 为什么（回指 `03a` §4.7） |
|---|---|---|
| 二元 **左**结合 | `Eₖ → Eₖ₊₁ ( op Eₖ₊₁ )*` | 星号 → 循环 → 旧树进左孩子 → 向左长 |
| 二元 **右**结合 | `Eₖ → Eₖ₊₁ op Eₖ \| Eₖ₊₁` | 右端递归**同层** → 结果进右孩子 → 向右长 |
| 二元 **非**结合 | `Eₖ → Eₖ₊₁ [ op Eₖ₊₁ ]` | 方括号至多一次 → 不循环不同层递归 → 只能有一层 |
| **前缀** | `Eₖ → op Eₖ \| Eₖ₊₁` | 递归同层 → `op op x` 合法 |
| **后缀** | `Eₖ → Eₖ₊₁ ( postfix )*` | 星号循环，每轮把旧树当接收者 |

**第 4 步：原子层收所有"自带边界"的东西**，并且内部的子表达式**回到 `E0`**。

套用一遍，就得到 §1 那份文法。**逐条核对**：

```
级 0  右结合  →  E0 → ID '<-' E0 | E1                    ✓ 右端递归同层
级 1  前缀    →  E1 → NOT E1 | E2                         ✓ 递归同层
级 2  非结合  →  E2 → E3 [ ('<='|'<'|'=') E3 ]            ✓ 至多一次
级 3  左结合  →  E3 → E4 ( ('+'|'-') E4 )*                ✓ 星号
级 4  左结合  →  E4 → E5 ( ('*'|'/') E5 )*                ✓ 星号
级 5  前缀    →  E5 → ISVOID E6 | E6                      ← 注意这里，§3.5 有话说
级 6  前缀    →  E6 → '~' E6 | E7                         ✓ 递归同层
级 7  后缀    →  E7 → E8 ( '.' ID '(' Args ')' | … )*     ✓ 星号
级 8  原子    →  E8 → … | '(' E0 ')' | IF E0 … | …        ✓ 子表达式回 E0
```

**第 0 级的赋值有个额外细节**：模板给的是 `E0 → E1 '<-' E0 | E1`，但 Cool 规定赋值左部**只能是标识符**（不能是 `f(x) <- 3`），所以写成 `ID '<-' E0`。这个收紧同时也是 §2.4 那个 LL(1) 冲突的来源。

**第 5 步（收尾）：文法 → 函数，一对一。**

```
非终结符 Eₖ        →  函数 parseEₖ
产生式右部的 Eₖ₊₁  →  调用 parseEₖ₊₁
星号 ( … )*        →  while 循环
方括号 [ … ]       →  单个 if
终结符 op          →  at(op) 判断 + advance() 消耗
多条产生式         →  switch / if-else 分派（靠 FIRST 集区分，见 §2）
```

按这个映射，函数链就是：

```
parseExpr(E0) → parseNot(E1) → parseCompare(E2) → parseAddSub(E3)
   → parseMulDiv(E4) → parseIsvoid(E5) → parseNeg(E6)
   → parseDispatch(E7) → parsePrimary(E8)
```

**和 `parser.h:34-42` 完全一致。** 现在这条链不是天降的了——它是优先级表 + 五个模板 + 一对一映射的必然结果。

> **可迁移性检验**：给你 Python 的优先级表（`or` / `and` / `not` / 比较 / `|` / `^` / `&` / 移位 / `+-` / `*/%` / 一元 / `**` / 下标调用属性），你现在能不能造出 13 层函数链？能。**这就是把"宣布"换成"推导"的收益。**

### 3.3 为什么括号那条要回到 `E0`

`E8 → '(' E0 ')'` 里为什么是 `E0` 而不是 `E8`？

因为**括号的语义就是"清空所有优先级约束"**。`(1 + 2) * 3` 里，括号内的 `1 + 2` 必须能用到级 3 的 `+`，而调用点在级 8。只有回到 `E0` 才能重新走完整条链。

代码里（`parser.cpp:263`）：

```cpp
case Tok::LPAREN: {
  advance();
  auto e = parseExpr();              // ★ 回到 E0，不是 parsePrimary
  expect(Tok::RPAREN, "')'");
  return e;                          // ★ 注意：不包 Paren 节点
}
```

**两个细节**：

1. **回到 `parseExpr`** = 优先级重置。若误写成 `parsePrimary()`，`(1+2)*3` 会在 `1` 之后见到 `+` 而报错。
2. **不创建 `Paren` 节点**——直接返回内部表达式的树。因为括号的作用是**影响树形**，树建好之后它的使命就完成了，留着它只是噪音。`ast.h` 里确实没有 `Paren` 节点。这是 `03c` 要讲的"AST 丢弃语法噪音"的第一个实例。

> **反例（什么时候需要保留括号）**：写代码格式化工具（clang-format）或者要做源码到源码变换的工具时，括号位置必须保留，那种树叫 **CST / concrete syntax tree**（Rust 的 `rowan`、Roslyn 的 red-green tree）。**编译器要 AST，重构工具要 CST。** 取舍点是"要不要还原出原始文本"。

### 3.4 ★ 为什么分层真的能实现优先级（层级契约）

这是 §0 问题 5。我给一个能自己验证的论证，而不是"就是这样"。

**层级契约（level invariant）**：

> `parseEₖ` 消耗的是剩余输入的一个前缀，该前缀构成一个表达式，其中**只含级别 ≥ k 的运算符**（即级 k 及更紧的）。它**绝不消耗级别 < k 的运算符**。

**归纳证明（自底向上）**：

- **基础**：`parseE8`（primary）只吃原子和自带闭合符的结构，不吃任何中缀运算符。契约成立（空集 ⊆ 任何集合）。

- **归纳步**：假设 `parseEₖ₊₁` 满足契约（只吃级 ≥ k+1 的）。看 `parseEₖ` 的模板 `Eₖ → Eₖ₊₁ ( opₖ Eₖ₊₁ )*`：
  - 它先调 `parseEₖ₊₁` —— 由归纳假设，吃掉级 ≥ k+1 的部分；
  - 然后循环条件是 `at(opₖ)` —— **只在级 k 的运算符上继续**；
  - 遇到级 < k 的运算符（更松），`at(opₖ)` 为假 → 退出循环 → **原样留给调用者**。
  - 所以 `parseEₖ` 消耗的运算符 ⊆ {级 k} ∪ {级 ≥ k+1} = {级 ≥ k}。契约成立。∎

**两条推论，它们就是"优先级生效"的机制**：

**推论 1（紧的先成树）**：级 k 的运算符要取右操作数时，调的是 `parseEₖ₊₁`。由契约，它会**贪心吃掉所有更紧的运算符**，返回一棵完整子树。于是更紧的运算符被"锁"在子树内部，位置比级 k 的算符更深。

> 深度 = 求值顺序。树越深越先算。**这就是"优先级高先算"在树结构上的实现。**

**推论 2（松的自动上浮）**：低层函数遇到更松的运算符会立刻退出，把它留在输入里。控制权层层返回，直到某一层的循环条件认得它。**运算符自己会"冒泡"到正确的层级。** 不需要任何全局协调。

**用 `1 * 2 + 3` 验证推论 2**：

```
parseAddSub(级3) → parseMulDiv(级4)
    parseMulDiv: lhs=1，见 '*'（级4，自己的）→ 吃掉，rhs=2 → 建 Binary(1*2)
                 继续循环：见 '+'？循环条件是 STAR||SLASH → 假 → 退出
                 返回 Binary(1*2)，'+' 还在输入里
parseAddSub: lhs=Binary(1*2)，见 '+'（级3，自己的）→ 吃掉，rhs=parseMulDiv()=3
             建 Binary((1*2)+3)
```

得 `+( *(1,2), 3 )`。`*` 在更深层 → 先算。✓

### 3.5 ★ 一个真实的实现偏差（我查出来的，顺手给你）

按 §3.2 的前缀模板，级 5 应该是：

```
E5 → ISVOID E5 | E6         ← 递归同层，允许 isvoid isvoid x
```

但 `parser.cpp:155` 写的是：

```cpp
std::unique_ptr<Expr> Parser::parseIsvoid() {
  if (at(Tok::ISVOID)) {
    Token t = cur_; advance();
    auto iv = std::make_unique<IsVoid>();
    iv->line = t.line;
    iv->expr = parseNeg();        // ★ 调的是 parseNeg（级 6），不是 parseIsvoid（级 5）
    return iv;
  }
  return parseNeg();
}
```

**操作数调的是下一层 `parseNeg`，不是同层 `parseIsvoid`。** 后果：

```cool
isvoid isvoid x     -- 按 Cool 手册（expr ::= isvoid expr）合法
                    -- 但这个实现会报错：unexpected token 'isvoid'
```

对比同为前缀的另外两个，它们都是递归同层、行为正确：

```cpp
parseNot:  n->expr = parseNot();     // ✓ not not x 可以
parseNeg:  n->expr = parseNeg();     // ✓ ~~x 可以
```

**所以这是 `parseIsvoid` 的一个 bug**，性质是"过严"（拒绝合法程序），不是"过松"。实践中 `isvoid isvoid x` 没人写（第一个 `isvoid` 返回 `Bool`，套第二层永远得 `false`），所以从没被测出来。

修法是一个字的改动：

```cpp
iv->expr = parseIsvoid();     // 改成递归同层
```

**这处偏差对你的价值不在"抓到一个 bug"，而在它印证了 §3.2 那套模板是有判别力的**：模板说该递归同层，代码没有，于是一类合法输入被拒。**能从文法反推出实现该长什么样，就能反过来审计实现对不对。** 这正是把"宣布"换成"推导"的第二个收益。

> 这个修法留到 §6 的动手题，你改完跑一下 `isvoid isvoid x` 验证。

```cpp
std::unique_ptr<Expr> Parser::parseExpr() {
  if (at(Tok::OBJECTID) && nxt_.kind == Tok::ASSIGN) {   // ★ 2 token 前瞻
    Token id = cur_;
    advance();          // 消费 ID
    advance();          // 消费 <-
```

```cpp
std::unique_ptr<Expr> Parser::parseCompare() {
  auto lhs = parseAddSub();
  BinOp op;
  if (at(Tok::LE)) op = BinOp::Le;
  else if (at(Tok::LT)) op = BinOp::Lt;
```

| 22 | `    parseMulDiv` | END | `b2 = Binary(2*3)`；`lhs = b2` | |
| 23 | `    parseMulDiv` | END | `while(STAR\|\|SLASH)`? 否 → 退出 | **`Binary(2*3)`** |
| 24 | `   parseAddSub` | END | `b->rhs = Binary(2*3)`；`lhs = Binary(1+(2*3))` | |
| 25 | `   parseAddSub` | END | `while(PLUS\|\|MINUS)`? 否 → 退出 | `Binary(1+(2*3))` |
| 26 | `  parseCompare` | END | `at(LE/LT/EQ)`? 否 → `return lhs` | `Binary(1+(2*3))` |
| 27 | ` parseNot` | END | （透传） | `Binary(1+(2*3))` |
| 28 | `parseExpr` | END | （透传） | `Binary(1+(2*3))` |

### 5.2 最终的树

```
        Binary(+)
        /       \
   IntConst(1)   Binary(*)
                 /       \
            IntConst(2)  IntConst(3)
```

= `1 + (2*3)` = **7** ✓

### 5.3 从这张表里读出四个要点

**① 第 12 步是"优先级生效"的瞬间。**

`parseMulDiv` 看到 `cur_=PLUS`，循环条件 `at(STAR)||at(SLASH)` 为假 → **一轮都不进，原样返回 `IntConst(1)`**。它**主动放弃**了 `+`，把它留给上层。这就是 §3.4 推论 2（松的自动上浮）的实况。

**② 第 15–23 步是"紧的先成树"的瞬间。**

`parseAddSub` 要取 `+` 的右操作数，调 `parseMulDiv()`。这一层**贪心吃掉了整个 `2*3`**（第 18–22 步），返回一棵完整子树。于是 `*` 被封装在子树里，深度比 `+` 大一层。这是 §3.4 推论 1 的实况。

> **对比一下如果写错**：假如 `parseAddSub` 的 `b->rhs` 写成 `parsePrimary()`（越过了乘除层），那第 16 步只会拿到 `IntConst(2)`，然后 `cur_=STAR` 冒泡上去，最终在某个 `expect` 处报错。**"右操作数调下一层"这个选择，就是优先级的全部实现。**

**③ `cur_` 只在 `advance()` 时变化，一共变了 5 次**（第 9、14、17、19、21 步），正好对应 5 个 token 被消耗。`03a` §4.2 那条契约在这里可视化了：**每次进入递归前都有 `advance()`，所以剩余 token 数严格递减，必然终止。**

**④ 第 1–8 步是 8 层"空穿透"。**

`1 + 2 * 3` 里没有 `<-`、`not`、比较、`isvoid`、`~`、`.`，所以最开始那 8 层函数每层只做一次判断就下钻。**层数 = 优先级级数，代价是每个表达式都要穿一遍全链。**

| 关心的问题 | 回答 |
|---|---|
| 性能上要紧吗？ | 不要紧。深度是**常数**（= 优先级层数，Cool 是 9），不随输入长度增长。每层只是一次 `if` + 一次函数调用，`-O2` 下大部分被内联。 |
| 有更省的写法吗？ | 有，**Pratt parsing / 优先级参数法**：一个函数带 `minPrec` 参数，用数值比较代替函数分层。Clang 的 `ParseRHSOfBinaryExpression(prec)` 就是这个。代码从 9 个函数缩成 1 个，但可读性下降。 |
| 那为什么我们选分层？ | 分层法的**每个函数名就是文档**，`parseAddSub` 一看就知道管什么；而且它和文法一一对应，便于审计（§3.5 就是靠这个对应关系抓出 `isvoid` 的偏差）。**教学和中小型语言用分层，追求代码量和灵活性用 Pratt。** 两者算法本质相同——一个把优先级编码在调用链**结构**里，一个编码在**数值参数**里。 |

### 5.4 自己再跑两个（答案我给了预期，过程你写）

| 输入 | 预期树 | 要观察什么 |
|---|---|---|
| `1 * 2 + 3` | `+( *(1,2), 3 )` | `parseMulDiv` 在第几步退出、`+` 怎么冒泡到 `parseAddSub` |
| `~x * y` | `*( Neg(x), y )` | `parseNeg`（级 6）比 `parseMulDiv`（级 4）紧，所以 `~` 只吃 `x` |
| `a <- b <- c` | `Assign(a, Assign(b, c))` | `nxt_` 在两次判断中各是什么 |
| `not x = y` | `Not( =(x,y) )` | `not`（级 1）比 `=`（级 2）**松**，所以 `not` 吃掉整个比较 |

最后一个值得多说一句：`not x = y` 解析成 `not (x = y)` 而不是 `(not x) = y`，因为 `parseNot` 在级 1，它的操作数调 `parseNot`→`parseCompare`（级 2），会把整个 `x = y` 吃进来。**这符合 `01` 篇 §5 的规定**，但和 C 系语言相反（C 里 `!` 比 `==` 紧，`!x == y` 是 `(!x) == y`）。写 Cool 时这是个真实的坑。

## 7. 术语表

| 术语 | 一句话 |
|---|---|
| FIRST(α) | 从 α 出发第一个可能出现的终结符集合；用途是**诊断几个 token 前瞻够不够** |
| FOLLOW(A) | 紧跟在 A 后面可能出现的终结符集合；用途是**确定循环终止点**与 ε-产生式决策 |
| LL(1) | 从左扫描 + 最左推导 + 1 token 前瞻；判定条件见 §2.4 |
| LL(k) | 需要 k 个 token 前瞻。**Cool 的表达式层是 LL(2)**（`nxt_` 的存在理由） |
| 左因子分解 | 把公共前缀提出来消除 FIRST 冲突：`ID \| ID '(' …` → `ID (ε \| '(' …)`；`parsePrimary` 的 `ID` 分支用的就是它 |
| 优先级爬升 | 每个优先级一层函数、层层下钻；把优先级编码进**调用链结构** |
| 层级契约 | `parseEₖ` 只消耗级别 ≥ k 的运算符，绝不碰更松的；§3.4 证明了它，它是优先级生效的原理 |
| Pratt parsing | 用 `minPrec` 数值参数代替函数分层的等价写法；Clang 用这个 |
| CST | 保留括号、空白等全部语法细节的树；格式化/重构工具需要，编译器不需要 |
| TentativeParsing | Clang 的"试解析 + 回溯"机制，用来对付无界前瞻的文法冲突 |
