## 精炼段

`09` 篇结束时我们手上有一份**能跑但很笨**的 IR：一个 `if n <= 1 then 1 else n * f(n-1) fi` 生成 65 条指令、3 次堆分配，其中一次分配的对象装完立刻被拆开丢掉。本篇的问题是：**凭什么可以把它改短？**

注意"凭什么"这个问法。把 `2 * 3` 换成 `6` 很显然；但把一条 `load` 从循环里提出来**可能是错的**（如果循环体里有人改了那块内存）。所以优化永远是两件事：**一个变换**，加上**一个证明这个变换保持语义的理由**。前者是小事（几行代码），后者才是编译原理——而"证明程序的某个性质在某一点成立"这件事的通用框架就是**数据流分析**：把程序看成控制流图，为每个基本块列一对方程（信息怎么流进来、块内怎么改变它），然后**迭代到不动点**。

本篇按这个顺序展开：先用我们自己的 IR 说明"哪些地方笨、为什么不能随便改"，再建立数据流框架并证明它**一定收敛**，然后用四种经典分析填满"forward/backward × may/must"这个矩阵。最后 §7 是三个实测实验，它们共同指向一个比算法更重要的认识：**优化器的能力不取决于它有多少 pass，而取决于你告诉了它多少事实**。`09` §7.2 那个"一行声明换掉一次堆分配"的实验，在这里会显出它的一般形式。

## 1. 先看清楚"笨"在哪：用我们自己的 IR

### 1.1 三个具体的浪费

拿 `main() : Object { out_int(1 + 2 * 3) }` 编译出来的 `Main.main`（`09` 的编译器，未优化，38 条指令）。三类浪费：

**① 编译期就能算的东西留到了运行时。** `1 + 2 * 3` 全是常量，但 IR 里老老实实做了 `mul` 和 `add`：

```llvm
%t3  = load i32, i32* %t2      ; 取常量 1 的值
%t6  = load i32, i32* %t5      ; 取常量 2 的值
%t9  = load i32, i32* %t8      ; 取常量 3 的值
%t10 = mul i32 %t6, %t9        ; 2*3
...
%t18 = add i32 %t3, %t17       ; 1+6
```

**② 中间结果被装箱，然后立刻拆箱丢掉。** `2*3` 的结果 `%t10` 被装进一个新 `%Int` 对象（`%t11 = call i8* @cool_alloc(i32 16)`），紧接着 `%t15/%t16/%t17` 又把它拆开——这个堆对象的**唯一用途就是被拆开**。

**③ 变量住在内存里。** `%self = alloca i8*` 加一次 `store` 一次 `load`，只为读一个从不改变的参数（`09` §3.2 解释了为什么我们故意这么生成）。

### 1.2 但"显然能改"不等于"随便能改"

这是本篇的入口。试着精确说出**为什么**可以把 `%t10 = mul i32 %t6, %t9` 换成 `6`：

> 因为 `%t6` 在这一点**一定**等于 2，`%t9` **一定**等于 3。

"一定"这个词要求你对**所有可能的执行**都成立。上面的例子里它成立，因为 `%t6` 来自一个 `constant` 全局。但把 `constant` 改成 `global`（可变），同一条推理**立刻失效**——别人可能在运行中改掉 `@int_2` 的内容。

**§7.1 会把这件事做成实验：只改这一个关键字，`-O2` 的折叠全部消失。** 所以请记住本篇的中心命题：

> 优化不是"看出能改"，而是"**证明改了不变**"。证明所依赖的前提，决定了你能证到多强。

## 2. 控制流图：分析的地基

### 2.1 基本块与 CFG

**基本块**（basic block）= 一段"只能从第一条进入、只能从最后一条离开"的直线指令序列。它的边界由两件事划定：**标签**（可能被跳入）和**终结指令**（`br`/`ret`/`unreachable`）。

我们生成的 IR 天然就是这个形状，因为 `09` §5 里每个 `emitLabel` 都开一个新块。真实例子（`while i < 3 loop { out_int(i); i <- i + 1; } pool` 经 `-O2`）：

```
        entry
          │
          ▼
    ┌──► bb1 ──┐         bb1 既是循环体又是条件判断
    │     │    │
    └─────┘    ▼
   （回边）   bb2  ret
```

**CFG** = 节点是基本块、边是"可能的控制转移"。`bb1 → bb1` 那条边叫**回边**（back edge），它是循环存在的标志，也是**数据流方程必须迭代求解**的根本原因（§3.3）。

### 2.2 为什么分析必须以块为单位

块**内部**是直线代码，信息怎么变化一目了然（顺序扫一遍即可）。困难全在块**之间**：

- 一个块可能有**多个前驱**（`if` 的汇合点）→ 信息要**合并**；
- 一个块可能有**多个后继**（分支）→ 信息要**分发**；
- 回边意味着"块 B 的输入依赖块 B 自己的输出"→ **循环依赖**。

这三条正好对应数据流框架的三个部件：**meet 操作**、**方向**、**迭代**。

## 3. 数据流分析框架

### 3.1 四个部件

所有数据流分析都是同一个模板。为每个基本块 `B` 定义两个"事实集合" `in[B]`、`out[B]`，满足：

```
in[B]  = ⨅ { out[P] : P 是 B 的前驱 }        ← meet：合并各路信息
out[B] = transfer_B( in[B] )                 ← transfer：块内如何改变信息
```

（上面写的是**前向**分析。后向分析把 `in`/`out` 和"前驱/后继"同时对调。）

定义一个具体分析 = 填四个空：

| 部件 | 含义 | 举例（活跃变量） |
|---|---|---|
| **格**（lattice） | 事实的取值空间 + 谁比谁"更精确" | 变量集合，⊆ 排序 |
| **方向** | forward / backward | backward |
| **meet** | 多路信息如何合并：∪（may）/ ∩（must） | ∪ |
| **transfer** | 单个块对事实的作用 | `use[B] ∪ (out[B] − def[B])` |

### 3.2 may 还是 must：一个判据

这是最容易记混的地方，但有个可靠判据：**问这个分析被用来做什么，错了会怎样。**

- **活跃变量**用于"能否复用寄存器"。**误判为活跃只是浪费，误判为死会算错**。所以要保守地宁可多算活跃 → 只要**某条**路径上还会用，就算活跃 → **∪（may）**。
- **可用表达式**用于"能否复用已算好的结果"。**误判为可用会算错**。所以必须**所有**路径都算过 → **∩（must）**。

**一句话**：**meet 的选择由"哪种误判是安全的"决定，不是由直觉决定。** 这和 `06a` 讲 soundness 时那条 `D_e ≤ S_e` 是同一种思维——保守的方向必须朝着"不出错"那边倾斜。

### 3.3 为什么必须迭代，以及为什么一定停

方程是**联立**的：`in[B]` 依赖前驱的 `out`，而有回边时前驱的 `out` 又（间接）依赖 `in[B]`。没法一趟算完，所以用**不动点迭代**：

```
初始化所有 in/out 为格的最小元（或最大元，取决于分析）
repeat
    对每个块重新代入方程
until 没有任何集合发生变化
```

**它一定会停**，理由要说准（这是本节唯一需要背的论证）：

1. **transfer 和 meet 都是单调的**（monotone）：输入变"大"，输出不会变"小"；
2. 每轮迭代中，每个集合**只可能单向变化**（比如 liveness 里只增不减）；
3. 格的**高度有限**（变量个数有限 → 集合个数有限）。

单调 + 有限高度 ⟹ 不可能无限变化 ⟹ 有限步内收敛。这是 **Kleene 不动点定理**在有限格上的形式。

> **和 `05b` §3 那个死循环的对照很有意思。** 那里 `conforms` 的 `for(;;)` 会真的转圈，因为继承图**有环且没有单调递减的量**。这里也有环（CFG 的回边），但**有单调性 + 有限性**做保证，所以能停。**"有环"不等于"不终止"，关键是有没有一个单调变化且有界的量。** 这个判据在你以后看任何迭代算法（包括 TVM 的调度搜索、GC 的三色标记）时都用得上。

### 3.4 精度：不动点不是唯一的

迭代得到的是**最小**（或最大）不动点，而它**未必等于"真实答案"**。原因是数据流分析沿着 CFG 的**所有路径**求解，包括**实际不可能走到的路径**：

```cool
if false then x <- 1 else x <- 2 fi    -- 分析仍会合并两个分支
```

这种"路径不敏感"（path-insensitive）是**故意的**：精确回答"哪些路径真能走"等价于判定程序性质，**不可判定**（Rice 定理）。所以静态分析永远是**保守近似**：

```
真实可达状态  ⊆  分析算出的状态
```

多算叫**假阳性**（false positive），是安全的；少算是**不安全**的，绝不允许。你见过的所有编译器警告、IDE 提示、静态扫描工具的"误报"，根源都在这一行包含关系里。

## 4. 活跃变量分析：完整走一遍

选它做详例有两个理由：它是 `11` 篇寄存器分配的**直接输入**，而且它是**后向**分析——把后向做熟了，前向是更简单的对称情形。

### 4.1 定义

变量 `v` 在程序点 `p` **活跃**（live）：存在一条从 `p` 出发的路径，在**重新定义 `v` 之前**读了 `v`。

每个块两个局部量（只看块内，不看上下文）：

- `use[B]`：在块内**被读**，且读之前块内没有重新定义它的变量；
- `def[B]`：在块内**被写**的变量。

**方程**（backward + may）：

```
out[B] = ⋃ { in[S] : S 是 B 的后继 }
in[B]  = use[B] ∪ ( out[B] − def[B] )
```

`in[B]` 的读法：**"块内就要读的"** ∪ **"出去以后还要读、而块内没覆盖掉的"**。

### 4.2 在真实 IR 上手算

用 `while i < 3 loop { out_int(i); i <- i + 1; } pool` 经 `-O2` 后的骨架（我把 SSA 名字简化，保留结构）：

```llvm
entry:
  b = cool_alloc(16)          ; 一个 Bool 盒子
  br label %bb1

bb1:                          ; preds = entry, bb1   ← 有回边
  i   = phi [ 0, %entry ], [ i2, %bb1 ]
  vt  = load (self 的 vtable 槽)
  call vt(self, i)            ; out_int(i)
  i2  = add i, 1
  c   = icmp slt i2, 3
  br i1 c, label %bb1, label %bb2

bb2:
  ret null
```

局部量：

| 块 | `use` | `def` |
|---|---|---|
| `entry` | `self` | `b` |
| `bb1` | `self`, `i` | `i`, `vt`, `i2`, `c` |
| `bb2` | ∅ | ∅ |

迭代（初始全 ∅，后向：先算 `bb2`）：

| 轮次 | `in[bb2]` | `out[bb1]` | `in[bb1]` | `out[entry]` | `in[entry]` |
|---|---|---|---|---|---|
| 0 | ∅ | ∅ | ∅ | ∅ | ∅ |
| 1 | ∅ | ∅ | `{self, i}` | `{self, i}` | `{self}` |
| 2 | ∅ | `{self, i}` | `{self, i}` | `{self, i}` | `{self}` |
| 3 | ∅ | `{self, i}` | `{self, i}` | `{self, i}` | `{self}` |

第 3 轮与第 2 轮相同 → **不动点**。

**读出两条有用的结论**：

1. `b`（那个 Bool 盒子）**在任何地方都不活跃**——它被分配、被写，然后再也没人读。**这就是死代码的判据**，也解释了 `09` §7 那次"`-O2` 删不掉它"为什么让人意外：分析**知道**它是死的，但删不掉，因为删除需要额外的前提（`cool_alloc` 无副作用），而这个前提不在 IR 里（§7.2）。
2. `i` 在 `out[bb1]` 里活跃——因为回边把它送回了自己的入口。**活跃区间跨越了整个循环**，所以 `11` 篇给它分配寄存器时必须整个循环都占着。

**注意第 2 条依赖回边。** 如果只看"`bb1` 里 `i` 用完就被 `i2` 取代了"，会误以为 `i` 的区间很短。**回边是循环里活跃区间变长的唯一原因**，也是寄存器压力在循环里最大的原因（你调 CUDA kernel 时遇到的 register pressure 正是这件事）。

## 5. 四种经典分析：填满矩阵

| 分析 | 方向 | meet | 事实是什么 | 支撑哪种优化 |
|---|---|---|---|---|
| **活跃变量** Liveness | backward | ∪ (may) | 变量之后还会被读吗 | 寄存器分配、死代码消除 |
| **到达定值** Reaching Defs | forward | ∪ (may) | 哪些赋值可能到达这里 | 常量传播、依赖分析 |
| **可用表达式** Available Exprs | forward | ∩ (must) | 表达式一定已算过且未失效 | 公共子表达式消除 |
| **常量传播** Constant Prop | forward | ∩ (must)† | 变量在这里恒为某常量吗 | 常量折叠 |

† 常量传播的格不是集合而是每个变量一个值：`⊤`（还不知道）/ 具体常量 / `⊥`（不是常量）。meet 规则：`c ⊓ c = c`，`c₁ ⊓ c₂ = ⊥`（不同常量），`⊤ ⊓ x = x`。

**这个格就是 `06a` 那个 lub 格的近亲**：都是"把多路信息合并成一个保守的共同上界"。`06a` 里 `lub(Cons, Nil) = List` 损失了精度但保持了 soundness；这里 `1 ⊓ 2 = ⊥` 同理。**"合并时必须后退到共同点"是整个编译器里反复出现的同一个模式**——类型系统、数据流分析、以及 `12` 篇 GC 的三色标记，都是它。

**SSA 让常量传播变简单**（`07` §3 那条论证的兑现）：非 SSA 形式下要问"`x` 在这里是常量吗"必须先做到达定值分析，找出所有可能到达此处的赋值；SSA 下 `%t10` 只有**一个**定义，直接看那一条指令即可。**分析退化成查表**——这就是为什么 LLVM 要求 IR 是 SSA。

## 6. 从"分析"到"变换"：几个经典优化

分析给出事实，变换利用事实。常见的对应：

| 优化 | 依赖的分析 | 做什么 |
|---|---|---|
| 常量折叠 constant folding | 常量传播 | `mul 2, 3` → `6` |
| 死代码消除 DCE | 活跃变量 | 删掉结果永不被读的指令 |
| 公共子表达式消除 CSE | 可用表达式 | 第二次 `a+b` 复用第一次的结果 |
| 循环不变量外提 LICM | 到达定值 + 副作用分析 | 把循环里不变的计算挪到循环外 |
| `mem2reg` | 支配关系 | `alloca`+`load/store` → SSA 值 + φ（`07` §4） |

**LICM 是本篇最值得琢磨的一个**，因为它的安全条件最不显然：要把一条指令提到循环外，必须证明 (a) 它的操作数在循环中不变，(b) 它**没有副作用**，(c) 它在循环外执行是安全的（比如不会多做一次可能崩的访存）。**§7.3 会实测：我们的 vtable 加载明明满足 (a)，LLVM 却不敢提——因为它无法确定 (b)。**

## 7. 三个实验：分析的精度由前提决定

> 这一节是本篇的核心。三个实验都可复现，命令给全。它们共同说明一件事：**同一个 `-O2`，喂给它的前提不同，结果差很多。**

### 7.1 一个关键字决定了常量折叠能不能做

源程序 `out_int(1 + 2 * 3)`。我们的编译器把整数字面量生成为**不可变**全局：

```llvm
@int_2 = constant %Int { i8* bitcast (%class_meta_t* @class_Int to i8*), i32 2 }
```

跑 `opt -O2`，看 `Main.main`：

```llvm
%t11 = tail call ptr @cool_alloc(i32 16)
store ptr @class_Int, ptr %t11, align 8
%t14 = getelementptr i8, ptr %t11, i64 8
store i32 6, ptr %t14, align 4        ; ← 2*3 被折成 6
...
store i32 7, ptr %t22, align 4        ; ← 1+6 被折成 7
```

**`mul`/`add` 和那三个 `load` 全部消失，只剩两个 `store` 常量。** 优化器看穿了装箱：它知道 `@int_2` 的内容永远是 2，于是 `load` 变常量、算术被折叠。

**现在只改一个关键字**（`constant` → `global`，即"可变全局"），其余一字不动：

```bash
sed 's/^@int_\([0-9]*\) = constant/@int_\1 = global/' cf.ll > cf_glob.ll
opt -O2 cf_glob.ll -S -o -
```

结果：

```llvm
%t3  = load i32, ptr getelementptr inbounds nuw (i8, ptr @int_1, i64 8), align 8
%t6  = load i32, ptr getelementptr inbounds nuw (i8, ptr @int_2, i64 8), align 8
%t9  = load i32, ptr getelementptr inbounds nuw (i8, ptr @int_3, i64 8), align 8
%t10 = mul i32 %t9, %t6
%t18 = add i32 %t10, %t3
```

**三个 `load`、`mul`、`add` 全部回来了。** 一个字都没改逻辑，只是撤回了"这块内存不会变"这个承诺，`-O2` 就什么也做不了了。

**这就是 §1.2 那个命题的实验形式**：优化器不是"看出 `2*3=6`"，而是**需要一个前提**才敢改。`constant` 就是那个前提。

> 顺带一个设计结论：`09` §3.1 里 `intConst` 把字面量生成成 `constant` 全局，当初的理由只是"去重省空间"。实测说明它还有一个**更重要的收益**：让优化器能穿透装箱。**一个看似只关乎空间的决策，实际决定了优化能力的上限。**

### 7.2 逐个 pass 量一下，谁真正在干活

同一份 `cf.ll`，逐个 pass 跑，只看 `Main.main`：

| pass | 指令数 | `cool_alloc` | `alloca` |
|---|---|---|---|
| （未优化） | 38 | 2 | 1 |
| `mem2reg` | 35 | 2 | **0** |
| `sroa` | 35 | 2 | 0 |
| `instcombine` | **15** | 2 | 0 |
| `gvn` | 17 | 2 | 1 |
| `dce` | 38 | 2 | 1 |
| `adce` | 38 | 2 | 1 |
| `licm` | 38 | 2 | 1 |
| `-O2`（全部） | **15** | **2** | 0 |

复现：`opt -passes=instcombine cf.ll -S -o -`

**四个读数**：

1. **`instcombine` 一个 pass 就达到了 `-O2` 的指令数**（15）。它是 LLVM 里最"全能"的 peephole pass，常量折叠、冗余 `bitcast`、装箱穿透基本都在它手里。
2. **`mem2reg` 消掉了 `alloca`（1→0）但只省了 3 条指令**。它的价值不在减少指令，而在**把值提升成 SSA 名字，为后续 pass 创造条件**（`07` §4 讲的分层）。这是"基础设施型 pass"的典型特征：单看收益很小，撤掉它后面全做不了。
3. **`dce`/`adce`/`licm` 一条指令都没删。** 死代码明明有（§4.2 算出 `b` 不活跃），但删不掉——原因见下一条。
4. **所有版本的 `cool_alloc` 都是 2，一次都没少。**

**第 3、4 条是同一个原因**，而且正是 `09` §7.2 那个实验的答案：`cool_alloc` 在 IR 里只有一行 `declare i8* @cool_alloc(i32)`，优化器**必须假设它有任意副作用**（写全局、做 IO），因此"结果没人读"**不足以**推出"可以删"。DCE 的安全条件是"无副作用 **且** 结果不活跃"，我们只满足了后者。

加上分配器属性后就能删（`09` §7.2 实测 3→2）。**所以 `dce` 删不掉死代码不是 `dce` 弱，是前提不足。**

### 7.3 循环不变量提不出去，因为一次间接调用

这个实验最贴近你的研究方向。源程序：

```cool
let i : Int <- 0 in while i < 3 loop { out_int(i); i <- i + 1; } pool
```

`out_int` 是动态分派，所以循环体里有 `09` §4.1 那三次间接寻址。`self` 在整个循环里**从不改变**，类元信息和 vtable 都是 `constant`——按理说这三次加载完全是循环不变量，应该被提到循环外。

实测 `opt -O2`，`Main.main` 的循环体 `bb1`：

```llvm
bb1:
  %t34 = phi ptr [ ..., %entry ], [ %t39, %bb1 ]
  %t0.03 = phi ptr [ @int_0, %entry ], [ %t36, %bb1 ]
  %t20 = load ptr, ptr %self_arg, align 8     ; ← 还在循环里
  %t22 = getelementptr i8, ptr %t20, i64 8
  %t23 = load ptr, ptr %t22, align 8          ; ← 还在循环里
  %t24 = getelementptr i8, ptr %t23, i64 48
  %t25 = load ptr, ptr %t24, align 8          ; ← 还在循环里
  %t27 = tail call ptr %t25(ptr nonnull %self_arg, ptr nonnull %t0.03)
  ...
```

**三次加载每轮都重做。** 为什么 LICM 不敢提？因为循环体里有 `%t25(...)` 这次**间接调用**——被调函数是运行时取出的函数指针，LLVM 不知道它是谁、会写哪块内存。它必须假设这次调用**可能修改 `self` 的元信息字段或 vtable**，于是下一轮的加载必须重做。

**验证这个解释**：给那三条加载加上 `!invariant.load`（意思是"这个地址的内容一旦初始化就永不改变"），其余不动：

```bash
sed -E 's/^(%t(20|23|25) = load [^,]+, [^ ]+ [^ ]+)$/\1, !invariant.load !0/' dv.ll > dv_inv.ll
printf '!0 = !{}\n' >> dv_inv.ll
opt -O2 dv_inv.ll -S -o -
```

结果，三次加载**全部移到了 `entry`**：

```llvm
entry:
  ...
  %t20 = load ptr, ptr %self_arg, align 8, !invariant.load !0
  %t22 = getelementptr i8, ptr %t20, i64 8
  %t23 = load ptr, ptr %t22, align 8, !invariant.load !0
  %t24 = getelementptr i8, ptr %t23, i64 48
  %t25 = load ptr, ptr %t24, align 8, !invariant.load !0
  br label %bb1

bb1:
  %t27 = tail call ptr %t25(...)      ; 循环体里只剩调用本身
```

循环体内的 `load` 从 **3 条降到 0 条**，输出仍然正确（`012`）。

**这个标注在我们的设计里是诚实的**：对象的第 0 个字段在 `allocateAndInit` 里写一次就再也没人写（`09` §6.3 读过那段代码），类元信息和 vtable 都是 `constant` 全局。所以"一旦初始化永不改变"是真的。**（对比 `09` §8 第 3 题那个 `allockind` 标注——那个的诚实性是可疑的，因为它声称返回未初始化内存。同样是"给优化器加前提"，一个成立一个存疑，区别必须自己判断。）**

**这就是"去虚化"（devirtualization）的一半**。真实编译器做得更远：如果能证明 `self` 的动态类型唯一，可以把间接调用直接换成 `call @IO.out_int`，进而**内联**。C++ 编译器靠 `final`/LTO 做这件事，Java 的 JIT 靠运行时类型 profile 做（`13` §2）。**而我们用一条元数据就拿到了它最容易的那部分收益。**

## 8. 接到工业与你的方向

### 8.1 LLVM 的 pass 体系

`opt` 就是一个 pass 调度器。有用的命令：

```bash
opt -passes='mem2reg,instcombine,gvn,simplifycfg' x.ll -S -o -   # 自选流水线
opt -O2 x.ll -S -o -                                              # 标准流水线
opt -passes='print<loops>' x.ll -disable-output                   # 看循环结构
llc -regalloc=greedy x.ll -o x.s                                  # 进到 11 篇的话题
```

**pass 的顺序有讲究**：`mem2reg` 必须在大多数 pass 之前（它创造 SSA 值），`instcombine` 通常跑多次（前面 pass 的产物给它新机会）。`-O2` 的流水线有上百个 pass，顺序是多年调出来的。

### 8.2 同一个框架，换个图就是深度学习编译器

把"基本块"换成"算子"、"变量"换成"张量"，数据流分析的框架**原样成立**：

| CS143 概念 | 深度学习编译器里的对应 |
|---|---|
| 基本块 / CFG | 算子 / 计算图（dataflow graph） |
| 活跃变量 | 张量生存期 → **显存规划**（memory planning） |
| 公共子表达式消除 | 公共子图消除 |
| 常量传播 | 常量折叠（把 BN 的参数折进卷积核） |
| 循环不变量外提 | 把不随 batch 变的计算提到循环外 |
| 死代码消除 | 剪掉不影响输出的子图 |
| **无副作用前提**（§7.2） | **算子是否 pure**，决定能否重排/融合 |

最后一行值得停一下。**算子融合（operator fusion）能不能做，取决于能否证明中间张量没有别的消费者、算子没有副作用**——和 §7.2 里 `cool_alloc` 那个问题**完全同构**。你在 vLLM / CUDA 里手动做的 kernel 融合，在 TVM/XLA 里就是一个建立在这类分析之上的自动变换。

**而 §7.3 那个"加一条元数据换来一次 LICM"的经验，在 AI 编译器里的对应物是：给算子标注 pure / 给 buffer 标注 read-only / 给 shape 标注静态**——**标注得越准，编译器越敢优化**。这是你做巨核推理优化时会反复遇到的权衡：动态 shape 灵活但挡住优化，静态 shape 束手束脚但能融合。

## 12. 本文你掌握了什么 / 易错点 / 下一步

**掌握**：优化的两个组成部分（变换 + 证明）；基本块/CFG/回边；数据流框架的四个部件；may/must 的判据是"哪种误判安全"；不动点迭代为什么必须、为什么一定停（单调 + 有限高度）；静态分析必然保守近似及其原因；活跃变量分析的完整方程与在真实 IR 上的手算；四种经典分析的矩阵；SSA 为何让常量传播退化成查表；三个实测实验（`constant` 关键字、逐 pass 计量、`!invariant.load` 提升）；以及把整套框架迁移到算子图的对应关系。

**易错点**：

1. **活跃变量是后向分析**（`out` 由后继的 `in` 决定）。写成前向是最常见的错。
2. `in[B] = use[B] ∪ (out[B] − def[B])`——要减掉 `def`，不是照搬 `out`。
3. **may 用 ∪、must 用 ∩**；判据是"哪种误判是安全的"（§3.2），别靠记。
4. **初始值取决于分析**：liveness 初始 ∅，常量传播初始 ⊤。取错会得到错误的不动点。
5. **不动点 ≠ 真实答案**（§3.4）。分析走所有路径，包括不可能走的。
6. **DCE 的条件是"无副作用 **且** 结果不活跃"**，两个条件。只看第二个会误以为优化器很弱（§7.2）。
7. **`mem2reg` 的价值不是减指令**（只省 3 条），是把值提升成 SSA 名字给后面的 pass 创造条件。
8. **pass 顺序影响结果**，不是集合语义（§9 第 3 题）。

**下一步**：读 `11_寄存器分配.md`。本篇 §4.2 算出的活跃区间正是它的输入——那里要回答的问题是：一个函数的 IR 里可以定义 **187** 个虚拟寄存器（我实测了一个六参数的算术函数就有这么多），而 x86-64 只有 **16** 个通用寄存器、实际能自由分配的更少，**怎么映射**？以及映射不下时"溢出"到底有多贵——`llc -regalloc=fast` 和 `greedy` 的实测差距大得出乎意料。
