## 精炼段

到这里，一条完整的编译流水线真的立起来了：`lexer`（02）→ `parser`（03）→ `symtab`（05a）→ `typechecker`（05b/06）→ `codegen`（09），加上 `runtime.c`，一共 **2493 行 C++**，把 Cool 源码编译成 LLVM IR，链接后产生能跑的 `.exe`。

但"跑通了"是这十四篇里**最不重要**的结论。真正值得带走的是两样东西：

**第一是那 10 个实测发现的缺陷**（§3）。它们不是我读代码读出来的，全部是**跑起来、量出来、用调试器逼出来的**。而且其中有 4 个是被同一类原因藏起来的：12 个测试全过，但测试只覆盖了"我想到的情况"。**§3 那张总账是本套笔记最有价值的一页。**

**第二是概念的复用密度**（§5）。十四篇下来真正全新的概念不超过二十个，其余都是同一组想法在不同层级上重复出现——"活跃区间"一个概念就撑起了寄存器分配、垃圾回收、显存规划三件事；"保守近似"在类型系统、数据流分析、GC 里各出现一次；"单调 + 有界 ⟹ 收敛"证明了三个不同算法的终止性。**看出这种复用，比记住任何单个算法都更有用。**

本篇按此组织：§1-2 是验收（清单 + 实测结果），§3 是缺陷总账，§4 是自测题，§5 做概念收口，§6 给进阶路径。

## 1. 完整编译器：清单与规模

```

│   ├── token.h             59 行   Token 定义（02）

│   ├── ast.h              152 行   AST 节点 + Visitor（03c）
│   ├── parser.h/.cpp      424 行   递归下降 + 优先级爬升（03b/03c）
│   ├── symtab.h            35 行   作用域栈（05a）
│   ├── typechecker.h/.cpp 522 行   类环境 + 19 条类型规则（05b/06a/06b）
│   ├── codegen.h/.cpp     854 行   代码生成 → LLVM IR（09）
│   ├── dump.h/.cpp        139 行   AST 打印（调试用）
│   └── main.cpp            46 行   管线入口
├── runtime.c               71 行   IO / 字符串 / 内存（08/09）
├── tests/*.cl              12 个   测试程序
└── build.bat                      一键构建
                         ─────────
                          2493 行
```

**这个分布本身就说明了问题的难度分布**：

| 阶段 | 行数 | 占比 | 为什么是这个量 |
|---|---|---|---|
| 词法 | 191 | 8% | 正则/DFA 是**成熟理论**，照着做即可 |
| 语法 | 424 | 17% | 递归下降的结构由文法直接决定（`03b`） |
| 语义 | 522 | 21% | 19 条规则 + 继承图 + SELF_TYPE 的四个位置 |
| **代码生成** | **854** | **34%** | **最难，也是缺陷最集中的地方** |
| 运行时 | 71 | 3% | 我们刻意做薄（`08` §7） |

**代码生成占三分之一**，而 §3 那 10 个缺陷里有 6 个在这里。原因 `09` §1 讲清了：它要跨越**树 → 序列**这个表示错配，而前面几个阶段都是"结构到结构"的转换。**"哪里的表示落差最大，哪里的 bug 最多"是一条很实用的经验。**

## 2. 验收：实测结果

### 2.1 构建

```bash
export PATH="/c/msys64/ucrt64/bin:$PATH"   # 见下面的注意事项
g++ -std=c++17 -Wall -Wextra -O2 -g -o coolc.exe src/*.cpp
```

**`-Wall -Wextra` 零警告通过。**

> **一个会反复咬你的环境坑**（我已经记进长期记忆了）：在 Git Bash 里如果不先 `export PATH`，`g++` 会**静默失败**——退出码 1、**stderr 完全为空**，连 `int main(){}` 都编不过。根因是 Git 自带的 `/mingw64/bin` 里的 DLL 遮蔽了 msys64 的。用 `ldd $(g++ -print-prog-name=cc1plus)` 能看到错误的 DLL 路径。**"没有任何报错的失败"几乎总是环境问题，不是代码问题。**

### 2.2 十二个测试全部通过

每个测试走完整链路：`coolc` → `llvm-as` 校验 IR → `clang` 链接 `runtime.c` → 运行。

| 测试 | 覆盖特性 | IR 校验 | 输出 |
|---|---|---|---|
| `hello.cl` | 字符串 + IO | ok | `Hello, compiler!` |
| `factorial.cl` | 算术 + if + 递归 + 动态分派 | ok | `120` |
| `list.cl` | 继承 + 重写 + SELF_TYPE | ok | `5` |
| `while_test.cl` | while 循环 | ok | `10` |
| `case_test.cl` | case 运行时类型分派 | ok | `Int`/`String`/`Bool`/`Bool`/`other` |
| `static_dispatch.cl` | 静态分派 `e@T.f()` | ok | `B`/`A`/`B` |
| `string_test.cl` | length/concat/substr | ok | `5`/`Hello World`/`ell` |
| `bool_test.cl` | 比较/not/isvoid/type_name | ok | `Bool`×4 + `yes`/`notfalse`/`strlt`/`le` |
| `inherit_test.cl` | 深层继承 + copy + type_name | ok | `dog!`/`dog`/`Dog`/`Dog` |
| `io_test.cl` | in_string/in_int（两种顺序） | ok | `name? donk`/`num? 42`/`num? 7`/`name? cool` |
| `lexer_test.cl` | 词法边界 | ok | （token 流） |
| `type_error.cl` | **负向测试** | — | `ERROR: line 3: arithmetic operands must be Int, got Int and String`，**退出码 1** |

**全部退出码 0（负向测试按设计返回 1），输出与 `README.md` 记录一致。**

**负向测试值得单独说一句**：它检验的是"**错误程序必须被拒绝**"。一个只测正确程序的编译器是没有验收过的——类型检查器的价值全在它拒绝了什么。注意它的退出码是 **1**：这让它能被 CI 和脚本检测。**`06b` §7 讲的错误恢复就是为这条服务的。**

### 2.3 同一份 IR 的两种执行方式

`13` §1.1 实测过：我们生成的 IR 既能 AOT 也能 JIT。

```bash
clang factorial.ll runtime.c -o factorial.exe && ./factorial.exe   # AOT → 120
llvm-link factorial.ll rt.ll -S -o f2.ll && lli f2.ll              # JIT → 120
```

**同一份 `.ll`，两条完全不同的后端路径，输出一致。** 这是 `07` §1 那个"IR 是稳定接口"论证最直接的验收——**我们只写了前端，却免费得到了 AOT 和 JIT 两种执行方式、以及所有 LLVM 支持的目标架构。**

### 3.1 一条反复出现的规律

**缺陷 5 和 9 是同一类**：12 个测试全过，但缺陷真实存在。

- 缺陷 5：没有一个测试在属性初始化式里用 `self`；
- 缺陷 9：没有一个测试的循环超过 10 轮。

> **测试覆盖的是实现者想到的情况，而不是规范允许的情况。**

这条在本套笔记里出现了**五次**（`06b` §8、`08` §8、`09` §6.2、`12` §7.3，加上这里的汇总）。它的可操作版本是：**别问"我的测试过了吗"，问"规范允许什么我没测"**。Cool 手册允许属性初始化式引用 `self`，允许循环跑一亿轮——**合法即必须支持**。

### 3.2 怎么发现的：四种手段的分工

把"怎么发现的"那一列归类，得到一张很实用的对应表：

| 失败的样子 | 该用什么 | 例子 |
|---|---|---|
| IR 不合法 | `llvm-as` 校验 | 缺陷 1、3 |
| 输出不对 | 端到端跑 + 对照期望 | 缺陷 2 |
| 崩溃 | **先看它死得多快**，再决定用 gdb 还是 timeout | 缺陷 6、9 |
| 静默错误（不崩、输出看似合理） | **构造规范允许但测试没覆盖的用例** | 缺陷 5 |
| 性能/资源问题 | **插桩计数 + 量化** | 缺陷 9、10 |

**第三行是我实测踩过的教训**（`06b` §8.3）：缺陷 6 我最初标成"挂死"，用了 `timeout` 去抓。但它 **62 ms 就死了**——那不是挂死，是崩溃，该用调试器。**先量它死得多快，再决定该怀疑什么。**

**第五行是缺陷 9 的发现路径，最值得学**。我不是去审计 codegen 才发现它的，而是在量 GC 效果时看到"根扫描直接标记了 403 个对象"这个**解释不通的数字**，追下去才撞上的。

> **一个你解释不了的测量值，比一次代码走查更容易把 bug 逼出来。** 而如果我当时只跑了 `-O2`（那组漂亮的 99.9% 垃圾率），这个缺陷会被完整地藏过去——因为 `mem2reg` 把症状消掉了。

## 5. 概念收口：十四篇里真正新的东西不多

在看答案之前，先看这个——**它比任何单道题都重要**。

### 5.1 三个贯穿全套的模式

**① 保守近似：合并时必须后退到共同点**

| 出现位置 | 形式 | 损失了什么 |
|---|---|---|
| `06a` 类型系统 | `lub(Cons, Nil) = List` | 精度，换来 soundness |
| `10` §3.1 数据流分析 | meet 操作（∪ 或 ∩） | 精度，换来 sound 的分析 |
| `10` §3.4 路径不敏感 | 合并不可达路径 | 精度，换来可判定 |
| `12` §2.1 GC 可达性 | "可达"近似"还会用到" | 多留垃圾，换来可判定 |

**四处的方向完全一致**：宁可多算（假阳性），绝不少算。而**判据统一是"哪种误判是安全的"**（`10` §3.2），不是直觉。

**② 单调 + 有界 ⟹ 收敛**

| 出现位置 | 单调变化的量 | 上界 |
|---|---|---|
| `05b` §3 `conforms` **死循环** | **没有** | — |
| `10` §3.3 数据流迭代 | 事实集合只增/只减 | 变量个数有限 |
| `12` §2.2 GC 标记 | 已标记集合只增 | 堆对象数有限 |

**`05b` 那个死循环是最有价值的一行**，因为它是**反例**：继承图有环、又没有单调递减的量，于是 `for(;;)` 真的转圈。**"有环 ≠ 不终止，关键是有没有一个单调变化且有界的量"**——这个判据你以后看任何迭代算法都用得上。

**③ 难问题 + 有结构的实例 ⟹ 启发式够用**

| 出现位置 | 理论难度 | 为什么启发式够用 |
|---|---|---|
| `11` §3.2 寄存器分配 | 图着色 NP 完全 | 真实干涉图稀疏 |
| `13` §7 自动调优 | 搜索空间上亿 | 性能是参数的连续函数，可用 cost model 引导 |

### 5.2 一个概念，四个名字

这是全套最漂亮的一处汇合。**"某个值从定义到最后一次使用的区间"**这一个概念：

| 篇 | 叫什么 | 要解决什么 | 结论 |
|---|---|---|---|
| `10` §4 | 活跃变量分析 | 为下游提供事实 | 后向 + may 的数据流方程 |
| `11` | 寄存器分配 | 哪些值能共用一个寄存器 | 干涉图着色 |
| `12` | 垃圾回收 | 哪些堆对象能回收 | 可达性（运行时版的活跃性） |
| `13` §8 | 静态显存规划 | 哪些张量能复用缓冲区 | 编译期算完，运行时零开销 |

**同一个概念，在寄存器上是 NP 完全问题、在堆上要运行时追踪、在张量上却能编译期算完。** 差别只在一件事：**生命周期是否编译期已知**。张量已知（`13` §8），Cool 对象不已知（所以需要 GC），寄存器介于两者之间。**这一行把 `10`/`11`/`12`/`13` 四篇串成了一条。**

### 5.3 一条命题贯穿后半程

> **优化 = 变换 + 证明变换安全；而证明能做到多强，取决于你提供了多少前提。**（`10` §1.2）

它在后五篇里被兑现了**六次**，每次都有实测：

| 加了什么前提 | 换来什么 | 出处 |
|---|---|---|
| `constant`（而非 `global`） | 常量折叠全部可做 | `10` §7.1 |
| 分配器属性 | DCE 敢删掉死分配（3→2） | `09` §7.2 |
| `!invariant.load` | LICM 把 3 条 load 提出循环（→0） | `10` §7.3 |
| `final` / 真实类型 | 去虚化 → 内联 → 整个循环塌缩成一条 `cmovgl` | `13` §2 |
| 栈映射表 | 才能用复制式 GC（我们没有，所以不能） | `12` §3.2 |
| 图级 IR（保留算子语义） | 融合变成平凡的改写（实测值 3.47 倍） | `13` §5 |

**最后一行是整个编译栈尺度的版本**：信息在下降过程中丢失，而优化需要信息，所以要在信息还在的那一层动手。**这就是 MLIR 多层 IR 和深度学习编译器存在的全部理由。**

## 6. 自测答案

**题 1**：左递归 `E → E + T` 让"分析 E"递归地要求"先分析 E"，无限递归。优先级爬升的解法是**每个优先级一层函数**，层内**左结合用循环、右结合用递归**，把优先级编码进调用链：`parseAddSub` 调 `parseMulDiv`，于是 `1 + 2 * 3` 里 `2 * 3` 先被更紧的层吃掉。**关键是"循环"替代了左递归**——`while (peek is +) { rhs = parseMulDiv(); ... }`。（`03b`）

**题 2**：`c : Bool`（[If] 要求）；`new Cons : Cons`、`new Nil : Nil`（[New]）；整个表达式类型 = `lub(Cons, Nil)` = 两者在继承图上的**最近公共祖先** = `List`。**注意 lub 是必须的**：if 的静态类型必须同时是两个分支的超类型，否则 soundness 不成立（`06a`）。

**题 3**：**三次**间接访问：① 从对象第 0 个字读类元信息指针 → ② 从类元信息读 vtable 指针 → ③ 从 vtable 的第 k 槽读函数指针。比直接调用多两次寻址。**妨碍内联的原因**是编译期不知道会调到哪个实现，所以无法把被调函数体展开——而**内联是很多其他优化的前置条件**，所以代价远大于那两次寻址（`13` §2 实测：能去虚化时整个循环都消失了）。（`08` §4）

**题 4**：SELF_TYPE 解决"继承时返回类型被写死"的问题。`copy() : SELF_TYPE` 在 `Object` 里返回 `Object`、在 `Dog` 里返回 `Dog`，所以 `(new Dog).copy()` 的静态类型是 `Dog` 而非 `Object`，能直接接着调 `Dog` 的方法。规则：方法返回 SELF_TYPE 时，调用结果的静态类型 = **接收者的静态类型**（`06a`）。

**题 5**：三个——`10` §3.3 数据流不动点迭代、`12` §2.2 GC 标记阶段、以及 `11` §4.2 图着色的 simplify/溢出迭代。**反例是 `05b` §3 的 `conforms`**：继承图有环，但它**没有任何单调变化且有界的量**，所以 `for(;;)` 真的死循环。**缺的条件是"单调 + 有界"这一对**，不是"无环"。

**题 6**：三层，**但只有两层成立**。成立的：内存浪费（`08` §6，16 字节装 4 字节）、堆分配（`09` §7，`-O2` 删不掉）。**不成立的是"抬高寄存器压力"**——`11` §6.3 实测 `greedy` 分配器在 187 个虚拟寄存器上做到**零溢出**，因为那些装箱临时值**活得极短**、彼此几乎不干涉。教训：**"名字多"不等于"压力大"，压力只取决于同时活跃的数量；代价要量，不要推。**

**题 7**：见 §5.2 那张表。核心差别是**生命周期是否编译期已知**：张量已知 ⟹ 静态规划、运行时零开销；Cool 对象不已知 ⟹ 需要运行时追踪（GC）；虚拟寄存器在函数内已知 ⟹ 编译期分配。

**题 8**：因为**在 LLVM IR 这一层，"这是两个算子"的信息已经丢了**，只剩循环和访存，融合需要重新证明边界相同、无依赖冲突、不别名、副作用可交换（`10` §6 那整套条件），证得出来的情形太少——实测连"两个独立、定长、`__restrict`"的循环都不融，而且这个 pass **`-O2`/`-O3` 都没启用**。而在图级 IR 上，生产者-消费者关系是**显式的**，融合就是把几个节点标成一个 kernel，**不需要证明**。（`13` §5）

## 7. 下一步：四条路径

按对你方向（AI Infra / 推理优化）的直接价值排序：

**① 先修掉缺陷 9（`12` §10.3）。** 这是投入产出比最高的一件事：改动集中（三处 `alloca` 统一提到 `entry`），修法我已经验证过（手工改 IR 后 `-O0` 跑 50 万轮通过），而且它让你完整走一遍"发现 → 定位 → 修复 → 回归"的流程。**注意那个坑**：`alloca` 可以提前，但 `store` 初始值不能跟着提前（`let` 的初始化式每轮都要重新求值）。

**② 把 `13` §5 和 §7 的实验搬到 H100 上重做。** 你有单卡 H100，这是你相对师姐的独特价值（真实硬件 profiling）。量融合前后的 DRAM 流量比和实测加速比，看两者在 GPU 上是否还像 CPU 上那样吻合——**GPU 的带宽/算力比例不同，结论可能不一样，而这个"不一样"本身就是能写进报告的发现。**
