## 精炼段

语法分析要解决的核心困难是**嵌套**：`((1+2)*3)` 的括号可以嵌任意深，而 DFA 只有有限个状态，**根本数不过来**（§1 会给你一个三行的证明）。上下文无关文法（CFG）用"产生式可以递归引用自己"补上了这个能力，代价是引入了两个新麻烦：**二义性**（同一个串有多棵树，`1+2*3` 就是）和**左递归**（`expr → expr + expr` 会让自顶向下分析原地死循环）。本篇把这两个麻烦彻底解剖。最关键的一节是 §4.5——教科书讲完"消除左递归"就收工了，但消完之后**结合性是错的**（`1-2-3` 会算成 `1-(2-3)`），正是这个被普遍省略的裂缝，解释了为什么 `coolc/src/parser.cpp` 里写的是 `while` 循环而不是教科书上的 `E'`。

## 1. 正则不够用：一个你可以自己动手的证明

### 1.1 先明确战场

02 篇里 lexer 干得很漂亮：正则 → NFA → DFA，线性时间扫完源码。那为什么不干脆用正则把整个程序语言描述完？

**因为要数括号。** 看这个 Cool 表达式：

```cool
((((1))))
```

合法。而：

```cool
((((1)))
```

非法——少一个右括号。**判断合法性 = 判断左右括号是否配平**。

把问题抽象成最小形式：语言 `L = { (ⁿ)ⁿ | n ≥ 0 }`（n 个左括号后跟 n 个右括号）。**这个语言不是正则的。**

### 1.2 三行证明（鸽笼原理）

> 这个证明值得你亲手在纸上重写一遍。它是"为什么编译器必须分两层"的全部理由。

**反证**：假设存在一个 DFA `M` 识别 `L`，`M` 有 `k` 个状态。

考虑 `k+1` 个输入前缀：

```
ε, (, ((, (((, ..., (ᵏ      ← 共 k+1 个
```

它们分别把 `M` 带到某个状态。**k+1 个前缀，只有 k 个状态** → 由鸽笼原理，必有两个不同的前缀 `(ⁱ` 和 `(ʲ`（`0 ≤ i < j ≤ k`）落到**同一个状态** `q`。

现在从 `q` 出发读入 `)ⁱ`：

- 因为 `(ⁱ)ⁱ ∈ L`，DFA 必须**接受** → 从 `q` 读 `)ⁱ` 到达接受态；
- 但 `(ʲ` 也在 `q`，所以 `(ʲ)ⁱ` 也会被**接受**；
- 而 `i ≠ j`，所以 `(ʲ)ⁱ ∉ L`。

矛盾。∎

### 1.3 这个证明真正告诉你的事

失败的根源不是"正则语法不够花哨"，而是 **DFA 的记忆是有限的**。要数清嵌套深度，你需要一个**能无限增长的计数器**。

```
需要数嵌套深度
   ↓
需要无界记忆
   ↓
需要一个栈  ← 后进先出，正好匹配"最近打开的括号最先关闭"
   ↓
栈 = 递归调用栈（自顶向下）或显式栈（自底向上）
```

**这是整条语法分析技术线的源头**：

| 方案 | 栈从哪来 | 对应技术 |
|---|---|---|
| 用函数调用栈 | 编译器自己的运行栈 | 递归下降（`03b`、`03c`） |
| 用显式数组当栈 | 手动维护 | LR / 移进-归约（`04`） |

> **和 02 篇的对照**：lexer 识别 `INT_CONST` 只需要"当前是不是数字"，是**有限**信息，DFA 够用。parser 识别 `expr` 需要"我现在在第几层括号里"，是**无界**信息，必须有栈。**有限 vs 无界，这是词法与语法的真正分界线**，不是"词 vs 句"这种比喻。

## 2. CFG：给"递归"一个记法

### 2.1 四元组定义

一个上下文无关文法 `G = (N, T, P, S)`：

| 记号 | 名字 | 是什么 | Cool 例子 |
|---|---|---|---|
| `N` | 非终结符（nonterminal） | **语法变量**，代表"一类结构" | `program`、`class`、`feature`、`expr` |
| `T` | 终结符（terminal） | **token**，lexer 的输出，不可再分 | `CLASS`、`ID`、`INT_CONST`、`+`、`(` |
| `P` | 产生式（production） | 形如 `A → α` 的重写规则 | `expr → expr + expr` |
| `S` | 开始符号（start symbol） | 从哪儿开始展开 | `program` |

**"上下文无关"是什么意思？** 左部只能是**单个**非终结符 `A`，不能是 `xAy → xαy`（那叫上下文相关）。含义：**`A` 能展开成什么，与它周围是什么无关**。

这条限制是把双刃剑：

- 好处：可以写出高效的分析算法（正是本篇和 `04` 的全部内容）；
- 代价：**很多语言规则表达不了**。比如"变量必须先声明后使用"、"实参个数必须等于形参个数"、"`x + y` 里 `x` 必须是 `Int`"——这些都**不是** CFG 能管的事，所以它们被推给了语义分析（`05`）和类型检查（`06`）。

> **这就解释了编译器为什么一定有"语义分析"这个阶段**：不是因为设计者想分那么多层，而是因为 CFG 的表达力就停在这里。上下文相关的部分只能另开一个阶段处理。

### 2.2 对上 Cool 的真实文法

`01` 篇 §4 的 BNF，翻译成标准 CFG 记法（取核心部分）：

```
program  → class ';' program  |  class ';'
class    → CLASS TYPEID '{' features '}'
         |  CLASS TYPEID INHERITS TYPEID '{' features '}'
features → feature ';' features  |  ε
feature  → ID '(' formals ')' ':' TYPEID '{' expr '}'     -- 方法
         |  ID ':' TYPEID                                  -- 属性（无初值）
         |  ID ':' TYPEID '<-' expr                        -- 属性（有初值）
expr     → ID '<-' expr
         |  expr '.' ID '(' args ')'
         |  expr '@' TYPEID '.' ID '(' args ')'
         |  ID '(' args ')'
         |  IF expr THEN expr ELSE expr FI
         |  WHILE expr LOOP expr POOL
         |  '{' block '}'
         |  LET ... IN expr
         |  CASE expr OF branches ESAC
         |  NEW TYPEID
         |  ISVOID expr
         |  expr '+' expr  |  expr '-' expr
         |  expr '*' expr  |  expr '/' expr
         |  '~' expr
         |  expr '<' expr  |  expr '<=' expr  |  expr '=' expr
         |  NOT expr
         |  '(' expr ')'
         |  ID  |  INT_CONST  |  STR_CONST  |  TRUE  |  FALSE
```

**先记住三个观察，后面每一节都会用到**：

1. **`expr` 是递归的**：`expr → '(' expr ')'`、`expr → expr '+' expr`。这正是 §1 说的"无界嵌套"能力所在。
2. **有 8 条产生式以 `expr` 开头**（`.`、`@`、`+`、`-`、`*`、`/`、`<`、`<=`、`=`）——**全是左递归**。这是 §4 的正主。
3. **有 3 条产生式以 `ID` 开头**（`ID <- expr`、`ID ( args )`、`ID`）。看到第一个 token 是 `ID` 时，你**不知道该选哪条**。这是 `03b` 的正主（也是 `parser.h` 里为什么有 `nxt_` 这个成员）。

### 2.3 推导：文法如何"生成"一个程序

**推导（derivation）** = 从 `S` 出发，每步挑一个非终结符，用某条产生式替换它，直到全是终结符。

用 `⇒` 表示一步，`⇒*` 表示多步。以 `1 + 2` 为例（只用 `expr`）：

```
expr
⇒  expr '+' expr        （用 expr → expr + expr）
⇒  INT_CONST '+' expr   （左边 expr → INT_CONST）
⇒  INT_CONST '+' INT_CONST
```

中间那些"还有非终结符的串"（如 `expr '+' expr`）叫**句型**（sentential form）；全终结符的叫**句子**（sentence）。

**文法生成的语言**：`L(G) = { w | S ⇒* w，w 全是终结符 }`。

> **换个角度看**：文法是**生成器**（从 S 长出所有合法程序），parser 是**反向工程**——给你一个串，倒推出"它是怎么被生成的"。这个视角很重要：**分析就是重建推导过程**。

### 2.4 最左推导 vs 最右推导：为什么这个区分不是吹毛求疵

每步有两个自由度：① 挑哪个非终结符 ② 用哪条产生式。把 ① 固定下来，就得到两种规范推导：

- **最左推导（leftmost）**：每步总是替换**最左边**的非终结符。
- **最右推导（rightmost）**：每步总是替换**最右边**的非终结符。

对 `1 + 2 * 3`，最左推导：

```
expr
⇒  expr '+' expr            ← 替换唯一的 expr
⇒  1 '+' expr               ← 替换最左的 expr
⇒  1 '+' expr '*' expr      ← 替换剩下的 expr
⇒  1 '+' 2 '*' expr
⇒  1 '+' 2 '*' 3
```

**为什么要关心这个区分？因为它就是两大类算法的分水岭：**

| | 最左推导 | 最右推导（的逆） |
|---|---|---|
| 方向 | 自顶向下：从 `S` 往下猜 | 自底向上：从 token 往上归约 |
| 与输入的关系 | 按**从左到右**的顺序产出终结符，正好对齐 lexer 的输出顺序 | 逆序进行，需要显式栈 |
| 算法 | LL(1)、递归下降（`03b`/`03c`） | LR、SLR、LALR（`04`） |
| 名字来源 | LL = **L**eft-to-right 扫描 + **L**eftmost 推导 | LR = **L**eft-to-right 扫描 + **R**ightmost 推导（的逆） |

**"LL"和"LR"两个字母的第二位就是这件事**——教科书一般不解释，所以很多人背了半天不知道 L 和 R 指什么。

`03b` 要写的递归下降 parser，**每一次函数调用就是最左推导的一步**。这个对应关系是下一篇的主线。

### 2.5 语法树 = 推导的"去顺序化"

同一棵树可以对应**多个**推导（因为"先展开左边还是先展开右边"不影响最终结构）。

`1 + 2` 的树：

```
      expr
    /  |   \
 expr  +   expr
  |          |
  1          2
```

这棵树可以由至少两个推导得到：

```
推导①：expr ⇒ expr+expr ⇒ 1+expr ⇒ 1+2     （先展开左）
推导②：expr ⇒ expr+expr ⇒ expr+2 ⇒ 1+2     （先展开右）
```

**树扔掉了"我先展开哪个"这个无关顺序，只保留了结构。** 所以：

> **语法树 = 推导的等价类**（把只差展开顺序的推导视为同一棵树）。
>
> 推论：**最左推导与语法树一一对应**（固定了顺序，就唯一了）。这条推论是下一节判定二义性的工具。

## 3. 二义性：文法的病

### 3.1 定义与判定

**二义（ambiguous）**：存在某个串 `w ∈ L(G)`，它有**两棵以上**不同的语法树。

由 §2.5 的推论，等价的判定法（更好用）：

> **存在某个串有两个不同的最左推导 ⟺ 文法二义。**

为什么二义是"病"？因为**树决定语义**。`1+2*3` 的两棵树算出 7 和 9，编译器必须知道选哪个。二义 = 编译器不知道该生成什么代码。

**这不是 Cool 手册的疏漏，而是一个刻意的分工**：BNF 只负责说"有哪些结构"，优先级和结合性由手册 §5 那张**单独的优先级表**补充。两份文件合起来才定义了唯一的树。

> **工业界同款做法**：C、C++、Java、Python 的标准文档全都是"二义 BNF + 单独的优先级表"。原因很实际——把优先级编进 BNF 会让文法膨胀好几倍（你马上会在 `03b` §3 看到 Cool 的 8 层优先级如何把 1 条 `expr` 规则炸成 8 条），可读性极差。**人读二义版 + 优先级表，机器用展开版。**

### 3.3 悬空 else：Cool 从语法设计上消灭了它

经典二义案例，C/Java 都有：

```c
if (a) if (b) x(); else y();      // else 归谁？
```

两种解读：`if(a){ if(b) x(); else y(); }` 或 `if(a){ if(b) x(); } else y();`。C 标准强行规定"else 配最近的 if"来打补丁。

**Cool 里这个问题不存在。** 看 Cool 的 if：

```
expr → IF expr THEN expr ELSE expr FI
```

有 `FI` 收尾，而且 `ELSE` 是**必需**的。所以：

```cool
if a then if b then x() else y() fi fi    -- 内层 if 配内层 fi
if a then if b then x() fi else y() fi    -- 一眼就能看出 else 归外层
```

**`fi` / `pool` / `esac` 这些"反着拼的结束符"不是为了复古好玩，是消除二义的语法设计。** 每个复合结构都有显式闭合标记 → 结构边界无歧义 → 文法在这方面天生无歧义。

> **同类设计**：Ruby 的 `if...end`、Algol 68 的 `if...fi`（Cool 的直接来源）、Verilog 的 `begin...end`。反面例子是 Python 用缩进——省了关键字，代价是 lexer 必须产出 `INDENT`/`DEDENT` 这种"虚拟 token"（02 篇没做这件事，因为 Cool 不需要）。
>
> **值得记住的一般原则**：**语言设计的选择会直接改变 parser 的难度**。设计者多写一个 `fi`，编译器作者就少写一个补丁。你以后设计 DSL 或 IR 文本格式时（比如 `13` 篇的 MLIR），这条经验会直接派上用场。

### 3.4 消除二义的三种手段

| 手段 | 做法 | Cool 用在哪 |
|---|---|---|
| ① 改写文法，把优先级分层编进去 | 每个优先级一个非终结符 | **本套笔记的做法**（`03b` §3 会亲手推导） |
| ② 文法保持二义，外挂优先级声明 | `%left` / `%right` / `%nonassoc` | bison 的做法（`04` §7） |
| ③ 语言设计上避免 | 加显式闭合符 | `fi` / `pool` / `esac`（§3.3） |

手段 ① 和 ② 产生**完全相同的树**，只是"谁来做展开"不同：① 你手工展开，② bison 自动展开。理解了 ①，②就是一层语法糖。

## 4. 左递归：递归下降的死刑判决

这是本篇的核心。原始的 03 笔记在这里只给了改写公式，没讲清任何一个"为什么"，所以这节我拆成六小步。

### 4.1 先看它怎么死

假设我们天真地照着文法写代码。文法：

```
expr → expr '+' expr  |  INT_CONST
```

天真的实现（**这段代码是错的，别抄**）：

```cpp
// ✗ 反面教材
std::unique_ptr<Expr> parseExpr() {
  // 第一条产生式：expr → expr '+' expr
  auto lhs = parseExpr();          // ← 为了分析 expr，先分析 expr……
  expect(Tok::PLUS, "'+'");
  auto rhs = parseExpr();
  return makeBinary(lhs, rhs);
}
```

**手工跑栈**，输入 `1 + 2`，`cur_ = INT(1)`：

| 调用深度 | 函数 | cur_ | 干了什么 |
|---|---|---|---|
| 1 | parseExpr | INT(1) | 第一行：调 parseExpr |
| 2 | parseExpr | INT(1) | 第一行：调 parseExpr |
| 3 | parseExpr | INT(1) | 第一行：调 parseExpr |
| … | … | INT(1) | … |
| ∞ | — | INT(1) | **栈溢出** |

**注意 `cur_` 那一列：从头到尾没动过。** 这是关键线索。

### 4.2 根因：递归下降有一条隐含契约

递归下降为什么一般能终止？因为它依赖这条不变量：

> **契约**：每次递归调用之前，必须已经**消耗掉至少一个 token**。

有了这条契约，"剩余 token 数"就是一个严格递减的非负整数 → 递归深度有上界 → 必然终止。这是标准的**良基递归**（well-founded recursion）论证。

**左递归恰好违反它**：`expr → expr '+' expr` 里，`expr` 出现在产生式**最左端**，它前面没有任何终结符可消耗。于是递归前 `cur_` 一动不动，契约破裂，"剩余 token 数"不再下降。

```
左递归  ≡  递归前无 token 可消耗  ≡  递归无法收敛  ≡  死循环
```

**推广（重要，比"避免左递归"这条口诀有用得多）**：

> 只要一条产生式的右部**以自己开头**（直接左递归 `A → Aα`），或者**能经过若干步推导后以自己开头**（间接左递归，如 `A → Bα`，`B → Aβ`），自顶向下分析就会死。
>
> 反过来，只要每条产生式在递归之前**至少吃掉一个终结符**，递归下降就安全。这是你写任何手写 parser 时的**自检准则**。

顺手验证一下真实代码遵守了这条准则。`coolc/src/parser.cpp` 的 `parseIf`：

```cpp
std::unique_ptr<Expr> Parser::parseIf() {
  Token t = cur_; advance();   // ← 先吃掉 IF，然后才递归
  auto n = std::make_unique<If>(); n->line = t.line;
  n->cond = parseExpr();       // 安全：已经消耗了 IF
  ...
```

`parsePrimary` 的 `LPAREN` 分支同理：先 `advance()` 吃掉 `(`，再 `parseExpr()`。**每个递归点前面都有一次 `advance()`，契约成立。** 这不是巧合，是设计出来的。

### 4.3 消除左递归：不是背公式，是解一个方程

现在来做正事。看这条产生式（`T` 代表更紧的一层，暂时当成原子）：

```
E → E '+' T  |  T
```

**第一步：问它到底生成什么语言。** 反复展开：

```
E ⇒ T
E ⇒ E+T ⇒ T+T
E ⇒ E+T ⇒ E+T+T ⇒ T+T+T
...
```

规律清楚了：

```
L(E) = { T,  T+T,  T+T+T,  T+T+T+T,  ... }
     = T (+T)*        ← 一个 T，后面跟零或多个 "+T"
```

**这一步是全节的枢纽。** 左递归产生式的语言，本质是一个**闭包（重复）**结构。

**第二步：用方程验证，不靠眼力。** 把产生式当集合方程（`·` 是连接，`∪` 是并）：

```
L(E) = L(E) · L(+T)  ∪  L(T)
```

记 `X = L(E)`、`α = L(+T)`、`β = L(T)`：

```
X = Xα ∪ β
```

这是形式语言里的标准方程，**最小解是 `X = βα*`**。验证它确实是解（代回右边）：

```
βα*·α ∪ β  =  β(α*α ∪ ε)  =  β(α⁺ ∪ ε)  =  βα*   ✓
```

所以 `L(E) = L(T)·L(+T)* = T(+T)*`，和第一步观察一致。

> 这条方程叫 **Arden 规则**，和 02 篇正则的 Kleene 闭包是同一套代数。**左递归消除不是语法技巧，是在解形式语言方程**——这就是为什么公式长那个样，而不是别的样。

**第三步：把 `T(+T)*` 写回 CFG。** CFG 没有 `*` 这个记号，只能用递归模拟"重复"。既然左递归不行，就用**右**递归：

```
E  → T E'
E' → '+' T E'  |  ε
```

**现在可以回答 §0 的问题 5 了：`E'` 是什么？**

> **`E'` 就是"剩下那串 `+T` 的重复"**，即 `L(E') = (+T)*`。它不是什么神秘符号，是**为了在没有 `*` 的记号系统里表达 `*`，而被迫引进的辅助非终结符**。
>
> 它有个关键性质：`E' → '+' T E'` 递归前**先吃掉 `+`** → 契约成立 → 不会死循环。这就是改写的全部目的。

**第四步：一般公式（现在它是推出来的，不是记住的）**

```
A → A α  |  β          （左递归）
─────────────────────
A  → β A'
A' → α A'  |  ε        （右递归）
```

两边都生成 `βα*`。多条规则的情形照搬：

```
A → A α₁ | A α₂ | β₁ | β₂
─────────────────────────
A  → β₁ A' | β₂ A'
A' → α₁ A' | α₂ A' | ε
```

### 4.4 拿 Cool 真实产生式练一次

Cool 的加减（从 §2.2 的 8 条左递归里取 2 条，`T` = 更紧的一层）：

```
E → E '+' T | E '-' T | T
```

对照公式：`α₁ = '+' T`，`α₂ = '-' T`，`β = T`：

```
E  → T E'
E' → '+' T E' | '-' T E' | ε
```

**自查**：`1 + 2 - 3` 能被生成吗？

```
E  ⇒ T E'              (T=1)
   ⇒ 1 E'
   ⇒ 1 '+' T E'        (T=2)
   ⇒ 1 + 2 E'
   ⇒ 1 + 2 '-' T E'    (T=3)
   ⇒ 1 + 2 - 3 E'
   ⇒ 1 + 2 - 3         (E' → ε)
```

能。✓ 而且 `E'` 每次递归前都消耗了 `+` 或 `-`，不会死循环。✓

### 4.5 ★ 坏消息：右递归把结合性弄反了

**这一节是本篇最重要的地方，也是绝大多数教科书和上一版 03 笔记跳过的地方。**

`1 - 2 - 3` 正确答案是多少？Cool 的 `-` 是**左结合**，所以应该是 `(1-2)-3 = -4`，不是 `1-(2-3) = 2`。

现在看改写后的文法给出的**树形**：

```
E  → T E'
E' → '-' T E' | ε
```

画 `1 - 2 - 3` 的语法树：

```
        E
       / \
      T   E'
      |   /|\
      1  - T  E'
           |  /|\
           2 - T  E'
                |   |
                3   ε
```

**看出问题了吗？** `3` 所在的 `E'` 嵌在 `2` 所在的 `E'` **里面**——树是向**右**长的。如果你照着这棵树的形状建 AST，会得到：

```
   -
  / \
 1   -        ← 错！这是 1-(2-3) = 2
    / \
   2   3
```

而正确的是：

```
     -
    / \
   -   3      ← 对：(1-2)-3 = -4
  / \
 1   2
```

**问题的准确表述**：

> 消除左递归保住了**语言**（生成的串集合一模一样），但**破坏了树形**。而树形就是语义。
>
> 原来的左递归 `E → E - T` 天然向左长（`E` 在左孩子位），正是左结合想要的形状。改成右递归后，递归的那一支跑到右边去了，树跟着向右长。**我们为了让 parser 能跑，把答案算错了。**

教科书的标准补救是**继承属性**（inherited attribute）：给 `E'` 传一个"左边已经攒好的树"当参数。写成伪码：

```
parseE():
    t = parseT()
    return parseEPrime(t)        // 把已建好的左子树传下去

parseEPrime(lhs):
    if cur == '-':
        consume('-')
        r = parseT()
        node = Binary(lhs, '-', r)    // lhs 放左孩子 → 向左长
        return parseEPrime(node)       // 累加器向下传递
    else:
        return lhs
```

**手工跑一遍 `1-2-3`**：

| 步 | 调用 | lhs 参数 | 动作 |
|---|---|---|---|
| 1 | parseE | — | t = `1` |
| 2 | parseEPrime | `1` | 见 `-`，r=`2`，node=`(1-2)` |
| 3 | parseEPrime | `(1-2)` | 见 `-`，r=`3`，node=`((1-2)-3)` |
| 4 | parseEPrime | `((1-2)-3)` | 无 `-`，返回 |

得到 `((1-2)-3)` = **-4**。✓ 结合性救回来了。

### 4.6 真正的解法：把尾递归拉直成循环

盯住上面 `parseEPrime` 的结构：它的递归调用是**函数体的最后一个动作**，返回值直接原样返回。这叫**尾递归**（tail recursion）。

尾递归可以机械地改写成循环——这是编译原理里的基本变换（`10` 篇会从优化的角度再讲一次）：

```
参数 lhs        →  局部变量 lhs
尾递归调用      →  循环回到开头
返回基例        →  跳出循环
```

改写：

```cpp
std::unique_ptr<Expr> parseE() {
  auto lhs = parseT();                  // ← 原来的 parseE 第一步
  while (at(Tok::MINUS)) {              // ← 原来的 if，现在是循环
    advance();
    auto r = parseT();
    lhs = makeBinary(std::move(lhs), BinOp::Minus, std::move(r));
                                        // ← 旧树进左孩子，累加器原地更新
  }
  return lhs;                           // ← 原来的基例
}
```

**现在把它和真实代码对照。** `coolc/src/parser.cpp:128`：

```cpp
std::unique_ptr<Expr> Parser::parseAddSub() {
  auto lhs = parseMulDiv();
  while (at(Tok::PLUS) || at(Tok::MINUS)) {
    BinOp op = at(Tok::PLUS) ? BinOp::Plus : BinOp::Minus;
    Token t = cur_; advance();
    auto b = std::make_unique<Binary>();
    b->line = t.line; b->op = op;
    b->lhs = std::move(lhs);            // ★ 旧树 → 左孩子
    b->rhs = parseMulDiv();
    lhs = std::move(b);                 // ★ 累加器更新
  }
  return lhs;
}
```

**一模一样。** §0 的问题 5（"为什么真实代码里找不到 `E'`"）现在有完整答案了：

> **`E'` 被编译掉了。** 它经历了三次变换：
>
> ```
> E → E+T | T                    左递归，parser 会死
>      ↓  解方程 X = Xα∪β，得 T(+T)*
> E → T E',  E' → +T E' | ε      右递归，能跑，但树向右长（结合性错）
>      ↓  加继承属性（累加器）
> parseEPrime(lhs)               树向左长（结合性对），但是尾递归
>      ↓  尾递归 → 循环
> while (at(+)) { lhs = Binary(lhs, ...) }    ← parser.cpp 的样子
> ```
>
> **`E'` 是推导路上的脚手架，不是终点。** 教科书停在第二步，所以你在代码里找不到它；而真实代码停在第四步，所以看起来和教科书毫无关系。**这四步就是那道鸿沟。**

### 4.7 顺便得到两条可推导的规则（不用背）

从 §4.5 的树形分析里，直接读出两条规则：

| 想要的结合性 | 代码结构 | 为什么 | 树形 |
|---|---|---|---|
| **左结合**（`+ - * /`） | **循环** + 累加器 | 每轮把旧树塞进**左**孩子 | 向左长 |
| **右结合**（`<-`） | **递归**同层 | 递归结果放进**右**孩子 | 向右长 |
| **非结合**（`< <= =`） | 只处理**一次**，既不循环也不同层递归 | 第二个运算符没人消费 → 留给调用者 → 报错 | 只有一层 |

右结合的代码形态（`parser.cpp:84`，赋值 `<-`）：

```cpp
std::unique_ptr<Expr> Parser::parseExpr() {
  if (at(Tok::OBJECTID) && nxt_.kind == Tok::ASSIGN) {
    Token id = cur_;
    advance(); advance();               // 吃掉 ID 和 <-
    auto a = std::make_unique<Assign>();
    a->line = id.line; a->name = id.lexeme;
    a->rhs = parseExpr();               // ★ 递归同层 → 结果进右孩子 → 右结合
    return a;
  }
  return parseNot();
}
```

`a <- b <- c` → `Assign(a, Assign(b, c))` = `a <- (b <- c)`。✓ 符合 `01` 篇 §5。

非结合的代码形态（`parser.cpp:110`，比较运算）：

```cpp
std::unique_ptr<Expr> Parser::parseCompare() {
  auto lhs = parseAddSub();
  BinOp op;
  if (at(Tok::LE)) op = BinOp::Le;
  else if (at(Tok::LT)) op = BinOp::Lt;
  else if (at(Tok::EQ)) op = BinOp::Eq;
  else return lhs;                      // ★ 没有比较运算符，原样返回
  Token t = cur_; advance();
  auto b = std::make_unique<Binary>();
  b->line = t.line; b->op = op;
  b->lhs = std::move(lhs);
  b->rhs = parseAddSub();               // ★ 注意：不是 parseCompare
  return b;                             // ★ 直接返回，没有 while
}
```

**`a < b < c` 会发生什么？（这个推理链值得完整走一遍）**

1. `parseCompare` 取 `lhs = a`；
2. 见 `<`，消耗，`rhs = parseAddSub()` 得到 `b`；
3. **直接 return** `Binary(a < b)`——此时 `cur_` 停在第二个 `<`；
4. 返回到 `parseNot` → `parseExpr`，都不认识 `<`，原样返回；
5. 最终返回到某个调用点（比如 `parseBlock` 在等 `;`，或 `parseIf` 在等 `then`）；
6. 那里调 `expect(...)`，发现 `cur_` 是 `<` 不是期望的 token → **报错**。

得到的错误信息形如 `line N: expected ';' but got '<'`。

> **这就是"非结合"在实现层面的真身**：不是在某处写了一条 `if (非结合) 报错`，而是**通过"不消费第二个运算符"让它自然地落到调用者的 `expect` 上**。语法约束由控制流结构表达，而不是显式检查——这是手写 parser 的典型风格，也是它错误信息质量高的原因之一（报错点是真实的语法位置）。

## 5. 工业接轨

### 5.1 左递归这道坎，各家怎么跨

| 方案 | 怎么处理左递归 | 代表 |
|---|---|---|
| 手写递归下降 + 优先级分层 | 人工做完 §4.3–4.6 的四步变换 | Clang、rustc、Go、**我们的 coolc** |
| LR / LALR（自底向上） | **天然支持**，不用改文法 | bison / yacc（`04` 篇） |
| PEG + 左递归特殊支持 | 靠 memo 表检测并打断左递归 | **Python 3.9+**（PEP 617 换掉了老的 LL(1) parser） |
| Pratt parsing | 用"绑定力"数值代替函数分层 | 很多 JS 引擎、部分 LLVM 前端工具 |

> **一句提醒**：我们这套"每个优先级一个函数"的写法，和 Clang 的做法**本质相同但形态不同**——Clang 用**一个**函数 `ParseRHSOfBinaryExpression(prec)` 带优先级参数，通过比较数值决定"继续循环还是递归下钻"。你在 `03b` 学完分层法之后，会发现两者是同一个算法的两种编码方式（一个把优先级编码在**调用链结构**里，一个编码在**数值参数**里）。分层法更好懂，参数法更省代码。

### 5.2 为什么这对你的方向有用

你在做 AI Infra，短期不会写通用语言的 parser。但**"文法 → 树"这套东西在你的战场上到处是**：

- **Triton**：`@triton.jit` 装饰的函数，Triton 不自己写 parser，而是用 Python 自带的 `ast` 模块拿到 AST，再遍历它生成 IR。**你写的 kernel 先变成一棵树，才变成 PTX。**
- **IR 文本格式**：LLVM IR（`07`）、MLIR（`13`）都有文本形式，都要被 parse。MLIR 的通用 op 语法（`%res = "dialect.op"(%a, %b) : (T, T) -> T`）是**刻意设计成无歧义、易解析**的——因为 IR 文本要被工具链反复读写，parser 的复杂度就是工具链的成本。这正是 §3.3"语言设计决定 parser 难度"那条原则在 IR 设计上的应用。
- **算子融合的模式匹配**：你在 W4 做的"识别 `silu(gate) ⊙ up` 这个模式并替换成一个 kernel"，在编译器里叫**树重写**（tree rewriting）。TVM 的 pattern matcher、MLIR 的 `PatternRewriter` 做的就是这件事。**先有树，才有模式匹配。** `10` 篇会把这条线接上。

> 所以这篇的地位：它是"把源码变成树"这条链的第一环。**树是后面一切分析和变换的对象**——类型检查在树上跑（`06`），codegen 在树上跑（`09`），优化在 IR 图上跑（`10`），而 IR 是从树降下来的（`07`）。

## 7. 术语表

| 术语 | 一句话 |
|---|---|
| 上下文无关文法（CFG） | 产生式左部只有单个非终结符的文法；能表达递归嵌套，但表达不了"先声明后使用"这类上下文约束 |
| 终结符 / 非终结符 | 终结符 = lexer 产出的 token（叶子）；非终结符 = 语法变量（内部节点） |
| 推导（derivation） | 从开始符号出发反复替换非终结符，直到全是终结符 |
| 句型 / 句子 | 句型 = 还含非终结符的中间串；句子 = 全终结符的串 |
| 最左推导 | 每步替换最左非终结符；与语法树一一对应；对应自顶向下分析 |
| 二义（ambiguous） | 存在某串有两棵以上语法树（等价地：两个以上最左推导） |
| 左递归 | 产生式右部以自身开头（`A → Aα`）；使自顶向下分析违反"递归前必消耗 token"契约而死循环 |
| Arden 规则 | 方程 `X = Xα ∪ β` 的最小解是 `X = βα*`；左递归消除公式的来源 |
| 继承属性 | 从父节点传给子节点的信息；这里用作"左边已建好的子树"累加器，救回左结合性 |
| 尾递归 | 递归调用是函数最后一个动作；可机械改写成循环，这一步把 `E'` 变成了 `while` |
| 悬空 else | `if a if b x else y` 里 else 归属不明的二义；Cool 用 `fi` 从设计上消灭 |

| 8 条左递归产生式（§2.2 观察 2） | `03b` §3 优先级爬升 | 下一篇把这 8 条一次性消完，顺带编码优先级 |
| 3 条 `ID` 开头的产生式（§2.2 观察 3） | `03b` §2 FIRST/FOLLOW | 下一篇解释为什么 `parser.h` 需要 `nxt_` |
| 树形决定语义（§4.5） | `03c` AST 设计、`09` codegen | 树形错了 codegen 就生成错的指令，这是整条链的第一个正确性关口 |
| 左递归天然支持（§5.1） | `04` LR/LALR | 自底向上不怕左递归，这是它相对 LL 的主要优势 |
| 尾递归 → 循环（§4.6） | `10` 程序分析与优化 | 同一个变换，那边是编译器自动做，这里是我们手工做 |
| 语言设计决定 parser 难度（§3.3） | `13` MLIR / IR 文本格式 | IR 语法刻意设计成无歧义，就是这条原则的工业应用 |
