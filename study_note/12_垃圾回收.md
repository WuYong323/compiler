## 精炼段

`11` 篇处理的是"值放哪"在**寄存器**这一侧，本篇是它在**堆**那一侧。我们的 `runtime.c` 只有一行 `void* cool_alloc(int n) { return malloc(n); }`——**全文没有一个 `free`**。实测：一个 2 万次的循环分配 6 万个对象、960 KB，一个字节都没还。

但本篇的重点不是"背三种算法"。**真正值得学的是这条推理链**：想回收内存 → 必须知道哪些对象还活着 → 活着的定义是"从根可达" → **那"根"到底是什么？** 答案是栈上和寄存器里的所有指针——而**谁知道栈上哪些槽位装着指针？只有编译器知道。** 于是 GC 这个看起来纯属"运行时"的话题，它的可行性完全捏在编译器手里。这就是为什么 GC 会出现在一门编译原理课里。

本篇按这条链展开：§1 先量清我们漏了多少；§2 建立可达性并指出它就是 `10` 篇那套不动点迭代；§3 讲根集问题，也就是编译器欠 GC 的那笔账；§4-6 是三种经典算法，每一种都回答"前一种的什么缺陷"；§7 是**本篇的实证核心**——我真的写了一个标记器挂到我们的编译器上，结果同时验证了分代假说（99.9% 是垃圾）和挖出了一个 `alloca` 缺陷；§8 分代与写屏障；§9 接到你的推理优化方向。

## 1. 先量：我们到底漏了多少

先把话说实。给 `runtime.c` 的每个分配点加计数器（完整代码见 §7.1），跑一遍测试集：

| 测试 | `cool_alloc`+`cool_copy` | 字节 | 字符串缓冲 | `free` |
|---|---|---|---|---|
| `hello.cl` | 1 | 8 | 0 | **0** |
| `factorial.cl` | 17 | 264 | 0 | **0** |
| `list.cl` | 6 | 96 | 0 | **0** |
| `while_test.cl` | 17 | 264 | 0 | **0** |
| `case_test.cl` | 3 | 32 | 0 | **0** |
| `string_test.cl` | 4 | 72 | 2（16 B） | **0** |
| `bool_test.cl` | 14 | 240 | 0 | **0** |
| `inherit_test.cl` | 5 | 88 | 1（5 B） | **0** |

这些数字都很小，看不出问题——**因为测试程序都是"跑一下就结束"**。把循环次数拉大，泄漏就是线性的：

```cool
while i < N loop { c <- (new Cell).set(i); i <- i + 1; } pool
```

| N | 分配次数 | 字节 |
|---|---|---|
| 10 | 33 | 520 |
| 100 | 303 | 4,840 |
| 1,000 | 3,003 | 48,040 |
| 10,000 | 30,003 | 480,040 |

**精确的 3N+3 次、每轮 48 字节。** 三个分配是哪来的？每轮 `new Cell`（16 B）+ `i + 1` 的结果装箱成 `Int`（16 B）+ `i < N` 的结果装箱成 `Bool`（16 B）。**`08` §6 那个装箱决策在这里第四次收税**：它让每轮循环多漏两个对象。

**关键观察**：上一轮的 `c` 在 `c <- ...` 赋值的那一刻就再也没人能碰到了——**它已经是垃圾**，但我们的运行时没有任何机制知道这件事。进程靠"退出时操作系统回收一切"兜底，**这对一个跑几小时的服务是不可接受的**。

## 2. 可达性：垃圾的定义

### 2.1 为什么只能用"可达"做判据

我们想问的是"这个对象将来还会被用到吗"。**这个问题不可判定**（又是 Rice 定理，`10` §3.4 那条）。所以 GC 退而问一个**可判定的、保守的**近似：

> 从**根**出发，沿指针能走到的对象是**活的**；走不到的是**垃圾**。

```
根（roots）: 栈上的变量槽、寄存器、全局变量
   │
   ├──► 对象A ──► 对象B ──► 对象C
   │                │
   │                ▼
   └──► 对象D     对象E
                    
        对象F   ← 没有任何路径能到达 → 垃圾
```

**这个近似的方向必须搞清楚**，它和 `10` §3.4 是同一种保守性：

```
真正还会被用到的对象  ⊆  可达的对象
```

**可达但不会再用**是允许的（多留一点垃圾，只浪费内存）；**不可达但还会用**是灾难（回收了正在用的对象 → 野指针）。所以 GC **只能**往"多留"这边错。§7.3 那个实测的 2/3 误留，就是这条允许的偏差被一个缺陷放大到了极致。

### 2.2 它就是一次不动点迭代

标记阶段的算法：

```
可达集 = 根集
repeat
    可达集 = 可达集 ∪ { 被可达集中某个对象指向的对象 }
until 可达集不再变化
```

**这个形状你在 `10` §3.3 见过一模一样的。** 对照一下：

| 数据流分析（`10` §3） | GC 标记阶段 |
|---|---|
| 格 = 变量集合 | 格 = 对象集合 |
| transfer 单调 | "加入被指向的对象"单调（只增不减） |
| 格高度有限（变量有限） | 堆上对象个数有限 |
| ⟹ 有限步收敛 | ⟹ 有限步收敛 |

**所以"标记阶段一定会停"的证明和 `10` 篇那个是同一个证明**：单调 + 有界。对象图里有环（`Cons` 互相指、甚至自己指自己）**完全不影响终止性**，因为已标记的对象不会被重复入队——这正是 `10` §3.3 那句"有环 ≠ 不终止，关键是有没有一个单调变化且有界的量"的第三次兑现（第一次是 `05b` §3 的 `conforms` 死循环，第二次是数据流迭代）。

**也顺便解释了引用计数的死穴**（§6）：引用计数**不做**这个迭代，它只看局部计数，所以环上的对象互相"撑住"对方，计数永远不归零。**追踪式 GC 从根出发，环再复杂也走不到就是走不到。**

## 3. 根集：编译器欠 GC 的那笔账

这一节是本篇和编译原理的真正接口，也是绝大多数教材一句话带过的地方。

### 3.1 问题

标记阶段的第一步是"根集 = 栈上和寄存器里的所有指针"。**但栈上的一个 8 字节字，它是指针还是整数？** 机器不知道——栈就是一片字节。

看我们自己生成的 IR（`09` §3.2）：

```llvm
%self = alloca i8*        ; 装指针
%t10  = alloca i8*        ; 装指针
```

我们运气好，**所有** `alloca` 都是 `i8*`（因为"一切皆 `i8*`"那个决策，`09` §2）。但真实编译器的栈帧里混着 `int`、`double`、指针、返回地址、溢出槽（`11` §6.2 数过的那些）。GC 必须能区分，否则：

- 把整数 `0x1400052c0` 误当指针 → 可能指到堆对象上 → **误留垃圾**（安全但浪费）；
- 漏掉一个真指针 → **回收了活对象**（灾难）。

### 3.2 两条出路

| | **精确式**（precise / exact） | **保守式**（conservative） |
|---|---|---|
| 怎么知道谁是指针 | 编译器生成**栈映射表**（stack map）：每个可能触发 GC 的点，记录本帧哪些偏移是指针 | 不知道，**把每个字都当可能的指针**试一遍 |
| 能否移动对象 | **能**（知道所有指针在哪，可以逐个改写） | **不能**（不敢改写一个可能是整数的字） |
| 精度 | 精确 | 会误留（把整数当指针） |
| 编译器负担 | 重（要维护栈映射、GC 安全点） | **零** |
| 代表 | JVM、Go、.NET | Boehm GC、早期 Mono |

**这张表就是那笔账**：想要复制式/压缩式 GC（§5），编译器**必须**吐出栈映射表；不吐，就只能用保守式，也就永远不能移动对象、永远得忍受碎片。

**我们的编译器一张栈映射表都没生成**，所以 §7 我只能写保守式的。**这不是偷懒，是被前面的设计决定了的**——`09` 篇 codegen 的每一个决策都没有为 GC 留任何信息。

### 3.3 GC 安全点：另一半账

还有一个更隐蔽的要求。GC 不能在任意时刻发生：

```llvm
%t11 = call i8* @cool_alloc(i32 16)   ; 刚拿到一块裸内存
                                       ; ← 如果 GC 在这里发生？
store i8* bitcast(... @class_Cell ...), i8** %tf   ; 对象头还没写！
```

**在这两条之间，`%t11` 指向的 16 字节是没有对象头的**——GC 走到它会读到垃圾类元信息。所以精确式 GC 要求编译器只在**安全点**（safepoint）允许 GC，并保证安全点上所有对象都是**格式良好**的。

**我把这件事实测出来了**，而且是意外撞上的：§7.1 的标记器在 `cool_alloc` 内部触发收集，结果每次都有一个对象分类不出类名。打出来看：

```
[live] size=8   first_word=00007FF7A7045420  是最新分配的吗=否
[live] size=16  first_word=00007FF7A7045390  是最新分配的吗=否
[live] size=16  first_word=0000000000000000  是最新分配的吗=是   ← 对象头是 NULL
[live] size=16  first_word=00007FF7A70451A0  是最新分配的吗=否
```

**第三行的对象头是 `0x0`，而且它恒等于"最新分配的那个"。** 它就是 §3.3 说的那个状态：`malloc` 已经返回、调用方还没写对象头。**如果我的标记器需要读对象头来找指针字段（精确式就需要），这里会直接崩。** 保守式不读对象头（它只是把每个字当指针试），所以侥幸活了下来。

> **这是本篇最值得记住的一个实测**：安全点不是理论洁癖。**在分配器内部触发 GC，必然看到一个半初始化的对象**——这是结构性的，不是偶发时序问题。

## 4. 标记-清除（Mark-Sweep）

**两个阶段**：

1. **标记（mark）**：从根出发做 §2.2 那个迭代，给可达对象打标记；
2. **清除（sweep）**：**线性扫过整个堆**，把没打标记的挂到空闲链表上。

```
标记前:  [A*][B ][C*][D ][E*]      * = 可达
标记后:  [A✓][B ][C✓][D ][E✓]
清除后:  [A ][空][C ][空][E ]      空闲链表: B → D
```

**代价**：

- 清除阶段 **与堆大小成正比**，而不是与垃圾量成正比。堆里 99% 是活对象也要全扫一遍。
- 产生**碎片**：回收出来的空洞大小不一。要分配一个 24 字节的 `Cons`，手里有两个 16 字节的洞也没用。

**优点**：**不移动对象**。所以它是**保守式 GC 唯一能用的算法**（§3.2 那张表）——这就是为什么 §7 我写的是标记器而不是复制器。

**它也解释了 `malloc` 为什么不是 O(1)**：`malloc`/`free` 维护的就是这么一个空闲链表，碎片化后要遍历找合适的块。我们的 `cool_alloc` 直接转发给 `malloc`，所以**已经在承受碎片的代价了**，只是没享受到回收的好处。

## 5. 复制收集（Copying / Cheney 半区法）

**它要解决的正是标记-清除那两个缺点。**

堆分成两个**半区** `from` / `to`，只在 `from` 里分配：

```
收集前:  from=[A*][B ][C*][D ][E*]   to=[                    ]
收集后:  from=[                    ]  to=[A][C][E]            ← 紧凑，无洞
         然后交换 from/to 的角色
```

1. 从根出发遍历 `from` 里的活对象；
2. **复制**到 `to`，顺序紧挨着放；
3. **更新所有指向它的指针**（用"转发指针"：在旧位置留一个"我搬到哪了"的记录）；
4. 交换 `from`/`to`。

**三个收益**：

1. **代价与活对象量成正比**，与堆大小和垃圾量都无关。**垃圾多的时候它几乎免费**——这一条是 §8 分代设计的全部基础。
2. **零碎片**，因为复制时紧凑排列。
3. **分配变成指针碰撞**（bump pointer）：`p = top; top += size;`，两条指令。比 `malloc` 找空闲块快一个数量级。

**两个代价**：

1. **一半内存闲着**。
2. **必须移动对象** ⟹ **必须精确式** ⟹ **编译器必须生成栈映射表**（§3.2）。

> **第 2 条对我们是硬门槛**：我们的编译器没有栈映射，所以**复制收集在我们的编译器上根本装不了**，不管我多想写 Cheney 算法。**这就是 §3.2 那笔账的实际后果——前面的设计决定了后面的可能性。**

## 6. 引用计数（Reference Counting）

每个对象带一个计数，指针赋值时 +1/-1，归零即回收。

**优点**：回收**及时**（不需要等一次收集）、**暂停时间短**（分摊到每次赋值）、不需要扫描根集。

**两个致命问题**：

1. **环形引用收不掉**。`a.next <- b; b.next <- a;` 然后两个变量都失效——计数都是 1，永远不归零。**§2.2 解释了根本原因**：引用计数不做从根出发的迭代，只看局部信息。
2. **每次指针赋值都要改计数**，而且多线程下要原子操作。开销分散但总量可观。

**工业选择**：Python 用引用计数 + 一个**环检测器**兜底；Swift 的 ARC 是编译期插入 retain/release（**这是编译器的活**，又一次），环要靠程序员写 `weak` 手动打破；C++ 的 `shared_ptr` 同理，`weak_ptr` 就是为了断环。

**"需要程序员手动断环"本身就是这个方案不完备的证据。**

## 7. 实测：给我们的编译器装一个标记器

> 这一节是本篇的证据。我没有停在"理论上可以"，而是真写了一个挂上去跑。结果有两个：**验证了分代假说**，和**挖出一个真实缺陷**。

### 7.1 做了什么

写了 `coolc/rt_gc.c`（用法：`clang your.ll rt_gc.c -o out.exe`，环境变量 `GC_EVERY=N` 控制每 N 次分配收一次，`GC_BYCLASS=1` 按类统计）。它是一个**语义与 `runtime.c` 完全一致**（同样从不 `free`）的替换品，加上：

- 每次分配登记 `(基址, 大小, 是否含指针)`；
- 一个**保守式标记器**（§3.2 右列，因为我们没有栈映射表）：
  - 根 = `GetCurrentThreadStackLimits` 拿到的栈区间 + `setjmp` 把寄存器逼到栈上；
  - 把每个机器字当候选指针，二分查表看是否命中某个对象的**基址**；
  - 用显式工作表做 §2.2 的传递闭包（不用递归——`09` §6.3 那次 4231 层栈溢出的教训）；
- **只标记，不清除**：报告"有多少字节其实已经不可达"，但不真的 `free`。

**为什么不真 free**：`interior_hits` 那个计数器实测到 18 次"指向对象内部而非基址"的候选字。保守式标记器对内部指针的处理不完备，加上 §3.3 那个半初始化对象的问题，**真 free 掉是不安全的**。**先量，不动手**——量出来的数字已经足够说明问题。

### 7.2 结果一：分代假说被强验证

`N=20000` 的循环，每 1 万次分配触发一次标记（`-O2` 编译）：

```
[gc] 已分配=10000  可达=6 (88 B)   垃圾=9994  (159904 B)   99.9% 是垃圾
[gc] 已分配=20000  可达=5 (72 B)   垃圾=19995 (319920 B)  100.0% 是垃圾
[gc] 已分配=30000  可达=4 (56 B)   垃圾=29996 (479936 B)  100.0% 是垃圾
[gc] 已分配=40000  可达=4 (56 B)   垃圾=39996 (639936 B)  100.0% 是垃圾
[gc] 已分配=50000  可达=4 (56 B)   垃圾=49996 (799936 B)  100.0% 是垃圾
[gc] 已分配=60000  可达=4 (56 B)   垃圾=59996 (959936 B)  100.0% 是垃圾
[heap] cool_alloc+copy=60003 (960040 B)  freed=0
```

**6 万个对象、960 KB，最后只有 4 个对象 56 字节是活的。** 那 4 个是：`Main` 自己、`keep` 指向的 `Cell`、它内部的 `Int`、以及 §3.3 那个半初始化的新对象。

**这不是我构造出来的极端例子，这是循环里创建临时对象的常态。** 它直接验证了 §8 分代收集的那条经验规律（"大部分对象早死"），而且验证得比教科书举的例子更极端。

**顺带看清了复制收集的优势有多大**（§5 收益 1）：代价与**活对象量**成正比。这里活对象是 56 字节，**一次复制收集几乎是免费的**，而标记-清除要扫 6 万个对象的登记表。**"垃圾越多、复制收集越划算"这条反直觉的性质，在这组数字面前变得非常直观。**

### 7.3 结果二：挖出一个真实缺陷

**同一个程序改用 `-O0` 编译，标记结果完全不同：**

| 编译选项 | 栈区间 | 根直接标记 | 判定可达 | 判定垃圾 |
|---|---|---|---|---|
| `-O2` | **1256 B（恒定）** | **4** | **4（56 B）** | **596（99.3%）** |
| `-O0` | 4784 B → **7984 B（在长**） | 203 → **403** | 401（6408 B） | 199（33.2%） |

两个异常一眼可见：**`-O0` 下栈区间随循环轮数增长**，而且**根扫描直接标记了 403 个对象**——一个 `while` 循环凭什么在栈上留下 403 个指针？

按类拆开看，规律非常刺眼：

```
-O0:   Cell 可达=400  垃圾=0      ← 每一个 Cell 都被留住了
       Int  可达=399  垃圾=0      ← 每一个 Int 也是
       Bool 可达=0    垃圾=399    ← 只有 Bool 被正确判定为垃圾
```

**"每一个都留住"不是保守式 GC 的正常噪声**（那应该是随机零星的），这是系统性的。查生成的 IR：

```llvm
entry:
  %self = alloca i8*
  ...
bb1:                        ; ← 循环体
  %t46 = alloca i8*         ; ← alloca 在这里！每轮都执行一次
```

**`alloca` 被发在了循环体里。** LLVM 的 `alloca` 只有函数返回才释放，所以**每轮循环都在栈上多占一个槽位，而且槽里存着那一轮对象的指针**——于是那些对象从"根"可达，全被误留。

**这个缺陷的另一面更严重。** 看 `-O0` 的汇编：

```asm
.LBB10_1:                   # 循环头
...
	movl	$16, %eax
	callq	___chkstk_ms
	subq	%rax, %rsp       # ← 每轮减 16 字节，直到函数返回都不还
	movq	%rsp, %rax
...
	jmp	.LBB10_1
```

**`rsp` 每轮单调下降。** 这不只是误留垃圾，**这是栈泄漏**。实测边界：

| 循环次数 | `-O0` | `-O2` |
|---|---|---|
| 100,000 | `survived` | `survived` |
| 129,000 | `survived` | `survived` |
| **130,000** | **崩溃** | `survived` |
| 2,000,000 | 崩溃 | `survived` |

`gdb` 确认是 `SIGSEGV`，`rsp = 0x403fb0` —— 栈一路向下撞到了保护页。**算一下印证**：PE 头 `SizeOfStackReserve = 0x200000`（2 MB），每轮 16 字节 → 131072 轮耗尽。实测 129000 过、130000 崩，**和预测差不到 2%**（差的那点就是函数本身的帧）。

**三处同源，逐个验证过**。我担心这只是 `let` 的问题，于是分别构造了只用 `new`、只用 `case` 的程序：

| 触发方式 | `alloca` 落在 | `-O0` 跑 20 万轮 |
|---|---|---|
| `let x : Int <- ...`（`codegen.cpp:327`） | 循环体 | **崩溃** |
| `new Cell`（`allocateAndInit`，`codegen.cpp:454`） | 循环体 | **崩溃** |
| `case o of x : Int => ...`（`codegen.cpp:363`） | 分支体 | **崩溃** |

**三个都独立崩。** 根因是同一个：`visit(Let)` / `visit(Case)` / `allocateAndInit` 都在**当前位置**发 `alloca`，而当前位置可能在循环里。

**为什么 12 个测试全没发现**：所有测试的循环次数都是个位数到 10。这是**第五次**遇到同一条教训——

> **测试覆盖的是实现者想到的情况，而不是规范允许的情况。** Cool 的 `while` 没有轮数上限，`let` 可以出现在循环体里，这完全合法。

**为什么 `-O2` 看起来没事**：`mem2reg`（`07` §4）把 `alloca` 提升成 SSA 值，`alloca` 本身被删掉了，泄漏和误留同时消失。**这比"没事"更危险**——缺陷在 `-O0` 调试时崩、开优化就好，是最难查的那类 bug。

**修法与验证**：把所有 `alloca` 统一发到函数的 `entry` 块（LLVM 的标准约定，也是 clang 自己的做法）。我手工改 IR 验证过这个修法：把循环体里那条 `alloca` 搬到 `entry`，其余一字不动，**`-O0` 下 50 万轮通过**（原先 13 万就崩）。

具体怎么改 codegen 留给你做（§10 第 3 题），因为它需要一点设计决策：`emitMethod` 里维护一个"入口块待插入列表"，`fresh()` 出槽位名后把 `alloca` 记进去、函数发完再统一插到 `entry`。

> **方法论上值得记住的是这次是怎么查出来的**：我并不是去审计 codegen 才发现它。我是在量 GC 效果时看到"根直接标记 403 个对象"这个**说不通的数字**，追下去才撞上的。**一个你解释不了的测量值，比一次代码走查更容易把 bug 逼出来。** §7.2 那组漂亮的 99.9% 如果我只跑了 `-O2`，这个缺陷就会被完整地藏过去。

### 7.4 小结：三个数字

| 量 | 值 | 说明 |
|---|---|---|
| 真实垃圾率 | **99.9%**（`-O2`，6 万对象活 4 个） | 分代假说的实证 |
| `-O0` 误留 | **2/3 的垃圾被误留** | 循环体 `alloca` 造成的假根 |
| 栈泄漏边界 | **13 万轮崩溃**（2 MB ÷ 16 B） | 同一缺陷的另一面 |

## 8. 分代收集：把 §7.2 那个数字变成设计

### 8.1 经验规律

> **绝大多数对象在很年轻时就死掉**（infant mortality / generational hypothesis）。

**§7.2 就是这条规律的一次强验证**：99.9%。而且注意它的形状——垃圾全是循环体里那些"创建、用一次、丢掉"的临时对象，活的是 `Main` 和 `keep` 这种从头活到尾的。**两类对象的寿命分布是双峰的，中间几乎没有东西。**

### 8.2 设计

把堆按**年龄**分代：

| | 新生代（young） | 老年代（old） |
|---|---|---|
| 收集频率 | 频繁 | 偶尔 |
| 用什么算法 | **复制收集** | 标记-清除/标记-压缩 |
| 为什么是它 | 垃圾率极高 ⟹ 代价与活对象成正比的算法几乎免费（§5 收益 1 + §7.2 的 99.9%） | 活对象多，复制代价太高；而且老年代不常收，能忍受碎片 |

**"熬过几次收集就晋升到老年代"**（promotion）。

**这个设计的每一条都是前面某个结论的直接推论**——不是拍脑袋的工程技巧：

```
§7.2 实测：新对象 99.9% 是垃圾
  + §5 收益 1：复制收集的代价 ∝ 活对象量
  ⟹ 新生代用复制收集，几乎免费
  
§5 代价 1：复制浪费一半内存
  ⟹ 只对小小的新生代这么干，不要对整个堆
  
老年代活对象多 ⟹ 复制不划算，退回标记-清除
```

### 8.3 写屏障：为什么它是必须的

分代的收益来自"**只扫新生代**"。但有个漏洞：

```
老年代对象 O  ──指向──►  新生代对象 Y
```

只从根扫新生代的话，走不到 `Y`（因为路径经过老年代的 `O`，而我们没扫 `O`）→ **`Y` 会被误回收**。这违反了 §2.1 那条"绝不允许少算"。

**朴素修法**是每次也扫一遍老年代——那分代就白分了。

**真正的修法是写屏障**（write barrier）：编译器在**每一个指针写操作**处插入一小段代码，记录"老年代产生了指向新生代的引用"。收集新生代时，把这些记录也当成根。

**注意这又是编译器的活**，而且比栈映射表更侵入——**每条指针 `store` 都要插代码**。代价是这样摊出来的：

```
每次指针赋值多几条指令（分摊、恒定）
  ⟺  换来每次 GC 不必扫老年代（省下大量扫描）
```

**这是一笔非常典型的交易**：把集中的大开销换成分散的小开销。你在 `11` §5 见过同构的取舍（JIT 宁可要更差的分配也要更快的编译），在 §6 引用计数那里也见过（分摊 vs 集中）。

> **我们的编译器如果要装分代 GC，`codegen.cpp` 里每一处 `store i8*` 都得改。** 数一下就知道这笔账有多大——这就是"GC 是编译器的话题"最具体的形式。

## 9. 接到你的方向：为什么推理引擎不要 GC

这一节对你最有用，因为它解释了你已经在做的事。

### 9.1 GC 的暂停是延迟敏感场景的天敌

| | GC | 手动/池化管理 |
|---|---|---|
| 内存安全 | 好（不会 use-after-free） | 靠程序员 |
| 吞吐 | 好 | 好 |
| **尾延迟** | **差（有暂停）** | 可控 |
| 内存占用 | 高（需要余量，复制还要一半） | 紧凑 |

**推理服务的 SLO 是 P99 延迟**。一次 100ms 的 GC 暂停会把 P99 直接打穿，而 GC 什么时候来是不确定的。**所以延迟敏感的系统宁可自己管内存。**

### 9.2 你写过的 KV Cache 就是一个手写内存管理器

你在 W6 做的 KV Cache，用本篇的语言可以完整重述：

| 你做的事 | 本篇的概念 |
|---|---|
| 预分配一大块显存 | 半区 / 内存池 |
| 按 block 切分、bump 分配 | §5 的指针碰撞分配 |
| 引用计数决定 block 能否复用（PagedAttention/prefix sharing） | §6 引用计数 |
| 序列结束后归还 block | 显式 `free`（**你知道生命周期，所以不需要追踪**） |
| block table 记录逻辑页→物理页 | 转发指针 / 页表 |

**最关键的一行是"你知道生命周期"**。GC 存在的全部理由是"编译器/运行时不知道对象什么时候死"。**推理引擎里你恰好知道**——一个 KV block 的寿命就是那条序列的寿命。**已知生命周期 ⟹ 不需要 GC，而且不该用 GC。**

**vLLM 用引用计数而不是追踪式 GC**，理由正是 §6 那张表：及时回收、无暂停；而它的死穴（环）在这里不存在——KV block 不会互相引用。**约束变了，方案的优劣就换了位置。**

### 9.3 显存碎片：你可能已经遇到过

`torch.cuda.OutOfMemoryError` 里那句 `reserved memory is much greater than allocated memory` 说的就是**§4 的碎片**：PyTorch 的缓存分配器手里有足够的总量，但没有一块足够大的连续空间。

- `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 是在缓解碎片；
- PagedAttention 的核心洞见就是**用分页（固定大小 block）消除碎片**——和 §5 复制收集"紧凑化消除碎片"是同一个目标的两种手段（一个靠移动，一个靠定长分块）。

> **接到你的 AMK 工作**：巨核融合会产生大量中间张量，**它们的生命周期在编译期就完全已知**（就是计算图上的一段）。所以 AI 编译器做的是**静态显存规划**（memory planning）——`10` §8.2 那张表里"活跃变量分析 → 显存规划"那一行。**这本质上是把 GC 的工作提前到编译期做掉**：既然编译器能算出每个张量的活跃区间（`10` §4），就能静态地复用缓冲区，运行时零开销、零暂停。**这是本篇和 `10`、`11` 三篇的汇合点：活跃区间这一个概念，在寄存器上叫寄存器分配，在堆上叫 GC，在张量上叫显存规划。**

## 13. 本文你掌握了什么 / 易错点 / 下一步

**掌握**：为什么只能用"可达"做垃圾的判据（不可判定 + 保守方向必须朝"多留"偏）；标记阶段与数据流迭代是同一个收敛论证，以及它为何天然处理环形引用；**根集问题为什么是编译器的责任**，精确式与保守式的分野及其后果（能否移动对象）；GC 安全点为什么是结构性要求（实测撞到半初始化对象）；标记-清除/复制收集/引用计数各自解决了前一个的什么缺陷；分代设计的每一条如何从"垃圾率极高 + 复制代价 ∝ 活对象量"推出来；写屏障的必要性与它的开销交易；**给自己的编译器装标记器实测出 99.9% 垃圾率**；以及由此挖出的循环体 `alloca` 缺陷（误留 2/3 垃圾 + 13 万轮栈溢出 + `-O2` 掩盖）。

**易错点**：

1. **垃圾 = 不可达**，不是"被赋值覆盖的"、也不是"作用域结束的"。没有显式 `delete`。
2. **GC 只能往"多留"错**，绝不能往"少留"错（§2.1）。这个方向和 `10` §3.2 的保守性同源。
3. **复制收集需要精确式 GC，精确式需要编译器生成栈映射表**。这条依赖链常被跳过，但它决定了能不能用某个算法（§3.2 → §5）。
4. **保守式 GC 不能移动对象**，所以它只能配标记-清除。
5. **引用计数收不掉环**，根因是它不做从根出发的迭代（§2.2），不是"实现不够好"。
6. **分代 GC 的写屏障不是优化，是正确性要求**——没有它会误回收活对象（§8.3）。
7. **新生代用复制收集是因为垃圾率高**（代价 ∝ 活对象量），不是因为"复制快"。
8. **`alloca` 必须发在 `entry` 块**。发在循环体里 = 每轮泄漏一个栈槽（§7.3），而且 `-O2` 会把症状掩盖掉。
9. **"`-O2` 下正常"不等于"没 bug"**。`mem2reg` 能掩盖 `alloca` 的误用（§7.3）。
10. **在分配器内部触发 GC 必然看到半初始化对象**（§3.3 实测），这是结构性的而非时序偶发。
