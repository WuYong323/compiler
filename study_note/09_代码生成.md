## 精炼段

这是流水线最后一环（CP4）。前面四篇做的都是**分析**——判断程序对不对；本篇第一次做**综合**：产出一个新程序。

分析和综合的难度来源不同。类型检查的难点是"规则从哪来"（`06b` 用推导规则回答了）；代码生成的难点是**表示的错配**：源语言是**树**且**每个表达式有值**（`1+2*3` 的子树 `2*3` 有值 6），目标语言是**线性指令序列**且**指令本身不是值**（`add i32 2, 3` 不是 6，它是"一条算出 6 的指令"）。把树压平成序列时，"子表达式的值"必须落到某个**能被后面引用的名字**上——这正是 `07` §1.2 那句"中间值需要名字"在实现层的兑现。

我们的答案是一条只有一行的约定：**`codegenExpr` 发射若干指令，并返回一个字符串，这个字符串是"能代表该表达式值的 LLVM 操作数"**。全篇 18 个 `visit` 都在履行这条约定，而本篇最有价值的部分（§6）是三个真实 bug——它们全部是这条约定在边界上失效：分支体自己开了新块（φ 前驱错）、属性初始化被内联展开（`self` 错、深递归栈溢出）。**约定本身很简单，维护它的不变式才是工程。**

## 1. 先把问题定清楚：树 → 序列的错配

### 1.1 一个三行的例子，暴露全部困难

Cool 源码 `n * f(n - 1)`。它是一棵树：

```
      Mul
     /   \
   n     Dispatch f
            |
          Sub
         /   \
        n     1
```

目标是指令序列。**序列没有嵌套**，所以必须先算内层、把结果存进某个名字、再让外层引用这个名字：

```llvm
%t44 = load i32, ...        ; n 的值
%t47 = load i32, ...        ; 1 的值
%t48 = sub i32 %t44, %t47   ; n-1 → 这条指令"定义"了名字 %t48
...
%t60 = call i8* %t59(i8* %t40, i8* %t49)   ; f(n-1) → 名字 %t60
%t64 = mul i32 %t39, %t63                  ; 外层引用内层的名字
```

**三个观察，对应三个设计决策**：

| 观察 | 决策 |
|---|---|
| 内层必须先算完，外层才能引用它的名字 | 代码生成是**后序遍历**（先递归子结点，再发自己的指令） |
| 每个子表达式的值都要有一个名字 | `codegenExpr` **返回**那个名字 |
| 名字不能重名（SSA：每个名字只定义一次，`07` §3） | 名字由一个**单调计数器**发（`fresh()`） |

### 1.2 那条返回值约定的准确表述

```cpp
// codegen.cpp:203
std::string CodeGen::codegenExpr(const Expr& e) { e.accept(*this); return result_; }
```

三行代码，但约定要说准：

> `codegenExpr(e)` 把"计算 `e` 的值"所需的指令**追加**到当前基本块，并返回一个**LLVM 操作数字符串**，该操作数在这些指令执行后**持有 `e` 的值**。

注意我说的是"**操作数**"而不是"寄存器"。这个区别很实在——返回值有三种形态：

| 形态 | 例子 | 来自 |
|---|---|---|
| 虚拟寄存器 | `%t48` | 绝大多数 `visit`（算术、调用、φ…） |
| 常量表达式 | `bitcast (%Int* @int_5 to i8*)` | `visit(IntConst)`、`visit(BoolConst)` |
| 字面 `null` | `null` | `visit(NoExpr)`、`visit(While)` |

**为什么必须允许后两种**：`5` 这个表达式不需要任何指令——它的值编译期就知道。如果强行给它发一条指令（比如 `%t = bitcast ...`），生成的 IR 会多出成千上万条无用指令。所以"返回操作数"比"返回寄存器"更宽松，而**正是这份宽松埋了一个雷**——`visit(While)` 返回 `null`，意味着 `while` 的值是个假值；老笔记 §6 记的那个"常量多带 `i8*` 前缀"的坑，也出在这三种形态的拼接规则不一致上（§6.4 会给这个坑一个更准确的定案）。

### 1.3 为什么用 visitor 而不是 `switch`

`ExprVisitor` 有 18 个 `visit`（`codegen.h:91-108`）。但注意：`visit` 的返回类型是 `void`，值是通过成员 `result_` 传出来的（`codegen.h:41`）。这是一个**妥协**——visitor 模式的 `accept/visit` 签名固定，没法直接返回 `std::string`，于是用一个成员变量当"输出参数"。

代价要说清楚：`result_` 是**共享可变状态**，所以 `codegenExpr` 必须在 `accept` 后**立刻**取走 `result_`，任何延迟都会被下一次 `codegenExpr` 覆盖。`08` 篇提过 typechecker 有同样的结构（那边是 `result_` 存类型）。**这类"用成员变量传返回值"的代码，读的时候要特别注意取值时机**。

## 2. 值的表示：一切皆 `i8*`

### 2.1 决策与它的理由

| Cool 值 | LLVM 表示 |
|---|---|
| 任何值 | `i8*`（指向堆对象） |
| `Int` | `%Int = type { i8*, i32 }`（元信息 + 值） |
| `Bool` | `%Bool = type { i8*, i32 }` |
| `String` | `%String = type { i8*, i32, i8* }`（元信息 + 长度 + 字符指针） |
| 用户类 `C` | `%C = type { i8*, i8*, ... }`（元信息 + 各属性） |
| `void` | `null` |

**理由不是"简单"，是 Cool 的类型系统逼出来的**。Cool 里 `Int ≤ Object`，所以这个程序必须能编译：

```cool
let o : Object <- 5 in o.type_name()
```

`o` 的静态类型是 `Object`，运行时装的是 `Int`。如果 `Int` 用裸 `i32` 表示、对象用指针表示，那么 `o` 这个变量的**宽度和含义就随运行时类型变化**，`type_name()` 也无从下手。统一成"指向带元信息的堆对象的指针"后，`o.type_name()` 和任何对象调用**走完全相同的代码**（§4.1）。

这就是 `08` §6 那个"装箱"的真正动机：**子类型多态要求一致的值表示**。

**代价也是实测过的**（`08` §6）：`%Int` 占 16 字节（8 元信息 + 4 值 + 4 填充）装 4 字节数据，且每次算术都要新分配。§7 会量化这个代价，并给出一个让 LLVM 替我们回收一部分的办法。

### 2.2 拆箱 / 装箱：四个小函数

算术要在 `i32` 上做，值却是 `i8*`，所以每个算术运算的形状固定是**拆箱 → 算 → 装箱**：

```cpp
// codegen.cpp:151  i8* -> i32
std::string CodeGen::unboxInt(const std::string& v) {
  std::string p = fresh(); emit(p + " = bitcast i8* " + v + " to %Int*");
  std::string f = fresh(); emit(f + " = getelementptr %Int, %Int* " + p + ", i32 0, i32 1");
  std::string r = fresh(); emit(r + " = load i32, i32* " + f);
  return r;
}
```

三条指令：`bitcast`（重新解释指针类型，不生成机器码）、`getelementptr`（算字段地址，也常常不生成机器码）、`load`（真的访存）。**GEP 的两个下标含义不同**——`i32 0` 是"第 0 个 `%Int` 结构"（指针当数组用），`i32 1` 是"结构里第 1 个字段"。这是 LLVM 新手最常错的地方：`getelementptr %Int, %Int* p, i32 1` 不是"取字段 1"，而是"跳到下一个 `%Int` 对象"。

装箱对称地做：`cool_alloc(16)` → 存元信息指针 → 存值（`codegen.cpp:169`）。

`boxBool` 上方那行注释值得单独看（`codegen.cpp:178`）：

```cpp
// 装箱为 Bool 对象：标签必须是 @class_Bool，否则 type_name()/case 会把 Bool 误认成 Int
```

因为 `%Int` 和 `%Bool` **布局完全相同**（都是 `{i8*, i32}`），区分它们的**唯一**东西就是元信息指针。布局相同却必须区分——这正是 `08` §5 用整数 class tag 做 `case` 分派的前提。**这条注释记录的是一个"布局不区分类型，元信息才区分"的事实，不是一句随手提醒。**

## 3. 简单构造：直接兑现约定

### 3.1 字面量：不发指令

```cpp
// codegen.cpp:205
void CodeGen::visit(const IntConst& e)    { result_ = intConst(e.value); }
void CodeGen::visit(const StringConst& e) { result_ = strConst(e.value); }
void CodeGen::visit(const BoolConst& e) {
  result_ = e.value ? "bitcast (%Bool* @bool_true to i8*)" : "bitcast (%Bool* @bool_false to i8*)";
}
void CodeGen::visit(const NoExpr&) { result_ = "null"; }
```

`intConst`（`codegen.cpp:116`）做两件事：**去重**（同一个数只生成一个全局常量）和**延迟发射**（攒进 `globals_`，最后统一贴到模块末尾，因为 LLVM 不允许全局定义出现在函数体里）。

`bool_true`/`bool_false` 是**唯一的两个** Bool 对象（在 prelude 里定义），所以 `true` 不分配内存。但 §2.2 那个 `boxBool` 每次比较都会新分配一个——**同一个语言概念，两条路径的开销差一个堆分配**。§7 的练习会让你去掉这个不一致。

### 3.2 变量读取：作用域链 → alloca

```cpp
// codegen.cpp:212
void CodeGen::visit(const Object& e) {
  for (auto it = scopes_.rbegin(); it != scopes_.rend(); ++it) {   // 从内向外
    auto f = it->find(e.name);
    if (f != it->end()) {
      std::string r = fresh(); emit(r + " = load i8*, i8** " + f->second);
      result_ = r; return;
    }
  }
  // 没找到 → 一定是属性（typechecker 保证）
  std::string self = fresh(); emit(self + " = load i8*, i8** " + selfSlot());
  ...
}
```

**注意 `scopes_` 里存的是什么**：不是值，是 **alloca 的名字**（`codegen.h:46` 的注释写着"变量名 → alloca 名"）。这是 `07` §4 那个决策的落地——我们**不生成 φ 来处理变量赋值**，而是让每个变量住在一个栈槽里，读就 `load`、写就 `store`，把"构造 SSA"整件事交给 LLVM 的 `mem2reg`。

`05a` 篇的符号表在这里第二次出现，但装的东西变了：typechecker 的作用域栈装**类型**，codegen 的装**存储位置**。同一个数据结构、同一套 `push/pop` 规则，服务两个完全不同的目的——**作用域规则是语言的性质，不是某个阶段的性质**。

两级查找失败就当属性处理，靠的是 typechecker 已经拒绝了未声明变量。**这是一个跨阶段契约**：codegen 里没有任何 `error` 分支，它的正确性建立在前一阶段的完备性上。`06b` §8.3 那个 bug 说明这种契约并不总是成立。

### 3.3 `Block` 和 `Let`：约定的两个干净示例

```cpp
// codegen.cpp:318
void CodeGen::visit(const Block& e) {
  std::string r = "null";
  for (auto& x : e.exprs) r = codegenExpr(*x);
  result_ = r;               // 块的值 = 最后一个表达式的值
}
```

四行就是 `{ e1; e2; ... en }` 的全部语义。前 n-1 个表达式的返回值被**丢掉**，但指令已经发出去了——**副作用留下，值不要**。这与 `06b` §1.3 讲的"`typeOf` 必须访问每个结点即使不要它的类型"是同一个模式的两次出现。

```cpp
// codegen.cpp:324
void CodeGen::visit(const Let& e) {
  scopes_.push_back({});
  for (auto& b : e.bindings) {
    std::string slot = fresh(); emit(slot + " = alloca i8*");
    std::string val = b.init ? codegenExpr(*b.init) : defaultFor(b.type);
    emit("store i8* " + val + ", i8** " + slot);
    scopes_.back()[b.name] = slot;      // 注册在"绑定完之后"
  }
  result_ = codegenExpr(*e.body);
  scopes_.pop_back();
}
```

**`scopes_.back()[b.name] = slot` 这一行的位置就是 `let` 的作用域规则**。它在 `codegenExpr(*b.init)` **之后**，所以初始化式看不见自己正在绑定的变量。`06a` 用推导规则说明了为什么（`let x <- x` 里的 `x` 指外层那个），这里是同一条规则的第二种写法：**规则的位置感在实现里表现为一行赋值的先后**。

而多个绑定共享**同一个** scope（只 `push` 一次），所以 `let a <- 1, b <- a in ...` 里的 `b` 能看见 `a`——因为 `a` 在处理 `b` 之前已经注册了。**顺序注册天然实现了"从左到右逐个可见"。**

## 4. 方法调用：`08` 的 vtable 蓝图落地

### 4.1 动态分派 = 三次间接寻址

```cpp
// codegen.cpp:251
int idx = methodIndex_.at(e.method);       // 编译期就定了槽号
std::string tag  = fresh(); emit(tag  + " = load i8*, i8** " + recv);              // ① 对象 → 元信息
std::string meta = fresh(); emit(meta + " = bitcast i8* " + tag + " to %class_meta_t*");
std::string vtf  = fresh(); emit(vtf  + " = getelementptr %class_meta_t, %class_meta_t* " + meta + ", i32 0, i32 1");
std::string vtp  = fresh(); emit(vtp  + " = load i8**, i8*** " + vtf);             // ② 元信息 → vtable
std::string slot = fresh(); emit(slot + " = getelementptr i8*, i8** " + vtp + ", i32 " + std::to_string(idx));
std::string fnp  = fresh(); emit(fnp  + " = load i8*, i8** " + slot);              // ③ vtable → 函数指针
std::string fn   = fresh(); emit(fn   + " = bitcast i8* " + fnp + " to " + funcType((int)args.size()));
emit(r + " = call i8* " + fn + "(" + ca + ")");
```

真实生成的 IR（`/tmp/demo.ll`，`Main.f` 里递归调用 `f`）：

```llvm
%t53 = load i8*, i8** %t40                                  ; ① 取元信息指针
%t54 = bitcast i8* %t53 to %class_meta_t*
%t55 = getelementptr %class_meta_t, %class_meta_t* %t54, i32 0, i32 1
%t56 = load i8**, i8*** %t55                                ; ② 取 vtable
%t57 = getelementptr i8*, i8** %t56, i32 10                 ;    槽号 10（编译期常量）
%t58 = load i8*, i8** %t57                                  ; ③ 取函数指针
%t59 = bitcast i8* %t58 to i8* (i8*, i8*)*
%t60 = call i8* %t59(i8* %t40, i8* %t49)
```

**关键是 `i32 10` 这个常量**。它在编译期定死，运行时**不查名字、不比较字符串**——这是 `08` §4 全局槽号分配的回报。实测 `@vtable_Main` 确实是 12 个槽，`Main.f` 在第 10 个：

```llvm
@vtable_Main = constant [12 x i8*] [
  @Object.copy, @Object.type_name, @Object.abort,          ; 槽 0-2
  @IO.in_string, @IO.out_string, @IO.in_int, @IO.out_int,  ; 槽 3-6
  i8* null, i8* null, i8* null,                            ; 槽 7-9 ← 填充
  @Main.f,                                                 ; 槽 10
  @Main.main ]                                             ; 槽 11
```

**那三个 `null` 就是 `08` §4 说的代价**：槽号全局编号，`String.length/concat/substr` 占了 7-9，而 `Main` 不是 `String`，那三格只能空着。用空间换"重写自动复用槽号"的简单性。

### 4.2 静态分派：为什么不能拼函数名

```cpp
// codegen.cpp:270 —— 这段注释是一个已修 bug 的墓碑
// 不能用 "@" + e.type + "." + e.method 拼函数名：若 e.type 只是继承了该方法而没有
// 定义它，那个函数并不存在（会生成 call @B.f 而只有 @A.f 被定义）。
// methods_ 已按继承链解析好，查表即可（存在性由 typechecker 保证）。
const MethodRef& ref = methods_.at(e.type).at(e.method);
emit(r + " = call i8* " + ref.funcName + "(" + ca + ")");
```

`e@B.f()` 里 `B` 继承了 `A.f` 而没有重写时，`@B.f` 这个函数**根本没被 emit**（`generate()` 只为每个类**自己定义的**方法发函数，`codegen.cpp:735`）。`methods_` 在 `buildClassInfo` 里已经按继承链复制好了（`codegen.cpp:81`），查表得到的是 `@A.f`——**正确答案一直在表里，错误做法是绕过表去拼字符串**。

这是 `08` §8.1 那个 bug 的修复（`08` 篇记录了发现过程）。一句话总结：**凡是"名字"可以由查表得到，就不要用字符串拼接重新推导它**——拼接复制了一份"名字规则"，而它和真实规则会分叉。

静态分派只有**一次** `call`，没有那三次间接寻址。这就是 `e@T.f()` 的性质：放弃动态派发换直接调用。

## 5. 控制流：φ 和基本块（本篇的核心难点）

### 5.1 `if` 需要 φ，是被 SSA 逼的

`if` 是表达式，所以它**有值**，而值来自两个分支之一。`07` §3 讲过 SSA 的约束：一个名字只能定义一次，所以不能让两个分支都往同一个名字里写。汇合处必须用 φ（`07` §3.4）。

```cpp
// codegen.cpp:285
void CodeGen::visit(const If& e) {
  std::string ci = unboxBool(codegenExpr(*e.cond));
  std::string b = fresh(); emit(b + " = icmp ne i32 " + ci + ", 0");
  std::string thenL = freshLabel(), elseL = freshLabel(), endL = freshLabel();
  emit("br i1 " + b + ", label %" + thenL + ", label %" + elseL);
  emitLabel(thenL);
  std::string tv = codegenExpr(*e.then_);
  std::string thenExit = currentBlock_;   // then 支可能自己开了新块
  emit("br label %" + endL);
  emitLabel(elseL);
  std::string ev = codegenExpr(*e.else_);
  std::string elseExit = currentBlock_;   // else 支同理
  emit("br label %" + endL);
  emitLabel(endL);
  std::string phi = fresh();
  emit(phi + " = phi i8* [ " + tv + ", %" + thenExit + " ], [ " + ev + ", %" + elseExit + " ]");
  result_ = phi;
}
```

**`thenExit`/`elseExit` 这两行是本篇最重要的两行代码**，§6.1 讲它们为什么必须存在。先看它生成的真实 IR（`Main.f` 的 `if n <= 1 then 1 else n * f(n-1) fi`）：

```llvm
  br i1 %t35, label %bb0, label %bb1
bb0:                                   ; then 支：常量 1，不需要任何指令
  br label %bb2
bb1:                                   ; else 支：算 n * f(n-1)，30 条指令
  ...
  br label %bb2
bb2:
  %t69 = phi i8* [ @int_1, %bb0 ], [ %t65, %bb1 ]
  ret i8* %t69
```

**`bb0` 是个空块**——只有一条 `br`。因为 `then` 分支是常量 `1`，`codegenExpr` 没发任何指令，直接返回了操作数 `@int_1`。这正是 §1.2 那个"返回操作数而非寄存器"的设计在起作用：φ 的入边可以直接写常量。（`llvm-dis` 显示 `-O2` 会把这个空块并掉。）

### 5.2 `while` 不需要自己的 φ

```cpp
// codegen.cpp:304
void CodeGen::visit(const While& e) {
  std::string condL = freshLabel(), bodyL = freshLabel(), endL = freshLabel();
  emit("br label %" + condL);
  emitLabel(condL);
  std::string ci = unboxBool(codegenExpr(*e.cond));
  std::string b = fresh(); emit(b + " = icmp ne i32 " + ci + ", 0");
  emit("br i1 " + b + ", label %" + bodyL + ", label %" + endL);
  emitLabel(bodyL);
  codegenExpr(*e.body);        // 返回值丢掉
  emit("br label %" + condL);  // 回边
  emitLabel(endL);
  result_ = "null";            // Cool: while 的值恒为 void
}
```

**为什么循环没有 φ**？循环里的变量确实会在回边上汇合（`i` 每轮都变），按 SSA 本该有 φ。但我们的变量住在 alloca 里（§3.2），`i <- i + 1` 编译成 `store`，**不产生新名字**，所以没有需要汇合的 SSA 值。φ 由 `mem2reg` 事后插入（`07` §4 实测过：`mem2reg` 后 alloca 归零、φ 出现）。

**这是"alloca + mem2reg"策略最直接的回报**：手写 codegen 完全不碰支配边界（dominance frontier）这套理论，φ 的插入位置由 LLVM 算。`07` §4.3 用 clang 的控制实验确认过这就是工业做法。

而 `result_ = "null"` 兑现了手册 `:594` 那条"the type of the entire loop is always Object"（`06a` §5 讲过它背后是"Cool 没有 ⊥ 类型"）：**规范说它的值无意义，实现就给一个无意义的值**。

### 5.3 `case`：φ 的入边数不固定

`case` 有 n 个分支，所以 φ 有 n 个入边，用一个 `results` 向量攒起来（`codegen.cpp:344`）：

```cpp
std::string r = codegenExpr(*br.body);
scopes_.pop_back();
std::string bodyExit = currentBlock_;   // 分支体可能自己开了新块
emit("br label %" + endL);
results.push_back({bodyExit, r});       // (前驱块, 值)
```

分派方式是 `08` §5 那套整数 tag 比较：取出对象的 class ID，对每个分支类型 `T` 生成 `id == ID(T1) || id == ID(T2) || ...`，其中 `T1..Tk` = `descendants_[T]`（`T` 及其所有后代）。**后代集合在 `buildClassInfo` 里预计算**（`codegen.cpp:54-58`），所以运行时只有整数比较，没有继承链遍历。

两处细节值得注意：

**① 检查链是"链"而不是"跳转表"。** 每个分支生成 `br i1 m, label %body, label %next`，`next` 成为下一个分支的检查块（`checkL = nextL`）。所以匹配第 k 个分支要做 k 次检查——**线性**。真实编译器会用跳转表（switch on class ID）做到 O(1)，我们这里是 O(分支数)。

**② 全不匹配 → `cool_abort()` + `unreachable`**（`codegen.cpp:372`）。这是 Cool 手册要求的运行时错误。`unreachable` 告诉 LLVM 这里不会返回，**它不是注释，是优化器能用的信息**。

`case` 还有一个 `08` §8.2 记录的、**尚未修**的缺陷：分支按**源码顺序**检查，而手册 `:319` 要求选**最接近的类型**（least type）。`class B inherits A` 时 `case x of a : A => ...; b : B => ...; esac` 传入 `B` 对象会错选 `A` 分支。它是 `08` §9.3 留给你的题。

## 6. 三个真实缺陷（全部实测，两个已修）

> 这一节是本篇最该细读的部分。三个 bug 有一个共同形状：**"返回一个操作数"这条约定在某个边界上没兜住**。

### 6.1 已修：分支体含控制流 → φ 前驱写错

**症状**。嵌套 `if` 生成的 IR 被 `llvm-as` 拒绝。老笔记 §3.3 展示的就是有 bug 的版本：

```cpp
emit("then:");  std::string tv = codegenExpr(*e.then_);  emit("br label %end");
emit(phi + " = phi i8* [ " + tv + ", %then ], [ " + ev + ", %else ]");   // ← 错
```

**为什么错**。φ 的入边必须是"控制流**真正流出**的那个块"（`07` §3.4 第 2 条规则）。上面的代码用了"**进入**分支时的标签"。当 `then` 分支只是字面量时两者相同；但当 `then` 分支里还有一个 `if`/`while`/`case` 时，**子表达式自己开了新块**，控制流离开 `then` 分支时早已不在 `%then` 块里了。

实测确认这个差异是真的：一个 `if` 的分支里放 `while`，进入时是 `bb0`，流出时是 `bb5`。

**修法**。把"当前在哪个块"这个不变式**集中到一个函数**（`codegen.h:58`）：

```cpp
void emitLabel(const std::string& l) { emit(l + ":"); currentBlock_ = l; }
```

然后所有开块的地方走 `emitLabel`，读前驱时用 `currentBlock_`（§5.1 的 `thenExit`/`elseExit`）。

**为什么用一个 helper 而不是在十处手工维护 `currentBlock_`**：因为不变式"`currentBlock_` 总等于最后发出的标签"只要有**一处**漏掉就失效，而失效表现为远处的 φ 前驱错。集中到一个函数后，这个不变式**在语法上不可能被违反**——你无法发射一个标签而不更新它。这是设计层面的收获，比修好这个 bug 更重要。

注意 `visit(While)` 和函数入口 `entry` 也必须改。`while` 自己没有 φ，但它**开了新块**，外层的 `if` 要读 `currentBlock_`，所以它必须维护这个变量。**不变式是全局的，不能只在"需要它的地方"维护。**

**验证**。修后 4 个原本非法的用例（嵌套 if / if 含 while / case 含 if / if 分支产生 φ）全部 `IR OK` 且输出正确，12 个测试无回归。

### 6.2 已修（本次新发现）：属性初始化式里的 `self` 指向错误的对象

这是三个里**最隐蔽**的一个：它不报错、IR 合法、退出码 0，**只是算错**。

**发现过程**。我在核对 `visit(Object)` 的属性路径时注意到它写死了 `%self`：

```cpp
std::string self = fresh(); emit(self + " = load i8*, i8** %self");   // ← 写死
```

而 `allocateAndInit` 把 `self` 绑到一个**新建的 alloca**（`codegen.cpp:454`）。两者不一致，于是构造了探针——**一个属性的初始化式读另一个属性**：

```cool
class Main inherits IO {
  main() : Object { (new A).show() };
};
class A inherits IO {
  x : Int <- 5;
  y : Int <- x;        -- 读兄弟属性
  show() : Object { out_int(y) };
};
```

**结果：输出 `1879076176`（垃圾值），期望 `5`。** IR 完全合法，编译器退出码 0。

**根因**，看生成的 `Main.main`：

```llvm
define i8* @Main.main(i8* %self_arg) {
entry:
%self = alloca i8*                     ; ← 外层方法的 self，指向 Main 对象
store i8* %self_arg, i8** %self
%t0 = call i8* @cool_alloc(i32 24)     ; new A
...
%t3 = alloca i8*                       ; ← allocateAndInit 为新 A 建的 self 槽
store i8* %t0, i8** %t3                ;    正确地存了 A 对象
%t4 = getelementptr %A, %A* %t1, i32 0, i32 1
store i8* bitcast (%Int* @int_5 to i8*), i8** %t4      ; x <- 5 ✓
%t5 = load i8*, i8** %self             ; ← 读了 Main 的 self！应该读 %t3
%t6 = bitcast i8* %t5 to %A*           ;    把 Main 对象当 A 用
%t7 = getelementptr %A, %A* %t6, i32 0, i32 1
%t8 = load i8*, i8** %t7               ;    读到越界垃圾（Main 只有 8 字节）
```

`%t3` 是对的，代码却去读 `%self`。**属性初始化式是在 `allocateAndInit` 里内联展开的**（§6.3），所以它运行在外层方法的函数体里，那里的 `%self` 指向**外层**对象。

同一个 bug 还有一个更容易发现的形态——当 `new` 发生在 `@main()` 里时，根本没有 `%self`：

```cool
class Main inherits IO { x : Int <- 5;  y : Int <- x;  main() : Object { out_int(y) }; };
```
```
llvm-as: error: use of undefined value '%self'
```

**为什么两种形态严重性差很多**：后者被 `llvm-as` 当场抓住；前者生成合法 IR、静默算错。**静默算错的 bug 比崩溃的 bug 危险**——这也是为什么 `08` §8 那条"把 `llvm-as` 加进 CI"的建议不够，它只能抓住后者。

**修法**。`self` 本来就在作用域链里（`allocateAndInit` 和 `emitMethod` 都注册了），所以和 §4.2 同一个教训：**查表，不要写死**。

```cpp
// codegen.h —— 当前 self 所在的槽
std::string selfSlot() const {
  for (auto it = scopes_.rbegin(); it != scopes_.rend(); ++it) {
    auto f = it->find("self");
    if (f != it->end()) return f->second;
  }
  return "%self";
}
```

两处调用点（`codegen.cpp:222` 读属性、`:240` 写属性）改成 `selfSlot()`。

**验证**：两个探针都输出 `5`；12 个测试全部 `IR OK`，输出与 `README.md` 逐项一致。

**为什么 12 个测试一个都没抓到它**：没有任何一个测试让属性初始化式去读另一个属性。这是 `06b`/`08` 反复出现的那条教训的**第四个实例**——**测试覆盖的是实现者想到的情况，而不是规范允许的情况**。

### 6.3 未修（根因已定案）：属性初始化环 → codegen 栈溢出

`06b` §8.3 记录了症状并把根因标为"推断"。本篇用 gdb 定案。

**症状**：属性初始化图上有环、且环从被实例化的类可达时，`coolc.exe` 被信号终止（`EXIT=127`），**耗时 62ms**。

```cool
class A { v : A <- new A; };
class Main { main() : Object { new A }; };
```

**先看那个耗时。** 62 毫秒不是"挂死"，是**崩溃**——一个真转圈的程序不会在 62ms 内消失。gdb 给出答案：`SIGSEGV`，栈深 **4231 帧**（最底是 `main`），递归环**周期恰好 4 帧**：

```
allocateAndInit(A)   codegen.cpp:458   ← 为属性 v 生成初始化代码
  └ codegenExpr      codegen.cpp:203
      └ New::accept  ast.h:105
          └ visit(New) codegen.cpp:385
              └ allocateAndInit(A)     ← 回到起点
```

环由 `visit(New)` 那**一行**闭合：

```cpp
void CodeGen::visit(const New& e) {
  result_ = allocateAndInit(e.type == "SELF_TYPE" ? currentClass_ : e.type);
}
```

**根因一句话**：属性初始化式是**内联展开**的（`allocateAndInit` 对每个属性调 `codegenExpr(*slot.init)`，`codegen.cpp:458`），于是 `new A` 要求先展开 `A.v` 的初始化式 `new A`，无穷递归。4231 ÷ 4 ≈ **1057 层**就打爆了默认栈。

**触发边界**（5 个探针实测）：

| 属性 | `Main` 里 | 结果 |
|---|---|---|
| `v : A <- new A` | `new A` | **EXIT=127**，62ms |
| `v : SELF_TYPE <- new SELF_TYPE` | `new A` | **EXIT=127**，65ms |
| `A.b : B <- new B`；`B.a : A <- new A` | `new A` | **EXIT=127**，61ms |
| `v : A <- new A` | `1`（不构造 `A`） | EXIT=0 |
| `v : A`（**无初始化式**） | `new A` | EXIT=0 |

三条结论：崩溃要求初始化式里真的有 `new`（`v : A` 完全合法）；要求那个类真的被构造（环不可达就没事）；**不限于自引用**（`A→B→A` 一样崩）。准确的触发条件是"**属性初始化图上有环，且从某个被实例化的类可达**"。

**"栈溢出"和"内存耗尽"的区别很重要**：如果是内存耗尽，加内存就能缓解；栈溢出意味着**递归深度**是硬约束，对策只能是结构性的——静态检测环并拒绝、给展开加深度上限、或者**根本不内联展开**（把属性初始化编译成一个 `init` 函数，靠调用复用代码）。**最后一种是主流做法**，也顺手解决了 §6.2：有了独立的 `init` 函数，`self` 就是它的形参，不存在"读到外层 self"的可能。

**这个 bug 暴露的是跨阶段契约缺口**：typechecker 通过 ≠ codegen 能处理完。目前没有任何机制保证这一点。留作 §8.2。

### 6.4 一个"老笔记记错了"的定案：常量前缀

老笔记 §6 记录过一个坑：常量的 `result_` 多带 `i8*` 前缀，产生 `bitcast i8* i8* bitcast (...)`，被 LLVM 拒绝，"修复：常量一律返回裸值"。

**这个修复没有完全做到，而且当前代码里就有痕迹。** `intConst` 首次调用返回 `bitcast (%Int* @int_1 to i8*)`，但**缓存里存的是裸的全局名** `@int_1`（`codegen.cpp:122` 存 `g`，而 `return` 的是拼好的 bitcast）。所以同一个常量**第一次和后续用法形态不同**，实测在一个函数里三种形态都出现了：

```llvm
%t23 = bitcast i8* bitcast (%Int* @int_1 to i8*) to %Int*   ; 首次：嵌套 bitcast
%t45 = bitcast i8* @int_1 to %Int*                          ; 后续：裸名
%t69 = phi i8* [ @int_1, %bb0 ], [ %t65, %bb1 ]             ; φ 入边：裸名
```

**为什么现在没出事**：LLVM 21 用**不透明指针**（opaque pointer），`llvm-dis` 显示两种形态都退化成 `bitcast ptr @int_1 to ptr`——一个 no-op。所以 `llvm-as` 接受，输出正确（实测 `f(3)=6`）。

**但这是"恰好没事"，不是"对"**：形态不一致靠目标平台的特性掩盖着。在旧版 LLVM（有类型指针）上，`bitcast i8* @int_1` 里 `@int_1` 的类型是 `%Int*` 而非 `i8*`，就是类型错误。**依赖"当前工具链恰好接受"的代码，会在工具链升级时集体失效**——这和 `06b` §8.2 那个"测试和实现共享同一个错误假设"是同一类问题：**不是错误被修好了，是错误暂时不可见**。

## 7. 代价：装箱到底花了多少，以及让 LLVM 帮忙回收

### 7.1 先量一下

`Main.f` 是 `if n <= 1 then 1 else n * f(n - 1) fi`，一行 Cool。实测生成的 IR：

| 指标 | 未优化 | `-O2` |
|---|---|---|
| `Main.f` 指令数 | 65 | 31 |
| `Main.f` 里 `cool_alloc` 调用 | 3 | **3** |

指令数砍了一半，**堆分配一个都没少**。三个分配是：`n<=1` 的结果装箱成 Bool、`n-1` 装箱成 Int、`n*f(n-1)` 装箱成 Int。

**其中第一个是纯浪费**：那个 Bool 对象装完立刻被 `unboxBool` 拆开喂给 `icmp ne`（§5.1 的 `if` 先 `codegenExpr(*e.cond)` 得到 `i8*`，再拆箱）。**装箱又拆箱，中间对象没有任何其他用途**，但 `-O2` 不敢删它。

### 7.2 为什么 `-O2` 不敢删

因为 IR 里 `cool_alloc` 只有一行声明：

```llvm
declare i8* @cool_alloc(i32)
```

LLVM 对它**一无所知**——可能有副作用（写全局、做 IO），所以删掉这个调用是不安全的。

**实验**：把它声明成一个"分配器"，告诉 LLVM 它无副作用、返回不别名的新内存：

```llvm
declare noalias i8* @cool_alloc(i32) allockind("alloc,uninitialized")
    mustprogress nounwind willreturn memory(argmem: readwrite, inaccessiblemem: readwrite)
```

只改这**一行声明**，其余 IR 一字不动，重跑 `-O2`：

| | `Main.f` 里的 `cool_alloc` |
|---|---|
| 原声明 + `-O2` | 3 |
| 加属性 + `-O2` | **2** |

那个死掉的 Bool 装箱被删了，且输出仍然正确（`6`）。

**这个实验的意义远超省一次 malloc**：它说明**优化不只是"跑 pass"，还包括"把你知道的事实告诉优化器"**。同一份 IR、同一个 `-O2`，一行声明的差别就决定了一次堆分配删不删。`10` 篇讲数据流分析时会看到这一点的一般形式：**分析的精度上限由它能假设的前提决定**。

> 顺便一个测量陷阱：整个模块的 `cool_alloc` 调用点在 `-O2` 后从 10 **涨到** 13，看着像优化把事情变糟了。其实是**内联**把调用点复制了（`@main` 里从 1 变成 4）。**统计全模块的指令数会被内联干扰，要按函数看。**

## 11. 本文你掌握了什么 / 易错点 / 下一步

**掌握**：树→序列的表示错配和它逼出的三个决策（后序、返回操作数、单调计数器）；装箱的动机是子类型多态要求一致表示；GEP 两个下标的区别；作用域栈存储位置 vs 存类型；动态分派三次间接寻址与那三个 `null` 槽的代价；`if` 的 φ、`while` 为什么不需要 φ、`case` 的线性检查链；三个实测缺陷的根因与修法；装箱代价的量化和"用声明属性换优化能力"。

**易错点**：

1. **φ 的入边是"流出块"不是"进入块"**（§6.1）。分支体只要含控制流就会暴露。
2. **`self` 不能写死 `%self`**（§6.2）。属性初始化式运行在外层函数体里。这个 bug **不报错、只算错**。
3. **GEP 的第一个下标是"第几个结构"**，字段下标是第二个。`getelementptr %Int, %Int* p, i32 1` 跳到了下一个对象。
4. **属性字段从 1 开始**（0 是元信息指针），所以 GEP 下标 = 属性序号 + 1（`codegen.cpp:461`）。
5. `%Int` 和 `%Bool` **布局相同**，只有元信息指针能区分。`boxBool` 存错标签会让 `type_name()`/`case` 全错（`codegen.cpp:178`）。
6. **全局常量必须在模块级**，所以 `globals_` 攒着最后贴（`codegen.cpp:739`）。
7. **`-O2` 删不掉无用的堆分配**，除非你把 `cool_alloc` 声明成分配器（§7.2）。
8. **统计优化效果要按函数看**，全模块计数会被内联干扰（§7.2 末）。

**当前状态**：12 个测试全部 `llvm-as` 通过、链接成功、输出与 `README.md` 一致（`type_error.cl` 按预期被类型检查拒绝）。§6.1、§6.2 已修并验证；§6.3（初始化环栈溢出）、§5.3 末（`case` least type）、§6.4（常量形态不一致）是已知未修项，都留成了动手题。
