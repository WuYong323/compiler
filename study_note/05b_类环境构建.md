## 精炼段

`05a` 处理的名字全都服从一条规律：**先声明后使用**。局部变量、形参、属性都满足它，所以我们能一趟搞定——`visit(Object)` 里 `lookup` 的同一瞬间就拿到类型。

类名不服从。我实测确认了这件事：

```cool
class Main inherits IO { main() : Object { (new Later).v() }; };
class Later { v() : Int { 7 }; };      -- 用在前，定义在后
```

这个程序**合法**（实测通过）。于是整个编译器的结构被迫改变：你不可能在遍历 `Main.main` 的时候查 `Later` 的方法表，因为那时它还没被读到。**必须先扫一趟，把所有类登记完，再开始检查表达式。**

这就是"多趟编译（multi-pass compilation）"的最小、最纯的实例。本篇从这一个事实出发，把 `buildEnvironments` 的每一项检查都推出来——不是"手册要求所以检查"，而是"不检查的话，具体哪一行代码会具体怎么坏掉"。最关键的是 §3：我把 `conforms` 单独抠出来编译运行，证明了继承环会让它跑 2000 万步不终止。你会看到"语义规则"和"实现必需"是两件事，而后者才是设计的真正驱动力。

§5 处理 `methodsOf`/`attrsOf` 的惰性递归——一个精巧但有代价的设计，代价是一个实测到的**漏报**。§7 交代三个实测缺陷，其中一个能让编译器崩溃，而我把崩溃的根因定位到了确切行号。

## 0. 本篇要回答的七个问题

1. 为什么类环境必须**单独一趟**？能不能边遍历表达式边建？（拿一个实测程序说话）
2. 六项检查里，哪些是"语义要求"，哪些是"实现不做就会坏"？这两类的地位一样吗？
3. 继承环如果不查，具体是哪个函数、哪一行会怎么坏？（不要答"逻辑错误"）
4. `methodsOf` 为什么是惰性 + 记忆化的？它比"一趟建完所有类"好在哪、差在哪？

6. 属性为什么**禁止**重定义，而方法**允许**重写？同一个继承机制，两条相反的规则，理由是什么？

## 1. 逼出多趟结构的那一个事实

### 1.1 实测：类可以前向引用

两个探针。第一个，使用在定义之前：

```cool
class Main inherits IO { main() : Object { (new Later).v() }; };
class Later { v() : Int { 7 }; };
```

```
$ ./coolc.exe fw1.cl -o o.ll
wrote o.ll (10683 bytes)          ← 合法
```

第二个，**继承**在定义之前：

```cool
class A inherits B { };
class B { };
class Main { main() : Object { new A }; };
```

```
$ ./coolc.exe fw2.cl -o o.ll
wrote o.ll (10346 bytes)          ← 合法
```

手册第 160 行给了依据：

> **All class names are globally visible.**

"globally visible" 就是"没有先后"。类名不在任何作用域栈里——它们在一个**平坦的全局命名空间**。

### 1.2 这一个事实如何决定编译器结构

假设我们不分趟，直接在遍历表达式时按需查类。走一遍 `fw1.cl`：

```
遍历 Main.main 的 body
  → visit(Dispatch)：receiver 是 new Later，类型 Later
  → 要查 Later 有没有方法 v
  → classMap_ 里有 Later 吗？
      没有。因为 parser 是顺序建树的，Later 的 ClassDef 在 Main 后面，
      我们还没走到它。
  → 报错 "class Later not defined"     ← 错！程序是合法的
```

**唯一的出路是分趟**：先把 `prog_.classes` 完整走一遍，把每个类登记进 `classMap_`/`parentMap_`，然后才开始检查表达式。看 `check()`（`typechecker.cpp:421`）：

```cpp
bool TypeChecker::check() {
  buildEnvironments();                                    // ← 第 1 趟：登记所有类
  if (errorCount_ > 0) return false;                      // ← 闸门
  if (classMap_.count("Main")) { /* main 方法检查 */ }
  for (auto& cls : prog_.classes) checkClass(*cls);        // ← 第 2 趟：检查表达式
  return errorCount_ == 0;
}
```

两趟，中间一道闸门。**整篇文档就是在讲第 1 趟。**

### 1.3 推广：前向引用 → pass 数量

`05a` §6.1 提过这条规律，这里把它讲完整。**语言里每一处允许前向引用的地方，都在编译器里逼出一趟额外的扫描**（或者一个延迟机制）。对照表：

| 语言 | 允许前向引用吗 | 编译器的应对 |
|---|---|---|
| **C**（函数） | 不允许 —— 所以要写函数原型 | 一趟够（原型把"声明"提前了，这是**让程序员替编译器分趟**） |
| **C++**（类成员） | 允许 —— 成员函数体里能用后面声明的成员 | 成员函数体**延迟解析**（late parsing）：先记下 token 序列，类定义结束后再解析 |
| **Java**（类/成员） | 允许 | 多趟：先建符号表（`Enter`），再 attribute，再 flow |
| **Rust**（item） | 允许 | `rustc_resolve` 是独立的 pass，跑在类型检查之前 |
| **Cool**（类名） | 允许 | 本篇的 `buildEnvironments` |

**C 那一行最值得想**。`#include` 的头文件本质上就是"人工前向声明"。C++ 的模块（module）、Rust 的自动 item 可见性，都是在把这件事从程序员手里收回到编译器里。你写 `.h` 文件写的每一个原型，都是在替 1972 年的单趟编译器做 `buildEnvironments`。

> **给你的判断工具**：以后看到一门新语言，问"它允许哪些前向引用"，你就能大致猜出它的编译器有几趟、以及哪一趟最复杂。

## 2. 六项检查，逐条推出理由

`buildEnvironments()`（`:70`）从上到下五段，加上 `methodsOf`/`attrsOf` 里的检查，一共六类。**关键在于：它们的地位不一样。** 我把它们分成两栏：

| # | 检查 | 类别 | 不做的后果 |
|---|---|---|---|
| 1 | 内建类不可重定义 | **语义** | 程序含义错乱，但编译器不崩 |
| 2 | 类不可重复定义 | **语义** | 后定义的静默覆盖前者 |
| 3 | 父类必须存在；`Int/String/Bool` 不可继承 | **语义 + 实现** | 见 §2.3 |
| 4 | **继承图无环** | **实现必需** | `conforms` **死循环**（§3 实测） |
| 5 | `Main` 必须存在且有无参 `main` | **语义** | `09` codegen 找不到入口 |
| 6 | 重写签名一致 / 属性不可重定义 | **类型安全** | 见 §6 |

**这个分栏是本节的重点。** 教科书和 DeepSeek 那版笔记会把六项并列成一个 checklist，让你以为它们性质相同。它们不同：第 4 项如果漏掉，编译器会挂死；第 1 项漏掉，编译器照样跑完，只是编译出一个语义错误的程序。两种失效模式对应完全不同的严重性和修法。

### 2.1 检查 1、2：注册循环

```cpp
for (auto& c : prog_.classes) {
  if (c->name == "Object" || c->name == "IO" || c->name == "Int" ||
      c->name == "String" || c->name == "Bool") {
    error(c->line, "class '" + c->name + "' cannot be redefined");
    continue;                                              // ← :78，记住这个 continue
  }
  if (classMap_.count(c->name)) {
    error(c->line, "class '" + c->name + "' already defined");
    continue;                                              // ← :83
  }
  classMap_[c->name] = c.get();
  parentMap_[c->name] = c->parent.empty() ? "Object" : c->parent;   // :84
}
```

`:84` 那个三元表达式就是手册"不写 `inherits` 默认继承 `Object`"的实现。一行，值得注意的是它把"缺省"**归一化**掉了——之后所有代码都可以假设 `parentMap_` 里每个类都有父类，不必到处判空。

> **这是个通用技巧，叫 normalization（归一化）**：在入口处把所有变体统一成一种形式，后续代码就只需处理一种情况。`03c` §3.3 的 self-dispatch 合成 `Object("self")` 节点是同一招（把 `f(3)` 归一化成 `self.f(3)`，于是 `06`/`09` 只需要处理 Dispatch 一种形式）。编译器里到处是这个模式，它的一般名字是 **desugaring**。

那两个 `continue` 是 §7.1 那个崩溃的源头。先记着。

### 2.2 检查 3：父类合法性

```cpp
for (auto& kv : parentMap_) {
  const std::string& name = kv.first;
  const std::string& parent = kv.second;
  if (parent == "Int" || parent == "String" || parent == "Bool") {
    error(classMap_.at(name)->line, "... cannot inherit from basic class ...");
  } else if (parent != "Object" && parent != "IO" && !classMap_.count(parent)) {
    error(classMap_.at(name)->line, "... inherits from undefined class ...");
  }
}
```

**为什么这一段必须是独立的循环，不能合进 §2.1 那个循环？** 因为前向引用。`fw2.cl` 里 `A inherits B` 而 `B` 在后面——检查 `A` 的父类时 `B` 还没进 `classMap_`。所以"登记"和"检查父类"必须是**两个循环**。

这是"分趟"思想在函数内部的再一次应用：`buildEnvironments` 自己就是由五个顺序依赖的小趟组成的。看清这个结构，你就明白为什么编译器代码里到处是"一个 for 循环只干一件事"——不是风格洁癖，是依赖关系逼的。

**`Int/String/Bool` 不可继承的理由**（手册 §359、364、366）：这三个类的对象在运行时有**特殊表示**。`08` 篇会讲，Cool 的 `Int` 在 codegen 里通常直接是机器整数或带特殊布局的对象，不是通用对象布局。如果允许 `class MyInt inherits Int { extra : String; }`，那 `MyInt` 的对象要既是机器整数又带一个额外字段——布局无法兼容。**这条"语义规则"的真实来源是运行时表示的约束。** 语言设计和实现从来不是两回事。

实测：

```
$ ./coolc.exe z_undefparent.cl        # class A inherits Ghost
ERROR: line 1: class 'A' inherits from undefined class 'Ghost'
type checking failed
```

### 2.3 检查 5：`Main` 与 `main`

这项在 `check()`（`:421`）里而不在 `buildEnvironments`：

```cpp
if (!classMap_.count("Main")) error(0, "no 'Main' class defined");   // :103，在 buildEnvironments 末尾
...
if (classMap_.count("Main")) {                                       // :424，在 check 里
  const auto& menv = methodsOf("Main");
  auto it = menv.find("main");
  if (it == menv.end()) { error(0, "class 'Main' has no 'main' method"); return false; }
  if (!it->second.argTypes.empty()) { error(0, "'main' method must take no arguments"); return false; }
}
```

拆成两处是有理由的：类的存在性在第 1 趟就能判；但 `main` **方法**的存在性要等 `methodsOf` 能跑（它依赖完整的 `parentMap_` 和无环性），所以只能放在闸门之后。

注意 `error(0, ...)` 的行号是 **0**——因为"缺少 Main 类"这个错误**没有源码位置**。`03c` §1.3 讲 `line` 字段时说"报错需要它"，这里是反面：有些错误是关于**整个程序**的，没有对应行。真实编译器对这类错误的处理是打印文件名而不是行号（`error: no main function` 而非 `foo.c:0:`）。我们用 0，能跑但不优雅。

用 `methodsOf("Main")` 而不是直接翻 `Main` 的 features，意思是 **`main` 可以是继承来的**。实测：

```cool
class Base { main() : Object { 1 }; };
class Main inherits Base { };          -- Main 自己没有 main
```
```
$ ./coolc.exe s_main_inherited.cl -o o.ll
wrote o.ll (9811 bytes)               ← 通过，继承的 main 算
```

## 3. 继承环：为什么它是"实现必需"而不是"语义要求"

这一节是本篇最重要的地方。

### 3.1 先问：环有什么错？

```cool
class A inherits B { };
class B inherits A { };
```

直觉答案是"A 是 B 的子类，B 又是 A 的子类，逻辑上讲不通"。这个答案**不足以驱动设计**——它说明程序没意义，但没说明编译器会怎么坏。而后者才决定了这项检查必须放在**哪里**（闸门之前还是之后）。

看 `conforms`（`:172`）：

```cpp
bool TypeChecker::conforms(const std::string& a, const std::string& b) {
  if (a == b) return true;
  if (b == "SELF_TYPE") return false;
  std::string cur = (a == "SELF_TYPE") ? currentClass_ : a;
  for (;;) {                                    // ← 无条件循环
    if (cur == b) return true;
    if (cur == "Object") return false;          // ← 唯一的正常出口
    if (parentMap_.count(cur)) cur = parentMap_.at(cur);
    else if (cur == "IO" || cur == "Int" || cur == "String" || cur == "Bool") cur = "Object";
    else return false;
  }
}
```

这个 `for(;;)` 的终止性**完全依赖一个外部假设**：沿 `parentMap_` 往上走，有限步内必到 `Object`。这个假设成立的前提就是**无环**。

### 3.2 实测：它真的不终止

别推理，跑一遍。我把 `conforms` 原样抠出来，喂给它一个环，加一个步数计数器：

```cpp
std::unordered_map<std::string,std::string> parentMap_ = {{"A","B"},{"B","A"}};
long steps = 0;
bool conforms(const std::string& a, const std::string& b) {
  /* 与 typechecker.cpp:172 完全相同，只加了这一行： */
  for (;;) {
    if (++steps > 20000000) { std::cout << "ABORT: no termination after 20M steps\n"; return false; }
    if (cur == b) return true;
    if (cur == "Object") return false;
    ...
  }
}
```

结果：

```
$ clang++ -std=c++17 -O0 -o cyc.exe cyc.cpp && ./cyc.exe
conforms(A,B) = 1 steps=2
conforms(A,Object) = ABORT: no termination after 20M steps  steps=20000001
```

**两个结果都重要**：

- `conforms(A, B)` **正常返回**（2 步：`cur=A`，走到 `B`，命中）。所以环不是"必然死循环"——运气好的查询照样返回。
- `conforms(A, Object)` **永不终止**。`cur` 在 `A → B → A → B → …` 之间震荡，`cur == "Object"` 这个唯一出口永远不成立。

第一条比第二条更有教育意义：**这类 bug 是间歇性的**。它只在特定查询上触发，所以测试很容易漏掉。而 `conforms(x, Object)` 在真实程序里极其常见（任何往 `Object` 类型的变量赋值都会查它），所以实际上几乎必然触发。

而 `A ≤ Object` 在数学上是**真**的（手册：Object 是根）。所以这不是"错误输入导致错误输出"，是"**在一个真命题上挂死**"。

### 3.3 于是检查的位置被确定了

因为后果是挂死而不是错误结果，环检查**必须**在任何 `conforms` 调用之前完成，并且必须**中止编译**。看 `check()`：

```cpp
buildEnvironments();              // ← 环检查在里面（:99-101）
if (errorCount_ > 0) return false;   // ← 闸门：有错就绝不进入第 2 趟
for (auto& cls : prog_.classes) checkClass(*cls);    // ← 这里才会调 conforms
```

那道 `if (errorCount_ > 0) return false` 不是"早退优化"，它是**防挂死的护栏**。如果去掉它，让编译器"尽量多报错"，带环的程序就会在第 2 趟挂死。

> **这是编译器设计里一个反复出现的张力**：错误恢复（尽量多报错，对用户友好）vs 安全（有些错误之后继续跑是不安全的）。真实编译器的做法是把错误分级：`warning` 继续，`error` 继续但不进下一阶段，`fatal error` 立即停。我们这里只有两级，而这道闸门就是 "error 之后不进下一阶段"。clang 里对应的是 `Sema` 在 `hasErrorOccurred()` 为真时跳过 codegen。

### 3.4 `hasCycle`：三色 DFS

```cpp
bool TypeChecker::hasCycle(const std::string& cls,
                           std::unordered_set<std::string>& visiting,
                           std::unordered_set<std::string>& done) {
  if (done.count(cls)) return false;                       // 黑：已确认无环
  if (visiting.count(cls)) {                               // 灰：正在访问 → 环！
    error(classMap_.at(cls)->line, "inheritance cycle involving class '" + cls + "'");
    return true;
  }
  visiting.insert(cls);                                    // 涂灰
  const std::string& parent = parentMap_.at(cls);          // ← :62，§7.1 的崩溃点
  if (classMap_.count(parent))                             // 只沿程序类递归（内建类无环）
    hasCycle(parent, visiting, done);
  visiting.erase(cls);                                     // 退灰
  done.insert(cls);                                        // 涂黑
  return false;
}
```

这是标准的**三色标记 DFS**：白（不在任何集合里）=未访问，灰（`visiting`）=在当前递归路径上，黑（`done`）=已完成。**遇到灰色就是环**——因为灰色意味着"这个节点在我当前的路径上"，再次到达它就说明路径闭合了。

为什么不能只用一个 `visited` 集合？因为两个节点可能有共同祖先：`A inherits C`、`B inherits C`。走完 `A→C` 后 `C` 被标记；再走 `B→C` 时如果只有一个集合，会误判成环。**灰/黑的区分就是在区分"在当前路径上"和"以前走过"。**

这个算法你在别处见过：拓扑排序判环、垃圾回收的三色标记（`12` 篇）、Go 的 `GOTRACEBACK` 检测循环依赖、npm 检测 circular dependency。**同一个算法，四个场景。**

实测四个环形态，全部正确捕获：

```
$ ./coolc.exe c1.cl     # class A inherits A（自环）
ERROR: line 1: inheritance cycle involving class 'A'
$ ./coolc.exe c2.cl     # A→B→C→A（三元环）
ERROR: line 1: inheritance cycle involving class 'A'
$ ./coolc.exe c3.cl     # Main 在前，环在后
ERROR: line 2: inheritance cycle involving class 'A'
$ ./coolc.exe c4.cl     # D→A，A⇄B（环外挂一个节点）
ERROR: line 2: inheritance cycle involving class 'A'
```

第四个尤其值得注意：`D` 不在环上，但递归会从 `D` 走到环里去。因为 `visiting` 在整个外层循环里是**共享**的（`:99` 声明一次，`:101` 的循环复用），从 `D` 进入时 `A`、`B` 还是白的，走到 `A→B→A` 就命中灰色。✅

## 4. `installBuiltins`：内建类为什么是硬编码

`:18`：

```cpp
void TypeChecker::installBuiltins() {
  { // Object
    auto& m = methodEnv_["Object"];
    m["abort"] = {{}, "Object"};
    m["type_name"] = {{}, "String"};
    m["copy"] = {{}, "SELF_TYPE"};
    attrEnv_["Object"] = {};
  }
  { // IO
    auto& m = methodEnv_["IO"];
    m = methodEnv_["Object"];              // ← 手工继承！
    m["out_string"] = {{"String"}, "SELF_TYPE"};
    m["out_int"] = {{"Int"}, "SELF_TYPE"};
    m["in_string"] = {{}, "String"};
    m["in_int"] = {{}, "Int"};
    attrEnv_["IO"] = {};
  }
  { // Int
    methodEnv_["Int"] = methodEnv_["Object"];
    attrEnv_["Int"] = {};
  }
  ...
}
```

**三个观察**：

**① `m = methodEnv_["Object"]` 是手工做继承。** `methodsOf` 那套自动继承机制（§5）对内建类不适用，因为内建类不在 `classMap_` 里（它们没有 `ClassDef`——没有源码）。所以这里手抄一遍。这是"两套机制处理同类事情"的典型技术债：如果将来给 `Object` 加一个方法，你要记得 `IO`/`Int`/`String`/`Bool` 四处都会自动拿到（因为它们拷贝 `methodEnv_["Object"]`）——但前提是拷贝语句在添加语句**之后**执行。当前代码里 `Object` 块在最前面，所以是对的。**这是一个顺序依赖的隐藏约束，没有任何注释或断言保护它。**

**② 另一条路：用 Cool 源码定义内建类。** 很多编译器这么做——把内建库写成目标语言本身，编译时先解析它。Java 的 `java.lang.Object` 就是真正的 `.java` 文件；Rust 的 `core` 是真的 Rust 代码。好处是消除了两套机制；代价是引导（bootstrapping）复杂度——`String` 的 `concat` 最终必须落到不能用 Cool 表达的原语上，所以还是需要一层 intrinsic。**我们选硬编码，是因为内建方法只有 11 个，且 `runtime.c` 已经提供了实现。**

**③ `copy() : SELF_TYPE` 这一行是 `06a` §5 的全部动机。** 它是 Cool 里 `SELF_TYPE` 最纯粹的用例：`(new Sally).copy()` 必须是 `Sally` 而不是 `Object`，否则 `copy` 对任何子类都没用。手册第 201 行就是用它来引入 `SELF_TYPE` 的。

## 5. `methodsOf` / `attrsOf`：惰性递归 + 记忆化

### 5.1 结构

```cpp
const std::unordered_map<std::string, MethodSig>&
TypeChecker::methodsOf(const std::string& cls) {
  auto it = methodEnv_.find(cls);
  if (it != methodEnv_.end()) return it->second;          // ① 记忆化命中
  static const std::unordered_map<std::string, MethodSig> EMPTY;
  if (!classMap_.count(cls)) return EMPTY;                // ② 未知类，静默返回空

  const std::string& parent = parentMap_.at(cls);
  const auto& penv = methodsOf(parent);                   // ③ 递归求父类环境
  auto& env = methodEnv_[cls];
  env = penv;                                             // ④ 继承：整体拷贝
  std::unordered_set<std::string> own;
  const ClassDef* cd = classMap_.at(cls);
  for (auto& f : cd->features) {
    auto* m = dynamic_cast<const Method*>(f.get());        // ⑤ Feature 用 dynamic_cast
    if (!m) continue;
    if (own.count(m->name)) {                             // ⑥ 同类内重复定义
      error(m->line, "method '" + m->name + "' defined multiple times in class '" + cls + "'");
      continue;
    }
    own.insert(m->name);
    MethodSig sig;
    for (auto& fm : m->formals) sig.argTypes.push_back(fm.type);
    sig.retType = m->type;
    auto pit = penv.find(m->name);
    if (pit != penv.end() && !(pit->second == sig))       // ⑦ 重写签名检查
      error(m->line, "method '" + m->name + "' overrides inherited method with incompatible signature");
    env[m->name] = sig;                                   // ⑧ 覆盖父类版本
  }
  return env;
}
```

几个点：

**③+④ 的顺序是继承的全部。** 先递归拿到父类的完整方法表，整体拷贝，再用自己的方法覆盖。`env[m->name] = sig` 的 `[]` 覆盖语义就是"子类方法覆盖父类同名方法"——和 `05a` §3.2 的 `add` 用 `[]` 是完全同一个模式。**容器 API 的选择第二次被语言语义锁定。**

**⑤ 用 `dynamic_cast` 而不是 Visitor**：`03c` §2.6 讲透了——`Feature` 只有 2 种子类（`Method`/`Attribute`），组合爆炸不成立，所以故意不上 Visitor。这里是那个决定的第二个使用现场。

**① 的记忆化不只是优化。** 考虑 `A → B → C → Object` 这条链，检查 `A`、`B`、`C` 三个类时都会走 `methodsOf`。没有记忆化，`C` 的环境会被重算 3 次。更要紧的是：**`error` 会被重复调用**——同一个重写错误会被报 3 次。所以 `methodEnv_` 的缓存同时承担了"错误去重"的职责。这是一个**副作用与缓存耦合**的设计：函数不纯（会 `error`），所以缓存的语义就不只是"省时间"，而是"保证每个类只检查一次"。

> **这是个值得警惕的模式。** 纯函数加缓存是安全的；有副作用的函数加缓存，缓存就变成了正确性的一部分。一旦有人为了"调试方便"清掉缓存，错误信息就会重复。真实编译器里这类耦合是 bug 的高发区。

### 5.2 惰性的代价：一个实测漏报

惰性（lazy）意味着 `methodsOf(C)` 只在**有人问 C** 的时候才跑。谁会问？`checkClass` 通过 `checkFeature → attrsOf` 问，`visit(Dispatch)` 通过 `methodsOf(t0p)` 问。**如果一个类从来没被 dispatch、也没被 checkClass 走到，它的方法检查就永不执行。**

⑥ 和 ⑦ 两个检查都在 `methodsOf` 里面，所以它们也是惰性的。实测：

```cool
class A { g() : Int { 1 }; g() : Int { 2 }; };      -- 同一个类里 g 定义两次
class Main { main() : Object { 1 }; };              -- 没人碰 A
```
```
$ ./coolc.exe lazy1.cl -o o.ll
wrote o.ll (10176 bytes)                            ← 漏报！
```

加一次 dispatch 就报出来了：

```cool
class Main { main() : Object { (new A).g() }; };     -- 现在有人问 A
```
```
$ ./coolc.exe lazy3.cl
ERROR: line 1: method 'g' defined multiple times in class 'A'
type checking failed
```

**同一个程序缺陷，报不报取决于别处有没有用到这个类。** 这违反了一条基本期待：编译错误应该只取决于被检查的代码本身。

**关键对照**：属性版本**不漏报**：

```cool
class A { v : Int <- 1; v : Int <- 2; };
class Main { main() : Object { 1 }; };
```
```
$ ./coolc.exe lazy2.cl
ERROR: line 1: attribute 'v' defined multiple times in class 'A'
type checking failed
```

为什么？因为 `checkFeature`（`:221`）对**每个类的每个 feature** 都调 `attrsOf(currentClass_)`，所以 `attrsOf` 对所有类都必然跑一遍。而 `methodsOf` 没有这样的无条件调用点——它只在 dispatch 时被问。

**这个对照是本节的核心**：两个结构几乎相同的函数，一个漏报一个不漏报，差别不在它们自己，而在**有没有人无条件调用它们**。惰性求值的正确性依赖于"所有需要的查询最终都会发生"，而这个前提没有任何机制保证。

**修法**（§8.2）：在 `check()` 的闸门之后加一个无条件循环：

```cpp
for (auto& cls : prog_.classes) { methodsOf(cls->name); attrsOf(cls->name); }
```

一行，把惰性变成饿性（eager）。这是惰性/饿性权衡的真实现场：惰性省了工作量（未使用的类不检查），代价是丢了完整性。**编译器这个场景里完整性远比性能重要**，所以应该选饿性。

## 6. 重写的两条相反规则

### 6.1 方法可以重写，但签名必须完全一致

⑦ 用的是 `MethodSig::operator==`（`typechecker.h:13`）：

```cpp
bool operator==(const MethodSig& o) const {
  return argTypes == o.argTypes && retType == o.retType;
}
```

**完全相等**——参数类型逐个相等，返回类型相等。不允许任何变化。

为什么这么严？手册第 247 行给了理由（这段推理值得逐步走）：

> ... we cannot substitute a value of type C for p, as it would result in **adding a string to a number**. Thus, if methods can be redefined arbitrarily, then subclasses may not simply extend the behavior of their parents, and much of the usefulness of inheritance, as well as type safety, is lost.

把它变成 Cool 代码。设允许参数类型任意改：

```cool
class A {
  f(x : Int) : Int { x + 1 };
};
class B inherits A {
  f(x : String) : Int { x.length() };   -- 假设允许改参数类型
};
class Main inherits IO {
  g(a : A) : Int { a.f(5) };            -- 静态类型 A，传 Int 给 f，合法
  main() : Object { out_int(g(new B)) }; -- B ≤ A，合法
};
```

每一步都通过类型检查。但运行时：`g` 收到的是一个 `B`，动态分派到 `B.f`，而 `B.f` 期望 `String`，实际收到整数 `5`，然后调 `5.length()`。**崩溃。** 静态类型检查通过了，运行时却类型错误——这正是 `06a` §1 会讲的 **soundness 被破坏**。

**那么允许哪些变化是安全的？** 类型理论的标准答案：

| 位置 | 安全的变化方向 | 名字 | 直觉 |
|---|---|---|---|
| 参数类型 | 只能**放宽**（父类方向） | 逆变 contravariant | 子类方法要能接受父类方法能接受的一切 |
| 返回类型 | 只能**收紧**（子类方向） | 协变 covariant | 子类方法的返回值要能当父类方法的返回值用 |

Cool 两个方向都不允许，只允许完全相同。**为什么放弃安全的那部分灵活性？** 教学语言的取舍：`operator==` 一行就实现了检查；如果要支持协变返回，`operator==` 要换成一个"签名兼容性"判断，而且要调 `conforms`，于是又引入对继承图的依赖和环检查的前置条件。**用可表达性换实现简洁**——和 `01` §3.6 讲 Cool 的字符串转义只有两个是同一种设计哲学。

工业现状供对照：Java 支持协变返回（Java 5 起），不支持参数逆变（改参数类型会变成 overload 而非 override，这是无数 bug 的来源，所以有了 `@Override` 注解）；C++ 支持协变返回指针/引用；Scala 的函数类型 `Function1[-A, +B]` 在类型系统层面直接标注了逆变/协变。**你现在能读懂那个 `[-A, +B]` 了。**

实测（注意这条也受 §5.2 的惰性影响——要有人碰到 `B` 才报）：

```
$ ./coolc.exe f2_override_used.cl        # B.f 改了参数类型，且 main 里 dispatch 了
ERROR: line 2: method 'f' overrides inherited method with incompatible signature
type checking failed
```

### 6.2 属性不可重定义

`attrsOf`（`:141`）的对应位置：

```cpp
if (env.count(a->name))
  error(a->line, "attribute '" + a->name + "' redefines inherited attribute");
else
  env[a->name] = a->type;
```

注意和 `methodsOf` ⑧ 的对比：那里是 `env[m->name] = sig`（覆盖），这里是 `if 已存在 then 报错 else 加入`。**同一个继承机制，方法覆盖、属性报错。**

手册第 228 行：

> Attributes are local to the class in which they are defined or inherited. **Inherited attributes cannot be redefined.**

为什么方法能覆盖、属性不能？**理由在运行时布局，`08` 篇展开，这里给出核心**：

- **方法**在运行时是**分发表（dispatch table）里的一个槽位**。子类覆盖 = 把槽位里的函数指针换掉。槽位索引不变，所以调用方（只知道静态类型）用同一个索引就能找到正确的实现——这就是动态分派的全部机制。**覆盖是免费的。**
- **属性**在运行时是**对象内存里的一个偏移量**。假设允许 `class B inherits A { v : String; }` 重定义 `A.v : Int`：那么一个 `B` 对象里 `v` 是一个 `String`，但任何拿着 `A` 类型指针的代码都会按 `Int` 去读那个偏移量。**要么两个 `v` 各占一个槽（那"重定义"就毫无意义，只是名字冲突），要么共用一个槽（那类型就不一致）。** 两条路都不通。

所以这两条相反的规则不是语言设计者的任意选择，是**方法和属性在运行时表示上的根本差异**决定的。方法是间接调用（可以换目标），属性是直接访存（偏移量和类型必须固定）。

> **这是本篇我最想你带走的一条**：语义规则的"为什么"往往不在语义层，而在**实现层**。§2.2 的 `Int` 不可继承是这样，§3 的环检查是这样，这里也是这样。以后碰到任何"语言为什么禁止 X"的问题，除了想"逻辑上讲不通"，一定要再问一句"**如果允许，编译器/运行时的哪个具体机制会坏掉**"。这个习惯会让你从"背规则"变成"推规则"。

### 6.3 一个遗留问题：`attrsOf` 返回 `unordered_map`

`attrEnv_` 的类型是 `unordered_map<string, unordered_map<string, string>>`。所以 `attrsOf(C)` 返回的属性集合是**无序**的。

`08` 篇要做对象布局，需要"先祖先后自身、同层按源码顺序"的**确定顺序**——因为父类指针必须能按同一个偏移量访问继承的属性。`unordered_map` 给不了这个。

我查了 `codegen.cpp`：它没有用 `attrEnv_`，而是自己维护了一个 `attrs_`（`codegen.cpp:23` 的 `attrs_.at(cls)`，是个 vector）。也就是说 codegen **重建了一遍**属性信息，只为了拿到顺序。

**这是一处真实的设计缺陷，不过是"重复工作"级别，不是正确性 bug**：两处独立计算同一件事，一旦对属性的理解不一致（比如 typechecker 认为某属性存在、codegen 漏了它），就会出现难以定位的错误。正确做法是 `attrEnv_` 用 `vector<pair<string,string>>`（保序），codegen 直接复用。留作 §8.7。

顺便注意 `checkFeature:221` 那个循环：

```cpp
for (auto& kv : attrsOf(currentClass_)) O_.add(kv.first, kv.second);
```

它遍历 `unordered_map`，顺序不确定——但因为是**全部塞进同一张符号表**、且属性名不重复（重复会在 `attrsOf` 里报错），顺序在这里**恰好**无关紧要。这是"恰好正确"，不是"设计正确"。如果哪天这个循环需要顺序（比如要按顺序生成初始化代码），它会静默出错，而且在不同 STL 实现上表现不同。

## 7. 我实测发现的三个真实缺陷

延续 `03b` §3.5、`03c` §7、`05a` §7 的做法：构建（`clang++ -std=c++17 -O0 -g -o coolc.exe src/*.cpp`），跑探针，只报告实测确认的。

### 7.1 重定义内建类 → 编译器崩溃（根因已定位到行号）

**现象**。五个内建类全部触发：

```
$ ./coolc.exe rb.cl        # class Int { };  class Main { main() : Object { 1 }; };
ERROR: line 1: class 'Int' cannot be redefined
ERROR: unordered_map::at                    ← 不是类型错误，是 C++ 异常
```

`Object`/`IO`/`Int`/`String`/`Bool` 五个都一样。`unordered_map::at` 这条是 `main.cpp` 的 `catch (const std::exception& e)` 捞到的 `std::out_of_range`。

**定位过程**（这部分比结论更值得学）。`.at()` 在 `typechecker.cpp` 里有 6 处（`:58 :62 :91 :94 :115 :153`）。怎么确定是哪个？用**错误顺序**做二分：

探针 C —— 在重定义之外再加一个"父类未定义"错误：

```cool
class Int { };
class Q inherits Ghost { };
class Main { main() : Object { 1 }; };
```
```
ERROR: line 1: class 'Int' cannot be redefined            ← 注册循环（:75）
ERROR: line 2: class 'Q' inherits from undefined class 'Ghost'   ← 父类检查循环（:88-95）
ERROR: unordered_map::at                                  ← 崩在这之后
```

父类检查循环**完整跑完了**（它报出了错误），所以崩溃不在 `:91`/`:94`。下一段代码就是环检查（`:99-101`）。

探针 A —— 去掉 `Main` 类：

```cool
class Int { };
```
```
ERROR: line 1: class 'Int' cannot be redefined
ERROR: unordered_map::at            ← 没有 "no 'Main' class defined"
```

对照组（不重定义，也没有 `Main`）：

```cool
class Zz { };
```
```
ERROR: line 0: no 'Main' class defined
type checking failed                ← 正常
```

"no Main" 的检查在 `:103`，**在环检查之后**。探针 A 里它没打印出来，说明崩溃发生在 `:103` 之前、`:95` 之后。**区间夹到了 `:99-101` 的环检查循环**，也就是 `hasCycle` 内部。

**根因**。看 `:99-101`：

```cpp
std::unordered_set<std::string> visiting, done;
for (auto& c : prog_.classes)                       // ← 遍历 AST 里的所有类
  if (!done.count(c->name)) hasCycle(c->name, visiting, done);
```

循环遍历的是 **`prog_.classes`（AST）**，而不是 `classMap_`（已成功注册的类）。`class Int` 因为 `:78` 的 `continue` **从未进入 `parentMap_`**。于是 `hasCycle("Int", ...)` 执行到 `:62`：

```cpp
const std::string& parent = parentMap_.at(cls);      // parentMap_ 里没有 "Int" → 抛 out_of_range
```

**为什么重复类名不崩？** 这是关键的对照实验：

```cool
class A { };
class A { };
class Main { main() : Object { 1 }; };
```
```
ERROR: line 2: class 'A' already defined
type checking failed                      ← 干净退出，不崩
```

因为**第一个** `A` 成功注册了，`parentMap_["A"]` 存在。`:83` 的 `continue` 只跳过了第二个，但名字已经在表里。而内建类重定义时，那个名字**从来没有**进过 `parentMap_`——`installBuiltins` 只填了 `methodEnv_` 和 `attrEnv_`，**没填 `parentMap_`**。

两个 `continue` 长得一样，一个安全一个致命，差别在于"名字是否已在表中"。

**修法**（§8.3）：把 `:101` 的条件改成只处理已注册的类：

```cpp
for (auto& c : prog_.classes)
  if (classMap_.count(c->name) && !done.count(c->name)) hasCycle(c->name, visiting, done);
```

**一般教训**：`continue` 跳过注册之后，**后续所有以"已注册"为前提的代码都成了地雷**。这类 bug 的通用防法是让错误处理路径和正常路径在数据结构上**汇合**——要么注册一个占位条目，要么在下游一律用 `find` 而非 `at`。`03c` §7 那个 `parseIsvoid` 是"漏了一个递归"，`05a` §7.1 是"漏了一个检查"，这里是"错误路径留下了不一致状态"。三种不同的缺陷形态，都是靠跑出来的。

### 7.2 `Main.main` 的检查在有错时被跳过

`check()` 的结构：

```cpp
buildEnvironments();
if (errorCount_ > 0) return false;        // ← 闸门
if (classMap_.count("Main")) { /* main 方法检查 */ }
```

`main` 方法的检查在闸门**之后**。所以任何 `buildEnvironments` 期间的错误都会让它被跳过。

**这是设计还是缺陷？** 我判断是**可接受的设计**，理由是 §3.3 那条：闸门是防挂死的护栏，`methodsOf("Main")` 会调 `conforms`（间接通过父链遍历），在有环时不安全。错误恢复的质量（一次能报多少条错误）让位于安全，这个取舍是对的。

但代价要说清楚：用户如果程序里同时有一个类名拼错和一个 `main` 签名错误，他要**编译两次**才能看到第二个错误。真实编译器会用更细的分级（比如把"无环"单独作为进入下一阶段的前提，而不是"零错误"）来减少这种往返。**我把它列在这里不是为了判它错，是为了让你看到"闸门"这个设计有代价，而代价是可以量化的：用户的编译-修错往返次数。**

### 7.3 `SymbolTable::empty()` 是死代码

`symtab.h:29` 有 `bool empty() const { return scopes_.empty(); }`。我 grep 了整个 `src/`：

```
$ grep -rn "O_.empty()" src/*.cpp src/*.h
（无输出）
```

没有任何调用者。`typechecker.cpp` 里两处 `.empty()` 都是别的东西（`:84` 的 `c->parent.empty()`、`:428` 的 `argTypes.empty()`）。

**这是死代码吗？** 值得想一下再答。对一个**库类型**的 public 方法，"没有内部调用者"不等于死代码——它是给外部用户的 API。但 `SymbolTable` 只在 `TypeChecker` 里用（一个成员 `O_`），事实上是私有实现细节，不是库。所以在当前项目里它确实是死代码。

**为什么值得提**：它最可能的用途是断言。`05a` §4.2 讲的那条"进出栈深度相同"不变式，如果要机械化验证，正好可以用 `empty()`：在 `checkFeature` 末尾加 `assert(O_.empty())`，任何 push/pop 不配对都会在 debug 构建里立刻暴露。**所以这不是该删掉的死代码，是该被用起来的死代码。** 留作 §8.4。
