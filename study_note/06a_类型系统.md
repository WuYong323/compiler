## 精炼段

到这里，`05` 两篇已经把环境全部建好：`O`（局部变量作用域栈）、`M`（每个类的方法签名）、`C`（当前类）。手册要的三元组齐了，但我们**一个表达式的类型都还没判断过**。

本篇不讲规则表——规则表在 `06b`。本篇讲的是规则表**背后那一个不等式**：

$$D_e \le S_e$$

"任何表达式的运行时类型，必须 conform 到编译期推断出的类型。"这个不等式看起来平淡，但它是整个类型检查器的**唯一设计约束**。从它出发，你能推出：为什么类型检查必须保守（拒绝一些其实能跑的程序）；为什么 `if` 的类型必须是两支的**最小上界**而不是随便一支；为什么 `lub` 必须存在（于是类型必须组成一个**格**）；为什么 `SELF_TYPE` 存在——它是在"不违反不等式"的前提下把 `S_e` 尽量压小的手段。

而最有说服力的部分在 §6：我实测找到了一个**违反这个不等式**的程序。它通过类型检查、通过 codegen、`clang` 编译成功，运行时段错误；把其中一个 token 改掉（那个 token 的改动在语义上"更弱"），程序正常打印 42。这个对照把"soundness 被破坏会发生什么"从抽象概念变成了一个 139 号退出码。

## 0. 本篇要回答的六个问题

1. `D_e ≤ S_e` 为什么是**这个方向**？反过来（`S_e ≤ D_e`）会怎样？
2. "宁可拒绝合法程序"是一种设计偏好，还是逻辑上的必然？
3. `if b then new Cons else new Nil fi` 的类型，为什么必须是 `lub`，而不能是 `Cons`、`Nil` 或 `Object`？——三个都要排除，理由各不相同。
4. 为什么 Cool 的类型必须构成**格（lattice）**？单继承和这件事有什么关系？
5. `SELF_TYPE` 只能用在 4 个地方。这 4 个地方有什么共同点，其他地方为什么不行？
6. `resolveSelf` 只有一行。它在哪些地方用是对的，哪些地方用是错的？——这一问引出 §6 的 soundness 漏洞。

## 1. 一个不等式

### 1.1 两种类型

| | 静态类型 static type | 动态类型 dynamic type |
|---|---|---|
| 谁算的 | 类型检查器，**编译期** | 没人"算"，它就是对象**运行时**的真实类 |
| 记号 | `S_e` | `D_e` |
| 存在形式 | `Expr::type` 字段（`03c` §1.3 留的那个） | 对象头里的 class tag（`08` 篇讲布局） |

一个例子把两者拉开：

```cool
let x : Object <- new Int in x
```

- `S_x = Object`（声明写的）
- `D_x = Int`（运行时真的是个 Int）

两者**不相等**，而且这完全正常。类型检查器无法知道 `D_x`——它不执行程序。它只能给出一个**保证**。

### 1.2 不等式及其方向

**Soundness（健全性）**：对程序中每个表达式 `e`，在任何一次执行中，

$$D_e \le S_e$$

其中 `≤` 是 conformance（`05b` 已保证继承图无环，所以这个关系良定义）。

**为什么是这个方向？** 把两个方向都推一遍。

先看正确的方向 `D_e ≤ S_e`，它意味着"**实际的比宣称的更具体（或相等）**"。这为什么有用？因为**编译器和使用方是按 `S_e` 生成代码的**。看 `05b` §6.2 讲的方法覆盖：

```cool
class List { isNil() : Bool { true }; };
class Cons inherits List { isNil() : Bool { false }; };

sum(l : List) : Int { if l.isNil() then 0 else ... fi };
```

`l.isNil()` 这次调用，编译器只知道 `S_l = List`。它生成的代码是"在分发表的第 k 个槽位取函数指针并调用"，其中 `k` 是 `isNil` 在 `List` 里的槽位索引。

运行时 `l` 可能是 `Cons`。这份代码为什么还对？因为 `Cons ≤ List` 保证了 **`Cons` 的分发表是 `List` 的分发表的扩展**——前 `k` 个槽位的含义完全相同（`05b` §6.2：覆盖只换槽位内容，不改索引）。所以"取第 k 个槽位"在 `Cons` 对象上也是取到 `isNil`，只不过取到的是 `Cons` 的版本。**这就是动态分派能工作的全部原因，而它的前提正是 `D_l ≤ S_l`。**

现在看反方向。假设某处 `S_e ≤ D_e` 而不是反过来，也就是**实际的比宣称的更一般**：

```
S_e = Cons          （编译器以为是 Cons）
D_e = List          （运行时其实只是个 List）
```

编译器按 `Cons` 生成代码。如果 `Cons` 有一个 `List` 没有的方法 `getCar`，编译器会生成"取第 m 个槽位"——而 `List` 的分发表**没有第 m 个槽位**。读到的是表外的内存，解释成函数指针，跳过去。**这不是"结果错误"，这是任意代码执行。**

所以不等式的方向不是约定，它对应了"**内存布局的扩展方向**"：子类的布局是父类布局的前缀扩展，所以"把子类当父类用"安全，反之不安全。§6 的实测漏洞就是这个方向被破坏后的实况。

### 1.3 保守性是逻辑必然

现在推最重要的一条。

类型检查器要保证 `D_e ≤ S_e` 对**所有可能的执行**成立。但 `D_e` 依赖运行时——依赖输入、依赖分支走向。所以检查器实际必须保证：

> 对 `e` 的**所有可能**的运行时类型 `D`，都有 `D ≤ S_e`。

也就是 `S_e` 必须是 `e` 所有可能动态类型的一个**上界**。

而"e 所有可能的动态类型"这个集合，一般是**不可计算的**。考虑：

```cool
if complicated_predicate() then new Cons else new Nil fi
```

`complicated_predicate()` 里可以是任意计算。判断它是否恒真，等价于停机问题。所以检查器**不可能**精确知道这个 `if` 会返回哪一支。

于是只剩一条路：**取所有分支的上界**。而"取上界"必然意味着——

> 如果 `complicated_predicate()` 事实上恒为真，那么 `D_e` 永远是 `Cons`，此时 `S_e = Cons` 本来是安全的。但检查器给出 `S_e = lub(Cons, Nil) = List`。于是"`S_e = Cons` 本来可以但我们给了 `List`"——一些**其实安全的程序**（比如往 `Cons` 类型的变量赋这个 `if`）会被拒绝。

**这就是保守性。它不是编译器作者谨慎，是停机问题的直接推论。** 任何 sound 且可判定的类型系统都必然拒绝一些正确程序，这叫 **incompleteness（不完备性）**。sound + complete + decidable 三者不可兼得，这是 Rice 定理的一个实例。

**三个选择，三种语言**：

| 取舍 | 代价 | 代表 |
|---|---|---|
| sound + decidable，放弃 complete | 拒绝部分正确程序 | Cool、Java、Rust、Haskell |
| complete + decidable，放弃 sound | 运行时可能类型错误 | TypeScript（故意 unsound，如协变数组）、C 的隐式转换 |
| sound + complete，放弃 decidable | 检查可能不终止 | 依赖类型语言（Idris、Agda）的一部分 |

**TypeScript 那一行值得记住。** TS 官方文档明确说自己的类型系统 unsound，因为它优先考虑"能表达 JS 的实际用法"。所以 TS 程序运行时仍可能 `undefined is not a function`。**"有类型系统"和"类型安全"是两件事**，区别就是这个不等式是否真的被保证。

> **这个推导是整篇的骨架**。回头看 `06b` 的 19 条规则表，每一条都是"在这个语法构造上，如何算出一个满足 `D_e ≤ S_e` 的、尽可能小的 `S_e`"。"尽可能小"是因为 `S_e` 越小、程序能通过的越多——`SELF_TYPE` 就是把某些 `S_e` 压小的专用工具（§5）。

## 2. conformance：`≤` 的定义与实现

### 2.1 定义

手册的 `≤`（读作 conform）由三条规则定义：

```
A ≤ A                              自反
C ≤ P     若 class C inherits P     继承（一步）
A ≤ P     若 A ≤ C 且 C ≤ P        传递
```

加上 `Object` 是根，所以 `∀A. A ≤ Object`。

用数学语言：`≤` 是继承关系的**自反传递闭包**。在单继承下，继承图是一棵以 `Object` 为根的树，而 `A ≤ B` 就是"**B 是 A 在这棵树上的祖先（或 A 自己）**"。

### 2.2 实现：为什么是向上走而不是向下搜

`typechecker.cpp:172`：

```cpp
bool TypeChecker::conforms(const std::string& a, const std::string& b) {
  if (a == b) return true;                          // 自反
  if (b == "SELF_TYPE") return false;               // §5.3 讲
  std::string cur = (a == "SELF_TYPE") ? currentClass_ : a;
  for (;;) {
    if (cur == b) return true;                      // 命中祖先
    if (cur == "Object") return false;              // 到根还没命中
    if (parentMap_.count(cur)) cur = parentMap_.at(cur);
    else if (cur == "IO" || cur == "Int" || cur == "String" || cur == "Bool") cur = "Object";
    else return false;
  }
}
```

**这是从 `a` 往上走，看能不能碰到 `b`。** 为什么不是"从 `b` 往下搜所有子孙，看 `a` 在不在里面"？

因为**方向的代价差**。单继承下：

- 往上走：每个节点只有**一个**父亲，所以是一条**链**，长度 = 继承深度 `d`。代价 `O(d)`。
- 往下搜：一个节点可以有**任意多个**孩子，所以是一棵**子树**，要遍历。代价 `O(子孙数)`。

`d` 在真实程序里是个位数，子孙数可以是几百。**单继承把"往上"变成了一条链，这是子类型判断能如此廉价的唯一原因。**

对比多继承：C++ 里一个类有多个基类，"往上"也变成了搜图（DAG），于是 `dynamic_cast` 需要运行时遍历继承图——这就是 C++ 的 RTTI 比 Java 的 `instanceof` 慢的根源之一。**`05b` §8.11 让你想"多继承会崩哪些地方"，这是第一处。**

> 顺便：`codegen.cpp` 里有个 `descendants_`（`05a` §7.1 的崩溃点），那是**预计算的子孙表**。codegen 做 `case` 分派时需要"所有 conform 到 T 的类"，那时就是往下的方向了，所以必须预先算好。**同一个关系，两个方向，两种数据结构**——取决于谁问。

这个 `for(;;)` 的终止性由 `05b` §3 的环检查保证。那里我实测了：有环时它跑 2000 万步不终止。**本篇每一次调用 `conforms` 都在花那道闸门买来的安全。**

### 2.3 内建类的 `else if` 分支

```cpp
else if (cur == "IO" || cur == "Int" || cur == "String" || cur == "Bool") cur = "Object";
```

为什么需要这一支？因为 `05b` §7.1 挖出的那个事实：**`installBuiltins` 只填了 `methodEnv_`/`attrEnv_`，没填 `parentMap_`**。所以内建类在 `parentMap_` 里查不到，走不到上一个分支。

这一支在这里补了个硬编码的"内建类的父亲是 Object"。**它能工作，但它是 `05b` §7.1 那个崩溃的同源问题**：`parentMap_` 不完整这件事，在 `conforms` 里被一个 `else if` 打了补丁，在 `hasCycle` 里就直接崩了。

**一般教训**：当你发现自己在多处给"同一个数据结构不完整"打补丁，正确的修法是把数据结构补完整（在 `installBuiltins` 里填 `parentMap_`），而不是继续加分支。每一处补丁都是一次"下次有人忘了加分支就会出 bug"的赌博。留作 §8.2。

## 3. 为什么必须是格：`lub` 的推导

### 3.1 `if` 的类型：三个候选全部排除

```cool
if b then new Cons else new Nil fi        -- Cons ≤ List, Nil ≤ List
```

类型检查器要给这个表达式一个 `S_e`。候选：

**候选 ①：`Cons`（取 then 支）。** 违反 soundness。如果 `b` 为假，`D_e = Nil`，而 `Nil ≤ Cons` 不成立。§1.2 讲过后果：按 `Cons` 生成代码去访问 `Nil` 对象不存在的槽位。**直接否决。**

**候选 ②：`Object`（取根）。** 满足 soundness（任何类型 `≤ Object`），但**过于保守**：

```cool
let l : List <- if b then new Cons else new Nil fi in l.isNil()
```

如果 `if` 的类型是 `Object`，那么 `conforms(Object, List)` 为假，这个合法程序被拒绝。而且 `l.isNil()` 也没法调（`Object` 没有 `isNil`）。**能用但太弱。**

**候选 ③：`List`（两支的最近公共祖先）。** 满足 soundness：`D_e` 只能是 `Cons` 或 `Nil`，两者都 `≤ List`。而且是**满足 soundness 的所有候选中最小的那个**——任何比 `List` 更小的类型都会漏掉一支。

所以 `S_e` 应该取"两支类型的所有共同上界中最小的那一个"，这叫**最小上界（least upper bound, lub / join / ⊔）**。

手册第 280、294 行：

> Let `T` and `F` be the static types of the branches of the conditional. Then the static type of the conditional is `T ⊔ F`. (think: **Walk towards Object from each of T and F until the paths meet.**)

括号里那句就是算法。

### 3.2 lub 存在 ⟺ 类型构成格

**lub 凭什么一定存在？** 这不是显然的。设想一个类型系统里 `A` 和 `B` 有两个共同上界 `P` 和 `Q`，而 `P` 和 `Q` 之间没有关系——那"最小上界"不唯一，`⊔` 无定义。

Cool 里不会发生，因为**单继承 ⇒ 继承图是树 ⇒ 任意两点有唯一的最近公共祖先（LCA）**。树上任意两个节点，各自到根的路径必定在某一点汇合，且第一个汇合点唯一。

用序理论的话说：Cool 的类型在 `≤` 下构成一个**交半格（join semilattice）**——任意两元素有 lub。（严格说因为有最大元 `Object`、且树结构下任意两点也有最大下界，它其实是个**格**；但类型检查只用到 join。）

**多继承会直接打破这个性质。** C++ 里 `class D : public B, public C`，`B` 和 `C` 都继承 `A`——菱形。此时两个类的"共同上界"可以不唯一。这就是为什么 Java 只允许单继承类（但允许多接口——接口没有字段，所以布局问题不存在），以及为什么 Python 需要 **C3 线性化**算法（MRO）来人为规定一个唯一顺序。**`05b` §8.11 的第二处。**

> **对你的方向**：这个"必须构成格"的要求在数据流分析（`10` 篇）里会**原样再来一次**。数据流分析的格是"程序点上的抽象状态"，`⊔` 是控制流汇合处的信息合并（比如 `if` 两支之后，变量可能是常量 3 也可能是常量 5，合并成 ⊤ = "不是常量"）。**同一个数学结构，两个完全不同的场景**：这里合并类型，那里合并抽象值。你学一次，用两次。MLIR 的 dataflow framework、LLVM 的 `LatticeVal` 都直接用 lattice 这个词。

### 3.3 实现：`lca` 与 `lub`

`lca`（`:185`）严格按手册那句括号里的话写：

```cpp
std::string TypeChecker::lca(const std::string& a, const std::string& b) {
  std::unordered_set<std::string> anc;
  std::string cur = a;
  for (;;) {                       // 第一趟：收集 a 的所有祖先
    anc.insert(cur);
    if (cur == "Object") break;
    /* 往上走一步 */
  }
  cur = b;
  for (;;) {                       // 第二趟：b 往上走，第一个在 anc 里的就是 LCA
    if (anc.count(cur)) return cur;
    if (cur == "Object") return "Object";
    /* 往上走一步 */
  }
}
```

两趟、一个哈希集合，`O(d)` 时间 `O(d)` 空间。这是 LCA 最直白的算法。

（补充：LCA 有更快的做法——欧拉序 + 稀疏表做到 `O(1)` 查询，或者离线的 Tarjan 并查集算法。`d` 是个位数时全无必要。但你要知道**这是个有名字的经典问题**，因为在 `10` 篇的支配树（dominator tree）上你会再见到它，那里规模大得多。）

`lub`（`:205`）在 `lca` 外面包了 `SELF_TYPE` 处理：

```cpp
std::string TypeChecker::lub(const std::string& a, const std::string& b) {
  if (a == b) return a;
  if (a == "SELF_TYPE") return lub(currentClass_, b);
  if (b == "SELF_TYPE") return lub(a, currentClass_);
  return lca(a, b);
}
```

对应手册第 290 行：`SELF_TYPE_D ⊔ A = D ⊔ A`。

注意第一行 `if (a == b) return a` 的必要性：它让 `lub(SELF_TYPE, SELF_TYPE) = SELF_TYPE`（**保留**了 SELF_TYPE，没有退化成 `currentClass_`）。如果去掉这一行，`if b then self else self fi` 的类型会从 `SELF_TYPE` 掉成 `currentClass_`——soundness 不破，但精度损失，一些合法程序会被拒。**这一行是精度优化，不是正确性必需。** §8.4 让你验证。

实测三个 lub 场景：

```cool
class P { }; class Q inherits P { }; class R inherits P { };
-- lub(Q, R) 应该 = P
let z : P <- if b then new Q else new R fi in z
```
```
$ ./coolc.exe k_lub.cl -o o.ll
wrote o.ll (11641 bytes)              ← 通过，lub(Q,R)=P 且 conforms(P,P)
```

把声明类型改成 `Q`（比 lub 更小）：

```
$ ./coolc.exe l_lub_bad.cl
ERROR: line 5: let initializer for 'z' has type P but declared type is Q
type checking failed                   ← 正确拒绝
```

**这条错误信息就是 §1.3 那段"保守性"的实况**：如果 `b` 恒真，这程序其实能跑；但检查器不知道，所以 `S_e = P`，赋给 `Q` 被拒。**用户看到这条报错时感到的"编译器真烦"，本质上是停机问题。**

## 4. `Object` 作为兜底值：一个设计模式

看 `visit(Object)`（`:252`）：

```cpp
auto t = O_.lookup(e.name);
if (!t) { error(e.line, "undeclared identifier '" + e.name + "'"); result_ = "Object"; return; }
```

查不到名字，**报错之后仍然给出一个类型** `Object`。这个模式在 `typechecker.cpp` 里出现了很多次（`visit(Assign)`、`visit(Dispatch)`、`visit(New)` 的错误路径都是 `result_ = "Object"`）。

**为什么不直接抛异常终止？** 因为错误恢复。用户希望一次编译看到所有错误，不是每次改一个。要继续检查，`visit` 就必须返回**某个**类型让父节点用。

**为什么选 `Object` 而不是别的？** 因为 `Object` 是格的**顶元素**——它是唯一一个"对任何后续 `conforms(x, Object)` 都返回真"的选择。选它意味着：**错误节点之后的检查尽量不产生级联报错**……

等等，这个推理需要修正。`conforms(Object, X)` 对 `X ≠ Object` 是**假**。所以 `Object` 作为兜底值会让"把它赋给任何具体类型"都失败，**反而产生级联错误**。`05a` §3.3 实测过这个现象：

```
$ ./coolc.exe ae_let_init_sees_self.cl        # let x : Int <- x + 1
ERROR: line 1: undeclared identifier 'x'
ERROR: line 1: arithmetic operands must be Int, got Object and Int   ← 级联
```

第二条是噪音——它完全由第一条导致。真实编译器怎么避免？引入一个**特殊的错误类型**（clang 叫 `ErrorType`，rustc 叫 `TyKind::Error`），规则是"**任何涉及错误类型的检查一律静默通过**"。这样一条真错误只产生一条报错。

所以 `Object` 兜底是一个**可工作但次优**的选择，代价是级联噪音。`06b` §4 会展开这个话题并给出修法。**这里的要点是：`Object` 被选中是因为它是顶元素这个直觉，在错误恢复这个场景下其实不成立。** 格的顶元素在"合并信息"时是安全兜底，在"检查约束"时不是。

## 5. SELF_TYPE：把 `S_e` 压小的专用工具

### 5.1 动机：不用 SELF_TYPE 会损失什么

`05b` §4 提过，内建库里就有一个：`Object::copy() : SELF_TYPE`。假设它声明成 `copy() : Object`：

```cool
class Sally inherits Silly { };
class Main {
  x : Sally <- (new Sally).copy();      -- copy 返回 Object，conforms(Object, Sally) 假
};
```

被拒。而运行时 `copy` 返回的**确实是**一个 `Sally`（浅拷贝保持类）。所以 `S_e = Object` 虽然 sound，但太松，**让 `copy` 对所有子类都不可用**（每次都要 case 一下才能用）。

`SELF_TYPE` 的作用：让返回类型"随接收者变化"，从而把 `S_e` 从 `Object` 压到 `Sally`。

**这正是 §1.3 末尾那句"`S_e` 越小、能通过的程序越多"的具体兑现。** 手册第 267 行：

> Inferring accurate static types for dispatch expressions is what justifies including SELF TYPE in the Cool type system.

实测：

```cool
class Silly { copy2() : SELF_TYPE { self }; };
class Sally inherits Silly { };
class Main { x : Sally <- (new Sally).copy2(); main() : Object { x }; };
```
```
$ ./coolc.exe o_selftype_ret.cl -o o.ll
wrote o.ll (11246 bytes)              ← 通过
```

### 5.2 Dispatch 规则里的替换

手册（`:491`）和实现（`:286`）：

```cpp
result_ = (sig.retType == "SELF_TYPE") ? t0 : sig.retType;
```

**若方法声明返回 `SELF_TYPE`，整个 dispatch 的类型是接收者的类型 `t0`**（不是 `"SELF_TYPE"`，也不是当前类）。

为什么 sound？手册第 267 行的论证：方法 `f` 的 `self` 参数 conform 到 `T0`（接收者的静态类型）；`f` 返回 `SELF_TYPE`，即返回值的类型 = `self` 的动态类型；`self` 的动态类型 `≤ T0`。所以返回值 `≤ T0`。✅

**注意这个论证的前提**："`f` 返回 `SELF_TYPE`"必须意味着"返回值的动态类型 = `self` 的动态类型"。这个前提**必须由方法体的检查来保证**。§6 就是这个前提被违反的地方。

### 5.3 `conforms` 里那行 `if (b == "SELF_TYPE") return false`

手册只给了两条 `SELF_TYPE` 的 conformance 规则：

```
SELF_TYPE_C ≤ SELF_TYPE_C          （自反）
SELF_TYPE_C ≤ P    当且仅当 C ≤ P   （左侧是 SELF_TYPE）
```

**没有** `P ≤ SELF_TYPE_C` 的规则（除了 `P` 本身是 `SELF_TYPE_C`）。实现里：

```cpp
if (a == b) return true;               // 覆盖 SELF_TYPE ≤ SELF_TYPE
if (b == "SELF_TYPE") return false;    // 其他任何 x ≤ SELF_TYPE 都是假
```

**为什么右侧是 SELF_TYPE 时必须拒绝？** 因为 `SELF_TYPE_C` 代表"`C` 或 `C` 的任意子类"，是一个**不确定**的类型。要让 `A ≤ SELF_TYPE_C` 成立，必须对 `SELF_TYPE_C` 的**所有**可能取值都成立——包括 `C` 最深的那个子类。而在编译期我们不知道有哪些子类（将来还能加）。唯一能保证的情况是 `A` 本身就是 `SELF_TYPE_C`。

举例说明危险：

```cool
class A { f() : SELF_TYPE { ... }; };
class B inherits A { extra() : Int { 1 }; };
```

如果允许 `A ≤ SELF_TYPE_A`，那么 `let x : SELF_TYPE <- new A in ...` 在 `B` 的上下文里就意味着 `x` 可以当 `B` 用（因为 `SELF_TYPE` 在 `B` 的实例上是 `B`），但 `x` 实际是个 `A`，没有 `extra`。**这正是 §6 漏洞的形状。**

### 5.4 四个合法位置，每个都有理由

手册第 214 行：

> Finally, SELF TYPE may be used in the following places: `new SELF_TYPE`, as the return type of a method, as the declared type of a let variable, or as the declared type of an attribute. **No other uses of SELF TYPE are permitted.**

四个位置。**共同点是什么？** 逐个看：

| 位置 | 为什么安全 |
|---|---|
| `new SELF_TYPE` | 产生的对象的类 = `self` 的类，**恰好就是 SELF_TYPE 的含义** |
| 方法**返回**类型 | 返回值来自方法体内，那里 `self` 可见，`SELF_TYPE` 有确定含义 |
| `let` 变量声明类型 | 变量在方法体内，`self` 可见 |
| 属性声明类型 | 属性属于对象自身，`self` 就是那个对象 |

共同点：**这四个位置都在"`self` 有意义"的范围内，而且都是被赋值/被初始化的一侧（协变位置）**。

**为什么方法的形参类型不行？** 这是最重要的禁止。假设允许：

```cool
class A { f(x : SELF_TYPE) : Object { ... }; };
class B inherits A { };
```

`B` 继承了 `f`。在 `B` 里，`f` 的形参类型是 `SELF_TYPE_B` = "B 或 B 的子类"。现在：

```cool
g(a : A) : Object { a.f(new A) };      -- 静态类型 A，形参是 SELF_TYPE_A，传 A，看起来合法
main() : Object { g(new B) };            -- B ≤ A，合法
```

运行时 `a` 是 `B`，动态分派到 `B.f`，而 `B.f` 的形参要求是 `B` 或其子类——**实际传进去的是一个 `A`**。类型错误。

**这个推理和 `05b` §6.1 讲"方法重写为什么要求参数类型完全一致"是同一个形状**：形参是**逆变**位置，而 `SELF_TYPE` 在子类里会变得**更具体**（协变），两者冲突。所以 `SELF_TYPE` 只能出现在协变位置，形参是逆变位置，禁止。

**你现在能自己推导这条规则了**，这比记住"四个位置"有用得多——因为你能用同样的推理判断任何语言里 `this.type`（Scala）、`Self`（Rust）能用在哪。（Rust 的 `Self` 在 trait 方法参数里能用，是因为 Rust 用的是静态分发 + 单态化，没有动态分派的这个问题；一旦用 `dyn Trait`，带 `Self` 参数的方法就不是 object-safe 的——**同一个约束，同一个理由，Rust 管它叫 object safety**。）

### 5.5 实测：位置限制根本没检查

```cool
class Main inherits IO { f(x : SELF_TYPE) : Object { x }; main() : Object { out_string("k") }; };
```
```
$ ./coolc.exe j_selftype_formal.cl -o o.ll
wrote o.ll (10201 bytes)              ← 形参用 SELF_TYPE，通过了
```

`isType`（`:11`）把 `"SELF_TYPE"` 列为合法类型名，但**没有任何地方检查它出现的位置**。这和 `05a` §7.1 是同源问题（那里是"未定义的类型名没检查"，这里是"合法但位置错误的类型名没检查"）——两者都该在同一个 `checkDeclaredType` 里处理，只是后者还需要一个"当前位置允许 SELF_TYPE 吗"的参数。归到 §8.5。

## 6. 我实测发现的 soundness 漏洞

这是本篇最重的内容：**一个通过类型检查、编译成功、运行时段错误的程序**。

### 6.1 程序

```cool
class A {
  mk() : SELF_TYPE { new A };      -- ★ 声明返回 SELF_TYPE，但体里返回 new A
};
class B inherits A {
  extra() : Int { 42 };            -- B 独有的方法
};
class Main inherits IO {
  main() : Object { out_int((new B).mk().extra()) };
};
```

`main` 那一行的推理链：

1. `new B` 的类型是 `B`。
2. `(new B).mk()`：`mk` 声明返回 `SELF_TYPE`，按 §5.2 的规则，dispatch 的类型 = 接收者类型 = **`B`**。
3. 于是 `.extra()` 合法——`B` 有 `extra`。

但运行时：`mk` 的方法体是 `new A`，返回的是一个 **`A`** 对象。`A` 没有 `extra`。

$$S_e = B,\quad D_e = A,\quad A \not\le B$$

**soundness 被破坏。**

### 6.2 实测

```
$ ./coolc.exe unsound.cl -o unsound.ll
wrote unsound.ll (12259 bytes)                 ← 类型检查通过

$ clang -O0 -o unsound.exe unsound.ll runtime.c
（只有一条 target triple 的 warning）           ← 编译成功

$ ./unsound.exe
Segmentation fault                              ← RUN_EXIT=139
```

### 6.3 排除干扰：三个对照

`03c` §7.2 记录过这台机器上有一个**与本 bug 无关**的 teardown 段错误（`clang -O1/-O2` 会段错误，`-O0` 正常）。所以我必须证明这个 139 不是那个已知问题。三个对照：

**对照 1（决定性的）——只改一个 token**：把 `new A` 改成 `self`，其余完全相同。

```cool
class A { mk() : SELF_TYPE { self }; };     -- 唯一的改动
```
```
$ ./sound.exe
42                                          ← SOUND_RUN_EXIT=0
```

**打印出了 42，正常退出。** 同一个编译器、同一个构建命令、同一个 `runtime.c`、同一个 `-O0`，程序结构完全相同，只差一个 token——一个段错误一个打印 42。

而且这个改动方向很关键：`self` 版本是 `SELF_TYPE` 的**正确**用法（返回值的动态类型确实等于 `self` 的动态类型，所以 `(new B).mk()` 真的返回 `B`，`.extra()` 真的存在）。**"改得更正确"和"不崩"精确同步。**

**对照 2 —— 基线**：

```
$ ./hello.exe
Hello, compiler!          HELLO_RUN_EXIT=0
```

**对照 3 —— 非平凡程序（递归 + dispatch）**：

```
$ ./fact.exe
120                       FACT_RUN_EXIT=0
```

三个对照合起来排除了"这台机器上什么都跑不了"和"teardown 崩溃"两种解释。**这是一个真实的 soundness 漏洞。**

（`-O0` 是 `03c` §7.2 确定的可用配置，我全程用它，所以三个对照与被测程序的构建条件完全一致。）

### 6.4 根因：`resolveSelf` 用错了位置

看 `checkFeature`（`:233-239`）：

```cpp
} else if (auto* m = dynamic_cast<const Method*>(&f)) {
  for (auto& fm : m->formals) O_.add(fm.name, fm.type);
  std::string t = typeOf(*m->body);
  std::string declared = resolveSelf(m->type);        // ← :236 这里
  if (!conforms(t, declared))
    error(m->line, "body of method ... has type ... but declared return type is ...");
}
```

`resolveSelf`（`typechecker.h:58`）：

```cpp
std::string resolveSelf(const std::string& t) const {
  return t == "SELF_TYPE" ? currentClass_ : t;
}
```

于是当 `m->type == "SELF_TYPE"` 时，`declared` 变成 `currentClass_`（这里是 `"A"`）。检查变成：

```
conforms(typeOf(new A), "A")  =  conforms("A", "A")  =  true    ✅ 通过
```

**这正是漏洞**。手册的 [Method] 规则（第 669 行附近）要求方法体的类型 conform 到 `SELF_TYPE_C` **本身**，而不是 conform 到 `C`：

```
OC[SELF TYPE_C/self][T1/x1]...[Tn/xn], M, C ⊢ e : T0'
T0' ≤ T0            其中 T0 = SELF_TYPE_C if 声明是 SELF_TYPE
```

按手册，检查应该是 `conforms("A", "SELF_TYPE")`。而 §5.3 那行 `if (b == "SELF_TYPE") return false` 会让它**返回假**——正确地拒绝这个程序。

**所以正确的修法是把 `:236` 的 `resolveSelf` 去掉**：

```cpp
std::string declared = m->type;      // 不要 resolveSelf
if (!conforms(t, declared)) error(...);
```

这样 `mk() : SELF_TYPE { new A }` 会被拒（`conforms("A","SELF_TYPE")` 为假），而 `mk() : SELF_TYPE { self }` 会通过（`typeOf(self)` 是 `"SELF_TYPE"`，`conforms("SELF_TYPE","SELF_TYPE")` 走 `a==b` 为真）。**§5.3 那行"看起来多余"的检查，正是为这个场景准备的——而 `resolveSelf` 把它绕过了。**

### 6.5 同一个根因的第二处

`checkFeature` 的属性分支（`:226`）有完全相同的模式：

```cpp
std::string declared = resolveSelf(a->type);
```

实测：

```cool
class A { v : SELF_TYPE <- new A; };      -- 属性声明 SELF_TYPE，初始化成 new A
```
```
$ ./coolc.exe ad_selftype_attr.cl -o o.ll
（通过，无错误）
```

按手册 [Attr-Init] 规则，同样应该被拒。

`visit(Let)`（`:335`）也是：

```cpp
std::string declared = resolveSelf(b.type);
```
```cool
class A { mk() : Object { let x : SELF_TYPE <- new A in x }; };
```
```
$ ./coolc.exe let_unsound.cl -o o.ll
wrote o.ll (10815 bytes)                  ← 通过
```

**三处同源缺陷**（`:226` 属性、`:236` 方法返回、`:335` let），根因都是"把 `SELF_TYPE` 提前塌缩成了 `currentClass_`"。

### 6.6 那么 `resolveSelf` 什么时候该用？

这一问才是真正的收获。对比两处用法：

| 位置 | 用途 | 对不对 |
|---|---|---|
| `visit(Dispatch):270` `resolveSelf(t0)` | 拿接收者类型去**查方法表** | ✅ **对**。方法表按类名索引，必须有一个具体类名。而 `SELF_TYPE_C` 的方法集合就是 `C` 的方法集合（子类只会覆盖不会删除），所以塌缩是安全的。 |
| `checkFeature:236` `resolveSelf(m->type)` | 拿声明类型去**做 conformance 判断** | ❌ **错**。`SELF_TYPE_C` 和 `C` 在 `≤` 关系里**不等价**：`A ≤ A` 真，但 `A ≤ SELF_TYPE_A` 假。塌缩丢掉了这个区别。 |

**判据**：`SELF_TYPE` 可以塌缩成 `currentClass_` 的场合，是那些"只需要知道有哪些成员"的查询（查方法表、查属性表）；**不能**塌缩的场合，是任何进入 `conforms`/`lub` 的地方——因为 `≤` 关系对 `SELF_TYPE` 有专门的、更严格的规则。

一句话记：**`SELF_TYPE` 在"查成员"时等于当前类，在"判子类型"时不等于当前类。**

（`lub`（`:205`）里也展开了 `SELF_TYPE` → `currentClass_`。那里是**对的**，因为手册第 290 行明文规定 `SELF_TYPE_D ⊔ A = D ⊔ A`——`⊔` 这个运算的定义本身就要求先展开。所以不是"凡 conforms/lub 都不能展开"，而是：`lub` 的展开有手册授权，`conforms` 的左侧展开也有授权（`SELF_TYPE_C ≤ P ⟺ C ≤ P`，正是 `:175` 干的事），**唯独"被 conform 的那一侧"不能展开**——而 `:226/:236/:335` 恰好都展开了那一侧。）

这是本篇最精细的一处区分，也是为什么这个 bug 能藏住：`resolveSelf` 在四个地方用，两个对两个错，长得一模一样。

## 7. 工业接轨

### 7.1 soundness 在真实语言里的状态

| 语言 | sound？ | 已知漏洞/取舍 |
|---|---|---|
| **Java** | 几乎 | 数组协变是**已知 unsound**：`Object[] a = new String[1]; a[0] = 1;` 编译通过，运行时 `ArrayStoreException`（用运行时检查补救） |
| **C#** | 同上 | 同样的数组协变问题 |
| **TypeScript** | **故意不 sound** | 官方文档明说：方法参数双变（bivariant）、`any` 逃逸口、类型断言。优先兼容 JS 习惯 |
| **Rust** | sound（safe 子集） | `unsafe` 块把责任交给程序员；soundness bug 被当作最高优先级（有专门的 I-unsound 标签） |
| **Cool（我们的实现）** | **否**，§6 | `resolveSelf` 三处误用 |

**Java 数组协变那条值得对照本篇**。Java 认为 `String[] ≤ Object[]`，这是协变；而数组的写入是逆变位置（往数组里放东西 = 传参）。**和 §5.4 推导"形参不能用 SELF_TYPE"是完全相同的形状**：协变的东西出现在逆变位置。Java 选择保留这个 unsound 的规则（为了泛型之前的代码好写），代价是每次数组写入都要做运行时检查（`aastore` 指令带类型检查）。

**这是一个通用权衡**：静态类型系统的漏洞，要么收紧规则（拒绝更多程序），要么加运行时检查（付性能）。Java 选后者，Cool/我们应该选前者（§6.4 的修法）。

### 7.2 对你的方向（AI Infra）

**① lattice 会再来一次。** §3.2 说过了，`10` 篇数据流分析的格、MLIR 的 dataflow framework 都是同一个结构。你现在掌握的"lub 必须存在 ⟸ 结构是树/格"这个推理，到那里可以直接复用。

**② soundness 在张量编译器里的对应物是 shape correctness。** 想想你在 nanoGPT 里见过的：

```python
x = x.view(B, T, n_head, head_dim).transpose(1, 2)
```

编译期（trace 期）能确定的 shape 是"静态 shape"，运行时真实的是"动态 shape"。**这就是 `S_e` 和 `D_e`。** 而"静态 shape 必须是动态 shape 的正确抽象"就是本篇的不等式。

具体对应：
- **动态维（`-1`、symbolic shape）** = 本篇的"保守上界"。`torch.export` 的 `Dim` 标注就是在说"这一维我不知道具体值，只知道约束"——和 `lub(Cons, Nil) = List` 是同一件事：不知道具体，给个安全的上界。
- **shape 推断规则** = `06b` 的 19 条类型规则。`torch.fx` 的 `ShapeProp`、ONNX 的 shape inference、TVM 的 `TypeRelation` 都是在做同一件事：从子节点的 shape 算出本节点的 shape。
- **不 sound 的后果** = kernel 越界访问，也就是 §6.2 那个段错误的 GPU 版（而 GPU 上更糟：没有 segfault，可能静默读到别的 tensor 的数据，产出错误结果而不报错）。

**③ 一个直接可用的判断工具。** 你将来给 GPU 计算图写图变换（小米那个课题），每一个 pattern rewrite 都要问一句：**"我这个重写，在什么前提下保持类型/shape 正确？"** 如果答不出来，就是在制造 §6 那种 bug——只是发现它的成本高得多（不是段错误，是模型精度莫名下降）。MLIR 的每个 Op 都有 verifier、每个 pattern 都要保证 `ResultType` 一致，就是把这个问题制度化了。
