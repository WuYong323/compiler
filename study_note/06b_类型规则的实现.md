## 精炼段

`06a` 讲了不等式 `D_e ≤ S_e` 和两个工具（`conforms`、`lub`）。本篇把它们用到 18 个 `visit` 上。

这本来是最容易写成"规则表 + 代码堆"的一篇——旧版 05/06 就是这么写的，一张 `| 规则 | 推理规则 | 实现函数 |` 的表，然后贴几段带 `// ...` 的代码。那样写的问题是：你读完表格，仍然不会**自己推导**一条新规则。所以本篇换一条路：

**先教你读推理规则**（§1）。那个横线不是装饰，它是"蕴含"；横线上方每一个前提，在代码里都对应一次 `typeOf(子表达式)` 调用；前提的**顺序**对应求值顺序；前提里出现的环境变化（`O[T/x]`）对应 `pushScope`。学会这个映射之后，19 条规则你不是"记住"而是"能翻译"。

**然后把 19 条规则归成四种形状**（§2–§5），每种给一个模板和一个代表。归完你会发现：18 个 `visit` 里有 6 个是纯常量（三行），5 个是同一个"传播并约束"模板，2 个开作用域，2 个求 lub，剩下 3 个是 dispatch 家族（唯一真正复杂的）。**复杂度集中在一处，这是好设计的标志。**

§6 系统处理级联报错——`06a` §4 指出 `Object` 兜底会产生噪音，这里给出实测对比和修法。§7 是 CP3 验收。§8 交代我实测发现的三个问题，主线是一处 **我们比手册更宽松**的缺陷（接受了手册明确禁止的程序）；顺着它我还发现 `01` 篇有一处事实性错误，以及 `tests/` 里有一条测试**和实现共享了同一个错误假设**因而"通过"了——后者是本次改写中最值得一看的发现。

## 0. 本篇要回答的六个问题

1. 推理规则那个横线是什么意思？怎么把一条规则**机械地**翻译成 `visit` 代码？
2. 19 条规则能不能压缩成几个模板？压缩之后，"新增一个语法构造"要写多少代码？
3. `visit(Block)` 只有四行，`visit(Dispatch)` 有二十行。这个差距说明了什么？
4. Dispatch 规则的三个部分，各自守护 soundness 的哪一环？去掉任一个，能构造出什么反例？
5. 一条真错误为什么会引发两条报错？怎么系统性地消除？
6. `while` 的类型为什么是 `Object` 而不是别的？——这一问会牵出"类型系统比运行时更保守"的一个例子。

## 1. 怎么读推理规则

### 1.1 记号

手册用的是自然演绎（natural deduction）风格：

```
        前提1        前提2   ...   前提n
      ─────────────────────────────────────
              O, M, C ⊢ e : T
```

读法：

- **横线 = 蕴含**。"如果上方全部成立，那么下方成立。"
- **`⊢`**（turnstile，读 entails / 推出）："在环境下能推出"。`O, M, C ⊢ e : T` 读作"在对象环境 `O`、方法环境 `M`、当前类 `C` 下，表达式 `e` 的类型是 `T`"。
- **前提里的 `⊢`** 是**递归**：要判断 `e` 的类型，先得判断它子表达式的类型。

**关键的翻译规则**——这是本节唯一需要记住的东西：

| 规则里的东西 | 代码里的东西 |
|---|---|
| 一个前提 `O,M,C ⊢ eᵢ : Tᵢ` | 一次 `std::string ti = typeOf(*e.子节点);` |
| 一个前提 `T ≤ T'` | 一次 `if (!conforms(t, tp)) error(...);` |
| 一个前提 `M(C,f) = (...)` | 一次 `methodsOf(...).find(...)` |
| 前提里环境变成 `O[T/x]` | `O_.pushScope(); O_.add(x, T);` … `O_.popScope();` |
| 结论的 `: T` | `result_ = T;` |
| 前提的**书写顺序** | 求值/检查顺序（手册明确规定了求值顺序，所以这不是自由的） |

### 1.2 一个完整的翻译示范

拿手册最简单的非平凡规则之一，[If]（手册 `:521` 附近）：

```
   O,M,C ⊢ e1 : Bool      O,M,C ⊢ e2 : T2      O,M,C ⊢ e3 : T3
  ────────────────────────────────────────────────────────────────
          O,M,C ⊢ if e1 then e2 else e3 fi : T2 ⊔ T3
```

机械翻译，逐项对应：

```cpp
void TypeChecker::visit(const If& e) {                    // :311
  std::string tc = typeOf(*e.cond);                       // ← 前提 1
  if (tc != "Bool") error(e.cond->line, "if condition must be Bool, got " + tc);
  std::string t2 = typeOf(*e.then_);                      // ← 前提 2
  std::string t3 = typeOf(*e.else_);                      // ← 前提 3
  result_ = lub(t2, t3);                                  // ← 结论的 T2 ⊔ T3
}
```

**四行代码，四个规则元素，一一对应。** 规则的排版和代码的结构是同构的。

注意一个细节：前提 1 是 `e1 : Bool`——规则里直接**写死**了 `Bool`，意思是"`e1` 的类型必须是 `Bool`"。代码里不能写 `typeOf` 然后期望它返回 `Bool`，必须**显式检查**（`if (tc != "Bool") error`）。**规则里"前提写成一个具体类型"= 代码里一次相等性检查。**

再注意：为什么是 `tc != "Bool"` 而不是 `!conforms(tc, "Bool")`？因为 `Bool` 在 Cool 里不能被继承（`05b` §2.2），所以唯一 conform 到 `Bool` 的类型就是 `Bool` 自己。两种写法等价，相等性检查更快也更直白。**但这是一个依赖"Bool 不可继承"的优化**——如果哪天语言允许了，这里就错了。这类隐式依赖值得在脑子里挂个标记。

### 1.3 自己翻译一条

试 [Isvoid]（手册 `:598`）：

```
     O,M,C ⊢ e1 : T1
  ───────────────────────
   O,M,C ⊢ isvoid e1 : Bool
```

前提里 `T1` 出现了但**没有任何约束**（没有 `T1 ≤ 某个东西`），结论的类型是固定的 `Bool`。所以：

```cpp
void TypeChecker::visit(const IsVoid& e) {     // :380
  typeOf(*e.expr);        // ← 必须调用（为什么？见下），但返回值不用
  result_ = "Bool";
}
```

**为什么明明不用返回值，还必须调 `typeOf`？** 三个理由，每一个都足以单独成立：

1. **子表达式本身可能有类型错误**，不递归就发现不了。`isvoid (1 + "s")` 里面的错误必须报出来。
2. **`typeOf` 有副作用**：它会写 `Expr::type`（`typechecker.h:63`）。`09` codegen 要读这个字段，漏掉一个节点，codegen 就拿到空字符串。
3. `isvoid` 的操作数是任意类型（`T1` 无约束），这对应手册"`isvoid` 对任何表达式都合法"。

第 2 条最容易忽略，而且后果最隐蔽（不是报错，是 codegen 拿到脏数据）。**`typeOf` 不是一个纯查询函数，它是一次"遍历并标注"。** 这是 `03c` §1.3 说 `Expr::type` 是"跨阶段共享数据结构"的兑现处。

## 2. 形状一：常量（6 条）

最简单的一类：结论类型固定，没有前提。

```
  ─────────────────────        ─────────────────────────
   O,M,C ⊢ i : Int              O,M,C ⊢ true : Bool
```

横线上方是空的——**无条件成立**（这叫公理 axiom，不是推理规则）。

```cpp
void TypeChecker::visit(const IntConst&)    { result_ = "Int"; }      // :248
void TypeChecker::visit(const StringConst&) { result_ = "String"; }   // :249
void TypeChecker::visit(const BoolConst&)   { result_ = "Bool"; }     // :250
void TypeChecker::visit(const NoExpr&)      { result_ = "Object"; }   // :417
```

注意参数没有名字（`const IntConst&` 而不是 `const IntConst& e`）——因为压根不用它。这是个小细节，但它在说"这条规则真的没有前提"。

`NoExpr` 是我们自己的产物，不是手册的规则。它代表"缺失的表达式"（没有初始化的属性/let 绑定）。给它 `Object` 是因为它**永远不会被真正检查**（`checkFeature` 里 `if (a->init)` 会跳过），所以这个值是什么都行。**这种"哨兵节点"是 AST 设计里常见的做法**，替代方案是用 `nullptr`——我们的 `ast.h` 对属性初始化用的确实是 `if (a->init)` 判空，所以 `NoExpr` 其实是个冗余的双轨设计。无害，但值得注意。

`visit(New)` 是"几乎常量"——加了一个存在性检查：

```cpp
void TypeChecker::visit(const New& e) {                          // :370
  if (e.type == "SELF_TYPE") { result_ = "SELF_TYPE"; return; }  // 手册 :469
  if (!isType(e.type)) {
    error(e.line, "cannot instantiate undefined type '" + e.type + "'");
    result_ = "Object"; return;
  }
  result_ = e.type;
}
```

对应手册 `:469`：`new T : SELF_TYPE_C if T = SELF_TYPE, else T`。

**这是 `isType` 唯一的调用点**——`05a` §7.1 那个缺陷的另一面：其他五处该查的地方都没查。

## 3. 形状二：传播并约束（5 条）

模板：**递归算出子表达式类型 → 检查约束 → 返回一个（通常固定的）类型**。

```
   O,M,C ⊢ e1 : Int      O,M,C ⊢ e2 : Int      op ∈ {+,-,*,/}
  ──────────────────────────────────────────────────────────────
                O,M,C ⊢ e1 op e2 : Int
```

模板代码：

```cpp
void TypeChecker::visit(const XXX& e) {
  std::string t = typeOf(*e.子表达式);        // 传播
  if (t != 期望) error(e.line, 诊断信息);      // 约束
  result_ = 固定类型;                          // 结论
}
```

三个实例，几乎逐字相同：

```cpp
void TypeChecker::visit(const Neg& e) {        // :405   ~e : Int
  std::string t = typeOf(*e.expr);
  if (t != "Int") error(e.line, "~ operand must be Int, got " + t);
  result_ = "Int";
}
void TypeChecker::visit(const Not& e) {        // :411   not e : Bool
  std::string t = typeOf(*e.expr);
  if (t != "Bool") error(e.line, "not operand must be Bool, got " + t);
  result_ = "Bool";
}
void TypeChecker::visit(const While& e) {      // :319
  std::string tc = typeOf(*e.cond);
  if (tc != "Bool") error(e.cond->line, "while condition must be Bool, got " + tc);
  typeOf(*e.body);                              // 检查但丢弃（同 §1.3 三个理由）
  result_ = "Object";
}
```

### 3.1 `while` 的类型为什么是 `Object`

手册（`:588` 附近）规定 `while` 的静态类型是 `Object`。但 `01` §7.4 说"循环的值 = void"。**两者不矛盾，而且这个不矛盾很有教育意义。**

`void` 不是一个类型——手册说它是"所有类型的成员"（`01` §6.4）。所以类型系统里没有 `Void` 这个类型可以给。那给什么？必须给一个所有类型的**上界**，也就是 `Object`。

于是出现一个有趣的现象：

```cool
while b loop x <- x + 1 pool      -- S_e = Object，D_e = void
```

`D_e` 是 `void`，而 `void` 不是任何类的实例。`06a` 的不等式 `D_e ≤ S_e` 在这里怎么解释？手册的处理是把 `void` 定义成 conform 到一切——它是格的**底元素（bottom）**。

**所以 Cool 的类型格严格说是**：顶是 `Object`，底是 `void`（不可写出的类型），中间是继承树。`void` 作为底元素让 `D_e ≤ S_e` 对 `while`、对未初始化变量都成立。

**工业对照**：这个"底类型"在真实语言里到处是——Rust 的 `!`（never type，`panic!`/`loop{}` 的类型）、Kotlin 的 `Nothing`、Scala 的 `Nothing`、TypeScript 的 `never`。它们的共同定义就是"conform 到一切"，用途就是给"不返回值"或"不终止"的表达式一个类型。**你现在能理解为什么 Rust 里 `let x: i32 = if c { 1 } else { panic!() };` 能编译**：`panic!()` 的类型是 `!`，`lub(i32, !) = i32`。

Cool 没把 `void` 做成可写的类型，所以只能退到 `Object`——**精度损失，但 sound**。又一个 `06a` §1.3 的保守性实例。

### 3.2 `visit(Assign)`：第一次出现 `conforms`

```
   O(id) = T      O,M,C ⊢ e1 : T1      T1 ≤ T
  ───────────────────────────────────────────────
           O,M,C ⊢ id <- e1 : T1
```

```cpp
void TypeChecker::visit(const Assign& e) {                            // :258
  if (e.name == "self") { error(e.line, "cannot assign to 'self'"); result_ = "Object"; return; }
  auto t = O_.lookup(e.name);                                          // ← O(id) = T
  if (!t) { error(e.line, "assignment to undeclared identifier '" + e.name + "'"); result_ = "Object"; return; }
  std::string t2 = typeOf(*e.rhs);                                     // ← e1 : T1
  if (!conforms(t2, *t))                                               // ← T1 ≤ T
    error(e.line, "cannot assign expression of type " + t2 + " to '" + e.name + "' of type " + *t);
  result_ = t2;                                                        // ← 结论 : T1
}
```

**注意结论是 `T1`（右手边的类型），不是 `T`（声明类型）。** 这是精度选择：`T1 ≤ T`，所以 `T1` 是更精确的那个，返回它能让更多程序通过。实测：

```cool
class Main inherits IO { v : Int <- 0; main() : Object { out_int(v <- 5) }; };
```
```
$ ./coolc.exe asgn.cl -o o.ll
wrote o.ll (10124 bytes)          ← 赋值表达式的值可以直接当 Int 用
```

`self` 检查在最前面，对应手册"`self` 可读不可写"。实测：

```
$ ./coolc.exe m_selfassign.cl        # self <- new Main
ERROR: line 1: cannot assign to 'self'
```

### 3.3 `visit(Binary)`：两条规则挤在一个节点里

`Binary` 节点承载了 7 个运算符（`+ - * / < <= =`），而手册给了**两条不同的规则**（[Arith] 和 [Compare]/[Equal]）。所以实现里有个 `switch`：

```cpp
void TypeChecker::visit(const Binary& e) {                    // :385
  std::string t1 = typeOf(*e.lhs);
  std::string t2 = typeOf(*e.rhs);
  switch (e.op) {
    case BinOp::Plus: case BinOp::Minus: case BinOp::Mul: case BinOp::Div:
      if (t1 != "Int" || t2 != "Int")
        error(e.line, "arithmetic operands must be Int, got " + t1 + " and " + t2);
      result_ = "Int";
      break;
    case BinOp::Lt: case BinOp::Le: case BinOp::Eq:            // ← §8.1 的缺陷在这里
      if (t1 == "Int" || t1 == "String" || t1 == "Bool" ||
          t2 == "Int" || t2 == "String" || t2 == "Bool") {
        if (t1 != t2)
          error(e.line, "comparison operands must have the same basic type, got " + t1 + " and " + t2);
      }
      result_ = "Bool";
      break;
  }
}
```

`=` 的规则（手册 `:624`）："任意类型可自由比较，**除了** `Int`/`String`/`Bool` 只能和同类型比。"代码的逻辑是"若任一侧是基本类型，则两侧必须相同"——这正确实现了 `=`。实测：

```
$ ./coolc.exe eq_mixed.cl      # new P = 1
ERROR: line 2: comparison operands must have the same basic type, got P and Int
$ ./coolc.exe eq_free.cl       # new P = new Q（两个不相关的类）
wrote o.ll (11367 bytes)       ← 正确允许（手册 :342「Any other types ... may be freely compared」）
```

**但 `<` 和 `<=` 被塞进了同一个分支，这是错的**——§8.1 展开。

## 4. 形状三：绑定并开作用域（2 条）

模板：**改变环境 → 在新环境里检查子表达式 → 恢复环境**。这是唯一会动 `O_` 的一类。

`[Let-Init]`（手册 `:550`）：

```
   O,M,C ⊢ e1 : T1      T1 ≤ T0      O[T0/x],M,C ⊢ e2 : T2
  ──────────────────────────────────────────────────────────
         O,M,C ⊢ let x : T0 <- e1 in e2 : T2
```

**注意前两个前提用的是 `O`，第三个用的是 `O[T0/x]`。** 这个差别就是 `05a` §3.3 讲的那条规则（初始化在"还没有 x"的环境里检查），也决定了代码里 `typeOf(init)` 必须在 `O_.add` 之前。`visit(Let)` 的完整分析在 `05a` §3.2–§3.3，这里不重复。

`[Case]`（手册 `:584`）：

```
   O,M,C ⊢ e0 : T0      O[T1/x1],M,C ⊢ e1 : T1'   ...   O[Tn/xn],M,C ⊢ en : Tn'
  ────────────────────────────────────────────────────────────────────────────────
     O,M,C ⊢ case e0 of x1:T1 => e1; ... esac : T1' ⊔ ... ⊔ Tn'
```

这条规则同时是形状三**和**形状四（每分支开作用域 + 结果求 lub）。代码（`:349`）：

```cpp
void TypeChecker::visit(const Case& e) {
  typeOf(*e.scrutinee);                       // ← e0 : T0（T0 无约束，丢弃）
  std::unordered_set<std::string> seen;
  bool first = true;
  std::string joined = "Object";
  for (auto& b : e.branches) {
    if (seen.count(b.type)) {                 // ← 分支类型互异（手册要求）
      error(e.line, "duplicate case branch type '" + b.type + "'");
      continue;
    }
    seen.insert(b.type);
    O_.pushScope();                           // ← O[Ti/xi]
    O_.add(b.name, b.type);
    std::string t = typeOf(*b.body);
    O_.popScope();                            // ← 恢复
    joined = first ? t : lub(joined, t);       // ← 逐步求 ⊔
    first = false;
  }
  result_ = joined;
}
```

**`first` 那个标志值得看一眼。** 为什么不初始化 `joined = "Object"` 然后直接 `lub`？因为 `lub(Object, X) = Object` ——如果从 `Object` 开始累积，结果**恒为 `Object`**，精度全毁。所以第一个分支必须**直接赋值**而不是 lub。

这是"求聚合值时初始值该取什么"的经典问题。数学上，`⊔` 的单位元应该是格的**底元素**（`lub(⊥, X) = X`）。而 Cool 没有可写的底类型（§3.1），所以代码只能用 `first` 标志模拟"从底开始"。**如果 `void` 是个可写类型，这里就能写成 `joined = "void"` 然后统一 lub，`first` 就不需要了。** 又一次看到"缺少底类型"带来的实现复杂度。

（同样的 `first` 模式你在 `reduce`/`fold` 没有初始值时见过——Python 的 `functools.reduce` 不给 `initializer` 时就是拿第一个元素当初值，理由完全相同。）

`joined` 初值 `"Object"` 只在分支数为 0 时生效。而 `03c` §7 记录过 `parseCase` 允许零分支（违反文法的 `(…)+`）——**两个缺陷在这里握手**：parser 放进来一个零分支的 `case`，typechecker 给它 `Object` 而不报错。手册 `:319` 明确要求 "Every case expression must have at least one branch"。

## 5. 形状四：汇合求 lub（2 条）+ Dispatch 家族（3 条）

### 5.1 `visit(Block)`：最简单的规则

```
   O,M,C ⊢ e1 : T1   ...   O,M,C ⊢ en : Tn
  ──────────────────────────────────────────
      O,M,C ⊢ { e1; ... en; } : Tn
```

```cpp
void TypeChecker::visit(const Block& e) {      // :326
  std::string t = "Object";
  for (auto& x : e.exprs) t = typeOf(*x);       // 每个都检查，只留最后一个的类型
  result_ = t;
}
```

四行。**为什么前 n-1 个的类型被丢弃却还要算？** §1.3 的三个理由，第三次出现。

`t` 初值 `"Object"` 同样只在空块时生效——而 `03c` §7 记录 `parseBlock` 允许空块（违反文法）。**第二次握手。**

### 5.2 Dispatch：唯一真正复杂的一条

手册 `:483-491`：

```
   O,M,C ⊢ e0 : T0
   O,M,C ⊢ ei : Ti                     (i = 1..n)
   T0' = (T0 = SELF_TYPE_C) ? C : T0                  ← ①
   M(T0', f) = (T1', ..., Tn', Tn+1')                  ← ②
   Ti ≤ Ti'                            (i = 1..n)      ← ③
   Tn+1 = (Tn+1' = SELF_TYPE) ? T0 : Tn+1'             ← ④
  ─────────────────────────────────────────────────────────
   O,M,C ⊢ e0.f(e1, ..., en) : Tn+1
```

四个额外前提。实现（`:268`）：

```cpp
void TypeChecker::visit(const Dispatch& e) {
  std::string t0 = typeOf(*e.receiver);
  std::string t0p = resolveSelf(t0);                          // ← ① 查表用，可塌缩
  const auto& menv = methodsOf(t0p);                          // ← ② 查方法表
  auto it = menv.find(e.method);
  if (it == menv.end()) {
    error(e.line, "method '" + e.method + "' not defined in class '" + t0p + "'");
    result_ = "Object"; return;
  }
  const MethodSig& sig = it->second;
  if (sig.argTypes.size() != e.args.size())
    error(e.line, "wrong number of arguments to method '" + e.method + "'");
  for (size_t i = 0; i < e.args.size() && i < sig.argTypes.size(); ++i) {
    std::string ti = typeOf(*e.args[i]);
    if (!conforms(ti, sig.argTypes[i]))                       // ← ③ 实参 conform 形参
      error(e.args[i]->line, "argument " + std::to_string(i + 1) + " to '" + e.method +
                             "' has type " + ti + " but expected " + sig.argTypes[i]);
  }
  result_ = (sig.retType == "SELF_TYPE") ? t0 : sig.retType;  // ← ④ 注意用 t0 不是 t0p
}
```

**①、③、④ 三者各守护 soundness 的不同环节。** 逐个去掉，看会漏掉什么：

| 去掉 | 漏掉的程序 | 运行时后果 |
|---|---|---|
| ② 方法存在性 | `(new A).nonexistent()` | 分发表里没这个槽位 → 跳到垃圾地址 |
| ③ 实参 conform | `f(x:String)` 传一个 `Int` | 方法体里把整数当字符串用 → 解引用非指针 |
| ④ SELF_TYPE 替换（若错误地返回 `"SELF_TYPE"` 字面量） | 调用方拿到一个不是具体类名的类型 | 后续 `conforms` 全部失效 |

**④ 用 `t0` 而不是 `t0p` 是关键，也是最容易写错的一处。** `06a` §5.2 讲了为什么：`t0` 是接收者的**静态类型**，返回值 conform 到它；`t0p` 已经把 `SELF_TYPE` 塌缩成了 `currentClass_`，用它会丢精度。举例：

```cool
class A { me() : SELF_TYPE { self }; twice() : SELF_TYPE { me() }; };
```

`twice` 的体是 `me()`（self-dispatch，`03c` §3.3 讲过它被 desugar 成 `self.me()`）。此时 `t0 = typeOf(self) = "SELF_TYPE"`，`t0p = "A"`。
- 用 `t0`：结果是 `"SELF_TYPE"` ✓ —— `twice` 声明返回 `SELF_TYPE`，匹配。
- 用 `t0p`：结果是 `"A"` ✗ —— 若按手册检查（`conforms("A","SELF_TYPE")` 为假）就会拒绝这个合法程序。

实测这个程序通过：

```
$ ./coolc.exe st_chain2.cl -o o.ll
wrote o.ll (10644 bytes)
```

（注意：由于 `06a` §6.4 那个 `resolveSelf` 缺陷，方法体检查目前是 `conforms("SELF_TYPE","A")`，恰好也真。所以这个程序在**修复前后都通过**——但理由不同。修复后它通过是因为 `t0` 用对了；修复前通过是因为检查被放松了。**两个 bug 互相掩盖，这是最难查的情形。** 做完 `06a` §8.1 的修复后，本例正是验证"修复没有引入回归"的关键测试。）

`StaticDispatch`（`:289`）只多一条前提（`T0 ≤ T`，手册 `:507`）：

```cpp
std::string t0 = typeOf(*e.receiver);
if (!conforms(t0, e.type))
  error(e.line, "receiver of static dispatch has type " + t0 + " but expected " + e.type);
const auto& menv = methodsOf(e.type);     // ← 查 T 而不是 T0'
```

其余二十行和 `Dispatch` **逐字重复**。这是真实的代码重复（约 18 行 × 2），应该抽成一个共享的 `checkCall(receiver_type, method_name, args, line)`。留作 §9.5。

## 6. 错误恢复：级联报错

### 6.1 现象

`06a` §4 指出 `Object` 兜底会产生噪音。实测（`05a` §3.3 那个程序）：

```cool
class Main inherits IO { main() : Object { let x : Int <- x + 1 in out_int(x) }; };
```
```
ERROR: line 1: undeclared identifier 'x'                              ← 真错误
ERROR: line 1: arithmetic operands must be Int, got Object and Int    ← 噪音
```

第二条完全由第一条导致：`visit(Object)` 报错后返回 `"Object"`，`visit(Binary)` 拿到 `Object` 和 `Int`，于是又报一次。

**用户要在两条错误里认出只有一个真问题。** 在有几十条错误的大文件里，这种噪音会让真错误被淹没——这是编译器可用性的真实问题，不是学术洁癖。

### 6.2 系统性修法：`<error>` 类型

引入一个特殊类型，约定"**任何涉及它的检查一律静默通过**"：

```cpp
static const char* ERR = "<error>";      // 故意用非法标识符，不会和真类型名冲突

bool TypeChecker::conforms(const std::string& a, const std::string& b) {
  if (a == ERR || b == ERR) return true;     // ← 吸收
  /* 原逻辑 */
}
std::string TypeChecker::lub(const std::string& a, const std::string& b) {
  if (a == ERR) return b;                    // ← 中性元
  if (b == ERR) return a;
  /* 原逻辑 */
}
```

然后把所有错误路径的 `result_ = "Object"` 改成 `result_ = ERR`，并在形状二/三的相等性检查里加 `t != ERR &&` 的短路。效果：第二条错误消失。

**为什么 `<error>` 能同时当 conforms 的吸收元和 lub 的中性元？** 因为它不是格里的真元素——它是一个**标记**，语义是"这里已经报过错了，别再报"。它在 `conforms` 里表现为"永远满足"（吸收），在 `lub` 里表现为"不影响结果"（中性）。这两个性质合起来就是"错误不传播"。

工业对照：clang 的 `ASTContext::getDependentSizedArrayType` 一族里 `ErrorType` 就这么用；rustc 的 `TyKind::Error` 有个专门的不变式叫 "error taints"——一旦某个类型是 `Error`，所有依赖它的检查都跳过，并且**编译器保证至少已经发过一个诊断**（有 `delay_span_bug` 机制在没发诊断时 panic，防止静默接受错误程序）。

**rustc 那个保证很重要**，它防止 `<error>` 被滥用成"万能通过"：如果某个 `<error>` 是凭空产生的（没有伴随诊断），程序就会被静默接受。所以修法要配一条不变式：**产生 `ERR` 的地方必须同时 `error(...)`**。留作 §9.4。

### 6.3 我们目前的取舍

值得说清：级联噪音是**可接受的缺陷**，不是 bug。它不影响正确性（不会接受错误程序，也不会拒绝正确程序），只影响诊断质量。在一个教学实现里，用 `Object` 兜底换 20 行代码是合理的。

**但它有一个真实代价**：`05b` §7.2 讲的"闸门"已经让用户可能需要编译两次；级联噪音又让每次编译的输出更难读。两者叠加起来，诊断体验就明显差于 clang。**诊断质量是编译器工程里被严重低估的一块**——Rust 编译器的口碑很大一部分来自它的错误信息，而那背后是大量专门的工程（span 追踪、建议生成、错误去重）。

## 8. 我实测发现的三个问题

### 8.1 `<` 和 `<=` 比手册宽松（顺带纠正 `01` 篇的一个错误）

**手册怎么说。** 第 342 行：

> Cool has three comparison operations: `<`, `<=`, `=`. **For `<` and `<=` the rules are exactly the same as for the binary arithmetic operations**, except that the result is a Bool.

而"binary arithmetic operations"的规则是第 341 行：

> The static types of the two sub-expressions **must be Int**.

形式化规则（手册 `:610` 附近，[Compare]）也明确：

```
   O,M,C ⊢ e1 : Int      O,M,C ⊢ e2 : Int      op ∈ {<, ≤}
  ──────────────────────────────────────────────────────────
              O,M,C ⊢ e1 op e2 : Bool
```

**`<` 和 `<=` 的两个操作数必须是 `Int`。** 只有 `=` 才是"任意类型可比"的特例。

**我们的实现。** `visit(Binary):385` 把 `Lt`、`Le`、`Eq` 塞进了**同一个 case 分支**，用的是 `=` 的宽松规则。实测：

```
$ ./coolc.exe lt_str.cl        # if "a" < "b" then 1 else 2 fi
wrote o.ll (10749 bytes)       ← 接受了，应该报错

$ ./coolc.exe lt_obj.cl        # if new P < new Q then 1 else 2 fi（两个无关的类）
wrote o.ll (11367 bytes)       ← 接受了，应该报错
```

第二个尤其严重：`new P < new Q` 在运行时要比较两个任意对象的"大小"，这在 `runtime.c` 里根本没有合理语义。**这是"接受了不该接受的程序"，是 soundness 方向的问题**（不是精度问题）——它会把一个无意义的比较放给 codegen。

**修法**（§9.1）：把 `Lt`/`Le` 拆出来，并入算术分支的检查逻辑：

```cpp
case BinOp::Lt: case BinOp::Le:
  if (t1 != "Int" || t2 != "Int")
    error(e.line, "comparison operands must be Int, got " + t1 + " and " + t2);
  result_ = "Bool";
  break;
case BinOp::Eq:
  /* 保留现有的基本类型配对逻辑 */
  break;
```

**顺带纠正 `01` 篇。** `01_Cool语言精讲.md:304` 写着：

> `<`、`<=`：Int 数值序；**String 字典序**；Bool 按 `false < true`。

这和手册第 342 行 + [Compare] 规则**矛盾**。手册只允许 `Int` 参与 `<`/`<=`，Cool 不提供字符串比较或布尔比较。所以 `01` 那一行是错的，应该改成"`<`、`<=`：两侧必须是 Int，数值序比较"。

我要标注一处边界：手册 §7.12 那段自然语言描述了 `=` 在各种类型上的语义，但 `<`/`<=` 的语义描述只提到"和算术运算规则相同"。我没有在手册里找到任何支持"String 字典序"的文字，而形式化 [Compare] 规则明确写了 `Int`。所以我判断 `01:304` 是 DeepSeek 生成时混入了其他语言（Java/Python 的字符串可比）的直觉。**这是本次改写中我在旧笔记里发现的第一个事实性错误**，我会一并修掉。

### 8.2 测试套件本身也编码了这个错误认识

查 §8.1 时我顺手 grep 了 `tests/`，发现 `tests/bool_test.cl:10`：


### 8.3 属性初始化构成环时，codegen 栈溢出崩溃

**现象**。这个程序让 `coolc.exe` 不产生任何输出、被信号终止（我的 shell 报 `EXIT=127`）：

```cool
class A { v : A <- new A; };
class Main { main() : Object { new A }; };
```
```
$ ./coolc.exe ctlA.cl -o o.ll
EXIT=127    （耗时 62ms）
```

**注意那个耗时。** 62 毫秒——这不是"挂死"，是**崩溃**。我起初按"无限递归 → 转圈"去理解它，于是习惯性加了 `timeout`，还把现象记成了挂死；但一个真正转圈的程序不会在 62ms 内就没了。**先看它死得多快，再决定该怀疑什么**：转圈要用 `timeout` 抓，崩溃要用调试器抓。

`SELF_TYPE` 版本同样（`EXIT=127`，65ms）。

**触发边界**（5 个探针，实测）：

| 探针 | 属性 | `Main` 里 | 结果 |
|---|---|---|---|
| s2 | `v : A <- new A` | `new A` | **EXIT=127**，62ms |
| s1 | `v : SELF_TYPE <- new SELF_TYPE` | `new A` | **EXIT=127**，65ms |
| s4 | `A.b : B <- new B`；`B.a : A <- new A` | `new A` | **EXIT=127**，61ms |
| s3 | `v : A <- new A` | `1`（不构造 `A`） | EXIT=0，9762 字节 |
| s5 | `v : A`（**无初始化式**） | `new A` | EXIT=0，9938 字节 |

三条结论：崩溃要求初始化式里**真的有 `new`**（s5 排除了"类型自引用"这个嫌疑——`v : A` 完全合法）；要求那个类**真的被构造**（s3：环存在但没人走进去，编译照样完成）；且**不限于自引用**，s4 的 `A→B→A` 互相引用一样崩。所以准确的触发条件是"**属性初始化图上有环，且环从某个被实例化的类可达**"。

```
#14 cool::CodeGen::allocateAndInit (this=0x5ff550, cls="A")    at src/codegen.cpp:458
#15 cool::CodeGen::visit ...                                   at src/codegen.cpp:385
#16 cool::New::accept ...                                      at src/ast.h:105
#17 cool::CodeGen::codegenExpr ...                             at src/codegen.cpp:203
#18 cool::CodeGen::allocateAndInit (cls="A")                   at src/codegen.cpp:458
        ... 以 4 帧为周期无限重复 ...
```

**信号是 SIGSEGV，不是内存耗尽**，而回溯把递归环精确地框出来了，**周期恰好 4 帧**：

```
allocateAndInit(A)   codegen.cpp:458   ← 为属性 v 生成初始化代码
  └ codegenExpr      codegen.cpp:203
      └ New::accept  ast.h:105
          └ visit(New) codegen.cpp:385  ← result_ = allocateAndInit(e.type)
              └ allocateAndInit(A)      ← 回到起点
```

`visit(New)` 只有一行（`codegen.cpp:385`），环就是它闭合的：

```cpp
void CodeGen::visit(const New& e) {
  result_ = allocateAndInit(e.type == "SELF_TYPE" ? currentClass_ : e.type);
}
```

而 `allocateAndInit` 对每个属性调 `codegenExpr(*slot.init)`——**属性初始化式是内联展开的**，于是 `new A` 要求先展开 `A.v` 的初始化式 `new A`，无穷递归。

栈深数据印证了这个结构：

```
$ gdb -q -batch -ex run -ex "bt" --args ./coolc.exe s2.cl -o s2.ll | grep -c '^#'
4231            # 最底一帧是 main (src/main.cpp:36)
```

4231 帧 ÷ 4 帧/层 ≈ **1057 层嵌套**就把默认栈打爆了。栈顶那个 `%t4212` 也自洽：约 4 个临时变量/层 × 1057 层 ≈ 4200。（`07` 篇 §2.2 讲虚拟寄存器"无限供应"时引用的就是这个编号。）

**为什么这个区分重要**：如果真是"耗尽内存"，加内存或换 64 位就能缓解；而栈溢出意味着**递归深度**是硬约束——真实编译器的对策只能是结构性的：要么静态检测环并拒绝（typechecker 侧），要么给展开加深度上限（codegen 侧），要么根本不内联展开（把属性初始化编译成一个运行时 `init` 函数，靠调用而非展开来复用）。后者是主流做法，也是为什么真实编译器不怕这个程序。

**为什么我不把它归到 typechecker**：类型上这个程序无可指摘（`conforms(A, A)` 为真），手册也没禁止它。问题出在 codegen 的展开策略。所以这属于 `09` 篇的范畴，我在这里记录是因为它是在做 06 的探针时撞见的，而且它**暴露了一个跨阶段的契约缺口**：typechecker 通过的程序，codegen 应当能在有限时间内处理完——这个契约目前没有任何机制保证。

留作 §9.6（在 `09` 篇再解决，本篇只记录）。
